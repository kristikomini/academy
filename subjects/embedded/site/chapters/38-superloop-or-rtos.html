Superloop or RTOS: choosing honestly

A while(1) with a state machine in it is a legitimate architecture, shipped in millions of products. Knowing when it stops being one — and being able to argue either side — is worth more in an interview than preferring one.

From the advert

Not in this advert, which names an RTOS directly. But the regional listings collected alongside it ask for “bare-metal and/or RTOS” as a pair, which is a deliberate phrasing: they want somebody who has made the choice, not somebody who only knows one.

What a superloop actually is

🧒 Simple

The simplest possible firmware: set everything up, then loop forever doing each job in turn. Read the sensor, update the display, check the buttons, repeat.

It works beautifully as long as no single job takes long. The moment one of them waits for something, everything else stops waiting too.

🎓 Professional

The shape, properly done, is not a naive list of calls. It is interrupts doing the urgent, time-critical capture, and a main loop running a set of non-blocking state machines over the results: 

int main(void) {
    hw_init();
    for (;;) {
        comms_step();      /* each returns promptly, always */
        control_step();    /* no waiting, no delays inside */
        ui_step();
        watchdog_kick();
    }
}

Each _step() is a state machine (chapter 07) that advances at most one transition and returns. Nothing blocks; anything that would have blocked becomes a state to be in.

What this buys is genuinely large and routinely undersold. No scheduler means no context switches, no per-task stacks, no kernel RAM and no kernel flash — on a part with 8 KB of SRAM that is not a saving, it is the difference between possible and impossible. There is exactly one stack, so stack analysis is one number rather than N guesses (chapter 12). And critically: there are no races between tasks, because there are no tasks. The only concurrency is with interrupts, which is one well-understood boundary rather than N×(N−1)/2 of them.

It is also fully capable of being real-time (chapter 37). Worst-case response is bounded by the longest single pass through the loop, and if you can state that number, you have a real-time system — arguably one that is easier to prove real-time than a priority-scheduled one.

Where it stops working

🧒 Simple

The trouble starts when two jobs have very different speeds. If one job must happen every millisecond and another takes fifty milliseconds, they cannot share one loop — the slow one has to be chopped into fifty pieces by hand, and that chopping is where the design turns ugly.

🎓 Professional

Four signals, in rough order of how strongly they argue for a kernel:

1. Widely separated timescales. A 1 ms control loop alongside a 200 ms flash write or a TLS handshake. In a superloop the slow work must be manually sliced so that every slice fits the fast deadline, and that hand-slicing is what an RTOS does for you with a context switch.

2. Blocking third-party middleware. A TCP/IP stack, a USB stack or a file system whose API assumes it can wait (chapter 52). You do not get to rewrite it, and it will not fit a non-blocking loop. This is the most common practical reason a project acquires an RTOS, and it is a perfectly honest one.

3. The state machines start nesting. When a step function has a state whose only purpose is “waiting for the other state machine to finish step 3”, you are hand-writing continuations. That is a real code smell, and it is the point where a task, which is just a continuation the kernel manages for you, is cheaper.

4. The team. Four people on one superloop must all understand the whole loop's timing. Four people on four tasks mostly need to understand their own. That is an organisational argument, not a technical one, and it is still a good argument.

Note what is not on the list: number of peripherals, project prestige, or a feeling that an RTOS is more professional. A superloop is not a beginner's architecture. It is the right architecture for a large fraction of products, and the middle ground — a cooperative or time-triggered scheduler, a few hundred lines that calls each step function on its own period — covers many of the cases in between without any of a kernel's costs.

⚠ Trap

Adding an RTOS to escape a badly written superloop imports the problem and adds races.

If the reason the loop misses deadlines is a HAL_Delay(100) or a blocking HAL_UART_Transmit buried in a step function, moving that code into a task does not fix it — it just means the blocked task is no longer obviously the problem. Now you also have shared state between tasks, priority assignment, per-task stacks, and every failure mode in chapter 40 and chapter 41.

The honest sequence is: make everything non-blocking first, measure the worst-case loop pass, and only then decide. If the loop is clean and the numbers still do not fit, you have a real argument for a kernel and you can state it in one sentence. That sentence is what an interviewer is listening for.

The mirror-image trap is a superloop with a watchdog kicked unconditionally at the bottom of the loop. It then proves only that the loop is still spinning, not that anything useful is happening — each step function should have to report progress before the kick (chapter 28).

Try it. Build the same small product twice. This is a long exercise and it is the one that makes the answer yours rather than borrowed.

Product: read an ADC every 1 ms, filter it, answer Modbus polls on a
UART, and blink an LED at 1 Hz.

VERSION A -- superloop.
  ADC in a timer interrupt into a ring buffer; three step functions;
  nothing blocks. Measure the worst-case loop pass by toggling a GPIO
  at the top of the loop and watching the longest gap on a scope.

VERSION B -- FreeRTOS.
  Three tasks, a queue from the ADC ISR, rate-monotonic priorities.

Then compare, with numbers rather than opinions:

  arm-none-eabi-size on both  -> flash and RAM cost of the kernel
  worst-case ADC response     -> the real-time comparison
  stack high water marks      -> one number vs three
  lines of code               -> usually closer than people expect

Now do the thing that decides it: add a 200 ms blocking flash write to
the product. Watch version A's worst-case loop pass jump to 200 ms and
the ADC deadline die. Watch version B absorb it by priority.

That experiment is the whole chapter, and the number you measured is a
better interview answer than any rule of thumb.
Golden rules
  • A superloop is interrupts plus non-blocking state machines, not a naive list of calls.
  • It can be fully real-time: worst-case response is the longest single pass through the loop.
  • No tasks means no races between tasks — one concurrency boundary instead of many.
  • One stack means stack analysis is one number.
  • Widely separated timescales are the strongest argument for a kernel, because hand-slicing slow work is what a context switch does for free.
  • Blocking third-party middleware is the most common practical reason, and an honest one.
  • State machines that wait on each other are hand-written continuations, which is the smell that says a task would be cheaper.
  • Fix the blocking calls before adding a kernel, or you import the problem and add races to it.
  • A cooperative or time-triggered scheduler is the real middle ground.

“Preferisce bare-metal o RTOS?”

“Nessuno dei due a priori: dipende, e il criterio ce l’ho. Un superloop fatto bene — interrupt per le cose urgenti e macchine a stati non bloccanti nel ciclo principale — è un’architettura seria, non da principianti: niente kernel in RAM e in flash, un solo stack quindi l’analisi dello stack è un numero solo, e soprattutto nessuna race fra task perché i task non ci sono. E può benissimo essere real-time: il caso peggiore è il giro più lungo del ciclo, e se so dire quel numero ho un sistema real-time. Passo all’RTOS quando ho scale di tempo molto diverse — un anello di controllo a un millisecondo insieme a una scrittura in flash da duecento — perché lì nel superloop dovrei affettare a mano il lavoro lento, che è esattamente quello che il cambio di contesto fa da solo. L’altro motivo, molto concreto, è una middleware di terzi che si blocca, tipo uno stack TCP/IP: quella non la riscrivo io. Quello che non faccio è mettere un RTOS per uscire da un superloop scritto male: se il problema è una HAL_Delay dentro una funzione, spostarla in un task non la risolve, mi porta dietro il problema e in più mi regala le race. Prima rendo tutto non bloccante e misuro, poi decido.”
