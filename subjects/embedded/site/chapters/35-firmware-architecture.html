Designing the software architecture of a firmware project

Three layers, one rule about which way the arrows point, and a seam that lets most of your code be compiled and tested on a PC. Plus the part nobody writes down: what a module's header is allowed to say, and what it must keep to itself.

From the advert

This chapter answers “Progettare l’architettura software per l’ambiente di sviluppo STM32” — a line that appeared in the anchor advert, and one of the very few that uses the word progettare rather than sviluppare.

The automotive advert in the corpus asks for the same thing in different words: “Progettare, sviluppare e mantenere requisiti e architetture software”. Both are asking whether you can decide where a line of code belongs before writing it, and defend the decision afterwards.

Three layers, and the only rule that matters

🧒 Simple

Split the code into three floors. The bottom floor knows about this exact chip: which pin, which register, which peripheral. The middle floor knows about things — a temperature sensor, a pump, a message link — without caring which chip they are wired to. The top floor knows what the product does: when the pump runs, what the alarm is, what to report.

Then one rule: a floor may only call downwards. The chip layer never calls the product layer. If it seems to need to, that is a signal travelling the wrong way, and the answer is a callback the upper floor registered — not a call upwards.

Everything else in this chapter follows from that rule, including the useful part: you can lift off the bottom floor, put a fake one underneath, and run the other two on your laptop.

🎓 Professional

The layering that survives contact with a real product:

  • Hardware layer. Startup, clocks, and the drivers that touch registers or vendor HAL calls. Everything from chapter 23 lives here, and it is the only place a peripheral name such as TIM3 or USART2 may appear.
  • Device / service layer. One module per real thing: the temperature sensor, the flow meter, the pump, the protocol link, the parameter store. Their headers speak in engineering units and outcomes, never in registers.
  • Application layer. The behaviour of the product: state machines (chapter 7), supervision, alarms, and the scheduling policy — superloop or RTOS tasks, which is chapter 38.

Dependencies point downwards only, and that is checkable rather than a matter of taste: grep the include graph, and an #include from a lower layer to a higher one is a defect. When a lower layer genuinely needs to notify upwards, invert it — the upper layer registers a callback or posts to a queue, and the lower layer calls a function pointer it was handed. That is dependency inversion, and on a microcontroller it costs one pointer.

Two cross-cutting concerns deserve deciding once, at the start, because retrofitting them is miserable. Error reporting: one error type, returned by value, checked at the layer that can do something about it — not an int in some modules and a bool in others. Time: a single monotonic tick source that everything reads, never a driver with its own private delay loop, so that timing is measurable rather than distributed.

Directory structure should make the layering visible from the file tree — hw/, dev/, app/, plus test/ and third_party/. If a reviewer cannot tell which layer a new file belongs in from its path, neither can the person who adds the next one.

What a header may say, and what it must not

🧒 Simple

A module's header file is a promise to everybody else: these are the things you may ask me to do. Everything not in that promise should be invisible — the variables, the buffers, the fact that there is a chip register involved at all.

The test is simple. If you replaced the whole module with a completely different implementation tomorrow, would anybody else's code need editing? If yes, you promised too much.

🎓 Professional

Concretely, for a C module pump: 

/* pump.h -- the entire promise. */
typedef struct pump pump_t;                 /* opaque: no fields here */

typedef enum { PUMP_OK, PUMP_E_RANGE, PUMP_E_HW } pump_err_t;

pump_err_t pump_init(pump_t *p, const pump_cfg_t *cfg);
pump_err_t pump_set_speed(pump_t *p, uint16_t rpm);
pump_err_t pump_read_speed(const pump_t *p, uint16_t *rpm_out);
void       pump_on_fault(pump_t *p, void (*cb)(void *ctx), void *ctx);

The design decisions in those six lines, each of which is worth being able to defend:

  • An opaque type. Callers hold a pointer and cannot reach inside, so the internals can change without touching a single other file. The struct is defined in the .c.
  • An explicit instance rather than a hidden global, so a second pump — or a test double — costs nothing. Firmware written around singletons is firmware that cannot be unit tested and cannot ship a two-channel variant.
  • Engineering units in the API. rpm, not a raw timer compare value. Scaling belongs inside the module that knows the hardware; a scaled integer convention rather than a float is the industrial habit, and chapter 58 is why.
  • Errors returned, not logged and swallowed. The caller decides whether a fault is fatal; the driver does not know.
  • No malloc. The caller owns the storage (chapter 11), which also means the memory map is knowable at link time.
  • Upward notification by callback, registered by the layer above.

Header hygiene that a reviewer will check: include guards, include what you use, forward-declare where you can, no #include "stm32f4xx.h" in anything above the hardware layer, and absolutely no variable definitions in a header — extern declarations only, since a definition in a header multiplies into one copy per translation unit (chapter 5).

The seam: why this architecture is testable on a PC

🧒 Simple

If the middle and top floors never mention the chip, then they are ordinary C. They can be compiled for your laptop, with a fake bottom floor that pretends to be the hardware, and tested in a second instead of in a flash-and-watch cycle.

That is not a testing trick. It is the actual reason for the layering: the architecture exists so that most of the product can be exercised without the product.

🎓 Professional

The seam is the hardware layer's interface, and it has to be a genuine interface rather than a convention. Two mechanisms, both ordinary C:

  • Link-time substitution. The device layer calls hw_i2c_write(...); the target build links hw_i2c_stm32.c and the host build links hw_i2c_fake.c. Zero runtime cost, and the build system decides — which is chapter 36.
  • A struct of function pointers passed at init, when you need two implementations in the same binary, or a test that swaps behaviour mid-run. Costs an indirect call; usually worth it at exactly one layer and nowhere else.

What the seam buys, in the order you will appreciate it: unit tests that run on every commit (chapter 64); protocol and state-machine logic exercised against recorded data; a simulator that lets the application team work before the board exists; and the ability to answer “does this bug need hardware to reproduce?” with evidence.

The trade to state honestly in an interview: a seam has a cost, and not every one pays for itself. Abstracting a GPIO toggle behind three layers to make it testable is architecture theatre — there is nothing to test. Put the seam where the logic is: the protocol parser, the control law, the state machine, the parameter store. Driver code stays thin enough to verify with a debugger and a scope, which is what those tools are for.

⚠ Trap

The vendor HAL leaks upwards, and six months later the architecture exists only in the diagram.

It happens the same way every time. CubeMX generates main.c with handles such as hi2c1 and htim3 as globals in the project root (chapter 30). Someone needs a sensor read from the application state machine on a deadline, calls HAL_I2C_Mem_Read(&hi2c1, ...) directly, and it works. Now the application layer depends on the vendor library, the host build will not compile, and the next person copies the pattern because it is the pattern they found.

Three defences, in increasing order of effectiveness. Regenerate into a fixed place — keep CubeMX output confined to the hardware layer, and treat it as a generated dependency rather than as your main. Make the host build part of CI: a layering violation then fails a build within minutes rather than being discovered at the next architecture review, because the fake hardware layer simply has no HAL_I2C_Mem_Read in it. And check the include graph mechanically — twenty lines of script that greps for forbidden includes per directory is a real architectural control, and the only one that is still enforced when you are on holiday.

The mirror-image failure is worth naming too: a hardware abstraction so elaborate that it reimplements the vendor HAL with different names, costs weeks, and abstracts nothing because it has exactly one implementation. The question that separates the two is “what is the second implementation?” If the honest answer is “the test fake”, that is a good answer. If there is no answer, do not build the layer.

Try it. This is the one chapter where the exercise is refactoring rather than building, and it is worth doing on code you already have.

1. Take any Cube project you have -- even a blinking LED with a UART --
   and draw its real include graph:

     grep -rn '#include "' Core Drivers | sed 's/:.*#include "/ -> /'

   Not the diagram you would draw; the one the compiler sees. Almost
   every beginner project turns out to be one layer with a HAL under it.

2. Restructure it into hw/ dev/ app/ without changing behaviour. Move
   files, fix includes, keep it compiling at every step. Time yourself:
   on a small project it is an hour, and it is an hour that teaches
   more about coupling than any article.

3. Now add the host build. A second Makefile target that compiles
   app/ and dev/ with gcc for your PC, plus hw/fake/*.c that records
   calls instead of touching registers. When `make host && ./test`
   runs your state machine on a laptop, the architecture is real.

4. Write the layering check and make it fail:

     ! grep -rl 'stm32\|HAL_' app/ dev/ || (echo "layer violation"; exit 1)

   Then deliberately add a HAL call in app/ and watch it fail. A control
   you have never seen fire is a control you do not know works.

5. Take one module and make its type opaque: move the struct from the
   header into the .c, add an init that takes a pointer, and fix
   everything that breaks. What breaks IS the coupling you had, and
   the list is the honest measure of the old design.
Golden rules
  • Three layers: hardware, device, application — and the file tree should make them visible.
  • Dependencies point downwards only. An include from a lower layer to a higher one is a defect, and it is mechanically checkable.
  • Notify upwards with a registered callback, never with a call upwards.
  • A peripheral name may appear only in the hardware layer. If TIM3 is in the application, the architecture has already failed.
  • Headers promise behaviour, not structure. Opaque types, explicit instances, engineering units, returned errors, no globals, no malloc.
  • Decide error handling and the time source once, at the start. Retrofitting either is a rewrite.
  • Put the seam where the logic is — protocol, control law, state machine — not around a GPIO toggle.
  • The host build is the architecture's test. If the code still compiles for a PC, the layering held; if it does not, it leaked.
  • Enforce layering with a script in CI, because a rule nothing checks is a preference.
  • Before adding an abstraction, name the second implementation. “The test fake” counts; silence does not.

“Come strutturerebbe da zero il software di una scheda?”

“Parto da tre livelli: il livello hardware, dove stanno startup, clock e i driver che toccano i registri o la HAL del produttore; un livello dispositivo, un modulo per ogni cosa reale — la pompa, il sensore, il link di comunicazione — che parla in unità ingegneristiche e non sa su che chip gira; e il livello applicativo, che è il comportamento del prodotto, le macchine a stati, gli allarmi. La regola è una sola: le dipendenze vanno solo verso il basso. Se un driver deve avvisare qualcuno, non chiama in su, ma richiama una callback che il livello sopra ha registrato. Il motivo pratico è che così i due livelli superiori sono C normale: li compilo per PC con un finto livello hardware sotto e li testo in CI, senza scheda. E quello per me è anche il test dell’architettura stessa — se la build per PC non compila più, vuol dire che la HAL è risalita dove non doveva, che è il modo tipico in cui questi progetti si degradano: uno chiama HAL_I2C_Mem_Read direttamente dall’applicativo perché ha fretta, e da lì in poi lo fanno tutti. Per questo metto anche un controllo automatico sugli include, venti righe di script: una regola che nessuno verifica è solo una preferenza. Dove non metto astrazioni: intorno a un GPIO. Prima di aggiungere un livello mi chiedo quale sia la seconda implementazione; se non c’è, non lo aggiungo.”
