The startup path: reset vector to main

Everything that runs before the first line of your code. It is short, it is readable, and it is the first place to look when a board does nothing at all — which is precisely the place beginners never look, because they assume main is where programs begin.

From the advert

Not named in this advert. But “debug e validazione dei sistemi” covers the case where a board comes back from production and does nothing, and this chapter is where that investigation starts.

What the hardware does, before any software

🧒 Simple

When power arrives, the processor does not know where your program is. So the rule is fixed in the silicon: look at the very first two words of memory. The first is where the stack should start; the second is the address of the first instruction to run.

That is the entire bootstrap. Two numbers, at a known place, put there by the linker.

🎓 Professional

On reset the Cortex-M core reads two words from the start of the vector table:

  • Word 0 — the initial Main Stack Pointer. Note this is unusual: on most architectures the stack pointer is set up by software. Here the hardware loads it, which is why C code can run immediately.
  • Word 1 — the reset vector, the address of Reset_Handler.

The table is at address 0 as far as the core is concerned, and on an STM32 the boot pins select what is aliased there — usually flash at 0x08000000, sometimes system memory (the factory bootloader) or SRAM. Later, SCB->VTOR can relocate the table, which is how an application launched by your own bootloader points the core at its own vectors (chapter 34).

The rest of the table is the exception and interrupt vectors in a fixed architectural order, which is why USART1_IRQHandler is called by that exact name: the startup file defines the table with those symbols, each declared weak and aliased to an infinite loop. Define a function with the right name anywhere in the project and the linker uses yours instead. Misspell it and yours is never called and nothing warns you — a real and frustrating bug with a trivial cause.

What Reset_Handler does

🧒 Simple

Before your program runs, somebody has to make its variables true. Variables that start with a value have that value stored in flash and must be copied into RAM. Variables that start at zero must actually be set to zero. That copying is what the startup code does.

🎓 Professional

Four steps, and the symbols come from the linker script (chapter 36):

1. Copy .data from flash to RAM. An initialised global lives in two places: its initial value in flash (the load address), and the variable itself in SRAM (the virtual address). The loop copies from _sidata to between _sdata and _edata. This is why an initialised global costs both flash and RAM, while a const one costs only flash (chapter 10).

2. Zero .bss. Uninitialised and zero-initialised globals occupy no flash; the startup loop writes zeros between _sbss and _ebss. This is the mechanism behind the C guarantee that globals start at zero — and it is why that guarantee does not extend to locals, which nobody zeroes.

3. Call SystemInit. On STM32 this is where the clock tree and the flash wait states are set up before the main clock is raised (chapter 25). Ordering matters: raising the clock before setting wait states reads garbage from flash.

4. Call __libc_init_array, then main. That call runs the constructors of file-scope C++ objects, which is why static C++ objects work at all — and why their order across translation units is unspecified — the static initialisation order problem, whose C++ side is chapter 20.

main is an ordinary function. Nothing in the hardware knows its name. If it returns, control falls into whatever the startup file does next — usually an infinite loop, which is why firmware main functions end in for(;;) rather than return 0.

⚠ Trap

A global that you rely on before the copy loop has run is not what you think it is — and the usual way to get there is by putting code in SystemInit, which runs before .data is copied on some startup files and after on others.

Check your startup file's actual order before assuming. The safe rule: SystemInit touches only hardware registers and local variables, never initialised globals.

The much more common failure in this area, though, is a board that appears dead, and there are only a few candidates. Attach a debugger and look at where the program counter actually is:

  • Stuck in Default_Handler — an interrupt fired that you never wrote a handler for. The vector table tells you which.
  • In HardFault_Handler — read the fault status registers rather than guessing (chapter 60).
  • At the reset vector, repeatedly — the watchdog is resetting you before initialisation finishes (chapter 28). Check the reset-cause flags in RCC; they survive the reset and tell you exactly which one it was.
  • Never reaching main at all, with word 0 of flash looking wrong — the image was linked or flashed at the wrong address, or the boot pins are selecting something other than flash.

Reading the reset-cause flags at startup and logging them is five lines that pay for themselves the first time a unit comes back from the field.

Try it. Step 1 is on a PC; the rest want a board and a debugger, and each takes minutes.

1. On a PC, see .data and .bss with your own eyes:

     cat > sec.c <<'EOF'
     int  zero_init;              /* .bss   -- no flash cost */
     int  value_init = 0x1234;    /* .data  -- flash AND ram  */
     const int constant = 0x5678; /* .rodata -- flash only    */
     int main(void) { return zero_init + value_init + constant; }
     EOF
     gcc -c sec.c -o sec.o && size -A sec.o

   Three variables, three different sections, three different costs.

2. On a board, open the startup .s file for your part. It is about 100
   lines and you can read all of it. Find the .data copy loop, the .bss
   zero loop, the SystemInit call and the __libc_init_array call. That
   is the whole of this chapter, in the file that is already in your
   project.

3. Set a breakpoint on Reset_Handler and single-step to main. Watch an
   initialised global change from garbage to its value as the copy loop
   runs past it. That moment makes .data concrete.

4. Break it deliberately: misspell an IRQ handler name -- USART1_IRQHander
   -- and watch the interrupt land in Default_Handler forever instead.
   No compiler warning, no linker error. Once you have seen it, you will
   recognise it in ten seconds rather than an hour.

5. Add reset-cause logging at the top of main:

     if (RCC->CSR & RCC_CSR_IWDGRSTF) log("reset: watchdog");
     if (RCC->CSR & RCC_CSR_PORRSTF)  log("reset: power on");
     RCC->CSR |= RCC_CSR_RMVF;   /* clear for next time */

   Then let the watchdog fire on purpose and confirm it tells you.
Golden rules
  • The core loads the initial stack pointer from word 0 and the reset vector from word 1. The hardware sets SP, which is why C runs immediately.
  • Boot pins select what is aliased at address 0, and VTOR relocates the table later — the mechanism a bootloader uses.
  • Handler names come from the startup file's weak symbols. Misspell one and yours is never called, with no warning.
  • .data is copied from flash to RAM; .bss is zeroed. That is where the guarantee about globals comes from, and it does not extend to locals.
  • SystemInit sets flash wait states before raising the clock, and must touch only registers and locals, never initialised globals.
  • __libc_init_array runs C++ static constructors, whose cross-file order is unspecified.
  • main is an ordinary function and must not return, which is why firmware ends in an infinite loop.
  • When a board seems dead, find the program counter: Default_Handler, HardFault, a watchdog reset loop, or never reaching main at all.
  • Log the reset cause from RCC at startup. Five lines that pay for themselves on the first field return.
