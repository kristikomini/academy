ARM Cortex-M: core, modes, registers

Sixteen registers, two stack pointers, two modes and one exception mechanism. It is a small architecture on purpose — and the exception model in particular is the reason C code can be an interrupt handler with no assembly wrapper at all.

From the advert

Not named in the anchor advert, which says STM32 and stops — but an STM32 is a Cortex-M with ST's peripherals around it, and the regional listings name Cortex-M directly. It is also the most portable knowledge in this course: the peripherals change when you change vendor, and this does not.

The register set

🧒 Simple

The processor has sixteen small boxes it can work with directly, called registers. Thirteen are for anything you like. The last three have fixed jobs: one remembers where the stack is, one remembers where to return after a function call, and one holds the address of the instruction being executed.

Everything else — every variable, every array — lives in memory and has to be loaded into one of those boxes before the processor can do arithmetic on it, then stored back.

🎓 Professional
  • R0–R12, general purpose. By the calling convention (AAPCS) R0–R3 carry the first four arguments and R0 the return value, and they are caller-saved; R4–R11 are callee-saved. That one sentence lets you read a disassembly and lets you write a C function that is called from assembly.
  • R13, the stack pointer — and there are two of them, banked: MSP, the main stack pointer, used by handlers and by default at reset, and PSP, the process stack pointer. An RTOS gives each task its own stack on PSP and keeps MSP for interrupts, which is exactly why FreeRTOS has a separate interrupt stack.
  • R14, the link register — the return address of the current call. It is why a leaf function needs no stack frame at all, and why a deep call chain does.
  • R15, the program counter.
  • xPSR, the program status register: the condition flags, the current exception number, and the Thumb bit — which must always be 1, because Cortex-M executes only Thumb-2 and clearing it faults instantly. A function pointer with a cleared low bit is exactly this failure.
  • CONTROL, two bits that matter: which stack pointer thread mode uses, and whether thread mode is privileged.

Two modes, two privilege levels. Handler mode is what the core is in while servicing an exception; it always uses MSP and is always privileged. Thread mode is everything else, and may be privileged or not. Bare-metal firmware runs privileged in thread mode and never thinks about it; an RTOS may drop tasks to unprivileged so that an MPU region can contain them. Being able to say which mode you are in, and which stack you are on, is the question behind half of all hard-fault debugging.

The exception model, and why an ISR is plain C

🧒 Simple

On many processors, an interrupt handler needs a wrapper written in assembly, because somebody has to save the registers the handler is about to use.

Cortex-M does that in hardware. When an interrupt arrives the processor itself pushes the registers a C function is allowed to clobber, then jumps to the handler. On return it pops them back. So the handler can be an ordinary C function with no special keyword and no wrapper — which is why the vector table in your project is just a list of function names.

🎓 Professional

On exception entry the core stacks eight words — R0–R3, R12, LR, PC and xPSR — onto the stack that was active, and with a floating-point unit in use it stacks the FPU registers too (lazily, by default). Those are precisely the caller-saved registers, so a compiler-generated C function is already a valid handler: the hardware saves what C would have clobbered, and the function's own prologue saves the rest. This is hardware stacking, and it is the single most practically useful fact about the architecture.

Consequences worth knowing:

  • EXC_RETURN. On entry, LR is loaded not with a return address but with a magic value encoding which mode and which stack to return to. Seeing 0xFFFFFFF9 or similar in LR during a debug session means you are in a handler — not that memory is corrupt.
  • Tail-chaining. If another exception is pending when one finishes, the core skips the pop and the push and goes straight to the next handler. Interrupt-heavy code is therefore cheaper than the naive arithmetic suggests.
  • Late arrival and pre-emption by priority, handled by the NVIC, which is part of the core and therefore identical across vendors.
  • The stack frame is your crash evidence. After a hard fault, the stacked PC tells you the instruction that faulted; with the fault status registers it usually names the bug in two minutes.

The four faults you will meet: HardFault (the catch-all, and the one that is actually an escalated other fault), MemManage (an MPU violation), BusFault (a bad address on the bus — frequently a peripheral whose clock is off) and UsageFault (undefined instruction, or an unaligned access, or a divide by zero if you enabled trapping). A production project should implement a fault handler that records the stacked PC, LR and the fault status registers into a no-init RAM area and resets, so that a field failure arrives as an address rather than as a story.

M0, M3, M4, M7 — and what actually differs

🧒 Simple

The family has several members. The small ones are cheap and slow, the big ones are fast and expensive, and the programming model is nearly the same across all of them — which is the whole point of a family.

🎓 Professional
  • Cortex-M0 / M0+ — the smallest. A reduced Thumb instruction set, fewer priority levels, often no MPU, and no bit-banding and no unaligned access. Code that works on an M4 can fault here, and that is the migration surprise.
  • Cortex-M3 — the full Thumb-2 set, hardware divide, bit-banding, MPU optional.
  • Cortex-M4 — M3 plus DSP instructions and an optional single-precision FPU. The F in a part name is the FPU, and using it means the float ABI flags from chapter 36 must be right everywhere.
  • Cortex-M7 — superscalar, with instruction and data caches. The caches are the reason an M7 needs cache maintenance around DMA buffers, which is the classic M7 bug described in chapter 27: the DMA writes to RAM, the CPU reads stale cache, and everything looks correct in the debugger because the debugger reads memory.
  • Cortex-M33 — ARMv8-M with TrustZone, increasingly common where security is a requirement.

Across all of them the memory map is architecturally fixed: code at 0x0000_0000, SRAM at 0x2000_0000, peripherals at 0x4000_0000, and the core's own peripherals — NVIC, SysTick, SCB, MPU — at 0xE000_E000. Those addresses are the same on every Cortex-M from every vendor, and CMSIS is ARM's header layer over them, which is why NVIC_EnableIRQ and __disable_irq look identical in an ST project and an NXP one.

⚠ Trap

A hard fault is treated as a mystery, when the core has already written down exactly what happened.

The usual reaction to HardFault_Handler is to add printfs and start bisecting the source. That is the slow path, and it is unnecessary: the core stacked eight words at the moment of the fault, and the System Control Block holds fault status registers naming the class of error.

The fast path, worth writing once and copying into every project: in the fault handler, work out which stack was in use (test bit 2 of EXC_RETURN in LR), take the stack pointer, and read the stacked PC — that is the faulting instruction; look it up in the map file or hand it to addr2line. Then read CFSR at 0xE000ED28 for the class, and BFAR or MMFAR for the offending address when the corresponding valid bit is set. Two minutes, no guessing.

Three faults that account for most of them, and what the evidence looks like. An address like 0x00000000 in BFAR is a null function pointer or null struct pointer. A PC with the low bit clear is a jump to a non-Thumb address — a corrupted function pointer, or a hand-built one. And a BusFault on an address in the 0x4000_0000 range is usually a peripheral accessed with its clock disabled, which ties straight back to chapter 21.

Try it. The first three need only a compiler; the rest want a board, and a Nucleo is about fifteen euro.

1. Read a disassembly and find the calling convention. Compile
   anything for ARM and look at a function with three arguments:

     arm-none-eabi-gcc -O1 -c -mcpu=cortex-m4 -mthumb f.c
     arm-none-eabi-objdump -d f.o

   Watch arguments arrive in R0, R1, R2 and the result leave in R0.
   Then give it five arguments and watch the fifth come off the stack.

2. Find the eight-word exception frame in the ARM programming manual
   (DDI0403 or the Cortex-M4 generic user guide) and write the order
   down: R0-R3, R12, LR, PC, xPSR. You will use it in exercise 4.

3. Write the fault handler ONCE, properly. A naked function that
   picks MSP or PSP from EXC_RETURN, passes the frame pointer to a C
   function, and stores PC, LR, CFSR, BFAR into a no-init section
   before resetting. Keep it; paste it into every future project.

4. Cause each fault on purpose and read the evidence:

     *(volatile uint32_t*)0 = 1;          // null pointer write
     ((void(*)(void))0x20000001)();       // jump to RAM, no code
     void (*f)(void) = (void(*)(void))0x08000100; f();  // low bit 0

   For each one, note PC, CFSR and BFAR, and check they say what you
   expected. Doing this deliberately, once, is what makes the real
   one at 3 a.m. a two-minute job.

5. Look at your RTOS project under the debugger and confirm which
   stack pointer is in use in a task versus in an ISR. If PSP is not
   in use in tasks, the RTOS is not configured the way you think.
Golden rules
  • R0–R3 carry arguments and R0 the return value; R4–R11 are callee-saved. That is enough to read any disassembly.
  • Two stack pointers. MSP for handlers and reset, PSP for RTOS tasks.
  • The Thumb bit must be set in every code address. A function pointer with the low bit clear faults immediately.
  • Handler mode is always privileged and always on MSP.
  • The core stacks eight words on exception entry, which is why a plain C function can be an interrupt handler.
  • EXC_RETURN in LR is not corruption; it encodes the mode and stack to return to.
  • Tail-chaining makes back-to-back interrupts cheaper than the naive arithmetic.
  • The stacked PC names the faulting instruction, and CFSR, BFAR and MMFAR name the class and the address. Read them instead of guessing.
  • M0 has no unaligned access and no bit-banding, so code that works on an M4 can fault there.
  • An M7 has caches, so DMA buffers need cache maintenance — and the debugger will hide the bug from you.
  • The core's own peripherals are at 0xE000_E000 on every vendor's part, which is what CMSIS wraps.

“Cosa succede esattamente quando arriva un interrupt su un Cortex-M?”

“Il core impila da solo otto parole sullo stack attivo — R0-R3, R12, LR, PC e xPSR — che sono esattamente i registri che una funzione C può sporcare. Per questo su Cortex-M un handler è una normalissima funzione C senza wrapper in assembly: l’hardware salva quello che salverebbe il chiamante, e il prologo della funzione salva il resto. In LR non ci va un indirizzo di ritorno ma un valore speciale, EXC_RETURN, che dice in che modo e su quale stack tornare: quando lo vedo nel debugger non è memoria corrotta, è la normalità. Ci sono due stack pointer, MSP e PSP: bare-metal uso solo MSP, con un RTOS i task stanno su PSP e gli interrupt su MSP. E la cosa che uso di più nel lavoro vero è che quel frame è la prova del crash: su un hard fault prendo il PC impilato, che è l’istruzione che ha fatto fault, poi leggo CFSR e BFAR nel System Control Block. In due minuti so se è un puntatore nullo, un puntatore a funzione con il bit Thumb a zero, o una periferica letta con il clock spento. Ho un handler di fault che scrive PC, LR e i registri di stato in una zona di RAM non inizializzata e resetta, così anche un guasto dal campo torna come un indirizzo e non come un racconto.”
