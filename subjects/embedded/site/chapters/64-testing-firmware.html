Testing firmware: off-target unit tests and HIL

Most of your code is ordinary C and can be compiled for a PC and tested in milliseconds. The rest needs a board, and some of it needs a board wired to a machine that can pretend to be the world. Knowing which is which — and where the seam between them goes — is the whole subject.

From the advert

Not named in the anchor advert, which says testare once, about protocols. It is here because regional listings ask for written test plans, because the automotive posting in the corpus sits on SWE.4 and SWE.5, and because being able to describe a test that runs without a board is what makes continuous integration possible at all.

Off-target: testing firmware on a PC

🧒 Simple

A surprising amount of firmware has nothing to do with the hardware: a protocol parser, a state machine, a scaling calculation, a ring buffer. That code is ordinary C, and ordinary C compiles and runs on your laptop.

Testing it there takes milliseconds instead of a flash-and-watch cycle, runs on every commit without a board attached, and can try a thousand awkward inputs that you would never manage by hand.

🎓 Professional

The prerequisite is the layering from chapter 35: if the device and application layers never mention a register, they compile for the host with a fake hardware layer beneath them. The seam is either link-time substitution — hw_i2c_stm32.c for the target, hw_i2c_fake.c for the host — or a struct of function pointers. That is not a testing trick added afterwards; it is the reason the architecture is shaped that way.

What deserves a host test, in rough order of payoff:

  • Protocol encode and decode — framing, CRCs, Modbus function codes, ISO-TP segmentation. Feed it truncated frames, doubled bytes, wrong lengths and garbage. This is where the bugs actually are, and none of them need silicon.
  • State machines — drive every transition including the illegal ones, and assert the machine never reaches an undefined state.
  • Scaling and units — the raw-count conversions from chapter 33, with the boundary values and the overflow cases.
  • Buffers and queues — full, empty, wrap, one-element, and the off-by-one at every edge.

Frameworks: Unity with CMock (C, tiny, the conventional embedded choice, often driven by Ceedling) or GoogleTest if the project is C++ and the team already knows it. Both are fine; what matters far more is that the tests run from one command and on every push (chapter 66).

Two techniques that punch above their weight. Record and replay: capture real traffic once with a logic analyser or a bus log, save it as a byte array, and replay it into the parser as a test. A field failure then becomes a permanent regression test, which is the cheapest quality improvement available to a firmware team. And property testing on the fuzzy edge: generate random byte streams into your frame parser and assert that it never reads outside its buffer and always recovers synchronisation. That single test finds more real defects than a dozen hand-written cases.

On target: what only the board can tell you

🧒 Simple

The host test proves the logic is right. It cannot prove the peripheral was configured correctly, that the timing holds, or that the whole thing survives a week of running.

🎓 Professional
  • Driver and integration tests on the board, ideally self-checking: a loopback test that ties TX to RX, an SPI transfer against a real device, a CRC of a flash sector after writing it. A small test harness that runs at boot behind a jumper is worth building.
  • Timing verification — worst-case ISR duration, loop period jitter, stack high-water marks. That is chapter 43, and it belongs in a report rather than in somebody's memory.
  • Soak tests. Run for days. A leak, a counter that wraps at 49.7 days, a fragmentation problem or a slow drift only appears with time, and the test is a table and patience.
  • Fault injection — the tests almost nobody runs and the ones that find what ships broken: pull the cable mid-transfer, brown out the supply, short an input, remove a sensor, cut power during a flash update. Every one of those is a defined behaviour in a requirement, or it is an accident waiting for a customer.
  • HIL — hardware in the loop: the real ECU wired to a rig that simulates its inputs and loads, running scripted scenarios automatically. In automotive that is a standard bench with restbus simulation; in a machinery company it is often a homemade panel with switches and a signal generator, and it counts just the same.

The pyramid for firmware is flatter than the web version, and worth being able to draw: many fast host tests, a moderate number of on-target integration tests, a few end-to-end tests on real hardware, and a short manual checklist for the things no rig can do — a connector's feel, a cabinet's temperature, a technician's workflow.

Making it run by itself

🧒 Simple

A test suite somebody has to remember to run is a test suite that stops being run. The value comes when it happens automatically on every change and tells you which change broke it.

🎓 Professional

A realistic firmware pipeline, in the order of what to build first:

  1. Build both targets — the firmware and the host test binary — on every push, with warnings as errors. Half the value arrives here, because the host build is also the layering check.
  2. Run the host tests, and publish the results.
  3. Run static analysis (chapter 65) and publish the size and the map (chapter 36), so flash consumption becomes a graph rather than a surprise.
  4. Optionally, a board on a runner. A Raspberry Pi with a probe attached, flashing the artefact and running the on-target suite nightly. It is more work than people expect and it is how you catch driver regressions before a release.

Coverage deserves one honest paragraph, because it comes up in interviews. On host tests gcov gives you line and branch coverage cheaply, and it is genuinely useful for finding code nobody exercises. It is a poor target: chasing a percentage produces tests that execute code without asserting anything, which is worse than no test because it reports green. Safety standards do demand coverage evidence, including MC/DC at the higher integrity levels, and that is a real obligation — but the reason to write a test is a behaviour worth protecting, not a number.

⚠ Trap

The mock is written from the same misunderstanding as the driver, so the test passes and the board does not work.

You believe the sensor returns its temperature register as big-endian. You write the driver that way, and you write the fake that way. The test passes forever, and the real device — which is little-endian, or which needs a repeated start, or which NAKs a read that follows a write without one — does not. The test proved that your code agrees with your belief, which is the one thing that was never in doubt.

The defences, in order of strength. Build the fake from captured traffic, not from your reading of the datasheet — a recorded transaction is evidence about the device, whereas a hand-written mock is a copy of your assumption. Keep one on-target test per driver, however small, that talks to the real part; its job is not coverage but to catch exactly this class of error. And when a field defect turns out to be a wrong assumption, fix the fake as well as the driver, so the regression test is real.

The same reasoning explains why the pyramid is flatter here than in web development: the proportion of firmware behaviour that depends on something outside your program is enormous, and a test suite that mocks the hardware entirely is testing a model of the world you wrote yourself. This is the same failure as the watchdog kicked by a timer ISR and the green build that only proves the linker ran: a check driven by the same thing it is checking always reports health.

Try it. Steps 1 to 4 need only a PC and a compiler.

1. Take the framing layer from chapter 47 and compile it for your PC.
   No test framework yet -- a main() with asserts is enough. Feed it a
   good frame, a truncated frame, a frame with a bad CRC, and two
   frames back to back in one buffer. If any of those four is not
   handled, you have found a real bug in twenty minutes.

2. Now add Unity, or GoogleTest, and turn those asserts into named
   test cases with one command to run them: `make test`. The naming
   matters more than the framework, because a failure should say what
   broke without anyone opening the file.

3. Write the property test: ten thousand random byte streams into the
   parser, asserting it never indexes outside its buffer and always
   resynchronises within N bytes. Run it under AddressSanitizer
   (-fsanitize=address), which is free on the host and impossible on
   the target. This exercise finds real defects; expect one.

4. Record and replay. Capture a real Modbus or I2C exchange with the
   logic analyser, paste the bytes into a C array, and make it a test
   case. That is how a field failure becomes a permanent regression
   test.

5. On the board: write a self-checking loopback test for your UART
   driver -- jumper TX to RX, send 256 bytes, verify. Then run it at
   boot behind a jumper so the production line can use it too.

6. Fault injection, once, deliberately: yank the RS-485 cable in the
   middle of a transfer and confirm the device recovers to a defined
   state rather than hanging. Then do it fifty times in a loop with a
   relay if you can. Almost nobody does this, and it is where the
   defects that reach customers live.
Golden rules
  • Most firmware logic is ordinary C. Compile it for the host and test it in milliseconds.
  • The host build is also the architecture check — if it stops compiling, the vendor HAL leaked upwards.
  • Test protocols, state machines, scaling and buffers off target, with the awkward inputs.
  • Build fakes from captured traffic, not from your reading of the datasheet.
  • Keep one on-target test per driver, to catch the assumption your mock shares.
  • Record and replay real traffic, so a field failure becomes a permanent regression test.
  • Property-test the parser with random input, under a sanitiser, on the host.
  • Soak tests and fault injection find what ships broken: pull the cable, brown out the supply, cut power mid-flash.
  • Measure worst-case timing and stack high-water marks, and put them in a report.
  • One command, every push, warnings as errors, plus size and static analysis published.
  • Coverage is a diagnostic, not a target. Tests that execute without asserting are worse than none.
  • A check driven by the same thing it checks always reports health.

“Come si testa un firmware, se il test non può girare sulla scheda?”

“La maggior parte del firmware in realtà non è hardware: il parser di protocollo, la macchina a stati, le conversioni di scala, i buffer circolari. Quella è C normale, quindi la compilo per il PC con uno strato hardware finto sotto e la testo in millisecondi, a ogni push, senza scheda. Ed è anche la verifica dell’architettura: se la build per host smette di compilare, vuol dire che la HAL del produttore è risalita dove non doveva. Sul parser ci metto anche un test a input casuali sotto AddressSanitizer, che sul PC è gratis e sul target è impossibile, e catturo del traffico vero con l’analizzatore logico per trasformarlo in test di regressione — così un guasto dal campo resta un test per sempre. La cosa a cui sto attento è il mock: se lo scrivo dalla mia interpretazione del datasheet, il test dimostra solo che il mio codice è d’accordo con la mia convinzione, che è l’unica cosa di cui non dubitavo. Quindi i fake li costruisco dal traffico registrato e tengo comunque un test su scheda per ogni driver, anche minimo. E poi le prove che quasi nessuno fa e che sono quelle che trovano i difetti che arrivano al cliente: soak test di giorni, e fault injection — staccare il cavo a metà trasferimento, abbassare l’alimentazione, togliere corrente durante un aggiornamento flash.”
