Memory-mapped I/O and the peripheral register

A pin is an address. That one sentence is the idea the entire field is built on — it is where the pointers of Part 2 meet actual copper, and it is why volatile exists.

From the advert

Not named in this advert, because it is below the level any advert describes. Every line about STM32, peripherals, protocols or debugging assumes it, and a candidate who cannot explain what GPIOA->ODR actually is has not yet started.

A pin is an address

🧒 Simple

On a PC, to draw on the screen you ask the operating system. On a microcontroller there is no operating system to ask. Instead, the hardware designers wired the peripherals so that they respond to ordinary memory addresses.

So turning on an LED is writing a number to a particular address. There is no function call to the hardware, no driver in between. You write to address 0x40020014 and a pin goes high, because somebody built a wire that does that.

🎓 Professional

The address space of a Cortex-M is 4 GB and mostly empty. The architecture fixes what lives where, which is why the map is the same shape on every vendor's part: 

0x0000_0000  code      (flash, usually aliased here too)
0x2000_0000  SRAM
0x4000_0000  peripherals   <- GPIO, UART, timers, ADC, DMA...
0x6000_0000  external RAM / devices
0xE000_0000  private peripheral bus (NVIC, SysTick, DWT, MPU)

A peripheral register is a fixed address inside that peripheral region, wired to logic rather than to memory cells. The load and store instructions are the same ones you use for a variable — there is no special I/O instruction on ARM, unlike x86 — but the effect is not.

The CMSIS headers express this as a struct overlay, and understanding that idiom is most of the chapter: 

typedef struct {
    __IO uint32_t MODER;    /* offset 0x00 -- pin mode          */
    __IO uint32_t OTYPER;   /* offset 0x04 -- push-pull / open-drain */
    __IO uint32_t OSPEEDR;  /* offset 0x08 */
    __IO uint32_t PUPDR;    /* offset 0x0C */
    __I  uint32_t IDR;      /* offset 0x10 -- input data, READ ONLY  */
    __IO uint32_t ODR;      /* offset 0x14 -- output data */
    __O  uint32_t BSRR;     /* offset 0x18 -- set/reset, WRITE ONLY  */
} GPIO_TypeDef;

#define GPIOA ((GPIO_TypeDef *) 0x40020000UL)

The struct's member offsets are laid out to match the hardware's register offsets exactly, so GPIOA->ODR compiles to a single store to 0x40020014. Note __IO, __I and __O: they expand to volatile, volatile const and volatile respectively, which is why chapter 06's poll loop works without you writing the keyword, and volatile const is exactly the read-only status register that chapter describes.

Why it is not memory, in four ways

🧒 Simple

It looks like a variable and it does not behave like one. Reading it twice can give two different answers. Reading it can change it. Writing a one can mean “clear this”. And some of it cannot be read at all.

🎓 Professional

1. It changes without you. A status bit is set by hardware. This is the whole of volatile, and it is why the optimiser must not cache a read (chapter 06).

2. Reading can have side effects. Many status flags are clear on read, and on several STM32 UARTs reading the data register clears the receive-not-empty flag. So inserting a debug read of a status register can make a bug disappear — the read consumed the event. This also makes stepping in a debugger misleading, because some debuggers read peripheral views automatically (chapter 60).

3. Writing does not always store. Many flags are cleared by writing one to them, not zero — “write 1 to clear” — so the natural REG &= ~FLAG is wrong twice over: it writes zero to the bit you meant, and it writes one back to every other currently-set flag, clearing events you never saw. For a W1C register, always write a plain mask with only the bit you intend: REG = FLAG;

4. Some registers are write-only, and some cannot be read back meaningfully. BSRR is the canonical example: writing bit n sets pin n, writing bit n+16 clears it, and reading returns nothing useful. That design exists precisely to give an atomic set or clear in one store — no read, no modify, no race with an interrupt that touches another pin on the same port (chapter 04). Using ODR ^= mask instead is the read-modify-write bug in its most common disguise.

⚠ Trap

You write a peripheral register, read it back, and it is still zero. Nothing is broken: the peripheral's clock is off.

Every peripheral on an STM32 has an enable bit in an RCC register, and they are off after reset to save power. Until it is set, the peripheral is not merely idle — its registers do not exist. Writes vanish, reads return zero, and there is no fault and no diagnostic. This is, without much competition, the most common single hour lost by somebody new to the part, and it is invisible because the code is correct. 

RCC->AHB1ENR |= RCC_AHB1ENR_GPIOAEN;   /* FIRST. Always. */
(void) RCC->AHB1ENR;                   /* read back: the write must land
                                          before the next access -- there
                                          are errata about exactly this */
GPIOA->MODER |= (1u << (5 * 2));       /* now this does something */

The read-back is not superstition. The write travels through a bus bridge, and on several families an immediate access to the freshly-enabled peripheral can be lost — it is documented in the errata sheet. CubeMX-generated code contains exactly this idiom, which is a good reason to read what it generates rather than skipping past it (chapter 30).

Try it. Steps 1 and 2 run on a PC. Steps 3 and 4 want a board, and are the ones that make it physical.

1. On a PC, prove the struct-overlay idiom to yourself with plain memory:

     #include <stdio.h>
     #include <stdint.h>
     typedef struct { volatile uint32_t A, B, C, D; } fake_t;
     static uint32_t backing[4];
     #define FAKE ((fake_t *)backing)
     int main(void) {
         FAKE->C = 0xAB;
         printf("offset of C = %zu, backing[2] = 0x%X\n",
                offsetof(fake_t, C), backing[2]);
     }

   offsetof(C) is 8 and backing[2] holds 0xAB. That is the entire
   mechanism -- a struct laid over an address. On a real part the
   address just happens to be wired to a pin.

2. Now open your part's reference manual at the GPIO chapter and find
   the register map table. Match every member of the CMSIS
   GPIO_TypeDef to a row. Do this once and the headers stop being
   magic.

3. On a board: comment out the RCC clock-enable line and watch every
   subsequent write silently do nothing. Read the register back and see
   zero. Then put it back. Ten seconds, and it inoculates you.

4. Toggle a pin two ways while watching it on a scope:

     GPIOA->ODR  ^= (1u << 5);            /* read-modify-write */
     GPIOA->BSRR  = (1u << 5);            /* atomic set */
     GPIOA->BSRR  = (1u << (5 + 16));     /* atomic clear */

   Compare the instruction counts in the disassembly. Then have a timer
   interrupt toggle a DIFFERENT pin on the same port in a tight loop,
   and watch the ODR version occasionally lose one of the two writes.
   That lost edge is the read-modify-write race, made visible.
Golden rules
  • A peripheral register is an address wired to logic, accessed with the same load and store instructions as any variable.
  • The CMSIS struct overlay matches member offsets to register offsets, so a member access is one store to a fixed address.
  • __IO is volatile and __I is volatile const — which is why the poll loop works without you writing the keyword.
  • Reading a register can have side effects. A debug read can consume the event and make a bug vanish.
  • Many flags are write-one-to-clear, so REG &= ~FLAG is wrong twice: it misses the bit and clears unrelated pending events.
  • BSRR sets and clears atomically in one store; ODR ^= mask is a read-modify-write and races with interrupts.
  • Enable the peripheral clock first, or the registers do not exist. Writes vanish and reads return zero, with no fault.
  • Read the enable register back before the first access — there are errata about exactly that.

“Cosa succede esattamente quando scrive su un registro di periferica?”

“È una normale store a un indirizzo: su ARM non esistono istruzioni di I/O separate, la periferica sta semplicemente nella mappa di memoria a partire da 0x40000000. Quello che cambia è che dietro quell’indirizzo non c’è una cella di memoria ma della logica, e quindi si comporta diversamente da una variabile: può cambiare da sola, quindi serve volatile — nei CMSIS c’è già, è __IO; leggerla può avere effetti collaterali, tanto che aggiungere una lettura di debug su un registro di stato a volte fa sparire il bug perché quella lettura ha consumato l’evento; e molti flag si azzerano scrivendoci uno, quindi REG &= ~FLAG è sbagliato due volte, perché non pulisce quello che voglio e in più riscrive uno su tutti gli altri flag attivi, cancellando eventi che non ho mai visto. Per i GPIO uso BSRR invece di ODR, perché setta e resetta in una sola store, atomica, mentre ODR ^= è read-modify-write e va in conflitto con un interrupt che tocca un altro pin della stessa porta. E la prima cosa che controllo quando una periferica ‘non risponde’: il clock nel registro RCC. Se è spento i registri non esistono proprio, le scritture svaniscono e le letture danno zero, senza nessun errore.”
