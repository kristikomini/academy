What ‘real-time’ actually means

Not fast. Predictable. This is the single distinction that decides whether an interviewer thinks you have worked on real-time systems or have only read the phrase in a job advert, and it takes one sentence to get right or wrong.

From the advert

This chapter answers “firmware in C/C++ su microcontrollori e sistemi operativi Real-Time (RTOS)”. The advert capitalises Real-Time and puts RTOS in brackets, as though the operating system were the definition. It is not: real-time is a property of a requirement, and an RTOS is one tool for meeting it.

Predictable, not fast

🧒 Simple

Imagine two people delivering post. One usually arrives in ten minutes but occasionally takes two hours. The other always takes thirty minutes, never less, never more.

The second one is real-time. If you are opening a valve so that a pump does not run dry, you do not care that it is usually quick. You care that it is never late.

🎓 Professional

A real-time system is one whose correctness depends on when the result is produced as well as on what the result is. A late answer is a wrong answer, not a slow one.

It follows that the quantity of interest is the worst case, and that the average is close to meaningless. A control loop with a mean latency of 40 µs and a worst case of 9 ms does not have a 40 µs latency; it has a 9 ms latency that is usually idle. This is also why throughput and real-time performance pull in opposite directions: caches, branch prediction, buffering and dynamic allocation all improve the average and widen the tail.

Three classes of deadline, and you should be able to give an example of each:

  • Hard — a missed deadline is a system failure. The commutation of a brushless motor; an airbag; an emergency-stop reaction.
  • Firm — a late result has zero value but causes no damage. A sample that missed its slot in a data-logging frame is discarded.
  • Soft — a late result still has some value, degrading with lateness. A display refresh; a temperature reading on an HMI.

Most real products contain all three at once, and part of design is knowing which is which. In the machine this advert describes, a leak interlock is hard, a flow sample is firm, and pushing a temperature to a web page is soft.

Latency, jitter, and why the tail is the number

🧒 Simple

Latency is how long it takes to respond. Jitter is how much that time varies. A system with lots of jitter is unpredictable even if it is usually quick.

🎓 Professional

Response time is the total from the event to the action: interrupt latency (about 12 cycles on a Cortex-M, plus any time spent with interrupts disabled or in a higher-priority handler), plus handler execution, plus any deferral to a task, plus that task's scheduling delay, plus its own execution.

Add them up as worst cases, not typical ones, and notice which term is usually largest: it is almost never your code. It is the longest critical section anywhere in the system, because during it nothing can pre-empt. One badly placed __disable_irq() around a 2 ms flash write sets a 2 ms floor on the worst-case latency of every interrupt in the product.

WCET — worst-case execution time — is the term to know. Establishing it properly is hard (it is undecidable in general, and caches and branch prediction make measurement pessimistic or optimistic depending on how you do it). In practice, on the class of part in this advert: measure with a GPIO pin and a scope over a long run including the awkward paths, take the maximum, and leave headroom (chapter 43).

A useful schedulability sanity check, if you have periodic tasks with deadlines equal to their periods and you assign priorities by rate: the rate-monotonic bound says a set of n tasks is certainly schedulable if total CPU utilisation stays under n(21/n − 1) — about 69 % as n grows. Above that it may still be fine, but it needs real analysis. Quoting the number is not the point; knowing that utilisation alone does not prove schedulability is.

⚠ Trap

“Real-time” in the phrase “real-time operating system” is a claim about the kernel's own bounds, not about your program. An RTOS guarantees that its operations — context switch, queue send, semaphore give — take a bounded time, and that the highest-priority ready task runs. That is all.

It does not make your code meet a deadline. You can miss every deadline in the product on a perfectly good RTOS by disabling interrupts too long, by choosing priorities badly, by calling a blocking HAL function with a 1000 ms timeout inside a control task, or by allocating memory in a fast path. Conversely, a bare superloop with no RTOS at all can be entirely real-time (chapter 38).

Saying “we used FreeRTOS, so it is real-time” is the answer that ends the technical conversation early.

Try it. Runs on a PC. This shows you the shape of a latency distribution, which is the thing the word “average” hides.

cat > jitter.c <<'EOF'
#include <stdio.h>
#include <time.h>
int main(void) {
    struct timespec a, b;
    long worst = 0, total = 0;
    for (int i = 0; i < 200000; i++) {
        clock_gettime(CLOCK_MONOTONIC, &a);
        /* stand-in for "the work": anything short */
        volatile int x = 0; for (int j = 0; j < 50; j++) x += j;
        clock_gettime(CLOCK_MONOTONIC, &b);
        long ns = (b.tv_sec - a.tv_sec) * 1000000000L
                + (b.tv_nsec - a.tv_nsec);
        total += ns;
        if (ns > worst) worst = ns;
    }
    printf("mean %ld ns   worst %ld ns   ratio %.0fx\n",
           total / 200000, worst, (double)worst / (total / 200000.0));
    return 0;
}
EOF
gcc -O2 jitter.c -o jitter && ./jitter

# On a PC the ratio is typically 100x or worse, because a general-purpose
# OS is optimised for throughput and will happily deschedule you.
#
# That ratio is the whole subject. A real-time design is one where you can
# state the worst number and defend it -- not one where the mean is small.
Golden rules
  • Real-time means predictable, not fast. A late answer is a wrong answer.
  • The worst case is the number. The average is nearly meaningless and usually misleading.
  • Hard, firm and soft deadlines coexist in one product, and knowing which is which is part of the design.
  • The longest critical section in the system sets a floor on the worst-case latency of every interrupt in it.
  • An RTOS bounds its own operations; it does not make your code meet a deadline.
  • A bare superloop can be perfectly real-time, and an RTOS project can miss every deadline.
  • Utilisation alone does not prove schedulability.

“Cosa intende quando dice che un sistema è real-time?”

“Che la correttezza dipende anche da quando arriva il risultato, non solo da quale sia: se arriva tardi è sbagliato, non è lento. Quindi il numero che conta è il caso peggiore, non la media — un anello di controllo con media 40 microsecondi e caso peggiore 9 millisecondi ha una latenza di 9 millisecondi, non di 40 microsecondi. Di solito il termine più grosso non è nemmeno il mio codice: è la sezione critica più lunga che c’è in giro, perché lì dentro niente può fare preemption. E distinguo i tipi di scadenza: l’interlock di un allarme è hard, un campione che salta il suo slot è firm, l’aggiornamento di una pagina web è soft — nello stesso prodotto ci sono tutti e tre. Una precisazione che mi sembra importante: l’RTOS garantisce i tempi delle sue operazioni e che giri il task a priorità più alta pronto. Non garantisce che io rispetti le scadenze: quello dipende da come assegno le priorità e da quanto tengo disabilitati gli interrupt.”
