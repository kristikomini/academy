DMA

Hardware that moves bytes while the CPU does something else. It is what makes a fast serial link and an idle processor compatible — and it brings a class of bug that only exists because two things now touch the same memory.

From the advert

Not named in this advert. It is nevertheless the difference between a UART that keeps up at 921600 baud and one that drops bytes (chapter 46), and it is a favourite follow-up once you mention high data rates.

A second mover on the bus

🧒 Simple

Normally the processor moves every byte itself: read it from the serial port, write it into memory, one at a time. If bytes arrive quickly, that is all the processor does.

DMA is a small separate machine whose only job is copying. You tell it where from, where to, and how many — and then it does the whole transfer on its own and tells you when it has finished. The processor is free the entire time.

🎓 Professional

A DMA controller is a second bus master. It arbitrates for the bus alongside the core, so a transfer is not free — it steals bus cycles — but it costs no instructions, and crucially no interrupts per byte.

Configuration is always the same five questions: source address, destination address, whether each increments, the transfer width, and the count. Plus the mode:

  • Normal — transfer N items and stop. For a known-length write.
  • Circular — on reaching the end, wrap to the start and continue forever. This is what makes a receive ring buffer work with zero CPU involvement, and it is the mode that matters most (chapter 46).

Three interrupts are available and you usually want the first two: half-transfer, transfer-complete, and transfer error. Half-transfer exists so that in circular mode you can process the first half of the buffer while the controller is filling the second — a double-buffer with one buffer, and the standard idiom for continuous ADC sampling or audio.

The remaining-count register is the other thing worth knowing: it counts down, so received = buffer_size - remaining tells you how far the transfer has got at any moment. That is precisely how the Modbus idle-line trick measures a variable-length frame (chapter 50).

On STM32, note that DMA request routing is not arbitrary: each peripheral can only reach certain channels or streams. On F4-class parts this is a fixed table in the reference manual and a common source of “the DMA does not trigger”; on newer families a DMAMUX makes any request reachable from any channel, which removes the problem entirely.

Two things now touch the same memory

🧒 Simple

The convenience has a price. Your program and the copying machine are both looking at the same buffer at the same time, and neither tells the other what it is doing.

So you have to be careful about where that buffer lives, how long it lives, and when it is safe to look at.

🎓 Professional

The buffer must outlive the transfer. Starting a DMA from a local array and returning from the function is a use-after-free with hardware doing the writing: the controller keeps filling stack memory that other code is now using. Buffers are static or file-scope, always.

The compiler does not know the DMA exists. Mark buffers volatile — or at minimum be certain the accesses around the transfer are not reordered or cached in a register (chapter 06). Note this is necessary and not sufficient, which is the next point.

The buffer must be in memory the DMA controller can reach. On an STM32F4 the core-coupled CCM RAM is invisible to DMA1 and DMA2; a buffer placed there produces a transfer error or silent nothing. On an H7, DMA1 and DMA2 cannot reach the fast DTCM where the linker puts things by default, which is why H7 examples place DMA buffers in a specific SRAM section. This is a linker-script question (chapter 36) and it is the second most common DMA failure.

Alignment and width. A 32-bit transfer needs 32-bit-aligned addresses; a mismatch between peripheral width and memory width has defined but surprising packing behaviour. Check both against the reference manual rather than assuming.

⚠ Trap

On a part with a data cache — Cortex-M7, so STM32F7 and H7 — DMA and the CPU can hold two different versions of the same memory, and nothing warns you. This is the single nastiest DMA bug and it is worth being able to describe precisely, because it is a favourite interview question for anyone claiming H7 experience.

The cache sits between the core and the bus; the DMA controller sits on the bus. So:

  • Receive. DMA writes new data into SRAM. The core reads the buffer and gets a stale cache line from before the transfer. You must invalidate the cache range after the transfer completes and before reading.
  • Transmit. The core writes the buffer; with a write-back cache the data is still sitting in the cache, not in SRAM. DMA reads SRAM and sends the old contents. You must clean the cache range before starting the transfer.

The symptom is the worst possible kind: it works in debug (where the cache is often disabled or the timing differs), works with small buffers, works most of the time, and corrupts occasionally under load. Two fixes, and the second is usually better: call SCB_CleanDCache_by_Addr and SCB_InvalidateDCache_by_Addr around every transfer — noting that they operate on 32-byte cache lines, so your buffer must be 32-byte aligned and a multiple of 32 bytes or you will corrupt a neighbour — or configure an MPU region covering the DMA buffers as non-cacheable and stop thinking about it.

Try it. This one genuinely wants a board, and it is among the best reasons to have one.

1. Start with UART receive in circular DMA plus idle-line detection
   (chapter 46). Toggle a GPIO pin inside the IDLE interrupt and put it
   on an analyser alongside the serial line. You will see ONE pulse per
   message instead of one per byte.

2. Measure what that buys. Instrument the idle task with a pin
   (chapter 43) and compare CPU load at 115200 baud between:

     - interrupt per byte
     - circular DMA + IDLE

   Then raise the baud rate until the interrupt version drops bytes and
   note where. That number is your own answer to "when do you need DMA?"

3. Break it on purpose, three ways, and learn each failure's signature:

     - put the DMA buffer on the stack of a function that returns
       -> corruption somewhere unrelated, intermittently
     - place the buffer in CCM RAM (F4) or DTCM (H7)
       -> transfer error, or simply nothing, with no obvious cause
     - forget the half-transfer interrupt in circular mode and process
       only on complete
       -> the first half is overwritten while you are still reading it,
          at high rates only

4. On an F7 or H7 with the D-cache enabled: run a receive without
   invalidating and watch stale data appear under load. Then add the
   invalidate, with a 32-byte-aligned buffer. Then try the MPU
   non-cacheable region instead and notice how much less there is to
   get wrong.
Golden rules
  • DMA is a second bus master: it costs bus cycles, but no instructions and no interrupt per byte.
  • Circular mode plus the half-transfer interrupt is how you process one half while the other fills.
  • The remaining-count register counts down, so buffer size minus remaining is how far the transfer has got — the basis of variable-length frame reception.
  • DMA buffers must be static or file-scope. A local array plus a return is a use-after-free with hardware writing.
  • The buffer must live in memory the controller can reach — not CCM on F4, not DTCM on H7.
  • Request routing is restricted on older families and free with a DMAMUX on newer ones.
  • With a data cache, clean before transmit and invalidate after receive, or the CPU and DMA see different data.
  • Cache maintenance works on 32-byte lines, so align and pad the buffer or you corrupt its neighbour.
  • An MPU non-cacheable region for DMA buffers removes the whole class of bug.

“Ha usato il DMA? Quali problemi ha incontrato?”

“Sì, soprattutto in ricezione su UART: DMA circolare più interrupt di linea idle, così ho un interrupt per messaggio invece di uno per byte e la lunghezza la ricavo dal contatore residuo del DMA, che decrementa. I problemi sono sempre gli stessi tre. Primo, il buffer deve sopravvivere al trasferimento: se parte da un array locale e la funzione ritorna, il controller continua a scrivere nello stack che nel frattempo usa qualcun altro, e la corruzione salta fuori altrove. Secondo, il buffer deve stare in una memoria che il controller raggiunge davvero: sugli F4 la CCM non è visibile al DMA, sugli H7 la DTCM non lo è per DMA1 e DMA2, e il sintomo è un transfer error oppure semplicemente niente. Terzo, e è il più cattivo, sui Cortex-M7 con la data cache attiva: la cache sta fra il core e il bus, il DMA sta sul bus, quindi in ricezione io leggo una linea di cache vecchia e in trasmissione il DMA legge la SRAM mentre il mio dato è ancora in cache. Va fatta invalidate dopo la ricezione e clean prima della trasmissione, con il buffer allineato a 32 byte perché le operazioni lavorano per linee di cache. Se posso preferisco configurare una regione MPU non cacheable per i buffer DMA, così il problema non si pone: funziona in debug e si corrompe sotto carico è il tipo di bug che non voglio.”
