Timers, PWM and input capture

A counter, a prescaler, a reload value and a few compare registers — and from those four things come PWM, frequency measurement, pulse width measurement, quadrature decoding, precise triggering of the ADC, and most of the software loops you should not have written.

From the advert

Not named directly, and behind two lines that are. A liquid-cooling controller drives pompe e ventole — pumps and fans — which is PWM, and reads their tachometer feedback, which is input capture. The same peripheral also triggers the ADC at exact instants, which is what makes a control loop deterministic rather than approximately periodic.

The counter, and the arithmetic

🧒 Simple

A timer is a counter that counts clock pulses. Two numbers control it. The prescaler decides how many clock pulses make one count — dividing a fast clock down to a manageable speed. The reload value decides how high it counts before starting again at zero.

So the time to go round once is: how long one count takes, multiplied by how many counts. Every timer question is a version of that sentence.

🎓 Professional
f_timer  = f_clk / (PSC + 1)
f_period = f_timer / (ARR + 1)        /* the update event rate */

/* 1 kHz PWM from an 84 MHz timer clock:
   pick PSC so the counter has useful resolution, then ARR.       */
PSC = 83     -> f_timer = 84e6 / 84 = 1 MHz   (1 us per count)
ARR = 999    -> f_period = 1e6 / 1000 = 1 kHz (1000 steps of duty)
CCR = 250    -> 25 % duty

Both PSC and ARR are minus one registers, which is responsible for a steady trickle of off-by-one frequency errors, and the trade between them is the real design decision: the prescaler costs you resolution, so use the smallest prescaler that keeps ARR inside the counter's width. A 16-bit timer with ARR = 999 gives you a thousand duty steps; the same frequency with ARR = 9 gives ten, and a fan that can only be driven in 10 % jumps.

Counting modes matter more than they look. Up is the default. Centre-aligned counts up then down, halving the update rate for the same ARR but producing symmetric pulses — standard in motor control because it puts less harmonic energy on the supply. And one-pulse mode generates a single pulse of an exact width and stops, which replaces an entire category of bit-banged delay.

Remember the clock-doubling rule from chapter 25: a timer on an APB bus whose prescaler is not 1 is clocked at twice the bus frequency. Half of all “my period is exactly double what I calculated” reports are that line.

PWM out, capture in

🧒 Simple

PWM means switching a pin on and off very fast, and changing what fraction of the time it is on. A motor or a heater cannot follow the switching, so it behaves as if it were getting a fraction of the power. An LED does the same and appears dimmed.

Input capture is the mirror image: instead of the timer driving a pin, a pin drives the timer. When an edge arrives, the hardware writes down the exact count at that instant. Two of those numbers and you know how long something took, with no software delay in the measurement at all.

🎓 Professional

PWM is output-compare mode: each channel has a CCR, the output changes state when the counter reaches it, so duty is CCR / (ARR + 1). Two things to get right. Use preload (the shadow registers, OCxPE and ARPE) so a new CCR takes effect at the next update event rather than mid-cycle — without it, writing a smaller CCR after the counter has passed it produces a glitched cycle at full width, which on a power stage is a real current spike. And on the advanced timers, complementary outputs with dead-time insertion exist precisely so that the high-side and low-side switches of a bridge are never on together; the dead time is a hardware guarantee, and it is not something firmware should be attempting in software.

Input capture latches CNT into CCR on a selected edge, and the useful patterns are:

  • Frequency — capture on every rising edge and subtract consecutive values. Unsigned subtraction handles the counter wrapping correctly, which is one of the few places where relying on wrap-around arithmetic is right rather than sloppy.
  • Pulse width / duty — PWM input mode uses two channels on the same pin, one capturing rising and one falling, giving period and width simultaneously with no software involvement.
  • Tachometer feedback — a fan's tach output is two pulses per revolution, so RPM is a division; and a stalled fan produces no edges at all, which means the missing capture is the fault signal. That should be a timeout, not an infinite wait.
  • Encoder mode — two channels decode quadrature in hardware, counting up and down with direction, so position is simply CNT. Doing this with interrupts instead is a classic way to lose counts at speed.

Two integrations worth knowing exist, because they are what makes a timer a system component rather than a gadget. A timer's update event can trigger the ADC directly, so samples are taken at exact instants regardless of what the CPU is doing — the foundation of any real control loop. And a timer can trigger DMA, so a whole table of duty values or output patterns can be played out with no CPU involvement whatsoever (chapter 27).

What a timer replaces

🧒 Simple

Most beginner firmware is full of waiting: wait a bit, toggle a pin, wait a bit. Every one of those waits is the processor doing nothing while the rest of the program cannot run.

Nearly all of them can be handed to a timer, which does the waiting in hardware and tells you when it matters.

🎓 Professional
  • A delay loop becomes a periodic interrupt or a state machine driven by a tick (chapter 7).
  • A software PWM in a loop becomes a hardware channel, with exact timing and zero jitter no matter what else is running.
  • A bit-banged protocol becomes a timer-driven one, or better, a real peripheral.
  • “Measure how long this takes” becomes a free-running counter read — start, end, subtract. This is the measurement instrument of chapter 43, and a spare timer left free-running at 1 MHz is the cheapest profiler in existence.
  • A timeout becomes a comparison against that counter, rather than a counted loop whose duration changes with optimisation settings.

The reason this matters beyond elegance: hardware timing does not degrade under load. A software delay is correct when the system is idle and wrong when it is busy, which means it is wrong precisely when the system is under the conditions you care about.

⚠ Trap

The capture-overflow bug: a measurement that is right for short intervals and silently wrong for long ones.

Capture two edges, subtract, and you have the interval — as long as the counter wrapped at most once, which unsigned arithmetic handles for you. Wrap twice and the result is plausible and wrong: a fan turning slowly reports a high RPM, a period measurement returns a small number, and nothing anywhere indicates a problem. It is the shape of bug that survives testing, because the bench case is a fast signal.

The fix is to count the overflows: enable the update interrupt alongside the capture interrupt and build a wider timestamp, or use a 32-bit timer where the part has one. Then decide what a very long interval means — a stopped fan, a disconnected sensor — and return that as a defined state rather than as a number. The general rule, which recurs throughout this course: a measurement needs a defined out-of-range answer, and the absence of an event must be detectable in bounded time.

Two smaller traps in the same family. Reading CNT on a 32-bit timer is fine, but reading a 16-bit counter and a separate overflow variable is a race unless you re-read and check for a wrap in between. And enabling a capture interrupt without reading CCR in the handler leaves the flag set forever, so the interrupt re-fires immediately and the system appears to hang — the same status-flag family as chapter 21.

Try it. A Nucleo and the logic analyser from chapter 29 cover all of this; the first exercise is arithmetic and needs nothing.

1. Do the arithmetic by hand before touching CubeMX. From an 84 MHz
   timer clock, find PSC and ARR for: 1 kHz with at least 1000 duty
   steps; 25 kHz (above audible, for a fan) with at least 500 steps;
   and 50 Hz with 20000 steps for a servo. Then check them in CubeMX
   and see whether you hit the same values.

2. Generate PWM on a pin and measure it on the logic analyser.
   Change duty at run time and confirm the edge moves. Then remove
   the preload bit and change duty rapidly in a loop -- look for the
   glitched cycle. That is why preload exists.

3. Loop a PWM output back into an input-capture pin with a jumper
   wire and measure your own signal. Print period and duty. Agreeing
   with what you set is the satisfying part; the point is that you now
   own both halves.

4. Then make it fail: lower the PWM frequency until the capture
   interval overflows the counter twice, and watch the measurement
   become confidently wrong. Fix it by counting update events. This
   is the trap above, felt rather than read.

5. Free-run a spare timer at 1 MHz and use it to measure how long
   your own functions take -- read CNT, call, read again, subtract.
   Keep the maximum. That is a profiler in four lines, and chapter 43
   builds on it.

6. If you have an encoder or can fake one with two PWM channels
   90 degrees apart, configure encoder mode and watch CNT track
   position and direction in hardware, with no interrupts at all.
Golden rules
  • Period is (PSC + 1)(ARR + 1) / f_clk, and both registers are minus-one registers.
  • Use the smallest prescaler that keeps ARR in range; the prescaler costs duty resolution.
  • A timer on an APB bus with a prescaler above 1 runs at twice the bus clock.
  • Use preload on CCR and ARR, so a duty change lands at the update event and never mid-cycle.
  • Dead time on complementary outputs is a hardware guarantee. Never attempt it in software.
  • Input capture timestamps in hardware, so the measurement carries no software latency.
  • Count overflows, or the measurement is silently wrong for long intervals.
  • Define what “no edge arrived” means — a stopped fan is a state, not a missing number — and detect it with a timeout.
  • Read CCR in the capture handler, or the flag stays set and the interrupt never stops.
  • Let the timer trigger the ADC and the DMA. That is what makes sampling exact and the CPU irrelevant.
  • Every delay loop is a timer you have not configured yet, and hardware timing does not degrade under load.

Per i giri userei l’input capture sul segnale di tach: l’hardware mi salva il valore del contatore esattamente sul fronte, quindi nella misura non c’è nessuna latenza software, e sottraendo due catture consecutive ho il periodo — la sottrazione fra unsigned gestisce da sola il wrap del contatore. La cosa a cui sto attento è l’overflow: se il contatore gira due volte la misura torna plausibile e sbagliata, e una ventola lenta mi risulta veloce. E soprattutto decido cosa vuol dire ‘non è arrivato nessun fronte’: ventola ferma è uno stato, non un numero mancante, quindi ci va un timeout e un valore di guasto esplicito.
