Types, sizes, and the integer rules that catch everyone

int is not 32 bits because you would like it to be. Fixed-width types, the promotion rules nobody reads, signed overflow, and the comparison that is always false on one compiler and fine on another.

From the advert

This chapter answers “Ottima conoscenza della programmazione in C (e C++) in ambito embedded”. On a PC the integer rules are trivia; on a microcontroller, where a variable may be 8 bits and a register exactly 32, they are the difference between code that works and code that works on the part you tested.

What the standard actually guarantees

🧒 Simple

You might expect int to mean “a number, 32 bits wide”. It does not. C only promises that an int is at least 16 bits, and leaves the exact size to whoever wrote the compiler.

So if you want exactly eight bits, ask for exactly eight bits: uint8_t. The name says what you mean, and it means the same thing everywhere.

🎓 Professional

The standard specifies minimum ranges, not sizes. Guaranteed minimum widths: char 8, short 16, int 16, long 32, long long 64. On arm-none-eabi (any Cortex-M) int is 32 bits and long is 32 bits; on an 8-bit AVR int is 16; on 64-bit Linux long is 64. Code that assumes any of these is portable only by luck.

So use <stdint.h>, and pick deliberately:

  • uint8_t, int16_t, uint32_t — exactly that many bits. Use these for anything that touches hardware, a protocol frame or a stored structure, where the width is part of the contract.
  • uint_fast8_t — at least 8 bits, whichever is fastest on this machine. Useful for loop counters, where forcing 8 bits costs masking instructions.
  • uint_least16_t — the smallest type with at least 16 bits.
  • size_t for sizes and counts of objects, ptrdiff_t for pointer differences, uintptr_t for an integer that must hold a pointer.

One more: char has three distinct types — char, signed char, unsigned char — and whether plain char is signed is implementation-defined. It is signed on x86 gcc and unsigned on ARM. Code that does char c = getbyte(); if (c < 0) behaves differently on your PC and on your target. For bytes, write uint8_t.

Integer promotion, and the arithmetic you did not ask for

🧒 Simple

Before C does arithmetic on small types, it quietly turns them into int first. So two uint8_t values added together are actually added as ints, and the result is an int.

Most of the time this is harmless. It stops being harmless when you shift, when you mix signed and unsigned, or when you assume the result wrapped at 8 bits.

🎓 Professional

Two rules, applied in this order:

1. Integer promotion. Any type narrower than int is converted to int (or unsigned int if int cannot represent all its values) before almost any arithmetic. So uint8_t a = 200, b = 100; a + b is 300, an int — not 44. It only becomes 44 if you assign it back to a uint8_t.

2. Usual arithmetic conversions. When the two operands have different types after promotion, they are brought to a common type — and when ranks are equal, the unsigned type wins. This is the source of the classic: 

int          i = -1;
unsigned int u =  1;
if (i < u) { /* NOT taken */ }
/* i is converted to unsigned: -1 becomes 4294967295, which is not < 1 */

/* The same bug, in the shape it really appears in: */
for (size_t i = n - 1; i >= 0; i--) { /* infinite: size_t is never < 0 */ }

And the embedded-specific one, which is a genuine portability bug rather than a curiosity: 

uint8_t reg = 0x80;
uint32_t v = reg << 8;     /* reg promotes to int, so this is fine here... */

uint16_t crc = 0xFFFF;
uint32_t x = crc << 16;    /* ...but this shifts an int by 16 into the sign
                              bit and beyond. On a 16-bit int target it is
                              undefined behaviour outright. */
uint32_t y = (uint32_t)crc << 16;   /* say what you mean */
⚠ Trap

Signed overflow is undefined behaviour; unsigned overflow is defined. This is not pedantry, and it is not the same as “it wraps”.

unsigned arithmetic is specified to wrap modulo 2N, which is why timer-difference arithmetic works correctly across a rollover if and only if the counters are unsigned: (uint32_t)(now - then) is right even when now has wrapped past zero.

signed overflow is undefined, which means the optimiser is allowed to assume it never happens — and it does assume it. It will delete a check like if (x + 1 < x) entirely, because in a program with no UB that can never be true. This is chapter 13's territory, and it is why a signed millisecond counter is a bug waiting for uptime to reach 24.8 days.

Also undefined: shifting by a negative amount, or by an amount greater than or equal to the width of the promoted type. x >> 32 on a 32-bit int is not zero — it is undefined, and on ARM it very often returns x unchanged, because the hardware shifter uses only the low 5 bits.

Try it. On a PC. Every one of these prints something a careful reader would not predict, and each is a real bug someone has shipped.

cat > ints.c <<'EOF'
#include <stdio.h>
#include <stdint.h>
int main(void) {
    uint8_t a = 200, b = 100;
    printf("1) %d  (not 44: both promote to int)\n", a + b);

    int i = -1; unsigned u = 1;
    printf("2) %s  (i < u is FALSE)\n", (i < u) ? "true" : "false");

    uint16_t crc = 0xFFFF;
    printf("3) 0x%08X  (shifted as int, sign bit reached)\n",
           (unsigned)(crc << 16));
    printf("4) 0x%08X  (cast first: what you meant)\n",
           (unsigned)((uint32_t)crc << 16));

    char c = 200;               /* signed on x86, UNSIGNED on ARM */
    printf("5) %d  (compile this for ARM and it prints 200)\n", c);

    uint32_t now = 5, then = 0xFFFFFFF0;
    printf("6) %u  (unsigned wrap is DEFINED: correct across rollover)\n",
           (uint32_t)(now - then));
    return 0;
}
EOF
gcc -Wall -Wextra -Wconversion -Wsign-compare ints.c -o ints && ./ints

# Now read the WARNINGS as carefully as the output. -Wconversion and
# -Wsign-compare catch most of this class at compile time, which is why
# firmware teams turn them on and then turn on -Werror.
Golden rules
  • C guarantees minimum ranges, not sizes. int is at least 16 bits and nothing more.
  • Use stdint.h exact-width types for hardware, protocols and stored data, where width is part of the contract.
  • Plain char is unsigned on ARM and signed on x86. For bytes, write uint8_t.
  • Everything narrower than int is promoted to int before arithmetic. Two uint8_ts add as ints.
  • When ranks match, unsigned wins the conversion — which is why -1 < 1u is false.
  • Unsigned overflow wraps and is defined; signed overflow is undefined and the optimiser assumes it cannot happen.
  • Cast before you shift when the result is wider than the operand.
  • Shifting by the width of the type or more is undefined, and on ARM often returns the value unchanged.

“Perché in embedded si usano uint8_t e uint32_t invece di int?”

“Perché il C garantisce degli intervalli minimi, non delle dimensioni: int è almeno 16 bit, e basta. Su Cortex-M è 32, su un AVR a 8 bit è 16 — quindi se scrivo un frame di protocollo o mappo un registro con int, funziona finché non cambio target. Con <stdint.h> la larghezza fa parte del contratto. Poi c’è la parte che sorprende: anche usando uint8_t, prima di ogni operazione tutto viene promosso a int, quindi 200 + 100 su due uint8_t fa 300, non 44 — fa 44 solo quando lo riassegno. E quando mescolo signed e unsigned della stessa dimensione vince unsigned, per cui -1 < 1u è falso. Un dettaglio pratico: su ARM il char puro è unsigned, su x86 è signed, quindi per i byte scrivo sempre uint8_t. E i contatori di tempo li tengo unsigned, perché l’overflow unsigned è definito e la differenza resta corretta anche dopo il rollover; con signed sarebbe undefined behaviour.”
