What is actually on the die

A microcontroller is not a small computer. It is a CPU sharing a bus with a dozen independent hardware state machines, and almost everything that surprises a beginner follows from taking that sentence literally.

From the advert

Not named in any advert, because it is the ground everything else stands on. Reading a block diagram and a reference manual is the day-one skill: every later chapter — registers, interrupts, DMA, clocks — is a detail of the picture drawn here.

The parts, and the bus between them

🧒 Simple

Open the datasheet of any microcontroller and the first picture is a block diagram. In the middle is the processor. Around it are blocks with names like UART, SPI, TIMER, ADC, DMA. Between them is a line called the bus.

The processor is one of the blocks, not the boss of all of them. Each peripheral is its own small machine that keeps working while the processor does something else entirely — a timer counts with nobody watching, a UART shifts bits out one at a time on its own schedule. The processor's job is to set them up, and then to be told when something needs attention.

Two kinds of memory sit on the same bus: flash, which holds your program and survives power off, and RAM, which holds your variables and does not.

🎓 Professional

Concretely, on a mid-range STM32:

  • The core — an ARM Cortex-M, licensed from ARM and identical across vendors (chapter 22). It is the least vendor-specific thing on the die, which is why Cortex-M knowledge transfers between an STM32, an NXP and a Nordic part and peripheral knowledge does not.
  • Flash, typically at 0x0800_0000, with wait states because it is slower than the core, plus a prefetch and cache in front of it on faster parts.
  • SRAM, typically at 0x2000_0000, often split into banks with different bus connections — which matters the moment you use DMA.
  • The peripherals, each a block of registers in the address space (chapter 23), grouped onto buses named AHB and APB by how fast they need to be.
  • The bus matrix, which is the part most people never picture: several masters — the core, each DMA controller, sometimes Ethernet or USB — competing for several slaves. This is why a DMA transfer can slow the CPU down, and why “the CPU is idle” is not the same as “the memory is idle”.
  • The clock tree and the power domains, which decide which of the above is even awake (chapters 25 and 28).

The distinction worth being able to state: a microcontroller has its memory and peripherals on the same die, boots from internal flash in microseconds and runs without an operating system; a microprocessor needs external DRAM and storage, boots Linux in seconds, and has an MMU. The advert's world is the first one. “Embedded Linux” on a CV means the second, and conflating them in an interview is a visible mistake.

A peripheral is a state machine, not a function

🧒 Simple

The hardest mental shift from PC programming is this: when you use a peripheral, you are not calling a function that does something. You are configuring a machine that will then do things by itself, at its own speed, whether or not your code is looking.

So the questions change. Not “did my function work?” but “is it enabled, is it clocked, what state is it in, and what will it do when the next byte arrives?”

🎓 Professional

Every peripheral in every reference manual has the same four groups of registers, and recognising the pattern lets you read a chapter about a peripheral you have never used:

  • Control — enable bits, mode selection, interrupt and DMA enables.
  • Status — flags saying what has happened. Read how they are cleared: write-one-to-clear, cleared by reading the data register, cleared by a software sequence. Getting this wrong gives an interrupt that fires forever, and it is a rite of passage.
  • Data — the byte in or out, often the same address for both.
  • Configuration — baud rate, prescaler, timing, which are frequently write-protected while the peripheral is enabled. The reference manual will say so in one sentence you can skim past, and the symptom is a setting that silently does not take.

Three properties of hardware that no API hides. Peripherals run concurrently with your code, so every shared variable is a concurrency problem (chapter 6). They are slow relative to the CPU — a byte at 115200 baud takes about 87 µs, which is roughly 15000 instructions at 168 MHz, and that arithmetic is the whole argument for interrupts and DMA. And they have no memory of your intentions: a peripheral half-configured when an interrupt arrives behaves as it is configured, not as you meant.

Reading the documentation set

🧒 Simple

There is not one document, there are four, and knowing which one answers which question saves more time than any other habit in this field.

🎓 Professional
  • The datasheet — what the part is: pinout, packages, electrical limits, timings, which peripherals this variant actually has. Per part number.
  • The reference manual — what the peripherals do: every register, every bit, the sequences. Per family, so it covers parts you do not have.
  • The programming manual — the core: instructions, the MPU, faults. Usually ARM's document, not the vendor's.
  • The errata sheet — where silicon disagrees with the reference manual. Read it before a long debugging session rather than after (chapter 67).

The habit that separates people who are fast from people who are not: go to the reference manual first and the internet second. A forum answer is somebody else's part, somebody else's silicon revision and somebody else's clock configuration; the register description is yours. The part number itself tells you which documents apply, and chapter 29 decodes it.

⚠ Trap

Everything is configured perfectly and the peripheral does nothing, because its clock was never switched on.

Every peripheral sits behind a clock enable bit, off at reset to save power. Write to a peripheral's registers with its clock disabled and, on most STM32 parts, the write is simply discarded — no fault, no warning. You then read the register back, see zeros, and conclude the chip is broken.

It is the single most common beginner failure in this field, it costs hours the first time, and it takes one line to prevent: enable the clock before touching anything, and when a peripheral appears dead, read its configuration registers back first. If they read as zero after you wrote them, the problem is the clock, not your logic (chapter 25).

The same shape recurs in three other places, and recognising the family is worth more than the individual facts: a GPIO that does nothing because the pin is not in the right alternate-function mode; a timer that does not count because it is held in reset; and a peripheral whose configuration would not take because it must be written while the peripheral is disabled. All four are “correct code, wrong prerequisite”, and all four are found by reading registers back rather than by staring at source.

Try it. No board needed — this is a documentation exercise, and it is the one that makes every later chapter cheaper.

1. Download the datasheet AND the reference manual for one part --
   STM32F407 is a good choice, it is everywhere and well documented.
   Find the block diagram in the datasheet and answer, out loud:

     - which bus is each peripheral on, AHB or APB?
     - how many DMA controllers are there, and what can they reach?
     - how many SRAM banks, at what addresses?

2. Pick a peripheral you have never used -- say the CRC unit or the
   RNG -- and read its register section cold. Identify its control,
   status, data and configuration registers. It should take ten
   minutes, and the point is to prove the pattern is real.

3. Find, in the reference manual, the sentence that says a status
   flag is cleared by reading the data register. There is always one.
   That single sentence is the difference between a working driver
   and an interrupt storm.

4. Compute the arithmetic that justifies interrupts: at 115200 baud,
   8N1, how long is one byte? At 168 MHz, how many instructions is
   that? Write both numbers down. Every later design decision about
   polling, interrupts and DMA is downstream of them.

5. Open the errata sheet for the same part and read one item end to
   end -- description, conditions, impact, workaround. Then ask
   yourself whether your code would have hit it.
Golden rules
  • The CPU is one master among several. DMA, Ethernet and USB also drive the bus matrix, so an idle CPU does not mean idle memory.
  • A peripheral is a concurrent state machine, not a function call. Ask what state it is in, not whether your line ran.
  • Every peripheral has control, status, data and configuration registers. Learn the pattern and you can read any chapter of any reference manual.
  • Know how each status flag is cleared. The wrong assumption gives an interrupt that never stops.
  • Configuration is often write-protected while the peripheral is enabled. Settings that silently do not take are usually this.
  • A disabled clock makes register writes disappear without a fault. Read registers back before blaming your logic.
  • Peripherals are slow compared with the core — one UART byte is thousands of instructions — and that arithmetic is the argument for interrupts and DMA.
  • Datasheet for the part, reference manual for the peripherals, programming manual for the core, errata for the truth.
  • Reference manual first, internet second. A forum answer is somebody else's silicon.
  • A microcontroller is not a small PC. Internal flash, no MMU, no OS, boots in microseconds — and that is a different job from embedded Linux.

“Mi descriva cosa c’è dentro un microcontrollore.”

“C’è un core — su STM32 un Cortex-M, che è la parte meno specifica del produttore e infatti è quella che mi porto dietro se cambio marca — flash e RAM interne, e poi una decina di periferiche, ognuna delle quali è una macchina a stati hardware che lavora per conto suo. Questa per me è la differenza mentale col PC: non chiamo una funzione che fa qualcosa, configuro una macchina che poi va avanti da sola mentre il core fa altro. Tutto è collegato da una matrice di bus, e i master non sono solo il core: anche il DMA, l’Ethernet, l’USB — quindi ‘la CPU è libera’ non vuol dire ‘la memoria è libera’. Le periferiche hanno tutte la stessa struttura di registri: controllo, stato, dato, configurazione; e le due cose che guardo subito nel reference manual sono come si azzera un flag di stato — se sbaglio quella, l’interrupt non smette più — e se la configurazione si può scrivere solo a periferica disabilitata. E la prima cosa che controllo quando una periferica sembra morta è il clock: se non è abilitato, le scritture sui registri spariscono senza nessun errore. Rileggo il registro: se torna zero, il problema è il clock, non il mio codice.”
