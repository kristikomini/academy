FreeRTOS concretely, and what else exists

The configuration file that decides everything, the dozen API calls you will actually type, and an honest map of the alternatives — because an advert that says “an RTOS” means FreeRTOS about three times in four, and knowing it is a category is worth saying.

From the advert

This is the concrete end of “sistemi operativi Real-Time (RTOS)”. The advert names no kernel, which is normal and is itself information: they expect you to have used one and to be able to move.

FreeRTOSConfig.h, where the decisions live

🧒 Simple

FreeRTOS is not a program that runs underneath yours. It is a few C files you compile into your project, plus one header full of settings that decides how it behaves and how big it is.

Most problems people blame on the RTOS are settings in that one header.

🎓 Professional

Ten C files, about 9 KB of flash and a few hundred bytes of RAM for the kernel itself, MIT licence. The settings that matter, and why:

configTICK_RATE_HZ — usually 1000. It is the resolution of every delay and timeout, and the rate of a periodic interrupt you are paying for. It is not the scheduling granularity: a task made ready by an interrupt runs immediately, not at the next tick (chapter 42). Raising it to 10 kHz to “get better timing” is almost always the wrong instrument; use a hardware timer.

configMAX_SYSCALL_INTERRUPT_PRIORITY — the ceiling from chapter 42, and the single most misconfigured value in the file.

configASSERT — define it in development. It catches the interrupt-priority error, stack overflows, and several API misuses on the first offending call rather than as corruption days later. Leaving it undefined is the most expensive default in the file.

The heap scheme, chosen by compiling exactly one of heap_1.c to heap_5.c. heap_1 allocates and never frees — the safest, and sufficient if all tasks are created at startup. heap_4 coalesces adjacent free blocks and is the sensible general choice. Better still, use the ...Static creation functions (xTaskCreateStatic, xQueueCreateStatic) and have no kernel heap at all, which is what chapter 11 argues for and what a safety-related project will require.

configCHECK_FOR_STACK_OVERFLOW = 2 and configUSE_TRACE_FACILITY — on in development. The first paints stacks and calls a hook; the second enables the high-water-mark queries from chapter 39.

The API you will actually type is small: xTaskCreate, vTaskStartScheduler, vTaskDelayUntil, xQueueCreate, xQueueSend/Receive and their FromISR forms, xSemaphoreCreateMutex, xSemaphoreTake/Give, xTaskNotifyGive/ulTaskNotifyTake, and portYIELD_FROM_ISR. That is most projects.

What else exists, and why it might be chosen

🧒 Simple

FreeRTOS is the most common, not the only one. The others exist because some projects need more than a scheduler, or need a certificate saying the kernel is safe to use in a machine that can hurt somebody.

🎓 Professional

FreeRTOS — MIT, Amazon-stewarded, on essentially every architecture, and the one every embedded engineer has seen. A scheduler and primitives, not an ecosystem: drivers, networking and a build system are yours to assemble. SAFERTOS is the independently certified sibling for IEC 61508 and ISO 26262 work (chapter 65).

Zephyr — Linux Foundation, Apache 2.0, and a different proposition: a kernel plus a device-driver model, device tree, Kconfig, networking, Bluetooth and a package manager. Much more capable and much more to learn; it is where a lot of new connected product work is going, and its device-tree-based configuration is the biggest conceptual jump for someone coming from CubeMX.

ThreadX (Azure RTOS, now Eclipse ThreadX) — mature, small, fast, with pre-existing safety and security certifications, and a full middleware suite. Common in medical and industrial products.

RT-Thread — large ecosystem, dominant in China, increasingly visible elsewhere. embOS (SEGGER) — commercial, excellent tooling, often paired with their trace tools. Micrium µC/OS — long-established, now open source, heavily used in certified products.

CMSIS-RTOS2 deserves a separate note because it is not a kernel: it is ARM's standard wrapper API that sits on top of FreeRTOS or another kernel. STM32CubeMX generates against it by default, which is why generated code says osThreadNew rather than xTaskCreate. It buys portability between kernels and costs a thin layer plus some loss of kernel-specific features — and being able to explain that in one sentence is a good answer to a question the generated code will prompt.

The honest framing for an interview: the concepts in Part 6 — tasks, priorities, blocking, the ISR boundary, inversion — are the transferable part and they are identical everywhere. The API names are a week.

⚠ Trap

Creating tasks, queues and semaphores without checking the return value. On a heap-based configuration every one of these allocates, and every one can fail — returning NULL or pdFAIL rather than trapping.

The classic sequence: a project grows, the kernel heap silently runs out during initialisation, xQueueCreate returns NULL, nobody checks, and the first xQueueSend to a null handle faults somewhere unrelated. The board resets at startup and the evidence points at whatever ran last.

Check every handle at creation, and treat a failure as fatal and loud rather than as something to continue past — there is no sensible recovery from “the system could not be built”. Better still, use the static creation functions, where the memory is yours and the failure cannot happen at all. Add vApplicationMallocFailedHook and vApplicationStackOverflowHook and make both of them stop visibly.

Try it. The POSIX simulator runs the real scheduler on your laptop, so most of this needs no hardware.

1. Build FreeRTOS for the POSIX/Linux port, or CubeMX-generate a project
   with FreeRTOS enabled for a Nucleo. Either way, start from the demo
   and delete everything you do not understand -- that deletion is the
   exercise.

2. Turn on the development settings before writing any code:

     #define configASSERT(x)  if((x)==0){taskDISABLE_INTERRUPTS();for(;;);}
     #define configCHECK_FOR_STACK_OVERFLOW  2
     #define configUSE_TRACE_FACILITY        1

   Then write vApplicationStackOverflowHook so it stops somewhere you
   will notice. You have just made two whole classes of bug loud.

3. Build the same three-task program twice: once with xTaskCreate
   (heap_4) and once with xTaskCreateStatic (no kernel heap at all).
   Compare arm-none-eabi-size output. Then look at what changed in the
   source -- it is less than you expect, and it is the difference
   between "we think it fits" and "the linker says it fits".

4. Make a queue creation fail on purpose: shrink configTOTAL_HEAP_SIZE
   until xQueueCreate returns NULL. Run it once without checking the
   return value and see where it faults -- somewhere unrelated, at a
   confusing moment. Then add the check. That is the whole argument.

5. Finally, open the CubeMX-generated main.c and find osThreadNew.
   Trace it down to xTaskCreate. Now you can answer the question the
   generated code invites: what CMSIS-RTOS2 is, and why it is there.
Golden rules
  • FreeRTOS is ten C files and a config header, compiled into your project — not something running underneath it.
  • The tick rate is delay resolution, not scheduling granularity. An interrupt-woken task runs immediately.
  • Define configASSERT in development. It is the most expensive default in the file.
  • Turn on stack-overflow checking and the trace facility, and write the hooks so they stop visibly.
  • Prefer the Static creation functions and have no kernel heap; otherwise heap_4 is the sensible default.
  • Check every creation return value. A null queue handle faults later, somewhere unrelated.
  • CMSIS-RTOS2 is a wrapper, not a kernel, and it is why generated code says osThreadNew.
  • Zephyr is a kernel plus an ecosystem; ThreadX and SAFERTOS carry safety certification.
  • The concepts transfer; the API names are a week.

“Che RTOS ha usato?”

“FreeRTOS, che è anche quello che si trova più spesso — dieci file C e un header di configurazione compilati dentro il progetto, non qualcosa che gira sotto. Le cose su cui sto attento sono nel config: configASSERT definito in sviluppo, perché prende al primo colpo l’errore di priorità degli interrupt e gli overflow di stack invece di farmeli trovare come corruzione tre giorni dopo; il controllo di stack overflow a 2 con il suo hook; e, dove posso, le funzioni di creazione statiche, così non ho heap del kernel e la memoria me la conferma il linker invece di sperarci. Una cosa che controllo sempre è il valore di ritorno di xTaskCreate e xQueueCreate: se l’heap finisce durante l’init quelle ritornano NULL, e la prima xQueueSend su un handle nullo va in fault in un punto che non c’entra niente. Degli altri conosco il panorama: Zephyr è un kernel più un ecosistema con device tree e Kconfig, ThreadX e SAFERTOS si usano dove serve la certificazione di sicurezza, e CMSIS-RTOS2 non è un kernel ma il wrapper che CubeMX genera sopra FreeRTOS. In ogni caso la parte che si trasferisce sono i concetti — task, priorità, bloccaggio, il confine con le ISR, l’inversione di priorità — i nomi delle funzioni sono una settimana.”
