Modbus TCP

The same register map as chapter 50, carried over a socket. A new seven-byte header, no CRC, no silent interval — and one genuinely new problem that the serial version never had: several masters talking at once.

From the advert

Not named directly, and directly implied by the pairing the anchor advert does name: protocolli seriali e Ethernet in the same line, next to l’ecosistema dell’automazione industriale. Modbus TCP is the usual upgrade path from Modbus RTU, and it is the point where a firmware engineer first has to talk to the customer's IT department rather than to their electrician.

What changes, and what does not

🧒 Simple

The message itself is almost unchanged: which function, which register, how many. What changes is the wrapping.

On a serial line, a message was recognised by silence around it and protected by a checksum. On a network, the network already guarantees that data arrives complete and in order, so both of those disappear. In their place is a short header saying how long the message is and which request it belongs to.

🎓 Professional
Modbus RTU frame:   addr | func | data ...            | CRC16
Modbus TCP frame:   MBAP header (7 bytes) | func | data ...

MBAP:  transaction id (2)   echoed back by the server
       protocol id    (2)   always 0 for Modbus
       length         (2)   bytes that follow, including unit id
       unit id        (1)   the old slave address, kept for gateways

Four differences that matter in practice:

  • No CRC, because TCP has its own checksum and guarantees ordered delivery. Computing one anyway is a common beginner error in a hand-written implementation.
  • No 3.5-character silence. The length field delimits the message instead — which means you must implement proper framing over a stream: read until you have the seven-byte header, then read exactly length more bytes. A TCP segment is not a message, and assuming one read equals one request is the single most common defect in embedded Modbus TCP servers.
  • The transaction id lets a master have several requests outstanding and match replies to them. A server must echo it back unchanged; a server that returns zero works with simple masters and breaks with pipelined ones.
  • The unit id survives as the old slave address, used when the device is a gateway onto a serial segment. A native TCP device conventionally accepts any unit id, or 0xFF, and being strict here breaks interoperability for no benefit.

Everything else — the four register spaces, the function codes, the one-based documentation against zero-based wire addressing, the exception responses with the high bit of the function code set — is exactly chapter 50. Port 502 by convention.

The genuinely new problem

🧒 Simple

On a serial line there was one master and it asked one question at a time. On a network, several computers can connect to your device simultaneously — a PLC, a supervision system, an engineer with a laptop, and a monitoring tool nobody told you about.

They can all read and write the same registers at the same time, and nothing in the protocol stops them. That is now your problem to think about.

🎓 Professional

Three consequences, all of which belong in a design rather than in an accident:

  • Atomicity across registers. A 32-bit value spans two registers, and a master reading while another writes can see half of an old value and half of a new one. The conventional answers are to build the response from a snapshot taken under a brief critical section, and to require multi-register writes to be applied together — which is why function 16 exists and why a device should reject a partial write of a paired value rather than accept it.
  • Who is allowed to command? Reading is harmless; writing a setpoint is not. A practical policy is that one connection holds control — the first to claim it, or one identified by address — while everybody else reads, with a timeout that releases control when that client disappears. Deciding this is a requirement question for the customer, and asking it at design time is the mark of somebody who has done it before.
  • Connection budget. Every connection costs a PCB and buffers (chapter 52). Decide the maximum, refuse politely beyond it, and time out idle connections — because the SCADA system will crash without closing, the laptop will be unplugged mid-session, and both leave sockets behind.

And the watchdog concept from chapter 58 becomes more important, not less. TCP will happily hold a connection open for minutes after the peer has vanished, so the absence of requests must be what triggers your safe state, not the absence of a connection. A device that keeps running a pump because the socket is still open is a device that has confused the transport with the application.

Meeting the IT department

🧒 Simple

The moment a machine has a network cable, it is on somebody else's network, with their rules: which address it gets, which ports are open, and whether it is allowed to talk to the internet at all.

🎓 Professional

The questions to settle before installation, each of which is a firmware requirement:

  • Static address or DHCP? Industrial devices are usually static, because a device whose address changes is a device the PLC cannot find. If DHCP is used, what happens when the lease cannot be renewed — keep the address and keep running, or stop? The answer must be designed, and “keep controlling the machine” is almost always right.
  • How is the address configured? A device with no display needs a way: DIP switches, a serial console, a discovery protocol, a default address documented in the manual. Getting this wrong makes commissioning painful at scale.
  • Which VLAN, and which ports? Port 502 must be open between the PLC and your device, and often nothing else should be.
  • Security, honestly. Modbus TCP has no authentication and no encryption at all. Anybody who can reach port 502 can write any register, which means anybody on that network can command the machine. The mitigation is network segmentation, and that is the customer's decision — but saying it out loud is your responsibility, and in Europe the Cyber Resilience Act is steadily turning it into a documented requirement rather than an assumption. Never let a Modbus device be directly reachable from the internet.

A practical middle path used by many products: keep Modbus TCP for the plant network where the PLC lives, and expose telemetry outward through MQTT over an authenticated, encrypted connection that the device itself initiates. That way the machine network stays closed, and the firewall conversation becomes an outbound one, which IT will accept.

⚠ Trap

One TCP read is treated as one Modbus request, so the device works with every tool you test and fails against the customer's PLC.

TCP is a byte stream with no message boundaries. Your test tool sends one request per packet and waits for the reply, so a naive server that parses whatever arrives in one recv works perfectly. The customer's master pipelines: it writes two requests into one segment, or the network splits a single request across two. Now the server reads a request and a half, parses the first, throws away the remainder, and the master times out on every second transaction — intermittently, under load, on their site only.

The fix is the framing discipline from chapter 47, applied to a stream instead of to a serial line: accumulate into a per-connection buffer, and loop — while you have at least seven bytes, read the length field; while you have a complete message, handle it and consume exactly that many bytes; keep the remainder. That loop is fifteen lines and it is the difference between a demo and a product. It also has to be per connection, which is a real design consequence: each socket needs its own reassembly buffer and its own state.

Two defensive habits that go with it. Validate the length field before trusting it — a value larger than your buffer is either a bug at the other end or somebody probing you, and the only correct response is to close the connection rather than to attempt the read. And never let a malformed request desynchronise the stream: if the content is nonsense but the framing is valid, answer with a Modbus exception and carry on; if the framing itself is broken, close, because there is no way to find the next boundary in a stream that has no delimiters.

Try it. All of this can be done on a PC first, and should be — the board adds nothing to the learning until the protocol is right.

1. Talk to somebody else's server first. Run a free Modbus TCP
   simulator (ModbusPal, diagslave) and query it with pymodbus in a
   few lines of Python. Then capture the exchange in Wireshark, which
   decodes Modbus natively, and read the MBAP header byte by byte.

2. Write the server in C on your PC, not on the board: a socket, the
   framing loop, and a small register map. Point pymodbus at it. When
   it works, THEN port it to the device, where the only difference is
   the API underneath.

3. Break the framing on purpose. Write a client that sends two
   requests in one send() call, and another that splits one request
   across two send() calls with a delay between them. A correct server
   handles both identically. This test is the whole trap, and it takes
   ten minutes.

4. Send a length field of 60000 and confirm your server closes the
   connection instead of trying to read it.

5. Open two clients at once and have one write a 32-bit setpoint
   across two registers while the other reads it in a loop. Watch for
   a torn value. Then fix it with a snapshot and confirm it is gone.

6. Then decide and implement a control policy: one writer, others
   read-only, control released after a timeout. Write down the
   requirement in one sentence first -- that sentence is what you
   would be asking the customer for.
Golden rules
  • Same registers, same function codes, new wrapper. The MBAP header replaces silence and CRC.
  • No CRC on TCP. Computing one is a beginner's tell.
  • Echo the transaction id unchanged, or pipelined masters break.
  • Accept any unit id on a native TCP device; it exists for gateways.
  • One TCP read is not one request. Accumulate per connection and loop on the length field.
  • Validate the length before trusting it, and close the connection on broken framing.
  • Answer nonsense content with an exception, and never let it desynchronise the stream.
  • Several masters can now write at once. Decide who may command, and release control on timeout.
  • Build multi-register responses from a snapshot, so a 32-bit value cannot be torn.
  • Budget connections, refuse politely, and time out idle ones.
  • The absence of requests triggers the safe state, not the absence of a socket.
  • Modbus TCP has no authentication or encryption. Say so; segment the network; never expose it to the internet.

“Che differenza c’è fra Modbus RTU e Modbus TCP?”

“Il messaggio è quasi lo stesso: stesse funzioni, stessi quattro spazi di registri, stesso sfasamento fra indirizzi documentati a uno e indirizzi sul filo a zero. Cambia l’involucro: su TCP spariscono il CRC, perché ci pensa il protocollo sotto, e il silenzio di 3,5 caratteri, sostituito dall’header MBAP con il campo lunghezza e il transaction id, che va rimandato indietro identico se no i master che mandano richieste in pipeline si rompono. E qui c’è l’errore più comune, che ho visto descritto ed è proprio un errore di framing: TCP è un flusso di byte, non di messaggi, quindi una read non è una richiesta. Serve un buffer per connessione e un ciclo: quando ho sette byte leggo la lunghezza, quando ho il messaggio completo lo servo e consumo esattamente quei byte, il resto resta lì. Un server che non lo fa funziona con tutti gli strumenti di prova, perché mandano una richiesta per pacchetto, e fallisce dal cliente. La cosa veramente nuova però è la concorrenza: adesso possono collegarsi PLC, supervisione e un portatile insieme, e scrivere tutti. Quindi decido chi ha il comando, con un timeout che lo rilascia, costruisco le risposte multi-registro da uno snapshot per non dare valori a 32 bit spezzati, e faccio scattare lo stato sicuro sull’assenza di richieste, non sull’assenza di connessione — perché TCP tiene aperta la socket anche quando dall’altra parte non c’è più nessuno. E dico sempre che Modbus TCP non ha né autenticazione né cifratura: chi arriva alla porta 502 comanda la macchina.”
