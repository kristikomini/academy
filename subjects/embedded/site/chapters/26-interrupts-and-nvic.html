Interrupts, the NVIC and the rules for an ISR

An interrupt is the only mechanism by which the outside world can get your attention. It is also the mechanism by which every subtle firmware bug enters the building, because an ISR runs at a moment your other code did not choose and cannot see.

From the advert

This chapter answers “Sviluppare e ottimizzare firmware in C/C++ su microcontrollori e sistemi operativi Real-Time (RTOS)”. Everything Part 6 says about an RTOS assumes the exception model described here — the scheduler itself is driven by two interrupts.

What actually happens when an interrupt fires

🧒 Simple

Your program is running along. A pin changes, or a byte arrives on the serial port. The processor stops what it is doing — mid-function, between any two instructions — writes down where it was, jumps to a small function you wrote, runs it, and then goes back exactly where it left off.

The main program never notices. That is the whole point, and it is also the whole danger: if the interrupt changed something the main program was in the middle of using, the main program carries on with half-old, half-new data and no idea anything happened.

🎓 Professional

On a Cortex-M the sequence is defined by the architecture, not by your compiler, and it is worth knowing because it is why ISRs are written in plain C with no special keyword:

  1. The core finishes the current instruction (or abandons a restartable one).
  2. It stacks eight registers automatically — R0–R3, R12, LR, PC and xPSR — onto the current stack. This is the caller-saved set, which is precisely why a handler can be an ordinary C function: the compiler saves the rest if it uses them.
  3. It loads the handler address from the vector table and sets LR to a special EXC_RETURN value.
  4. Your handler runs, in handler mode, using the Main Stack Pointer.
  5. Returning branches to EXC_RETURN, which the core recognises and turns into an unstack.

Latency on an M3/M4 is about 12 cycles, and two optimisations matter in interview conversation. Tail-chaining: if another exception is pending on return, the core skips the unstack/restack pair and goes straight to the next handler. Late arrival: if a higher-priority exception appears while the core is still stacking, it redirects to that one without starting over.

Priority, and the number that runs backwards

🧒 Simple

Several things can want attention at once, so each interrupt has a priority. The confusing part is that a smaller number means a more urgent interrupt. Priority 0 beats priority 5.

🎓 Professional

The NVIC — the Nested Vectored Interrupt Controller — is part of the core, not a peripheral, which is why interrupt handling is identical across every vendor's Cortex-M.

Lower numeric value is higher priority. Reset, NMI and HardFault have fixed negative priorities and always win. Everything else is configurable.

Only some of the priority bits exist. The architecture allows 8 bits; STM32 parts implement the top 4, giving 16 levels, and the bits live in the upper half of the byte. This is why raw register values look strange (priority 1 appears as 0x10) and why you use NVIC_SetPriority() rather than writing the byte.

Pre-emption group versus sub-priority. The 4 bits split between a group (which decides whether one interrupt can pre-empt another) and a sub-priority (which only breaks ties among simultaneously pending interrupts of the same group). Most projects set the grouping once at startup to “all bits are pre-emption” and never touch it again; if you are using FreeRTOS, do exactly that, because its configuration assumes it.

Nesting is on by default. A higher-priority interrupt pre-empts a running handler. This is a feature and a stack-depth risk: your worst-case stack must survive the deepest legal nesting chain (chapter 12).

What an ISR is allowed to do

🧒 Simple

Keep it short. Do the thing that only the interrupt can do — read the byte, clear the flag, note the time — and let the main program do the thinking later.

🎓 Professional

The list, in the order it gets you into trouble:

Be short. While your handler runs, every interrupt of equal or lower priority is waiting. An ISR that takes 200 µs has added 200 µs to the worst-case latency of everything below it, and worst-case latency is what real-time means.

Never block. No waiting on a flag, no HAL_Delay(), no busy-wait on another peripheral. The thing you are waiting for may be delivered by an interrupt you are currently blocking.

Defer the work. The standard shape is: the ISR reads the hardware, pushes one item into a queue or sets one flag, and returns; a task or the main loop does the parsing, the arithmetic and the logging. Under an RTOS this is the FromISR API and it has its own rules — chapter 42.

Mark shared state volatile, and remember that does not make it atomic (chapter 06). Anything wider than one machine word, or any read-modify-write, needs a critical section or a lock-free structure designed for one producer and one consumer.

No malloc, no printf. The allocator takes a lock the interrupted code may already hold, and printf is both enormous and typically blocking (chapter 61).

Clear the flag, and clear it correctly. Most peripheral interrupts stay pending until the source flag is cleared in the peripheral, not in the NVIC. Forgetting means the handler re-enters immediately and the system appears frozen.

⚠ Trap

Clearing a flag on the last line of the handler can re-enter it once anyway. The write to the peripheral register travels through a write buffer and a bus bridge, and the core may return from the exception before the peripheral has actually seen it. The NVIC then still sees the line asserted and re-enters.

The fix is the one the vendor errata and the ARM application notes both give: clear the flag early in the handler, and if it must be last, follow it with a read-back of the same register (or a __DSB()) so the write has provably landed before you return.

The symptom — a handler that runs twice for one event, sometimes — is unusually hard to find by reading code, because the code is correct in the abstract machine and wrong in the bus.

Try it. This one wants a board. If you have none yet, read the disassembly step on a PC instead — the stacking convention is visible in any Cortex-M vector table listing.

1. Toggle a GPIO pin as the FIRST and LAST line of your UART interrupt
   handler, and put a scope or a logic analyser on it (chapter 62).
   You are now measuring, in nanoseconds, the thing everyone estimates.

2. Now make the handler do something silly on purpose -- a floating-point
   divide in a loop, say -- and watch the pulse widen. That width is what
   you have added to the worst-case latency of every lower-priority
   interrupt in the system.

3. Comment out the line that clears the peripheral flag. The pulse train
   becomes solid: the handler is re-entering forever and main() never
   runs again. That is what "the board is frozen" usually means.

4. Put the clear back, but as the very last statement, and add a long
   handler body. On some parts you will occasionally see a double pulse
   for a single event. Add a read-back of the status register after the
   clear and it goes away.
Golden rules
  • An interrupt runs between two instructions of code that cannot see it coming. Every shared-data bug starts there.
  • Lower numeric priority means higher urgency, and STM32 implements only the top 4 bits of the priority byte.
  • An ISR must be short and must never block. While it runs, everything at equal or lower priority waits.
  • Defer the work: read the hardware, post one item, return. Parse in a task.
  • Shared state needs volatile, and volatile is not enough for anything wider than a word or any read-modify-write.
  • No malloc and no printf in an ISR.
  • Clear the peripheral flag early, or read it back before returning, or the handler can re-enter once for a single event.

“Che regole segue quando scrive una routine di interrupt?”

“La regola di fondo è una sola: l’ISR deve essere corta e non deve mai bloccarsi, perché finché gira, tutto quello che ha priorità uguale o più bassa è fermo — quindi la sua durata entra direttamente nel worst case degli altri. In pratica faccio solo quello che solo l’interrupt può fare: leggo il dato dalla periferica, pulisco il flag, metto un elemento in coda, e torno. Il parsing e i conti li fa un task. Niente malloc e niente printf dentro l’handler. Le variabili condivise con il main le dichiaro volatile, sapendo però che volatile non le rende atomiche: se c’è un read-modify-write serve una sezione critica. E una cosa imparata a caro prezzo: il flag della periferica lo pulisco all’inizio, non in fondo — se lo pulisco sull’ultima riga la scrittura può non essere ancora arrivata alla periferica quando esco, e l’handler rientra una seconda volta per lo stesso evento.”
