Why embedded code avoids malloc

Almost every firmware team has a rule about dynamic allocation, almost none of them write it in a job advert, and almost every interviewer asks about it. The reasons are better than “tradition”, and the alternatives are worth knowing by name.

From the advert

Not in this advert. It is a house rule rather than a requirement, and it is one of the handful of questions that reliably separates candidates who have written firmware from candidates who have written C.

Three reasons, and only one of them is about memory

🧒 Simple

On a PC, asking for memory while the program runs is normal. If the computer runs low, the operating system finds more, or stops your program and tells you.

On a microcontroller there is no more, and nobody to tell. You have, say, 64 KB, forever. If you ask for memory and there is none, the answer is a null pointer — and most code does not check.

🎓 Professional

1. Fragmentation, with no MMU to hide it. This is the real reason, and it is not the same as running out of memory. Allocate and free blocks of varying sizes long enough and the free space becomes a lot of small holes. A later request for a contiguous 512 bytes fails even though 30 KB is free in total. A desktop hides this behind virtual memory: the MMU can map scattered physical pages into a contiguous virtual range. A Cortex-M has no MMU, so the holes are real and permanent.

Note the failure mode: it is time-dependent. The device works on the bench, it works through a week of testing, and it fails after 40 days in a customer's plant. There is no test that reliably catches it and no log entry that explains it.

2. Non-deterministic timing. malloc walks a free list. How long that takes depends on the heap's history, so the call has no useful worst-case bound — which makes it disqualifying inside anything with a deadline (chapter 37). It also usually takes a lock, which is one of the concrete reasons it must never appear in an ISR.

3. You cannot prove it fits. With static allocation, the linker tells you at build time whether the program fits, in one line (chapter 10). With a heap, the answer depends on runtime behaviour, and the honest version is “we think so”. For a product that must run unattended in a machine, that is a materially worse position, which is why MISRA and the functional-safety standards restrict it hard (chapter 65).

What firmware uses instead

🧒 Simple

Decide up front how many of each thing you can ever have, reserve exactly that many, and reuse them. Ten message buffers, and if all ten are in use, the eleventh request is refused — immediately, visibly, and at a moment you can handle.

🎓 Professional

Static allocation. File-scope or static objects, sized at build time. The default, and the reason most firmware has almost no heap at all.

Fixed-block memory pools. When you genuinely need allocate/free semantics: a pre-allocated array of N identical blocks plus a free list. Allocation is O(1) — unlink the head — and fragmentation is impossible, because every block is the same size and any free block satisfies any request. Several pools of different block sizes cover most real needs. This is what FreeRTOS's heap_4 and heap_5 approximate, and what a proper pool allocator does exactly.

Ring buffers. The standard structure for streams: UART receive, log lines, sample capture. Fixed capacity, O(1) at both ends, and with one producer and one consumer they can be written lock-free with careful use of volatile indices and a barrier. The design decision that matters is what happens when full — overwrite the oldest, or refuse the newest — and it is a product decision, not a coding one. For a log, overwrite. For a command queue, refuse and report.

Allocate once at startup, never free. The pragmatic middle ground, and it is legitimate: if every allocation happens during initialisation and nothing is ever released, there is no fragmentation and no unbounded call in the hot path. Many products with an lwIP stack (chapter 52) work exactly this way.

⚠ Trap

“We don't use malloc” is frequently false. It arrives through the back door, and part of the job is knowing where the doors are.

  • printf("%f") and friends pull in a large formatting machinery, and some newlib configurations allocate a buffer on first use.
  • A C++ std::string, std::vector, std::function or a captured lambda allocates — which is a main reason for the flag list in chapter 18.
  • The RTOS itself: xTaskCreate() allocates the task stack and TCB from the FreeRTOS heap. The static variants (xTaskCreateStatic()) exist precisely so that you can say no.
  • Vendor middleware — USB stacks, file systems, TCP/IP — frequently allocates internally.

The way to find out is not to grep for malloc. It is to look at the map file for the heap symbols, or set a breakpoint on malloc and see who stops. On a --specs=nano.specs build, also check that _sbrk is not silently handing out memory that collides with the stack growing down — that collision is one of the nastier bugs in the field, and a correct _sbrk that refuses is worth writing.

Try it. On a PC, but constrain the heap so it behaves like a microcontroller. This produces fragmentation on purpose, which is otherwise hard to see.

cat > frag.c <<'EOF'
#include <stdio.h>
#include <stdlib.h>
#define N 2000
int main(void) {
    static void *p[N];
    /* allocate alternating small and large blocks */
    for (int i = 0; i < N; i++) p[i] = malloc((i % 2) ? 32 : 512);
    /* free only the large ones: leaves 32-byte holes everywhere */
    for (int i = 0; i < N; i += 2) { free(p[i]); p[i] = NULL; }

    /* plenty of bytes are free -- but are they contiguous? */
    int ok = 0;
    for (int i = 0; i < 500; i++) if (malloc(4096)) ok++;
    printf("4 KB blocks obtained after fragmenting: %d of 500\n", ok);
    return 0;
}
EOF
gcc frag.c -o frag && ./frag

# glibc is a very good allocator on a machine with virtual memory, so it
# will often still succeed. THAT IS THE POINT: run the same pattern on a
# Cortex-M with 64 KB and no MMU, where the holes cannot be papered over,
# and the failure is permanent.
#
# Now do the honest version. In your next firmware project, replace one
# malloc/free pair with a fixed-block pool:
#
#   static msg_t  pool[10];
#   static bool   used[10];
#   msg_t *msg_alloc(void) { for (int i=0;i<10;i++) if(!used[i]) { used[i]=true; return &pool[i]; } return NULL; }
#   void   msg_free(msg_t *m) { used[m - pool] = false; }
#
# Ten lines, O(1), no fragmentation possible, and the failure is a NULL you
# can handle on the line you asked -- not a reset after 40 days.
Golden rules
  • Fragmentation is the real reason, not shortage: without an MMU the holes are permanent, and the failure appears after weeks.
  • malloc has no useful worst-case bound, so it is disqualifying inside anything with a deadline, and never allowed in an ISR.
  • Static allocation lets the linker prove it fits at build time. A heap replaces that proof with a hope.
  • A fixed-block pool cannot fragment, because any free block satisfies any request.
  • A ring buffer's real design decision is what happens when it is full — overwrite for a log, refuse for commands.
  • Allocate at startup and never free is a legitimate strategy.
  • Check whether you actually avoid malloc: the RTOS, printf, C++ containers and vendor middleware all allocate.

“Usa allocazione dinamica nel firmware?”

“Di regola no, e il motivo principale non è la quantità di memoria — è la frammentazione. Senza MMU i buchi restano buchi: dopo settimane ho magari 30 KB liberi ma non 512 byte contigui, la malloc fallisce e il guasto si vede in campo dopo quaranta giorni, non sul banco. Poi malloc non ha un caso peggiore utilizzabile, quindi in un percorso con una scadenza non ci va, e in un ISR men che meno perché prende un lock. E soprattutto, con l’allocazione statica è il linker a dirmi a build time se ci sta: con l’heap quella certezza la perdo. In pratica uso allocazione statica, e se mi serve davvero allocare e liberare uso un pool a blocchi fissi — O(1) e non può frammentare, perché ogni blocco libero va bene per ogni richiesta. Una cosa che verifico sempre: se davvero non uso l’heap. Fra xTaskCreate, la printf e le middleware del produttore, spesso c’è e nessuno lo sa.”
