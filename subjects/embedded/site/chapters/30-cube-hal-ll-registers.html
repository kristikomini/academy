CubeMX, CubeIDE, HAL, LL and the bare registers

Four ways to write the same GPIO line, three of which somebody will tell you is the only professional choice. What each actually costs, what each hides, and the honest answer to “do you use the HAL?” — a question with a wrong confident answer in both directions.

From the advert

This chapter answers “Progettare l’architettura software per l’ambiente di sviluppo STM32” and “Esperienza (anche accademica o di stage) su ambiente di sviluppo STM32”. The phrase ambiente di sviluppo is doing real work: they are naming a toolchain, and this is what is inside it.

The same pin, four ways

🧒 Simple

To turn on an LED you eventually have to set one bit in one place in memory. Everything else is a layer of convenience on top of that, written by somebody else, for people who do not want to look up which bit.

The layers are not free. Each one makes the easy thing easier and makes it harder to see what actually happened.

🎓 Professional

From the top down:

CubeMX is a configurator, not a library. You click pins and clocks in a graphical view and it emits an .ioc project file plus generated initialisation code. Its genuinely valuable output is the clock tree solver — working out PLL dividers by hand from the reference manual is slow and error-prone (chapter 25) — and the pin-conflict checker.

CubeIDE is Eclipse with CubeMX, the GCC arm-none-eabi toolchain and a GDB front end for ST-LINK, in one installer. Free. It is what the advert most likely means.

HAL — Hardware Abstraction Layer. Portable across the whole STM32 range, handle-based (HAL_UART_Transmit(&huart2, buf, n, 100)), with blocking, interrupt and DMA variants of most calls. Large, several layers deep, and it hides the registers.

LL — Low Layer. Thin inline functions over the registers, near-zero overhead, per-peripheral rather than portable. LL_GPIO_SetOutputPin(GPIOA, LL_GPIO_PIN_5) compiles to essentially the register write. It is the layer most people do not know exists, and mentioning it is a good signal.

CMSIS registers — the vendor's struct overlay on the peripheral memory map: GPIOA->BSRR = (1u << 5);. This is the bottom, and it is still C with named constants, not assembly (chapter 23).

The honest answer to the question

🧒 Simple

Neither “always use the library” nor “real engineers use registers” is right. Use the convenient thing where convenience is free, and go underneath where it is not — and be able to say which is which.

🎓 Professional

The answer that lands is a criterion, not a preference:

Use CubeMX for the clock tree and the pin map. Refusing it to prove something costs you a day and gets the PLL wrong.

The HAL is fine for anything not in a hot path — initialisation, a configuration EEPROM, a status LED. Being productive is a real engineering value and the code is readable by the next person.

Go to LL or registers where timing, size or control matters. A bit-bang sequence, a pin toggled inside an ISR, a high-rate DMA path. The measurable version: a HAL GPIO write is a function call with parameter checking; the register write is one store. In a 10 kHz control loop that difference is the budget.

Never use a blocking HAL call with a long timeout anywhere that matters. HAL_UART_Transmit(&h, buf, n, HAL_MAX_DELAY) in a task that also has a deadline is a design error, and HAL_Delay() in an interrupt handler is worse: it depends on the SysTick interrupt, which your handler may be blocking, so it can hang the system outright (chapter 26).

Read the HAL source when it misbehaves. It ships with the project, it is ordinary C, and it is frequently the fastest way to find out that a function returns HAL_BUSY for a reason nobody documented.

⚠ Trap

Regenerating from the .ioc file overwrites your code, unless it is inside the magic comments. This is the first genuinely painful thing that happens to everybody on an STM32 project, and it is a first-week question in an interview precisely because it is universal. 

/* USER CODE BEGIN 2 */
  my_app_init();          /* survives regeneration */
/* USER CODE END 2 */

  MX_GPIO_Init();         /* outside the markers: regenerated, your edits gone */

Three habits that make it a non-issue. Keep your application out of main.c entirely — one call to your own app_init() and app_run() inside the markers, everything else in your own files, which is also what chapter 35 asks for on architectural grounds. Commit before regenerating, always, so the diff tells you what it did. And if a generated file needs a change that will not survive, either move it into a marker block or stop regenerating that file and own it.

Try it. This one wants a board — a Nucleo is under twenty euro and this exercise is the reason to buy one.

1. In CubeMX, configure one GPIO as output. Generate, build, flash.
   Toggle it in a loop four ways and put a scope on the pin:

     HAL_GPIO_TogglePin(GPIOA, GPIO_PIN_5);
     LL_GPIO_TogglePin(GPIOA, LL_GPIO_PIN_5);
     GPIOA->ODR ^= (1u << 5);
     GPIOA->BSRR = (1u << 5);   /* then BSRR = (1u << 21) to clear */

   Measure the maximum toggle frequency of each. The numbers are the
   argument, and they are yours rather than something you read.

2. Note WHY BSRR exists while you are there: writing ODR is a
   read-modify-write and can lose a concurrent change from an interrupt;
   BSRR sets and clears atomically in one store (chapter 04).

3. Now cause the trap deliberately. Add a line to main.c OUTSIDE the
   USER CODE markers, go back to the .ioc, change anything, regenerate.
   Your line is gone. Do it once here, on purpose, and it will never
   cost you an afternoon later.

4. Finally, open the HAL source for HAL_GPIO_TogglePin and read it. It
   is about six lines. Knowing that is what lets you answer the "do you
   use the HAL" question without guessing.
Golden rules
  • CubeMX is a configurator, not a library. Its real value is the clock-tree solver and the pin-conflict checker.
  • Four layers: CubeMX, HAL, LL, CMSIS registers. Knowing LL exists is a good signal on its own.
  • The answer to “do you use the HAL?” is a criterion, not a preference.
  • HAL for anything not in a hot path; LL or registers where timing, size or control matters.
  • Never use a blocking HAL call with a long timeout where a deadline exists, and never HAL_Delay in an ISR — it depends on an interrupt you may be blocking.
  • Regeneration overwrites everything outside the USER CODE markers. Commit first, and keep your application out of main.c.
  • BSRR sets and clears atomically; ODR is a read-modify-write and can lose a concurrent change.
  • Read the HAL source. It ships with the project and it is ordinary C.

“Lavora con la HAL o direttamente sui registri?”

“Tutti e due, secondo un criterio. CubeMX lo uso sempre per l’albero dei clock e la mappa dei pin: rifarlo a mano dal reference manual mi costa una giornata e sbaglio il PLL. La HAL va benissimo per tutto quello che non è in un percorso critico — inizializzazioni, una EEPROM di configurazione, un LED di stato — perché essere produttivi è un valore e il codice lo legge anche il collega dopo di me. Scendo su LL o sui registri dove contano i tempi, la dimensione o il controllo: dentro un’ISR, un anello a 10 kHz, un bit-bang. Una regola che non rompo: mai una chiamata HAL bloccante con timeout lungo dove c’è una scadenza, e mai HAL_Delay dentro un handler, perché dipende dal SysTick che magari sto bloccando io e pianta tutto. E una cosa pratica imparata sbagliando: il codice mio sta fuori da main.c, con una sola chiamata dentro i marcatori USER CODE, e committo prima di rigenerare — altrimenti la rigenerazione dall’.ioc si porta via quello che ho scritto.”
