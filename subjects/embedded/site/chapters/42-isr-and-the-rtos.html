Interrupts and the RTOS: the FromISR rule

The first thing that goes wrong on a real RTOS project, and it fails quietly rather than loudly: calling the ordinary kernel API from an interrupt handler. Why there are two versions of every function, and why the priority ceiling that governs it is the setting people get wrong.

From the advert

Not named in this advert. It is where chapter 26 and chapter 39 meet, and it is the seam where the two halves of “firmware su microcontrollori e sistemi operativi Real-Time” actually touch each other.

Why there are two of every function

🧒 Simple

When a task asks the kernel for something that is not available yet, the kernel's answer is “fine, go to sleep, I will wake you”. That works because a task is something that can be put to sleep.

An interrupt handler is not. There is nothing to put to sleep — it is a piece of work the processor is doing right now, on behalf of nobody. So if a handler asks for something unavailable, the kernel has no valid answer, and the usual result is that everything stops.

🎓 Professional

The blocking API's contract is “block the calling task until this succeeds or the timeout expires”. In handler mode there is no calling task: the interrupt arrived asynchronously and the kernel cannot identify an owner to move to the Blocked list, let alone perform a context switch out of an exception whose return path is already fixed.

So kernels supply a parallel, interrupt-safe API. In FreeRTOS it is the FromISR suffix, and the differences are systematic:

  • No timeout parameter. The call either succeeds immediately or fails immediately. xQueueSendFromISR returns errQUEUE_FULL rather than waiting, and you must check the return value — a full queue in an ISR is data loss, and silently discarding it is how a link develops a mysterious 0.1 % drop rate.
  • A pxHigherPriorityTaskWoken out-parameter, described below.
  • Different internal locking, because it cannot take a mutex or suspend the scheduler the way the task-side call does.

And one rule with no exception: an ISR must never take a mutex. Not the FromISR variant either — there is no such variant, deliberately. A mutex has an owner so that priority inheritance can promote it (chapter 41), and an interrupt handler is not a task and has no priority the scheduler can raise. The inversion would be unbounded by construction. Signal a task; let the task take the lock.

The yield parameter, and what it is for

🧒 Simple

Suppose the interrupt wakes up a task that is more urgent than the one that was running before the interrupt arrived. When the handler finishes, the processor would normally go back to the interrupted task — and the urgent one would wait for no reason.

So the kernel hands you a small flag: “something more urgent is now ready”. You pass it to one macro at the end of the handler, and the switch happens immediately instead of at the next tick.

🎓 Professional

The pattern, and it is the same every time: 

void USART1_IRQHandler(void)
{
    BaseType_t woken = pdFALSE;          /* MUST be initialised to false */

    uint8_t b = (uint8_t) USART1->RDR;   /* also clears RXNE on this part */

    if (xQueueSendFromISR(rx_queue, &b, &woken) != pdTRUE) {
        rx_overflow++;                    /* count it -- never ignore it */
    }

    portYIELD_FROM_ISR(woken);           /* switch NOW if a higher-priority
                                            task became ready; otherwise a
                                            no-op */
}

Omitting portYIELD_FROM_ISR is not a crash. It is worse: the system works, and the woken task simply does not run until the next SysTick or the next yield for some other reason. You have silently added up to one tick period — typically 1 ms, which on a control loop is enormous — to the response time of the highest-priority path in the product. Nothing reports it, and it will not show up in any test that does not measure latency.

Note also that woken must start as pdFALSE and can be passed to several FromISR calls in the same handler, accumulating; you yield once, at the end.

⚠ Trap

An interrupt at a priority above configMAX_SYSCALL_INTERRUPT_PRIORITY must not call any kernel function at all — and on STM32 the default priority is zero, which is above it. This is the single most common RTOS configuration bug, and it is not obvious from the code.

The kernel protects its internal data by masking interrupts up to that ceiling, using BASEPRI rather than disabling them entirely — which is the good bargain: it means genuinely urgent interrupts above the ceiling keep running even inside the kernel's critical sections, so their latency is unaffected by the RTOS. The price is that those interrupts are outside the kernel's protection and therefore may not touch it.

The failure mode when you get it wrong is intermittent queue or list corruption that appears under load, days later, and looks like a memory bug. FreeRTOS ships an assertion (configASSERT plus vPortValidateInterruptPriority) that catches it on the first offending call — turn configASSERT on in development and this whole class of bug becomes a loud failure on the first run instead.

Remember the numbering is inverted (chapter 26): numerically lower is more urgent, so an interrupt that wants to call the kernel needs a priority number greater than or equal to the ceiling. Any peripheral you enable through CubeMX and do not explicitly assign a priority to gets 0, which is the most urgent possible, and it will trip the assertion the first time it calls xQueueSendFromISR.

Try it. On a board with FreeRTOS. All three of these are deliberate breakages, and each one takes a minute and saves a day later.

1. Turn on configASSERT first:

     #define configASSERT(x) if((x)==0){taskDISABLE_INTERRUPTS();for(;;);}

   Then set a UART interrupt to priority 0 and call xQueueSendFromISR
   from it. You will stop inside vPortValidateInterruptPriority on the
   first byte received. That is the assertion earning its place.

2. Fix it -- NVIC_SetPriority(USART1_IRQn, 5) or anything numerically
   greater than or equal to configMAX_SYSCALL_INTERRUPT_PRIORITY -- and
   confirm it runs.

3. Now delete portYIELD_FROM_ISR and measure instead of guessing.
   Toggle a pin in the ISR and another at the top of the woken task, and
   look at the gap on a scope:

     with the yield     -- a few microseconds
     without the yield  -- up to one full tick period

   Nothing has crashed. Nothing is logged. That gap is the bug, and it
   is invisible to every test that does not look at time.

4. Finally, call the plain xQueueSend (no FromISR) from the handler and
   watch what your kernel does. With asserts on, it stops here too.
Golden rules
  • An ISR has no calling task to block, which is why the blocking API cannot work there.
  • Use the FromISR variants: no timeout, so they succeed or fail immediately.
  • Check the FromISR return value. A full queue in an ISR is data loss.
  • An ISR must never take a mutex — there is no owner to promote, so the inversion is unbounded by construction.
  • Initialise the woken flag to false, accumulate it, and yield once at the end.
  • Omitting portYIELD_FROM_ISR does not crash — it silently adds up to a tick to your most urgent path.
  • Interrupts more urgent than configMAX_SYSCALL_INTERRUPT_PRIORITY may not call the kernel at all.
  • CubeMX gives unassigned interrupts priority 0, which is above the ceiling and will trip the assertion.
  • Turn configASSERT on in development. It converts a class of intermittent corruption into a first-run stop.

“Cosa cambia a chiamare l’API dell’RTOS da dentro un interrupt?”

“Le funzioni normali hanno come contratto ‘blocca il task chiamante finché non riesce’, ma dentro un handler un task chiamante non c’è: non c’è nessuno da mettere in Blocked. Per questo esistono le versioni FromISR, che non hanno il timeout — o riescono subito o falliscono subito — e il valore di ritorno lo controllo sempre, perché una coda piena dentro un’ISR è perdita di dati e ignorarla dà quei link che perdono un pacchetto ogni mille. Poi c’è il parametro pxHigherPriorityTaskWoken: se l’interrupt ha risvegliato un task più prioritario di quello interrotto, passo il flag a portYIELD_FROM_ISR e il cambio di contesto avviene subito. Se lo dimentico non crasha niente: il task parte al tick successivo, e mi sono mangiato fino a un millisecondo sul percorso più urgente del prodotto, senza che nessuno me lo dica. La cosa su cui ho perso più tempo però è un’altra: un interrupt con priorità più urgente di configMAX_SYSCALL_INTERRUPT_PRIORITY non può chiamare il kernel, e CubeMX assegna priorità 0 a tutto quello a cui non gliela dico io — cioè la più urgente possibile. Con configASSERT acceso salta fuori alla prima chiamata invece di corrompere una lista fra tre giorni. E in un’ISR non prendo mai un mutex: non ha un proprietario da promuovere, quindi segnalo un task e il lock lo prende lui.”
