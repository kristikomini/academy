Git, code review and the release

The version control part is the same everywhere. What is different in firmware is the release: a binary that ends up inside metal, in somebody's hands, for ten years — and the question you must always be able to answer, which is exactly which software is on that board.

From the advert

Not in the anchor advert, which never mentions version control — and that omission is normal rather than meaningful. The second advert in the corpus does name it: “Dimestichezza con sistemi di versionamento del codice, preferibilmente Git”.

Dimestichezza is a modest word, and it is worth reading correctly: nobody expects rebase-fu from a junior. They expect that you will not lose work, will not force-push over somebody, and can explain what you changed. The release half of this chapter is what separates a candidate who has used Git at university from one who has shipped something.

Branching that fits hardware

🧒 Simple

A branch is a private copy of the project where you can make a mess safely. You work there, you show it to somebody, and then it joins the main line. That part is the same as any other software.

The difference with firmware is that a version can escape onto a physical object. Once a hundred boards have shipped with version 1.4 inside them, that exact code must stay findable and buildable for years — because a fault report will arrive and the only useful question is what was actually running.

🎓 Professional

A workable model for a small firmware team, without ceremony:

  • One integration branch that always builds and always passes the host tests. Not “usually”: a red main branch stops being a reference point, and once it is not a reference point, nobody can tell whether their own change broke something.
  • Short-lived feature branches, reviewed, merged, deleted. Long-lived branches are where firmware projects go to die, because the hardware moves under them — a pin reassignment or a driver change lands on main and the two-month branch now conflicts with reality rather than with text.
  • A tag for every build that leaves the building. Tags are the release record, and an annotated tag can carry who, when and why.
  • A maintenance branch per shipped version, created from the tag, and only when a fix for shipped hardware is genuinely needed. Create it on demand, not in advance.

Commits should be readable by the person bisecting them in two years. One logical change per commit; a subject line that says what changed and why, not “fix”; and the body carrying the reasoning, because the diff already shows the what. In firmware add the context nobody else can recover: the board revision it was tested on, the scope measurement that proved it, the datasheet page that justifies the magic number. That is the difference between a log and an engineering record.

Two firmware-specific habits. Vendor code and generated code get their own commits — a CubeMX regeneration touches hundreds of lines, and mixing it with your change makes both unreviewable; keep it separate and say which tool version produced it. And binaries do not belong in Git, with one exception: a released hex, tagged, may be worth archiving somewhere permanent, and a release artefact store is the better home. The baseline idea from the automotive chapter says the same thing more formally.

Reviewing code you cannot run

🧒 Simple

In most software you can check out somebody's change and try it. In firmware you often cannot: there is one board, and it is on their desk. So the review has to be done by reading — which means the reviewer needs to know what to look for rather than what to click.

The good news is that the list is short, and almost all firmware review findings are on it.

🎓 Professional

The checklist that finds real defects, in the order they occur:

  • Concurrency. Is any variable touched by both an ISR and the main context? Then it wants volatile and, if it is wider than a word or read as a pair, a critical section (chapter 6, chapter 42). This is the single most productive question in a firmware review.
  • Blocking. Does anything wait in a place that must not wait — a delay in an ISR, an unbounded while on a hardware flag with no timeout? Every wait on hardware needs an escape and a defined behaviour when it expires.
  • Buffers and indices. Length checks before a copy, index types that cannot wrap, no strcpy family (chapter 14).
  • Error paths. Is every returned status examined? A driver call whose result is ignored is the trap door under most field failures.
  • Resource lifetime. Is everything initialised before an interrupt that uses it is enabled? Interrupt-before-init is a classic, and it appears only at cold start on a cold day.
  • Layering. Does the diff put a register access somewhere it does not belong (chapter 35)?
  • Evidence. How was this tested? “It works” is not an answer; a host unit test, a scope capture or a log excerpt is.

On being reviewed: a pull request should be small enough to read in twenty minutes, should say in its description what it does, how it was verified and what is still open, and should not mix a refactor with a behaviour change — a reviewer cannot see a bug through a thousand moved lines. On reviewing: separate must fix from suggestion explicitly, ask a question where you are unsure rather than asserting, and remember that in a firmware team the reviewer is often the only other person who will ever read that code before it is in a customer's machine. Static analysis and MISRA belong in CI, not in review comments — a human arguing about brace placement is a wasted human.

The release, and knowing what is in the field

🧒 Simple

Releasing firmware means: decide this is the version, give it a number, build it in a way anybody can repeat, put that number inside the binary so the device can tell you what it is running, and keep the pieces — the binary, the map, the tag, the notes — somewhere they will still be in five years.

The reason for all of it is one moment: a board comes back, and somebody has to say what software it has and what changed since the one that worked.

🎓 Professional

A release procedure that fits on a card:

  1. Tag the commit, annotated, with a version. Semantic versioning works if you define what a breaking change means for a device — usually a change to a protocol, a parameter layout, or bootloader compatibility.
  2. Build from the tag, clean, in CI, with the pinned toolchain from chapter 36. Never ship a binary built on somebody's laptop; it cannot be reproduced and nobody knows what was in the working tree.
  3. Embed the identity: version string and git describe output — which gives you the tag, the distance from it, the short hash and a dirty marker — compiled in and readable over the diagnostic interface, alongside the hardware revision.
  4. Archive the artefacts: hex or binary, the ELF (for decoding a future crash), the map, the build log with the toolchain version, and the test report.
  5. Write release notes aimed at the people who will read them — production, service, the customer — not a commit log. What changed, what it fixes, what it breaks, and whether the bootloader or the tooling must be updated with it.
  6. State the compatibility: which hardware revisions this runs on, which bootloader it needs, and whether a downgrade is possible. If a parameter block changed layout, say what happens to the parameters of a device being updated — because something will happen to them either way.

Versioning is a product decision as much as an engineering one. A device that cannot report its own version is a device whose field population is unknown, and an unknown field population makes every subsequent decision — recall, update campaign, root cause — guesswork. It is two lines of code and it is the difference between a product and a prototype.

⚠ Trap

A board comes back from a customer, and nobody can say what is on it.

The chain of small conveniences that leads there is always the same, and each link is reasonable on its own. Somebody flashed a quick fix from their laptop to unblock a test. The working tree had one uncommitted line. The version constant was not bumped because “it is only a test”. The board went to a customer because it was the only one available. Six months later the fault report arrives, the version says 1.4.0, main says 1.4.0, and the two are not the same software.

Everything in this chapter exists to break one link of that chain. Embed git describe, including the dirty flag, so that a binary built from modified sources says so out loud — that one change alone makes the story above self-diagnosing. Refuse to release from a laptop, and make CI the only path to an artefact anybody may flash onto something that leaves. And make the device report version, Git hash and hardware revision over its diagnostic interface — in automotive that is exactly what ReadDataByIdentifier is for, and in an industrial product it is one Modbus register block.

The second, quieter version of the same trap: a released version that no longer builds. The toolchain moved, a submodule's remote disappeared, a vendor library was downloaded rather than vendored. Building every tag in CI on a schedule sounds paranoid until the first time a five-year -old product needs one line changed.

Try it. All of this is doable on your own project today, and it is one of the few things on a junior CV that reads as professional rather than academic.

1. Make your build stamp itself. In the Makefile:

     GIT_VER := $(shell git describe --tags --always --dirty)
     CFLAGS  += -DFW_VERSION=\"$(GIT_VER)\"

   Print it at startup on the UART. Then modify a file WITHOUT
   committing, rebuild, and watch "-dirty" appear. That suffix is the
   whole point of this chapter.

2. Tag and release once, properly, on a personal project:

     git tag -a v0.1.0 -m "First release: "
     git push --tags

   Then write the release notes for an imaginary service technician
   rather than for yourself. It is harder than it sounds, and it is
   the skill the advert is really testing.

3. Practise bisect, because it is the Git command that pays best in
   firmware. Create a repo, commit 20 small changes, break something
   in the middle, then:

     git bisect start; git bisect bad; git bisect good HEAD~20

   Five steps to the culprit. Do it once so that you reach for it
   under pressure.

4. Practise recovering. Delete a branch, then get it back with
   `git reflog`. Reset --hard by mistake, then recover the commit the
   same way. Knowing that almost nothing is really lost is what makes
   somebody calm with Git, and calm is what "dimestichezza" means.

5. Review somebody else's firmware. Find a small open-source driver
   on GitHub, read one file against the seven-point checklist above,
   and write the review you would post. Two or three real findings is
   a good result -- and it is an excellent thing to be able to talk
   about in an interview, because almost no junior has done it.
Golden rules
  • Main always builds and passes the host tests. A red main is not a reference point.
  • Short branches. In firmware the hardware moves under a long one.
  • One logical change per commit, and a message that records the reasoning, the board revision and the evidence.
  • Generated and vendor code gets its own commit, naming the tool version.
  • Review for concurrency, blocking, buffers, error paths, init order, layering and evidence. Leave style to the tools.
  • A pull request is small, described, and does not mix a refactor with a behaviour change.
  • Every build that leaves the building is tagged and built by CI from that tag, with a pinned toolchain.
  • Embed git describe with the dirty flag, and let the device report it over its diagnostic interface.
  • Archive hex, ELF, map, build log and test report. The ELF is how you decode a crash five years from now.
  • Release notes are for service and production, and must state hardware and bootloader compatibility.
  • If a device cannot report its own version, its field population is unknown — and every decision after that is guesswork.

“Come gestisce il versionamento e il rilascio di un firmware?”

“Git, con un ramo principale che deve sempre compilare e passare i test host, rami di feature corti — nel firmware un ramo lungo è un problema, perché nel frattempo cambia l’hardware sotto — e un tag per ogni build che esce dall’azienda. Nei commit ci metto anche le cose che dal diff non si recuperano: su quale revisione di scheda è stato provato, la misura che lo dimostra, la pagina del datasheet del numero magico. Il codice generato da CubeMX lo tengo in commit separati, se no la revisione è illeggibile. Sul rilascio la regola che considero non negoziabile è che il binario lo produce la CI dal tag, con toolchain fissata, mai il mio portatile: e dentro il binario ci va git describe con il flag dirty, leggibile dal dispositivo via diagnostica — in automotive con un ReadDataByIdentifier, in ambito industriale con un blocco di registri Modbus. Il motivo è molto concreto: quando torna indietro una scheda dal campo, la prima domanda è quale software ha sopra. Se qualcuno ha flashato al volo una modifica non committata e la versione dice 1.4.0 come il main, ma non sono lo stesso software, quella scheda non è diagnosticabile. Il suffisso dirty risolve da solo metà di quella storia. E archivio hex, ELF, mappa, log di build e report di test: l’ELF è l’unica cosa che fra cinque anni mi permette di decodificare un crash.”
