Makefile, CMake and the linker script

Leaving the IDE. What the four steps of a build actually are, how a cross-compiler is told which machine it is building for, and how to read the .ld file that decides where every byte of your program lands — including the one that tells you that you have run out of RAM.

From the advert

Not named in the anchor advert, which assumes the STM32 development environment and leaves the build inside it. It is here because a project that can only be built by one person clicking a button in an IDE is not a project a team can ship — and because the second advert in the corpus asks in so many words for somebody to “supportare le attività di build e integrazione software”.

Chapter 64a is what that job looks like from the process side. This is the mechanism underneath it.

The four steps, and where each one fails

🧒 Simple

Building is four steps, and knowing which one broke tells you almost everything about the error message in front of you.

The preprocessor pastes headers together and resolves the #ifs. The compiler turns each of those files, on its own, into machine code. The linker joins all those pieces, resolves the names each one left open, and places everything at real addresses. Then a small tool copies the result out into the plain hex file a programmer can flash.

A missing header is step one. A syntax error is step two. “Undefined reference” is step three — the compiler was happy, nobody supplied the function. And “region RAM overflowed” is also step three, telling you the program does not physically fit.

🎓 Professional

Chapter 2 walked the path; this is the part you configure. For an STM32 the toolchain is arm-none-eabi-: the none is the operating system, which is to say there is not one, and eabi is the calling and object-file convention. Three groups of flags do the real work, and being able to say what each is for is a reasonable interview bar:

  • Architecture flags, which must be identical for every object file and every prebuilt library you link: -mcpu=cortex-m4 -mthumb -mfpu=fpv4-sp-d16 -mfloat-abi=hard. A mismatch here produces either a link error about incompatible float ABIs, or — worse — a binary that runs until the first float crosses a function boundary.
  • Language and warning flags: -std=c11 -Wall -Wextra, plus -Werror in CI. Firmware warnings are rarely stylistic; -Wall catches a good share of the undefined behaviour in chapter 13.
  • Optimisation and debug: -O0 for a first bring-up, -Og for daily debugging, -Os for a size-constrained release. Always -g, in every configuration including the shipped one: debug symbols live in the ELF, not in the hex, so they cost nothing on the device and are the only thing that will let you decode a crash from the field.

Two more that pay for themselves: -ffunction-sections -fdata-sections with -Wl,--gc-sections, which lets the linker discard anything unreferenced instead of dragging in a whole object file for one function; and -Wl,-Map=build/out.map, which writes the map file — the single most underused artefact in embedded work, and the subject of the exercise below.

Make or CMake? A hand-written Makefile is fine and completely transparent, and for one board it is often the right answer. CMake earns its keep when you have several targets (the device build and the host test build from chapter 35), several variants, and an IDE that somebody else insists on using. The concept that matters in CMake is the toolchain file: a small file naming the cross-compiler and the architecture flags, passed once with -DCMAKE_TOOLCHAIN_FILE=..., which is how the same project configures for the target or for the host. Whichever you pick, build out of tree — every artefact under build/, nothing generated beside the source — so that a clean build is a directory deletion rather than an act of faith.

Reading the linker script

🧒 Simple

The chip has two kinds of memory at fixed addresses: flash, which keeps its contents with the power off, and RAM, which is fast but forgets. Your program is made of pieces with different needs: instructions and constants can live in flash; variables must end up in RAM.

The linker script is the small file that says where each kind of piece goes. It is also the file that says how big each memory is — which is why it, and not the compiler, is what tells you that your program no longer fits.

🎓 Professional

An .ld file has two halves. MEMORY declares the regions, and SECTIONS places the input sections into them: 

MEMORY
{
  FLASH (rx)  : ORIGIN = 0x08000000, LENGTH = 512K
  RAM   (rwx) : ORIGIN = 0x20000000, LENGTH = 128K
}

SECTIONS
{
  .isr_vector : { KEEP(*(.isr_vector)) } > FLASH   /* must be first */
  .text       : { *(.text*) *(.rodata*) } > FLASH
  .data       : { _sdata = .; *(.data*) _edata = .; } > RAM AT> FLASH
  .bss        : { _sbss  = .; *(.bss*)  _ebss = .; } > RAM
}

The line worth understanding completely is .data. Initialised globals need two addresses: a load address in flash, where their initial values are stored, and a virtual address in RAM, where the program will find them. > RAM AT> FLASH is exactly that, and the symbols around it are what the startup code from chapter 24 uses to copy the block across before main. .bss has no load address because it is zeroed, which is why a large zero-initialised array costs RAM but no flash — and why moving an array from = {0} to = {1} can suddenly cost kilobytes of flash. KEEP on the vector table prevents --gc-sections from discarding it, since nothing in C ever references it.

Three things you will actually need to do to a linker script in a real project: reserve a region for the bootloader and move the application's ORIGIN past it; place a small no-init section that survives a warm reset to carry a crash reason across it; and put a buffer in a particular memory — CCM RAM, or a DMA-capable region, which is a real constraint on many parts (chapter 27). All three are a couple of lines, and all three are invisible until somebody has read this file once.

The build a team can trust

🧒 Simple

A build is trustworthy when anybody can check out the code on any machine, run one command, and get exactly the same binary. That sounds obvious and is surprisingly rare: the usual project builds differently depending on which version of the compiler happens to be installed, and produces a different binary every time because it stamps the current date into it.

Getting to one command that anybody can run is the difference between code that works and a product a team can release.

🎓 Professional

What to fix, roughly in order of payoff:

  • Pin the toolchain and print its version in the build log. A container image or a downloaded, checksummed toolchain archive; not “whatever is on the PATH”. Different GCC versions produce different code, different sizes and occasionally different behaviour, and a safety argument names the compiler version explicitly.
  • Remove non-determinism. __DATE__ and __TIME__ in the firmware are the usual culprits; replace them with the Git describe output, which changes only when the source does. Then verify by building twice from clean and diffing the binaries.
  • Stamp identity into the binary: version, Git hash, dirty flag, and make it readable over the diagnostic interface. When a board comes back from the field, the first question is which software is on it, and chapter 66 is about being able to answer it.
  • Build variants from one source tree, with the variant name in the artefact name, so make VARIANT=pump2 release yields build/pump2/app-pump2-v1.4.2.hex. The moment variants live on branches instead of in the build system, merging becomes the product's main engineering cost.
  • Publish the size and the map on every build. arm-none-eabi-size in the log turns “we ran out of flash” from a surprise into a graph.
⚠ Trap

The link succeeds, the board boots, and you are already out of RAM — because the linker checked the static footprint and nobody checked the stack.

region RAM overflowed counts .data and .bss. It does not count how deep your call graph goes at run time, and on most default scripts the stack is simply placed at the top of RAM and grown downwards with nothing between it and your variables. Add a 488-byte buffer to a function, and one day an interrupt arrives at the wrong moment and the stack writes over .bss. The symptom is a variable changing value on its own, which is the single most expensive bug class in this field (chapter 12).

What to do, all of it cheap. Read the map file after every significant change and know your static total, rather than discovering it at 99 %. Compute a worst-case stack depth — GCC's -fstack-usage emits per-function frame sizes, and a small script over the call graph turns those into a number. Put a guard region between the stack and .bss in the linker script, filled with a pattern, and check it; or use the MPU to make the overflow a fault instead of a corruption. And in an RTOS, remember each task has its own stack and the linker sees it as one anonymous array, so the high-water mark API is the only measurement that means anything.

Related, and very common in interviews: “why is my hex file smaller than my ELF?” Because the ELF carries debug information and section metadata and the hex carries only the bytes that go into flash. And “why did my float printf add 20 KB?” Because the standard library's formatted output pulls in floating-point conversion; newlib-nano and -u _printf_float exist precisely so that this is a decision rather than an accident.

Try it. Everything here works on an ordinary PC with gcc-arm-none-eabi installed, with no board attached — you are inspecting build artefacts, not running them.

1. Take a CubeIDE project and build it from a terminal instead. Cube
   can generate a Makefile (Project Manager -> Toolchain: Makefile);
   generate it, run `make`, and read the first compile line it prints
   in full. Every flag in it is one of the three groups above -- name
   each one out loud. That exercise alone removes most of the mystery.

2. Add the map file and read it:

     LDFLAGS += -Wl,-Map=build/out.map,--cref
     arm-none-eabi-size -A build/app.elf

   Find your three biggest objects in the map. It is almost never what
   you expect, and it is frequently a library you did not know you
   linked.

3. Make something not fit, on purpose. Add `uint8_t big[100000];` and
   read the error. Then make it `static` and unused and watch it still
   not fit -- .bss is reserved whether or not you use it. Then turn on
   -ffunction-sections -fdata-sections -Wl,--gc-sections and compare
   sizes before and after on the real project.

4. Move the application. Change ORIGIN of FLASH from 0x08000000 to
   0x08008000 and LENGTH down by 32K, as if a bootloader lived there,
   and rebuild. Then look at the hex file's first record and confirm
   the addresses moved. That is the entire mechanism behind chapter 34.

5. Prove reproducibility. Build twice from clean into two directories
   and diff the hex files. If they differ, find the __DATE__ or the
   absolute path that leaked in and remove it. A reproducible build is
   a concrete, demonstrable thing to have done.

6. Then do it in CI: a GitHub Actions or GitLab job that installs a
   PINNED toolchain, builds, prints `size`, and uploads the hex and
   the map as artefacts. That job is a genuinely good portfolio item,
   and chapter 70 explains why it is worth more on a CV than another
   blinking LED.
Golden rules
  • Know which of the four steps failed — preprocess, compile, link, objcopy. “Undefined reference” and “region overflowed” are both the linker, and they mean opposite things.
  • Architecture flags must match everywhere, including prebuilt libraries. A float-ABI mismatch is a link error on a good day and a silent corruption on a bad one.
  • Always compile with -g, including releases. Symbols live in the ELF, not in the hex.
  • --gc-sections with -ffunction-sections is usually the cheapest size win available.
  • Generate and read the map file. It is the only place the truth about size lives.
  • The linker script owns the memory map: MEMORY for regions, SECTIONS for placement, and > RAM AT> FLASH is why .data has two addresses.
  • .bss costs RAM and no flash, so a zero-initialised array is free in flash and a non-zero one is not.
  • The linker does not know about the stack. Measure it; guard it; in an RTOS use the high-water mark.
  • Build out of tree, one command, pinned toolchain, and print the toolchain version in the log.
  • Stamp version and Git hash into the binary and make them readable from the device.
  • Variants belong in the build system, never on branches.

“Sì, e lo considero il passaggio che rende un progetto di squadra invece che di una persona. La toolchain è arm-none-eabi, e i flag li divido in tre gruppi: architettura — mcpu, mthumb, fpu e float-abi, che devono essere identici per tutti gli oggetti e anche per le librerie precompilate, se no al link mi salta fuori un errore di ABI incompatibile; linguaggio e warning, con -Wall -Wextra e -Werror in CI; e ottimizzazione, con -g sempre, anche in release, perché i simboli stanno nell’ELF e non nell’hex, quindi sul dispositivo non costano niente e senza di quelli un crash dal campo non lo decodifico. Il linker script ha due parti: MEMORY, che dichiara flash e RAM con indirizzo e dimensione, e SECTIONS, che piazza le sezioni. La riga che vale la pena saper spiegare è la .data, che ha due indirizzi — sta in RAM ma è caricata in flash — ed è il motivo per cui lo startup prima di main copia quel blocco; la .bss invece viene solo azzerata, quindi costa RAM e non flash. La cosa che guardo sempre è il file di mappa, e soprattutto lo stack: il linker mi dice se .data e .bss ci stanno, non mi dice quanto è profonda la mia catena di chiamate, e l’overflow dello stack si manifesta come una variabile che cambia da sola. Quindi -fstack-usage, una regione di guardia o l’MPU, e su RTOS la high-water mark per task.”
