const, volatile, and the compiler that deleted your poll loop

If an embedded interview asks you exactly one language question, this is the one. Not because the keyword is difficult, but because answering it well requires you to say something about the compiler rather than about your program — and most candidates cannot.

From the advert

Not in this advert. No posting has ever written the word volatile. It is nevertheless the most frequently asked single question in embedded hiring worldwide, and the reason is in this chapter: it is a cheap question that separates people who have driven hardware from people who have only read about it.

What an optimiser is allowed to assume

🧒 Simple

The compiler is allowed to rewrite your code, as long as the result is the same. If you write a variable and then read it back, it does not need to actually visit memory — it already knows what is there, so it can keep the value in a register and skip the trip.

That is almost always a good deal. But a hardware register is not an ordinary variable. It can change on its own, because a wire outside the chip changed. The compiler does not know that, so it cheerfully optimises away the very read you needed.

🎓 Professional

The C abstract machine permits any transformation that preserves observable behaviour. Absent other information, the compiler assumes a variable changes only when the code it can see changes it. Under that assumption, reading the same address twice with nothing in between is redundant, and a loop whose condition it has already proved constant can be replaced by nothing, or by an unconditional jump to itself.

Three things violate that assumption, and all three occur constantly in firmware:

  • A memory-mapped peripheral register that hardware writes.
  • A variable written by an interrupt service routine, which from the main loop's point of view runs at no particular moment.
  • A variable shared with another task, or with a DMA controller writing into a buffer.

volatile is how you tell the compiler this. It means: every read in the source must produce a real load, every write a real store, and you may not reorder them relative to each other. It is a statement about the compiler's freedom, not about the variable's contents — which is exactly why the question is a good filter.

The empty while loop that proves it

🧒 Simple

The classic example is a flag that an interrupt sets, and a loop in the main program that waits for it. Without volatile the compiler reads the flag once, sees it is zero, and turns the wait into “loop here forever”. The interrupt sets the flag, and nobody is listening any more.

🎓 Professional

Written out, with what the compiler does to each: 

/* WRONG. The optimiser hoists the load out of the loop. */
static int ready = 0;

void EXTI0_IRQHandler(void) { ready = 1; }   /* set by hardware event */

void wait(void) {
    while (ready == 0) { }   /* becomes: if (ready == 0) for (;;) ; */
}

/* RIGHT. Every iteration performs a real load. */
static volatile int ready = 0;

The failure is not theoretical and not rare. It is also asymmetric in the worst way: at -O0 the code works, because the optimiser is off. It breaks when somebody turns on -O2 for the release build — which is chapter 13's subject in general, and this in particular.

The same applies to a hardware status register. while ((USART1->ISR & RXNE) == 0); only works because the CMSIS headers declare the peripheral struct members volatile. If you roll your own register definitions and forget it, the wait loop never exits.

⚠ Trap

volatile is not atomic, and it is not a memory barrier, and it does not make code thread-safe. This is the follow-up question, and it is where most candidates who got the first half right fall over.

volatile uint32_t counter; counter++; still compiles to load, add, store — three instructions, interruptible between any two. If an ISR also increments it, you lose counts. volatile guaranteed the memory traffic happens; it guaranteed nothing about it happening indivisibly.

Nor does it order accesses to non-volatile objects around it, and on a multi-master system (a Cortex-M7 with a data cache, or DMA writing into your buffer) it says nothing to the hardware about visibility — that needs __DMB(), cache maintenance, or a non-cacheable MPU region. For shared counters, use a critical section, an RTOS primitive (chapter 40), or <stdatomic.h> where the part supports it.

const, and why it is not the opposite of volatile

🧒 Simple

const is a promise you make: “this code will not change this thing.” It does not promise that nothing else will.

On a microcontroller it has a second, very practical effect: a const table can live in flash memory, of which you usually have plenty, instead of RAM, of which you usually do not.

🎓 Professional

const constrains the program, not the object. Two consequences worth having ready:

It is a placement decision. A file-scope const array goes in .rodata, which the linker places in flash; the same array without const goes in .data and costs you both flash (for the initialiser) and RAM (for the copy made at startup). On a part with 20 KB of SRAM, a 4 KB lookup table is the difference between fitting and not — chapter 10.

It is an interface document. void send(const uint8_t *buf, size_t n) tells every caller that the buffer is not modified, which means it may be a literal, a const table in flash, or a shared buffer. Omitting it forces callers to copy defensively.

And the two are not opposites: const volatile is meaningful and common. A read-only hardware status register is exactly that — your code must not write it, and it changes without your code's involvement. Read declarations right to left: const volatile uint32_t *p is a pointer to a const volatile uint32_t.

Try it. On a PC, with nothing but gcc. This is the fastest way to make the point stick, because you see the instruction disappear.

cat > poll.c <<'EOF'
int flag;                 /* try again with: volatile int flag; */
void wait(void) { while (flag == 0) { } }
EOF

# -S stops after the compiler, leaving assembly you can read
gcc -O2 -S poll.c -o - | sed -n '/^wait:/,/ret/p'

# Without volatile you will see the load happen ONCE before a bare
# infinite jump back to itself, something like:
#     movl  flag(%rip), %eax
#     testl %eax, %eax
#     jne   .done
# .spin:
#     jmp   .spin          <- the flag is never read again
#
# With volatile, the load is INSIDE the loop body. That single moved
# instruction is the entire answer to the interview question.
Golden rules
  • volatile is a statement about the compiler's freedom, not about the variable's contents.
  • It means every read and write in the source really happens, in order, and none is optimised away.
  • Use it for hardware registers, ISR-shared variables and DMA buffers — the three things that change without your code changing them.
  • volatile is not atomic and not a barrier. A volatile increment is still load, add, store.
  • const is a promise your code makes, and on a microcontroller it is also a decision to spend flash instead of RAM.
  • const volatile is normal, and describes a read-only hardware status register exactly.
  • Works at -O0, breaks at -O2 is the signature of a missing volatile.
