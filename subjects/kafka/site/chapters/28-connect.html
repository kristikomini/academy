Kafka Connect: sources and sinks

Moving data in and out of Kafka without writing a producer or consumer. Configuration instead of code — and the distributed worker model that makes it worth using rather than writing the integration yourself.

From the advert

“Familiarity with Kafka tools (such as Kafka Streams, Connect, and Zookeeper)”.

Configuration instead of code

🧒 Simple

Connect is a service that runs ready-made connectors. A source pulls data from somewhere into Kafka; a sink pushes it from Kafka to somewhere else.

You configure them with JSON — you do not write the integration.

🎓 Professional

Connectors exist for the things you would otherwise write badly: JDBC, S3, Elasticsearch, MongoDB, HDFS, and the CDC connectors in chapter 29. Each handles the parts everyone gets wrong the first time — offset tracking so a restart resumes where it stopped, retries, schema propagation to the registry, and batching.

The argument for it over a hand-written consumer is not effort but correctness. A sink connector that resumes exactly where it left off after a crash is a solved problem; the version you write in an afternoon usually is not, and the bug appears months later as missing rows.

Workers, tasks and distributed mode

🧒 Simple

Connect runs as its own small cluster. You submit connector configurations to it over HTTP, and it spreads the work across its workers.

🎓 Professional

A connector is split into tasks — typically one per table, or per partition — distributed across workers. Distributed mode is what you want in production: workers coordinate through Kafka itself (using the consumer group protocol), store connector configuration, offsets and status in internal topics, and redistribute tasks when a worker dies. Standalone mode is for a laptop.

Management is entirely through a REST API — create, pause, resume, restart, inspect status — which makes it scriptable and pipeline-friendly. That also means connector configuration is state living inside a running cluster, so it belongs in version control and should be applied by your pipeline rather than by whoever last ran a curl.

Try it. Create a sink from a topic to a database with one HTTP call, then check its status. Nothing here is code you maintain.

# a JDBC sink: topic -> table, with upsert semantics on the key
curl -X PUT http://connect:8083/connectors/orders-to-oracle/config \
  -H 'Content-Type: application/json' -d '{
    "connector.class": "io.confluent.connect.jdbc.JdbcSinkConnector",
    "topics": "orders.enriched",
    "connection.url": "jdbc:oracle:thin:@//db:1521/ORCL",
    "insert.mode": "upsert",
    "pk.mode": "record_key",
    "pk.fields": "order_id",
    "auto.create": "false",
    "tasks.max": "3",
    "errors.tolerance": "all",
    "errors.deadletterqueue.topic.name": "orders.enriched.dlq",
    "errors.deadletterqueue.context.headers.enable": "true"
  }'

curl http://connect:8083/connectors/orders-to-oracle/status | jq

Transforms, and where they stop

🧒 Simple

Connect can apply small changes on the way through — rename a field, drop one, change the key. Anything more than that belongs elsewhere.

🎓 Professional

Single Message Transforms operate on one record at a time: mask a field, extract a nested value, set the key from a field, route by content. They are genuinely useful and strictly limited — no joins, no aggregation, no access to other records.

Which gives a clean division worth stating: Connect moves data, Streams transforms it. When you find yourself chaining six SMTs, the logic has outgrown Connect and wants a Streams application (or ksqlDB) in the middle: source connector into a raw topic, Streams into a clean topic, sink connector out.

⚠ Trap

Set errors.tolerance and a dead-letter queue deliberately. The default is to fail the task on the first bad record, so one malformed message stops the whole connector — the poison-pill problem from chapter 19, now silent, because a stopped connector produces no alerts unless you monitor connector status. Failing tasks are not an error anyone sees by default.

Golden rules
  • Configuration, not code — and the reason is correctness, not effort.
  • Distributed mode in production. Config, offsets and status live in Kafka topics.
  • Managed over a REST API. So keep the configs in git and apply from the pipeline.
  • SMTs are per record. No joins, no aggregation.
  • Connect moves, Streams transforms. Six chained SMTs means you crossed the line.
  • Set errors.tolerance and a DLQ, and monitor connector status.

“Come porterebbe i dati di Kafka dentro un database?”

“Con un sink connector di Kafka Connect, non con un consumer scritto a mano — e il motivo non è il tempo risparmiato ma la correttezza: il connector gestisce il tracciamento degli offset, i retry e la ripartenza esattamente dal punto giusto dopo un crash, che è proprio la parte che una versione fatta in casa sbaglia e se ne accorge mesi dopo. Lo eseguo in distributed mode, tengo le configurazioni in git e le applico dalla pipeline via REST, e imposto errors.tolerance con una dead letter queue, altrimenti un singolo record malformato ferma il connector in silenzio.”
