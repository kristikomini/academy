REST Proxy, and clients in other languages

Not everything that needs to reach Kafka can run a Java client. The non-JVM clients, the REST proxy, and the bridges you build for systems that cannot speak the protocol at all.

From the advert

“architetture applicative con competenze su REST, SQL e Apache Kafka”. Architecture means the systems that cannot use the Java client — and there are always some.

The non-JVM clients

🧒 Simple

Kafka’s official client is Java, but there are good clients for other languages — almost all of them built on one C library.

🎓 Professional

librdkafka is the C implementation underneath the Python, .NET, Go, Node and PHP clients, so they share its behaviour and much of its configuration vocabulary. That is useful to know: a configuration answer for confluent-kafka-python usually translates directly to the .NET client.

They are mature and production-grade, with two caveats worth stating. Feature parity lags the Java client — transactions and especially Kafka Streams are JVM-only, so a stateful streaming job in Python means a different tool entirely (Flink, Faust, or a plain consumer with your own state). And the ecosystem’s reference documentation is written for Java, so translation is a permanent small tax.

REST Proxy

🧒 Simple

If a system can only make HTTP calls, a proxy in front of Kafka lets it produce and consume over REST.

It is slower and simpler — and sometimes it is the only thing the other side can do.

🎓 Professional

The Confluent REST Proxy exposes produce and consume over HTTP, handling serialisation and schema registry integration. Legitimate uses: a language with no good client, a system behind a firewall that only permits HTTP, a browser, or a partner integration where you will not ship a Kafka client.

The costs are real. Consuming over REST needs a server-side consumer instance held between polling calls, which makes consumer groups and rebalancing awkward; throughput is far lower than the native protocol; and you have added a stateful component to operate and scale. Use it for produce far more readily than for consume — producing over HTTP is nearly stateless and works well; consuming over HTTP fights the model.

⚠ Trap

The proxy is a single point of failure and a bottleneck that native clients do not have, because every record now passes through an extra hop that must be sized, monitored and made redundant. Reaching for it because HTTP feels simpler than a client library is trading a library dependency for an operational one, and the operational one is more expensive.

Bridging systems that cannot speak at all

🧒 Simple

Some systems will never talk to Kafka: a machine on a factory floor, an FTP drop, a partner that sends a nightly file. You write a small service that translates.

🎓 Professional

This is the industrial integration pattern from Java chapter 34 seen from the Kafka side: a gateway subscribes to OPC UA or MQTT, or polls Modbus, normalises readings into domain events, and produces them. For file-based partners a Connect source (chapter 28) or a small scheduled service does the same job.

Two design rules carry most of the value. Translate at the edge: the bridge emits domain events, not the source system’s vocabulary, so no consumer inherits a vendor’s register numbers or a partner’s CSV column order. And make the bridge idempotent and restartable, since it will be restarted mid-file and mid-poll, and duplicate readings must be harmless.

Golden rules
  • Most non-JVM clients are librdkafka, so their configuration vocabulary is shared.
  • Streams and transactions are JVM-only. Stateful streaming in Python is a different tool.
  • REST Proxy for produce, reluctantly for consume. Consuming over HTTP fights the model.
  • The proxy is a hop you must size, monitor and make redundant.
  • Bridges translate at the edge. Domain events out, never the vendor’s vocabulary.
  • Assume the bridge restarts mid-stream. Idempotent and resumable.

“Un sistema esterno non può usare un client Kafka. Come lo integrate?”

“Dipende da cosa riesce a fare. Se può fare HTTP, il REST Proxy va bene soprattutto in produzione di messaggi: produrre è quasi stateless, mentre consumare via REST richiede un consumer lato server tenuto vivo tra una chiamata e l’altra e complica gruppi e ribilanciamenti. Se invece non parla affatto — un PLC, un partner che manda un file la notte — scrivo un piccolo gateway che traduce: si sottoscrive o fa polling, normalizza in eventi di dominio e produce su Kafka. La regola che seguo è tradurre al bordo: non voglio che i consumatori ereditino i numeri di registro del fornitore o l’ordine delle colonne di un CSV.”
