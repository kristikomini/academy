Schema Registry and schema evolution

The contract between producers and consumers, made explicit and enforced. Subjects, versions, the magic byte, and the mechanism that stops one team’s deployment from breaking another team’s consumer.

From the advert

“Apache Kafka — producer/consumer development, topic design, schema registry”, from the aggregated Kafka-developer requirement lines.

What it is and why it exists

🧒 Simple

A registry is a service that stores the shape of the data on each topic. Producers register the shape they write; consumers fetch the shape they need to read.

So the agreement between two teams becomes a thing you can check, instead of a conversation somebody remembers.

🎓 Professional

Chapter 19 established that the broker validates nothing. The registry fills that gap: it stores schemas under subjects (by default topicName-value and topicName-key), assigns each a version and a globally unique id, and — critically — refuses a registration that violates the subject’s compatibility rule (chapter 21).

That refusal is the entire value. Without it, an incompatible change is discovered by a consumer at three in the morning; with it, the producer’s deployment fails in CI with a message naming the incompatible field.

The magic byte

🧒 Simple

Each record carries a small header saying which schema it was written with. The consumer reads that, fetches the right schema, and decodes correctly.

🎓 Professional

The Confluent wire format is: one magic byte (zero), then a four-byte schema id, then the payload. So the schema is not embedded per record — only a reference is, which is why the overhead is five bytes rather than a repeated schema.

Clients cache schemas by id, so the registry is consulted rarely and is not on the hot path. It is, however, on the start-up path: a consumer that cannot reach the registry cannot decode anything, so the registry is a dependency to include in availability planning. Knowing the wire format also explains a very common confusion — reading an Avro topic with a plain string consumer shows leading rubbish, and that rubbish is the magic byte and schema id.

⚠ Trap

auto.register.schemas defaults to true, which lets any producer register a new schema version on the fly — including from a developer laptop, into the shared registry. Turn it off in production and register schemas through your pipeline, or your compatibility rules are enforced against whatever somebody happened to run last.

Evolution in practice

🧒 Simple

Data outlives code. A schema has to be able to change without breaking consumers that have not been updated yet.

🎓 Professional

Avro resolves the writer’s schema against the reader’s, which is what makes evolution work: a reader with a newer schema can read older data if new fields have defaults, and a reader with an older schema can read newer data by ignoring unknown fields. Defaults are what make a field addition safe, and forgetting one is the most common evolution mistake.

Practical habits: give every new field a default, never reuse a field name for a different meaning, prefer adding a field to changing one, and treat a rename as “add the new, migrate, remove the old” — the same expand-and-contract discipline as a database migration (Java chapter 29), for exactly the same reason.

Golden rules
  • The registry enforces the contract the broker will not. Its refusals are the value.
  • Wire format: magic byte, schema id, payload. Five bytes, not a repeated schema.
  • Clients cache by id, but the registry is a start-up dependency.
  • Turn off auto.register.schemas in production.
  • Every new field gets a default. That is what makes addition safe.
  • Renames are expand-and-contract, exactly as in a database.

“A cosa serve lo Schema Registry?”

“Il broker non valida niente: memorizza byte. Quindi senza registry il contratto tra chi produce e chi consuma esiste solo negli accordi verbali, e il primo segnale che si è rotto è un consumer che non riesce più a deserializzare. Il registry conserva gli schemi per subject e versione e, soprattutto, rifiuta una registrazione che viola la regola di compatibilità — quindi l’errore compare nella pipeline di chi produce, non alle tre di notte da chi consuma. Sul filo passa solo un magic byte e l’id dello schema, cinque byte, e i client fanno cache per id.”
