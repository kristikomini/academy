Ordering: what Kafka guarantees and what it does not

Kafka orders within a partition and nowhere else. Every way a system accidentally gives that up — and there are more of them than people expect, most of them invisible until volume rises.

From the advert

Not in any advert. And the assumption that breaks quietly: systems work perfectly at low volume and produce wrong answers under load, because ordering was never guaranteed in the way somebody assumed.

The guarantee, stated exactly

🧒 Simple

Records in one partition are read in the order they were written. Records in different partitions have no order relative to each other at all.

So “is this topic ordered?” has no answer. “Is this key ordered?” does.

🎓 Professional

The guarantee is per-partition, and the key chooses the partition (chapter 07). So ordering is really per key, and the size of the guarantee is the size of the key.

There is no global ordering across a topic and there cannot be, because partitions live on different brokers and are written concurrently. Any design that needs total ordering needs one partition — which means one consumer, no parallelism, and a throughput ceiling. If somebody proposes that, the right question is whether they need total order or only order per entity, and the answer is almost always the second.

The four ways you lose it

🧒 Simple

Even within a partition, you can end up processing out of order — by retrying, by changing the partition count, by processing in parallel, or by having no key at all.

🎓 Professional

Producer retries could reorder before idempotence; with enable.idempotence the broker rejects out-of-sequence batches, so this is handled (chapter 09). Adding partitions rehashes keys, so a key’s new records go to a different partition than its old ones — ordering across that boundary is gone permanently (chapter 02). A null key means records are spread arbitrarily, so there was never a guarantee to lose.

The fourth is the one that catches people: parallel processing inside the consumer. Hand a batch to a worker pool and the records of one partition are processed concurrently — Kafka delivered them in order and you undid it. If you need parallelism and ordering, partition the work by key across your workers, so all records for one key go to the same worker.

⚠ Trap

Retry topics break ordering too, and it is rarely noticed. A record that fails and is republished to a retry topic is processed later than records that came after it — so for that key, the sequence is now wrong. For a status lifecycle that can mean applying shipped before paid. If ordering matters for a key, failure has to block that key rather than being deferred past it.

Designing so it does not matter

🧒 Simple

The best systems do not depend on order arriving correctly. They are written so that a record arriving late or twice still produces the right answer.

🎓 Professional

Two techniques carry most of it. Carry a version or a timestamp in the event and ignore anything older than the state you already hold — a last-write-wins guard that makes late arrival harmless. And send state, not deltas, for the same reason idempotency prefers it (chapter 16): a record saying “the status is now SHIPPED, version 4” is safe to apply in any order relative to version 3; “advance the status” is not.

That is the answer worth giving in an interview, because it moves the discussion from “how do I force ordering” to “how do I not need it” — which is the design most distributed systems eventually arrive at anyway.

Golden rules
  • Ordering is per partition, therefore per key. There is no topic-wide order.
  • Total ordering means one partition, one consumer, and a throughput ceiling.
  • Adding partitions breaks ordering for existing keys. Permanently.
  • A worker pool inside the consumer undoes the guarantee. Partition workers by key.
  • Retry topics reorder. If order matters, failure must block the key.
  • Version your events and send state, not deltas. Then late arrival is harmless.
