Kafka Streams: the topology

A library, not a cluster — which is the first thing to say about it and the thing most people get wrong. The processor topology, how parallelism is derived, and when Streams is the right tool instead of a plain consumer.

From the advert

“Familiarity with Kafka tools (such as Kafka Streams, Connect, and Zookeeper)”.

A library, not a cluster

🧒 Simple

Kafka Streams is a Java library you add to your application. There is nothing extra to deploy — your service is the stream processor.

That is the main difference from Flink or Spark, which are clusters you submit jobs to.

🎓 Professional

Streams runs inside your JVM. You deploy it like any other Spring Boot service: a container, a Deployment, the same probes and the same pipeline (Java chapter 42). Scaling is scaling instances, and coordination happens through Kafka’s own consumer group protocol — there is no scheduler, no job manager, no separate cluster to operate.

That is a real operational advantage for a team that already runs Spring services and does not want a second platform. The trade is that it is Kafka-to-Kafka only: sources and sinks are Kafka topics. If you need to read from a database or write to Elasticsearch as part of the job, that is Connect (chapter 28) or a different tool.

The topology

🧒 Simple

You describe the processing as a graph: read from a topic, filter, transform, group, write to another topic. That graph is the topology.

🎓 Professional

Source processors read from topics, stream processors transform, sink processors write. You build it with the DSL (filter, map, groupBy, join, aggregate) or, when you need per-record control over state and timing, the lower-level Processor API.

The topology is compiled and fixed at start-up, so topology.describe() prints the whole graph including the internal topics Streams will create for you — repartition topics and changelogs. Reading that output before deploying is a genuinely useful habit: it shows you where an accidental repartition is about to cost you a full round trip through Kafka.

Try it. Build it, print the topology, and read the output before you run anything. The internal topics it names are the ones you did not know you were creating.

var builder = new StreamsBuilder();

KStream<String, Order> orders = builder.stream("orders.placed",
        Consumed.with(Serdes.String(), orderSerde));

orders.filter((key, order) -> order.total().compareTo(THRESHOLD) > 0)
      .mapValues(order -> new HighValueAlert(order.id(), order.total()))
      .to("orders.high-value", Produced.with(Serdes.String(), alertSerde));

var topology = builder.build();
System.out.println(topology.describe());     // <- read this before deploying

var props = new Properties();
props.put(StreamsConfig.APPLICATION_ID_CONFIG, "high-value-alerts");   // = group.id
props.put(StreamsConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
props.put(StreamsConfig.PROCESSING_GUARANTEE_CONFIG, StreamsConfig.EXACTLY_ONCE_V2);

var streams = new KafkaStreams(topology, props);
Runtime.getRuntime().addShutdownHook(new Thread(streams::close));
streams.start();

Tasks, threads and parallelism

🧒 Simple

Streams splits the work into tasks — one per input partition. Those tasks are shared out across your running instances.

So the partition count is the ceiling here too.

🎓 Professional

The topology is divided into sub-topologies, and each gets one task per partition of its input. Tasks are assigned to num.stream.threads threads across all instances of the same application.id, using the consumer group protocol — so adding an instance rebalances tasks, exactly as in chapter 13.

Two consequences. Maximum parallelism is the partition count of the input topics, so a Streams application scales no further than the topics it reads. And application.id is the group id: it must be unique per application and stable, because it also prefixes every internal topic Streams creates. Changing it orphans the old state and starts from nothing — which is occasionally what you want and usually an accident.

Golden rules
  • A library in your JVM. No cluster, no scheduler, deploy it like any service.
  • Kafka-to-Kafka only. Other sources and sinks are Connect’s job.
  • Print topology.describe() and read the internal topics it names.
  • One task per input partition. Partition count is the parallelism ceiling.
  • application.id is the group id and prefixes every internal topic.
  • Changing application.id orphans all state.

“Quando userebbe Kafka Streams invece di un consumer normale?”

“Quando il lavoro è stateful e resta dentro Kafka: aggregazioni, join tra stream, finestre temporali. Con un consumer normale dovrei gestire io lo stato e la sua ricostruzione dopo un riavvio; Streams mi dà state store locali con changelog su Kafka, quindi il recovery è già risolto, e con processing.guarantee=exactly_once_v2 ho anche la transazionalità. Il punto a favore rispetto a Flink è che è una libreria: gira dentro il mio servizio Spring, non devo gestire un secondo cluster. Se invece devo solo leggere e scrivere su un database, un consumer semplice o Connect sono la scelta giusta.”
