Change data capture with Debezium

Turning an Oracle or MySQL transaction log into a Kafka topic. This is how Kafka usually arrives in an Italian company: not greenfield, but as a way to get events out of a gestionale nobody is allowed to rewrite.

From the advert

Not in any advert. And the most likely way you will actually meet Kafka in this region — which is why it is here despite no posting naming it.

Reading the database’s own log

🧒 Simple

Every relational database already keeps a log of every change, so it can recover after a crash. CDC reads that log and turns each change into an event.

The application does not have to be modified at all — which is the point.

🎓 Professional

Debezium tails the database’s transaction log — MySQL binlog, PostgreSQL logical replication, Oracle LogMiner or XStream, SQL Server CDC tables — and emits a record per row change to Kafka, with before and after images and the operation type. It runs as a Kafka Connect source connector (chapter 28).

Why the log rather than polling: polling with a updated_at column misses deletes entirely, misses intermediate states between polls, and puts query load on the source database. The log has every change, in commit order, and reading it costs the database almost nothing. That comparison is the answer to “why not just poll?”, and it is a question you will be asked.

Why this matters here

🧒 Simple

Most Italian companies already have a gestionale holding all the data, and nobody is going to rewrite it. CDC lets new systems consume its changes without touching it.

🎓 Professional

The realistic adoption path is exactly this: a decade-old system that cannot be modified, new requirements for search, reporting, or an integration, and no appetite for changing the legacy application. CDC gets events out without a single line of change to it, which is the only proposal that survives the meeting.

It is also the enabler for the strangler pattern (Java chapter 45): stream the old system’s changes into Kafka, build the new service as a consumer, run both, and move writes across when the new one is trusted. Being able to describe that path is a strong answer for the software houses behind these adverts, because it is what they actually need.

Snapshots, ordering and the schema you inherit

🧒 Simple

Before it can stream changes, Debezium reads the whole table once. On a large table that takes a while and is the operationally risky part.

🎓 Professional

The initial snapshot reads existing rows before switching to the log; on a very large table this is long, and older versions could hold locks. Incremental snapshotting makes it interruptible and resumable, and is the feature to ask about.

Two more, both worth naming. Ordering is per table-key, not global: the default topic-per-table with the primary key as the message key gives you per-row ordering, and there is no cross-table transaction ordering unless you consume the transaction metadata topic. And you inherit the database schema as your event schema — column names, nullability and all — so every consumer becomes coupled to the legacy table structure, and a DDL change propagates straight through.

⚠ Trap

That last point is the real design trap. Publishing raw CDC to consumers turns “somebody renamed a column” into a broken downstream service, and hands every consumer the vocabulary of a schema from 2011. The standard remedy is a Streams stage between the raw CDC topic and the topics consumers actually read: raw in, domain events out, so the legacy schema stops at your boundary. It is also why the outbox pattern (chapter 39) is preferred when you can change the application.

Golden rules
  • Read the transaction log, not the table. Polling misses deletes and intermediate states.
  • Runs as a Connect source connector.
  • This is how Kafka arrives in a legacy shop — without touching the application.
  • The initial snapshot is the risky part. Ask about incremental snapshotting.
  • Ordering is per row, not across tables.
  • Raw CDC couples consumers to the legacy schema. Put a translation stage in front.

“Come porterebbe fuori gli eventi da un gestionale che non si può modificare?”

“Con change data capture, tipo Debezium: legge il log delle transazioni del database — binlog, logical replication, LogMiner a seconda del motore — e pubblica su Kafka un record per ogni modifica di riga, senza toccare l’applicazione. Rispetto al polling su una colonna updated_at non perdo le cancellazioni né gli stati intermedi, e non carico il database di query. Le due attenzioni sono lo snapshot iniziale, che su tabelle grandi è la parte delicata, e il fatto che erediterei lo schema del database come schema degli eventi: quindi non pubblico il CDC grezzo ai consumatori, ci metto in mezzo uno stage che traduce in eventi di dominio, altrimenti una rinomina di colonna rompe tutto quello che sta a valle.”
