KStream, KTable and the duality

A stream of events and a table of latest values are the same data read two ways. This is the concept that makes streaming click, and the one that most reliably impresses in an architecture conversation.

From the advert

Not in any advert. Stream–table duality is the idea behind compaction, changelogs, CDC and event sourcing all at once — four things that look unrelated until you have it.

The duality

🧒 Simple

A bank statement is a list of transactions. Your balance is a single number. Neither is more real than the other — the balance is the transactions added up, and the transactions are every change the balance went through.

A stream and a table are the same relationship.

🎓 Professional

A KStream is a record stream: every record is an independent fact, and two records with the same key are two separate events. A KTable is a changelog stream: each record is an update to the value for that key, so a later record for the same key replaces the earlier one.

Reading a compacted topic (chapter 22) as a KTable is exactly this: the topic keeps the latest value per key, and the table is that materialised. And the reverse holds — a table changing over time emits a stream of updates, which is what a database changelog and Debezium (chapter 29) are. Same data, two readings.

Which one you want

🧒 Simple

Ask whether two records with the same key are two things that both happened, or one thing that changed.

Two payments are two events. Two addresses for one customer are one address, updated.

🎓 Professional

Model as a KStream anything where each record is a fact that occurred: OrderPlaced, PaymentReceived, a sensor reading. Model as a KTable anything that is a current value keyed by an entity: customer address, product price, account status.

Getting this wrong produces wrong numbers rather than errors. Aggregating a KTable’s updates as if they were events double-counts — the aggregate has to subtract the old value and add the new one, which is exactly what Streams does automatically when you aggregate a table and not when you aggregate a stream. Choosing the wrong abstraction gives a total that is quietly too large.

⚠ Trap

A GlobalKTable is not a KTable with a bigger scope in the way people assume: it replicates every partition to every instance, so it does not need co-partitioning and does not scale with your data. It is right for small, slow-moving reference data — currency codes, country lists — and wrong for anything large, where it silently multiplies your memory footprint by the number of instances.

Joins, and co-partitioning

🧒 Simple

You can join a stream to a table to enrich events — adding the customer’s name to each order, say.

But both sides must be partitioned the same way, or the matching record is on another machine entirely.

🎓 Professional

Stream–table joins are the common case: enrichment, where each event is looked up against current state. Stream–stream joins need a window (chapter 25), because you must decide how long to wait for the other side. Table–table joins produce a new table.

The requirement people trip over is co-partitioning: both inputs must have the same key, the same partition count and the same partitioning strategy, because task n holds partition n of both sides and cannot see any other. If they differ, Streams inserts a repartition topic — a full extra round trip through Kafka — or, for a mismatched partition count, fails at start-up. That repartition is exactly what topology.describe() from chapter 23 shows you.

Try it. Build the enrichment join, print the topology, and look for the repartition topic. Then make the key of the stream match the table’s and watch it disappear.

var builder = new StreamsBuilder();

// current state per customer, from a COMPACTED topic
KTable<String, Customer> customers =
    builder.table("customer.state", Consumed.with(Serdes.String(), customerSerde));

// events, keyed by customerId so the join is co-partitioned
KStream<String, Order> orders =
    builder.stream("orders.placed", Consumed.with(Serdes.String(), orderSerde));

orders.join(customers,
        (order, customer) -> new EnrichedOrder(order, customer.name(), customer.country()),
        Joined.with(Serdes.String(), orderSerde, customerSerde))
      .to("orders.enriched", Produced.with(Serdes.String(), enrichedSerde));

System.out.println(builder.build().describe());
// if orders were keyed by orderId, you would see a KSTREAM-REPARTITION node here
Golden rules
  • A KStream is facts; a KTable is the latest value per key.
  • A compacted topic read as a table is the duality made concrete.
  • Ask whether two records for one key both happened, or are one thing updated.
  • Aggregating a table subtracts the old value. Aggregating a stream does not — wrong choice, wrong totals.
  • GlobalKTable replicates everything everywhere. Small reference data only.
  • Joins require co-partitioning, or you pay for a repartition topic.

“Che differenza c’è tra KStream e KTable?”

“È la stessa dualità tra un estratto conto e il saldo. Un KStream è un flusso di fatti: due record con la stessa chiave sono due eventi distinti, entrambi accaduti. Un KTable è un changelog: un record con la stessa chiave sostituisce il precedente, quindi rappresenta lo stato corrente. Un topic compattato letto come tabella è esattamente questo. La scelta è concreta: se aggrego un KTable, Streams sottrae il valore vecchio e aggiunge quello nuovo; se aggrego uno stream li somma entrambi. Sbagliare astrazione non dà un errore, dà un totale sbagliato.”
