Kafka on Kubernetes and OpenShift

Running a stateful, disk-bound, identity-sensitive system on a platform designed for stateless ones. Strimzi, StatefulSets, persistent volumes — and the honest question of whether you should be doing this at all.

From the advert

“Java 17 (Spring Boot), OpenShift/Kubernetes, Apache Kafka/RabbitMQ, MongoDB e Oracle DB”.

Why it is not like deploying a service

🧒 Simple

Kubernetes is built for interchangeable copies of a stateless application. A Kafka broker is not interchangeable: it has an identity and a disk full of data.

🎓 Professional

Three properties make brokers awkward. Identity: broker 2 is not broker 5, because partition assignments and replica placement refer to specific ids. Storage: each broker owns its partition data and must reattach to the same volume after a restart. Network: clients connect directly to the leader for each partition, so every broker needs an individually addressable endpoint — the advertised.listeners problem from chapter 03, now with a service mesh in the way.

StatefulSet exists for exactly the first two: stable ordinal names, stable network identities, and a PersistentVolumeClaim per pod that survives rescheduling. A Deployment would give you neither, which is why running Kafka as one does not work.

Strimzi and the operator model

🧒 Simple

An operator is software that knows how to run a specific system on Kubernetes. You describe the cluster you want; it does the work.

🎓 Professional

Strimzi is the standard open-source Kafka operator (and the basis of Red Hat’s AMQ Streams on OpenShift). You declare a Kafka custom resource — replicas, storage, listeners, authentication, config — and it manages StatefulSets, certificates, rolling upgrades in the right order, and cluster rebalancing via Cruise Control. Topics and users become resources too (KafkaTopic, KafkaUser), so topic configuration and ACLs live in git and are applied by your pipeline.

That last point is the strongest argument for it: declarative topic and ACL management solves the problem from chapters 28 and 34 of configuration living only inside a running cluster. Do not attempt to run Kafka on Kubernetes without an operator; the rolling-restart and certificate logic is where the difficulty is, and it is already written.

⚠ Trap

Storage class matters more than anything else here. Kafka wants fast local disk; network storage adds latency to every write and every replication fetch. And a volume that cannot reattach because the pod was rescheduled to another zone means a broker that comes up empty and has to re-replicate everything — which on a large cluster is hours of degraded durability. Pin brokers to zones and match volumes to them.

Should you run it yourself

🧒 Simple

It is entirely possible and it is real work. If nobody on the team wants to own it, a managed service is usually the better answer.

🎓 Professional

Running it yourself makes sense when you have the operational appetite, a data-residency or cost reason, or an existing platform team. Managed (chapter 31) makes sense when Kafka is infrastructure rather than a product for you — which for most of the companies behind these adverts it is.

The mature answer in an interview is that this is a team-capacity question rather than a technical one: “can we?” is yes; “should we?” depends on whether somebody is going to be on call for it. And note that on OpenShift the same SCC constraint from Java chapter 42 applies — arbitrary non-root UIDs — which the operator handles for the brokers and which you still have to handle in your own application images.

Golden rules
  • Brokers have identity, disks and per-broker addressability. StatefulSet, never Deployment.
  • Use an operator. Strimzi, or AMQ Streams on OpenShift.
  • Declarative topics and ACLs in git is the operator’s best feature.
  • Storage class decides your latency. Local disk beats network storage.
  • A volume that cannot reattach means a broker re-replicating from empty.
  • “Should we?” is a team-capacity question, not a technical one.

“Fareste girare Kafka su Kubernetes?”

“Si può fare, ma non come un servizio stateless. I broker hanno identità, un disco con i dati e devono essere indirizzabili singolarmente, perché i client si collegano direttamente al leader di ogni partizione: quindi StatefulSet con un volume persistente per pod, non Deployment. E userei un operator, Strimzi o AMQ Streams su OpenShift, perché la parte difficile — riavvii in sequenza, certificati, ribilanciamento — è già scritta, e in più mi dà topic e ACL come risorse dichiarative, quindi in git. L’attenzione principale è la storage class: Kafka vuole disco locale veloce, e un volume che non si riattacca significa un broker che riparte vuoto e deve replicare tutto da capo.”
