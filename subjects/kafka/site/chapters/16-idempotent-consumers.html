Idempotent consumers and deduplication

Exactly-once gets the attention; idempotent handling of at-least-once is what production actually runs. Being able to design one is a stronger signal than being able to define the other.

From the advert

Not in any advert. And the practical answer to every delivery-guarantee question, which is why it sits immediately after chapter 15.

What idempotent means here

🧒 Simple

An operation is idempotent when doing it twice leaves the world the same as doing it once.

“Set the status to PAID” is idempotent. “Add 10 to the balance” is not.

🎓 Professional

The cheapest idempotency is the kind you get from the operation’s shape. An upsert keyed by a business identifier — “this order’s status is now PAID” — is naturally repeatable; an increment or an append is not. Reformulating a handler from “apply this delta” to “set this state” is often the entire fix, and costs nothing at runtime.

When the operation genuinely cannot be reshaped — charging a card, sending an email — you need explicit deduplication: record that you have handled this event, and check before acting.

Explicit deduplication

🧒 Simple

Give every event an id, and keep a record of the ids you have already handled. Before doing the work, check.

The important part: the check and the work must happen together, or two copies arriving at once will both pass the check.

🎓 Professional

The event carries a stable identifier — an event id from the producer, or a natural key like (orderId, eventType). The consumer writes that id and performs the work in one transaction against its own database, relying on a unique constraint rather than a prior read.

That distinction is the one interviewers probe. if (!seen(id)) followed by a write is a race: two copies delivered concurrently both read “not seen”, both act. Inserting the id with a unique constraint and treating the violation as “already done” is atomic, and it is the correct shape.

Try it. The two versions look equivalent and are not. Run the second under two consumers processing the same event concurrently — the constraint is what saves you.

// WRONG: check-then-act is a race between two deliveries
if (!processed.existsById(event.id())) {
    payments.charge(event.orderId(), event.amount());
    processed.save(new Processed(event.id()));
}

// RIGHT: one transaction, and let the unique constraint arbitrate
@Transactional
public void handle(OrderPaid event) {
    try {
        processedRepo.insert(event.id());        // PK / unique constraint on event_id
    } catch (DuplicateKeyException alreadyHandled) {
        return;                                   // a second delivery: do nothing, commit
    }
    payments.charge(event.orderId(), event.amount());
}

// BEST, where the domain allows it: no dedup table at all
@Transactional
public void handle(OrderPaid event) {
    orders.setStatus(event.orderId(), PAID);      // upsert: repeating it changes nothing
}

Making it practical

🧒 Simple

A table of every event id you have ever seen grows forever. It needs a retention rule, and it only needs to cover the window in which duplicates can actually arrive.

🎓 Professional

Bound the dedup store. Duplicates arise from retries and rebalances, so they arrive within minutes, not months: keep processed ids for a window comfortably longer than your worst redelivery (a few days is generous) and delete older rows on a schedule. An unbounded table is a slow-motion outage.

Two further notes. If the side effect is in another system — an HTTP call — push idempotency to that system with an idempotency key (Java chapter 17), because your local transaction cannot cover it. And if the handler both writes to your database and produces to Kafka, you have the dual-write problem, which is chapter 39.

Golden rules
  • Reshape the operation first. “Set to PAID” beats “add 10”.
  • Check-then-act is a race. Two concurrent deliveries both pass the check.
  • Insert the id under a unique constraint, in the same transaction as the work.
  • Treat the constraint violation as success. It means somebody already did it.
  • Bound the dedup store. Duplicates arrive in minutes; keep days, not years.
  • External side effects need their own idempotency key.

“Come evita di elaborare due volte lo stesso messaggio?”

“Prima provo a non doverlo evitare: se l’operazione è un upsert su una chiave di business — ‘lo stato di questo ordine è PAID’ — rielaborare non cambia niente e il problema sparisce. Quando non posso, ogni evento porta un id stabile e nella stessa transazione inserisco quell’id con un vincolo di unicità ed eseguo il lavoro: se l’insert viola il vincolo, vuol dire che è già stato fatto e mi fermo. Quello che non faccio è leggere prima e scrivere dopo, perché due consegne contemporanee passerebbero entrambe il controllo. E la tabella dei duplicati la tengo limitata nel tempo: i duplicati arrivano nell’arco di minuti, non di mesi.”
