Partitioning: how a key chooses a partition

The most consequential design decision in a Kafka system, made in one line of code by someone who was often not told that. How the default partitioner works, what a null key does, and how a hot partition happens.

From the advert

Not in any advert. Chapter 02 established that the key decides ordering; this is the mechanism, and the failure modes.

The default partitioner

🧒 Simple

With a key, Kafka hashes it and divides by the number of partitions — so the same key always goes to the same place.

Without a key, it spreads records around to fill batches efficiently.

🎓 Professional

With a key: murmur2(key) % numPartitions. Deterministic, so the same key always maps to the same partition for a given partition count — and changes if that count changes (chapter 02).

With a null key, modern clients use sticky partitioning: fill one partition’s batch, send it, then switch. That is a throughput optimisation over the old strict round-robin, which produced many small batches. The important part for design is unchanged: no key means no ordering guarantee for related records.

Choosing the key

🧒 Simple

Ask one question: what needs to stay in order relative to what? The answer is your key.

🎓 Professional

The key is the unit of ordering and the unit of parallelism at the same time, and those pull in opposite directions. A coarse key (say, tenantId) gives strong ordering and poor distribution; a fine key (orderId) gives good distribution and orders only within one order’s events.

Pick the smallest scope that preserves the ordering your domain actually requires. For an order lifecycle, orderId — you need placed before paid for the same order, and you do not care about the relative order of two different orders. Getting this right also makes idempotency and state stores easier later, so it is worth ten minutes at design time.

⚠ Trap

A key with skewed distribution produces a hot partition. If one customer is 60 % of traffic and the key is customerId, one consumer does most of the work, adding consumers changes nothing, and lag climbs on exactly one partition. The fix is a composite key (customerId + orderId) or a different key entirely — but changing it means the ordering guarantee changes too, so it is a design decision, not a tuning knob.

Custom partitioners, and when not to

🧒 Simple

You can write your own rule for choosing the partition. You almost never should.

🎓 Professional

Implementing Partitioner is straightforward, and the legitimate cases are narrow: isolating one very large tenant onto dedicated partitions, or preserving a partition mapping during a migration.

The reason to avoid it is that the mapping becomes invisible knowledge. Every producer must use the same partitioner or the ordering guarantee silently breaks, and anyone debugging “why is this record in partition 4” must find and read your class. A composite key achieves most of the same effects and is self-documenting, because it is in the data.

Golden rules
  • murmur2(key) % partitions — deterministic, and changes when the count does.
  • Null key means no ordering guarantee. Sticky batching is about throughput, not order.
  • The key is ordering and parallelism at once. They pull opposite ways.
  • Pick the smallest scope your domain actually needs ordered.
  • Skewed keys make hot partitions, and more consumers will not help.
  • Prefer a composite key to a custom partitioner. Logic in the data beats logic in a class.

“Un consumer è molto più indietro degli altri. Cosa controlla?”

“Se il lag è concentrato su una partizione sola, quasi sempre è una partizione calda: la chiave non distribuisce bene. Tipico è usare customerId quando un cliente fa metà del traffico — tutti i suoi record finiscono nella stessa partizione, un solo consumer li elabora, e aggiungere consumer non serve a niente perché una partizione va comunque a un solo membro del gruppo. Controllo la distribuzione dei record per partizione; se è quello, valuto una chiave composta. Se invece il lag è su tutte le partizioni, il problema è la velocità di elaborazione, non la chiave.”
