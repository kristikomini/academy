ksqlDB, and when SQL is enough

Streaming SQL over Kafka topics. What it is genuinely good at, where you will outgrow it, and why knowing that a tool is unnecessary is a senior signal.

From the advert

Not in any advert. It earns its place here as the honest answer to “do we need a Streams application for this?” — which is often no.

SQL over a stream

🧒 Simple

Instead of writing a Java application, you write SQL: create a stream from a topic, filter it, join it, write the result to another topic. It keeps running.

🎓 Professional

ksqlDB is a server that runs continuous SQL queries built on Kafka Streams underneath — the same topologies, state stores and changelogs, expressed as SQL. CREATE STREAM and CREATE TABLE map exactly onto chapter 24’s KStream and KTable.

Two query kinds are worth distinguishing: a push query (EMIT CHANGES) runs forever and emits each update — that is the streaming job; a pull query reads current state from a materialised table, like a normal database lookup.

What it is good at

🧒 Simple

Exploring what is actually on a topic, and building simple filters and enrichments without a deployment.

🎓 Professional

Its best use is exploration: pointing at an unfamiliar topic and finding out what is in it, in seconds, without writing a consumer. That alone justifies having it in a development environment.

Beyond that, straightforward filtering, projection, enrichment joins against reference data, and simple windowed aggregations are all a few lines of SQL — and crucially they are accessible to data analysts who will not write a Java topology. Lowering that barrier is a real organisational benefit, not just a convenience.

Try it. Point it at a topic you do not know and look. This is the fastest way to answer “what is actually in there?” that exists.

-- what is on this topic?
CREATE STREAM orders_raw (
    order_id   VARCHAR KEY,
    customer   VARCHAR,
    total      DECIMAL(10,2),
    status     VARCHAR
) WITH (KAFKA_TOPIC='orders.placed', VALUE_FORMAT='AVRO');

SELECT * FROM orders_raw EMIT CHANGES LIMIT 10;      -- push: watch it live

-- a continuous filter into a new topic, no deployment
CREATE STREAM high_value AS
    SELECT order_id, customer, total
    FROM orders_raw
    WHERE total > 1000
    EMIT CHANGES;

-- a materialised table you can query like a database
CREATE TABLE totals_per_customer AS
    SELECT customer, COUNT(*) AS orders, SUM(total) AS revenue
    FROM orders_raw GROUP BY customer;

SELECT * FROM totals_per_customer WHERE customer = 'ACME';   -- pull query

Where you outgrow it

🧒 Simple

As soon as the logic stops being expressible as SQL — or you want to test it properly — you are better off writing the Streams application.

🎓 Professional

The limits arrive in a predictable order. Complex logic becomes an unreadable pile of nested queries or a user-defined function in Java, at which point you have written Java anyway with worse tooling. Testing is genuinely weak — there is no equivalent of TopologyTestDriver, so continuous SQL in production with no unit tests is a real risk. Version control and CI need discipline, because queries created interactively in a session are trivially lost.

And operationally it is another server to run, which for a team already deploying Spring services may be more cost than the SQL saves. The honest position: excellent for exploration and for analyst-facing work, a reasonable choice for simple transformations, and not where a core pipeline should end up.

⚠ Trap

A ksqlDB query left running in a shared cluster is a production job that nobody owns: no repository, no review, no test, and no on-call story. That is how a temporary exploration becomes load-bearing. If a query is going to stay, it belongs in git and in the pipeline like any other code.

Golden rules
  • Kafka Streams underneath, SQL on top. Same topologies, same state stores.
  • Push queries stream; pull queries read state.
  • Best for exploration — the fastest way to see what is on a topic.
  • Testing is the real weakness. No TopologyTestDriver equivalent.
  • A query left running is an unowned production job. Put it in git.
  • Knowing a tool is unnecessary is worth saying.

“Avete valutato ksqlDB?”

“Lo trovo ottimo per esplorare: se devo capire cosa c’è davvero su un topic, con due righe di SQL lo vedo in tempo reale, senza scrivere un consumer. E per filtri e arricchimenti semplici abbassa la barriera, perché ci arrivano anche gli analisti. Per una pipeline centrale invece preferisco Kafka Streams: la logica complessa in SQL annidato diventa illeggibile, e soprattutto posso testare una topology con il TopologyTestDriver, cosa che in ksqlDB non ho. Il rischio concreto è la query lasciata attiva in un cluster condiviso: diventa un job di produzione che non è in git e non è di nessuno.”
