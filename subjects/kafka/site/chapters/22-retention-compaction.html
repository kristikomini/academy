Retention, compaction and tiered storage

How long data stays, and the second cleanup policy that turns a topic into a table. Log compaction is the mechanism behind KTables in Part 6 and behind every “Kafka as a database” argument.

From the advert

Not in any advert. And it decides two things people care about a great deal: how far back you can replay, and how much disk you are paying for.

Time and size retention

🧒 Simple

A topic keeps records for a while and then deletes them — after a set time, or once it exceeds a set size, whichever comes first.

That window is how far back you can replay.

🎓 Professional

retention.ms (default seven days) and retention.bytes (per partition, default unlimited) both apply; whichever triggers first wins. Deletion happens at segment granularity (chapter 03), so records are removed in blocks and a record can outlive its nominal retention until its segment is closed and eligible.

Set it from the replay window you actually want, not from a default. If a new consumer should be able to rebuild state from the beginning, retention must cover the whole history — or you need compaction instead. And note the GDPR problem this creates: you cannot delete one record from a Kafka topic, so personal data either lives in a compacted topic where a tombstone can remove it, or it does not go in the log at all.

Compaction: a topic as a table

🧒 Simple

With compaction, Kafka keeps the latest record for each key and eventually removes the older ones — forever, rather than for a week.

So the topic stops being a history and becomes a current-state table.

🎓 Professional

cleanup.policy=compact retains at least the most recent value per key. The head of the log is uncompacted (recent records are all present); a background thread compacts older segments. A record with a null value is a tombstone: it marks the key deleted, and is itself retained for delete.retention.ms so consumers have time to see the deletion before it disappears.

This is what makes a topic a durable, replayable table — the mechanism behind __consumer_offsets (chapter 12), behind KTables (chapter 24) and behind changelog topics for state stores (chapter 26). compact,delete combines both: keep the latest per key, but drop anything older than the retention window regardless.

⚠ Trap

Compaction guarantees only that the latest value per key survives — not that every intermediate value does, and not that it happens promptly. A consumer reading a compacted topic from the beginning gets a valid snapshot of current state, not the full history. Using a compacted topic as an audit trail loses the intermediate events, silently.

Try it. Create both, produce the same key twice, and read from the beginning. The compacted topic shows you a table; the retained one shows you a history.

# a table: latest value per key, kept indefinitely
kafka-topics.sh --bootstrap-server localhost:9092 --create \
  --topic customer.state --partitions 3 --replication-factor 3 \
  --config cleanup.policy=compact \
  --config min.cleanable.dirty.ratio=0.1 \
  --config delete.retention.ms=86400000

# a history: everything, for 30 days
kafka-topics.sh --bootstrap-server localhost:9092 --create \
  --topic orders.events --partitions 6 --replication-factor 3 \
  --config retention.ms=2592000000

# delete a key from the compacted topic: produce a null value (a tombstone)
kafka-console-producer.sh --bootstrap-server localhost:9092 \
  --topic customer.state --property "parse.key=true" --property "key.separator=:"
# > cust-42:            <- empty value = tombstone

Tiered storage

🧒 Simple

Keeping years of data on the brokers’ own disks is expensive. Tiered storage moves older segments to cheap object storage and fetches them when somebody actually reads that far back.

🎓 Professional

Older segments are offloaded to S3 or equivalent while remaining transparently readable, so long retention stops being a broker-sizing problem. It also decouples storage from compute: adding retention no longer means adding brokers, and rebalancing a cluster no longer means moving years of data between them.

Reads from the tier are slower, so it suits replay and backfill rather than live consumption. The reason to know about it in an interview is that it changes the answer to “can we keep everything?” from “not affordably” to “yes, with a latency caveat” — which is a meaningful shift in what event-sourced designs are practical.

Golden rules
  • Retention is time or size, whichever first, and deletion is per segment.
  • Set retention from the replay window you want. The default is seven days.
  • Compaction keeps the latest value per key. A topic becomes a table.
  • A null value is a tombstone. That is how a key is deleted.
  • A compacted topic is a snapshot, not an audit trail. Intermediate values are lost.
  • Tiered storage makes long retention affordable, at read latency.
