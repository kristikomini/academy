Brokers, the cluster and the controller

What a broker holds, how a cluster agrees on who owns what, and why a client only needs one address to find all of them. This is the part that turns Kafka from a library into an operable system.

From the advert

Not in any advert. The adverts name Kafka as a technology; this chapter is what makes “why is one broker doing all the work?” a question you can answer.

What a broker is

🧒 Simple

A broker is one Kafka server. It stores some of the partitions, accepts writes for the ones it leads, and serves reads.

A cluster is several brokers sharing the partitions between them.

🎓 Professional

Each partition has one leader broker and zero or more followers. All produce and consume traffic for a partition goes to its leader; followers replicate from it (chapter 04). Partitions of one topic are spread across brokers, which is how both storage and traffic distribute.

On disk, a partition is a directory of segment files with an index alongside each. Records are appended to the active segment; older segments are closed and eventually deleted or compacted by retention (chapter 22). That layout is why retention is cheap — deleting a whole segment file, not individual records.

Bootstrap servers and metadata

🧒 Simple

You give a client one or two broker addresses. It asks them where everything is, and from then on talks directly to the right broker for each partition.

🎓 Professional

bootstrap.servers is a starting point, not a proxy: the client connects, fetches cluster metadata — which broker leads which partition — and then connects directly to leaders. It refreshes that metadata when it goes stale or a leader moves.

This is why the advertised.listeners setting causes so much confusion in Docker and Kubernetes: the client reaches the bootstrap address fine, receives metadata containing the broker’s advertised hostname, and then cannot resolve it. The symptom is a client that connects and then times out producing, which looks like a Kafka problem and is a networking one.

⚠ Trap

List more than one bootstrap server. A single address is a single point of failure at connection time — the cluster is fine, but a client starting while that one broker is down cannot join at all. It costs nothing to list three.

The controller

🧒 Simple

One broker has an extra job: keeping track of which brokers are alive and deciding who leads each partition when something fails.

🎓 Professional

The controller maintains cluster metadata and performs leader election when a broker fails or rejoins. Historically this state lived in ZooKeeper; in KRaft mode (chapter 05) it lives in an internal Raft-replicated metadata log, and a quorum of controllers elects one active controller among themselves.

For an application developer the controller is mostly invisible — it matters because it explains what happens during a broker failure: leadership for that broker’s partitions moves to in-sync followers, clients see a brief metadata refresh and some retryable errors, and then traffic continues. Knowing that failover is a metadata operation rather than a data movement is the useful part.

Golden rules
  • One leader per partition. All produce and consume traffic for it goes there.
  • A partition on disk is segment files. Retention deletes segments, not records.
  • bootstrap.servers is a starting point; clients then talk to leaders directly.
  • advertised.listeners is the Docker/Kubernetes trap. Connects, then times out.
  • List several bootstrap servers. One is a needless single point of failure.
  • Failover is a metadata operation. Leadership moves; data does not.

“Cosa succede se cade un broker?”

“Le partizioni di cui quel broker era leader vengono riassegnate: il controller elegge come nuovo leader una replica in-sync. I client se ne accorgono perché ricevono un errore retryable, rinfrescano i metadati e ricominciano a scrivere sul nuovo leader — quindi c’è una pausa breve, non una perdita. Non si spostano dati: si sposta la leadership. Se però il replication factor è 1, quelle partizioni sono semplicemente non disponibili finché il broker non torna, e se il disco è perso lo sono per sempre.”
