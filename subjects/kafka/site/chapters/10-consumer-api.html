The consumer API

poll() is not a network call for one record — it is the heartbeat, the fetch loop and the rebalance participation all at once. Understanding that explains max.poll.interval.ms, why the consumer is not thread-safe, and why a slow handler removes you from the group.

From the advert

“Sviluppatore Java e Kafka”. Producing is the easy half; almost every real Kafka problem is on this side.

The poll loop

🧒 Simple

A consumer runs a loop: ask for records, process them, ask again. That single call does more than fetch — it is also how the consumer tells the group it is still alive.

So if your processing takes too long between calls, the group assumes you died.

🎓 Professional

poll(Duration) fetches a batch (up to max.poll.records), and also drives group membership: joining, receiving partition assignments, and — in older clients — heartbeating. Modern clients heartbeat on a background thread, but max.poll.interval.ms still bounds the time between polls: exceed it and the coordinator considers the consumer dead and rebalances its partitions away.

Which produces the classic failure: a handler that takes longer than five minutes for a batch (the default) is evicted mid-processing, the group rebalances, another consumer picks up the same records, and throughput collapses while nothing reports an error. The fixes are to reduce max.poll.records, raise the interval, or move slow work off the poll thread.

One consumer, one thread

🧒 Simple

A consumer object may only be used by one thread. If you want to process faster, run more consumers — not more threads sharing one.

🎓 Professional

KafkaConsumer is explicitly not thread-safe (the only exception is wakeup(), which exists to interrupt a blocked poll for shutdown). The two standard models are one consumer per thread — simple, and parallelism is capped by the partition count — or one consumer handing records to a worker pool, which decouples processing speed from the poll loop but makes offset management substantially harder, because you may no longer commit in order.

Start with one consumer per thread. Reach for the worker pool only when a single thread genuinely cannot keep up with one partition, and be aware that you have taken on the job of tracking which offsets are safe to commit (chapter 12).

⚠ Trap

Increasing consumer instances beyond the partition count does nothing at all: a partition goes to exactly one member of a group, so extra consumers sit idle. People scale a deployment to ten replicas against six partitions and are surprised nothing improves — the ceiling is the partition count (chapter 02).

Try it. Run two instances against a three-partition topic and watch the assignment, then a third, then a fourth. The fourth is the one that proves the ceiling.

var props = new Properties();
props.put(BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
props.put(GROUP_ID_CONFIG, "billing");
props.put(ENABLE_AUTO_COMMIT_CONFIG, false);          // commit after processing, on purpose
props.put(MAX_POLL_RECORDS_CONFIG, 100);
props.put(AUTO_OFFSET_RESET_CONFIG, "earliest");

try (var consumer = new KafkaConsumer<String, String>(props)) {
    consumer.subscribe(List.of("orders.placed"));
    while (running) {
        var records = consumer.poll(Duration.ofMillis(500));
        for (var record : records) {
            handle(record);            // must be idempotent — chapter 16
        }
        consumer.commitSync();         // after the work, not before
    }
} catch (WakeupException expectedOnShutdown) { /* wakeup() was called */ }

subscribe or assign

🧒 Simple

subscribe joins a group and lets Kafka hand you partitions. assign takes specific partitions yourself, with no group and no rebalancing.

🎓 Professional

subscribe is what you want almost always: dynamic assignment, automatic rebalancing when instances come and go, and offsets stored per group. assign bypasses the group protocol entirely — useful for a one-off tool reading a known partition, or a system doing its own assignment.

Note the consequence: with assign there is no rebalancing, so a crashed instance is simply not replaced. The partitions it held stop being consumed and nothing notices. That makes it the wrong default for a service and a perfectly good choice for a debugging script.

Golden rules
  • poll() is the fetch loop and group participation together.
  • max.poll.interval.ms bounds processing time, not just idle time.
  • A slow handler gets you evicted and triggers a rebalance, with no error.
  • KafkaConsumer is not thread-safe. One consumer per thread.
  • More consumers than partitions do nothing. The partition count is the ceiling.
  • subscribe for services, assign for tools.

“Il consumer ogni tanto smette di consumare e riparte da capo. Perché?”

“Il sospetto principale è max.poll.interval.ms: se l’elaborazione di un batch supera quel tempo, il coordinator considera morto il consumer e fa ribilanciare il gruppo. Le partizioni vengono riassegnate, un altro consumer riprende dagli ultimi offset committati — quindi rielabora record già processati — e il throughput crolla, senza che venga sollevato nessun errore evidente. Guardo quanto dura l’elaborazione per batch, abbasso max.poll.records o alzo l’intervallo, e se il lavoro è davvero lungo lo sposto fuori dal thread di poll.”
