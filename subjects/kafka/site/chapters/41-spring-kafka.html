Spring Kafka in practice

Everything in this course, assembled in the framework you will actually use. @KafkaListener, error handlers, retry topics and the dead-letter topic — and where Spring’s defaults quietly disagree with what earlier chapters said you want.

From the advert

“Back-end development experience with Java and skills in modern technologies like Springboot and Kafka”. This is where the two halves of the advert meet.

@KafkaListener and the container

🧒 Simple

You annotate a method with the topic name and Spring calls it for each record. Underneath, a container runs the poll loop from chapter 10 for you.

🎓 Professional

@KafkaListener is backed by a MessageListenerContainer that owns the consumer, the poll loop, the commits and the error handling. concurrency sets how many consumer threads that listener runs — capped, as always, by the partition count (chapter 11).

Two defaults worth checking against earlier chapters. Spring Boot sets enable.auto.commit=false and uses AckMode.BATCH, committing after the batch is processed — which is the at-least-once behaviour chapter 12 wanted, so the default is right here. And the listener runs on the container’s thread: no SecurityContext, no request-scoped beans, and the transaction boundary is yours to declare.

Errors, retry topics and the DLT

🧒 Simple

When your handler throws, Spring can retry it, and after a few attempts move the record to a separate topic so the rest can continue.

🎓 Professional

DefaultErrorHandler with a BackOff retries in place, then hands the record to a recoverer — usually DeadLetterPublishingRecoverer, which publishes to <topic>.DLT with the exception in the headers. Classify exceptions: addNotRetryableExceptions for anything that will fail identically forever (deserialisation, validation), so it goes straight to the DLT instead of retrying five times for nothing.

@RetryableTopic gives non-blocking retries: failures go to timed retry topics (...-retry-0, -retry-1) rather than blocking the partition. That is the right choice when throughput matters — and the wrong one when ordering does, because as chapter 18 said, a retried record is now processed after records that came behind it. That trade is the single most important thing to understand in this chapter.

⚠ Trap

A dead-letter topic nobody monitors is a delete with extra steps. Records land there silently, the consumer keeps up, every dashboard is green, and the business data is quietly incomplete. Alert on any record arriving in a DLT — it should be rare enough that an alert is reasonable, and if it is not, that is itself the finding.

Try it. A listener configured the way the previous forty chapters argued for: manual acks, classified errors, a DLT, and idempotent handling.

@Component
class OrderListener {

    @KafkaListener(topics = "sales.order.placed", groupId = "billing", concurrency = "3")
    @Transactional                                   // local DB transaction, not a Kafka one
    public void on(@Payload OrderPlaced event,
                   @Header(KafkaHeaders.RECEIVED_KEY) String key) {
        // at-least-once: this MUST be safe to run twice (chapter 16)
        billing.chargeOnce(event.eventId(), event.orderId(), event.total());
    }

    @DltHandler
    public void dlt(OrderPlaced event, @Header(KafkaHeaders.DLT_EXCEPTION_MESSAGE) String why) {
        alerts.raise("order.placed landed in DLT: " + why);   // somebody must look
    }
}

@Bean
DefaultErrorHandler errorHandler(KafkaTemplate<String, Object> template) {
    var handler = new DefaultErrorHandler(
        new DeadLetterPublishingRecoverer(template),
        new ExponentialBackOffWithMaxRetries(3));
    handler.addNotRetryableExceptions(               // will fail identically forever
        DeserializationException.class,
        MethodArgumentNotValidException.class);
    return handler;
}

Testing it

🧒 Simple

Test against a real broker, in a container, for the same reason you test against a real database.

🎓 Professional

@EmbeddedKafka is convenient and is not the broker you deploy; Testcontainers with a real Kafka image is the honest version, for exactly the reasons in Java chapter 39. Test the round trip: produce, consume, assert the effect — and specifically test that processing the same record twice produces the same result, because that is the property everything else depends on.

For Streams topologies, TopologyTestDriver runs a topology with no broker at all, so windowing and aggregation logic can be unit-tested in milliseconds. That is the capability ksqlDB lacks (chapter 27), and it is a good reason to prefer Streams for anything whose correctness matters.

Golden rules
  • The container owns the poll loop. concurrency is capped by partitions.
  • Boot’s defaults commit after the batch — at-least-once, as you want.
  • Classify exceptions. Non-retryable ones go straight to the DLT.
  • @RetryableTopic trades ordering for throughput. Know which you need.
  • A DLT nobody watches is a delete. Alert on arrivals.
  • Testcontainers, and test that processing twice is safe.

“Come configurerebbe un consumer Kafka in Spring Boot?”

“@KafkaListener con concurrency non superiore al numero di partizioni, e i default di Boot vanno già bene: auto-commit disattivato e commit dopo il batch, quindi at-least-once — che è quello che voglio, e infatti scrivo l’handler idempotente. Poi un DefaultErrorHandler con backoff esponenziale e un DeadLetterPublishingRecoverer, classificando le eccezioni: quelle di deserializzazione o validazione non sono retryable e vanno direttamente in DLT invece di essere ritentate inutilmente. Se il throughput conta uso @RetryableTopic per non bloccare la partizione, ma solo dove l’ordine non è importante, perché un record ritentato viene elaborato dopo quelli che gli stavano dietro. E metto un allarme sugli arrivi in DLT: un dead letter topic che nessuno guarda è una cancellazione.”
