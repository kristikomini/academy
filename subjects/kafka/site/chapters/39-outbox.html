The outbox pattern and dual writes

Why writing to the database and to Kafka in the same method is a bug, and the standard fix. This is the most common correctness defect in event-driven systems and the one with the cleanest, most explainable solution — which makes it ideal interview material.

From the advert

Not in any advert. And the answer to the question that follows every event-driven design: “what if the database write succeeds and the publish fails?”

The dual-write problem

🧒 Simple

Your method saves the order to the database and then publishes an event. Two systems, two writes, and no way to make both happen or neither.

If the second one fails, the order exists and nobody was told.

🎓 Professional

There is no transaction spanning your database and Kafka (chapter 17), so any method doing both has three outcomes rather than two: both succeed, both fail, or one succeeds. That third case is the bug, and it is silent.

Neither ordering saves you. Database first, then publish: a crash in between leaves an order nobody was told about — the invoice is never raised. Publish first, then database: a crash leaves consumers acting on an order that does not exist — an invoice for nothing. And retrying the publish inside a catch does not fix it either, because the process can die during the retry.

⚠ Trap

The version that looks safest is the most dangerous: publishing inside the transaction. The record reaches Kafka immediately and is visible to consumers, and then the transaction rolls back — so consumers are now acting on something that never happened, and there is nothing to correct it with. At least the other ordering fails in a direction you can detect.

The outbox

🧒 Simple

Write the event into a table in your own database, in the same transaction as the business change. Then something else reads that table and publishes it.

Now there is only one write, so either both happened or neither did.

🎓 Professional

The order and the outbox row are committed together by the database’s own transaction — one atomic write, no distributed transaction. A separate process then relays outbox rows to Kafka: either CDC reading the transaction log (chapter 29, and the approach Debezium has a dedicated outbox transform for), or a poller selecting unpublished rows.

The relay is at-least-once, so an event can be published twice — which is fine, because consumers are idempotent (chapter 16). That is the whole design, and its elegance is that it converts an impossible problem (atomicity across two systems) into two solved ones: a local transaction, and idempotent consumption.

Try it. The broken version and the fixed one. The difference is one table and one relay, and it is the difference between a system that loses events and one that does not.

// BROKEN: two systems, three outcomes
@Transactional
public void placeOrder(NewOrder cmd) {
    Order order = orders.save(Order.from(cmd));
    kafka.send("sales.order.placed", order.getId(), OrderPlaced.from(order));
    // crash here -> order exists, nobody told
    // or: transaction rolls back AFTER the send -> consumers act on nothing
}

// FIXED: one transaction, one write
@Transactional
public void placeOrder(NewOrder cmd) {
    Order order = orders.save(Order.from(cmd));
    outbox.save(new OutboxEvent(
        UUID.randomUUID(),                 // event id -> consumer dedup key
        "sales.order.placed",
        order.getId().toString(),          // the Kafka message key
        json.write(OrderPlaced.from(order))));
}   // both rows commit together, or neither does

// then either Debezium's outbox transform on the outbox table,
// or a relay:
@Scheduled(fixedDelay = 500)
@Transactional
public void relay() {
    for (OutboxEvent e : outbox.findUnpublished(100)) {
        kafka.send(e.topic(), e.key(), e.payload());   // at-least-once: consumers dedup
        e.markPublished();
    }
}

The costs, and the alternative

🧒 Simple

It adds a table, a relay and a little latency. In exchange you stop losing events.

🎓 Professional

Costs: a table that needs pruning, a relay to operate, and latency between commit and publish — sub-second with CDC, a poll interval with a poller. Ordering is preserved if the relay reads in insertion order and uses the aggregate id as the message key.

The alternative worth naming is event sourcing, where the events are the state and there is no dual write to have — a much larger commitment that solves this problem as a side effect. And the third option, for systems you cannot modify at all, is plain CDC on the business tables (chapter 29), accepting that consumers then see database rows rather than domain events. The outbox is the middle path, and it is the one that fits an existing application.

Golden rules
  • There is no transaction across your database and Kafka. Ever.
  • Either ordering has a silent failure case. Retrying in a catch does not close it.
  • Publishing inside the transaction is the worst version — consumers act on a rollback.
  • Write the event to an outbox table in the same transaction. One atomic write.
  • Relay with CDC or a poller. At-least-once, so consumers dedup.
  • Key the message by aggregate id to keep per-entity ordering.

“Salva sul database e pubblica su Kafka nello stesso metodo. Cosa può andare storto?”

“È il problema del dual write: sono due sistemi e non esiste una transazione che li copra entrambi, quindi ho tre esiti invece di due — e il terzo è che uno dei due riesce. Se salvo e poi il publish fallisce, l’ordine esiste e nessuno lo sa; se pubblico e poi la transazione va in rollback, i consumatori stanno lavorando su qualcosa che non è mai successo. La soluzione è l’outbox: scrivo l’evento in una tabella del mio database nella stessa transazione del dato di business, così o si committano entrambi o nessuno dei due, e poi un relay — CDC con Debezium oppure un poller — pubblica da quella tabella. Il relay è at-least-once, ma i consumer sono idempotenti, quindi va bene.”
