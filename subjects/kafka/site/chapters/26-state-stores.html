State stores, RocksDB and interactive queries

Where streaming state lives, how it survives a restart, and why understanding that recovery path is the difference between a restart taking seconds and taking an hour.

From the advert

Not in any advert. Stateful streaming is where Streams earns its place over a plain consumer, and the state’s recovery story is the operational question that follows immediately.

State is local, and backed by a topic

🧒 Simple

An aggregation has to remember running totals. Streams keeps them on the local disk of the instance doing the work — fast, because there is no network call per record.

And it writes every change to a Kafka topic, so the state can be rebuilt if the machine dies.

🎓 Professional

State stores are local, backed by RocksDB — an embedded key-value store on local disk with an in-memory cache. Every update is also written to a changelog topic, which is compacted (chapter 22), so it holds the latest value per key and is exactly the size of the state rather than the size of its history.

That is the whole design: local for speed, changelog for durability. Reading state is a local disk lookup, not a network round trip, which is what lets Streams handle high throughput with state at all — and the changelog means losing an instance loses no data, only time.

Recovery, and why a restart can take an hour

🧒 Simple

If an instance loses its local disk, it has to replay the changelog topic from the beginning to rebuild what it knew. With a lot of state, that takes a long time.

🎓 Professional

On restart with the local store intact, Streams replays only what it missed — fast. On a new node with an empty disk, it must read the entire changelog for its assigned partitions before processing anything. For gigabytes of state that is minutes to hours of doing nothing, and it happens exactly when you least want it: during a rolling deploy in Kubernetes, where every pod gets a new empty volume.

Three mitigations, worth knowing as a set. Persistent volumes so the store survives a pod restart. num.standby.replicas, which keeps warm copies of the state on other instances so a failover has somewhere to go without a full restore. And static membership (chapter 11), so a rolling restart does not reassign tasks at all. Naming those three in an interview is a strong answer, because it is clearly the answer of someone who has operated one.

⚠ Trap

RocksDB memory is off-heap. Its block cache and write buffers do not appear in your JVM heap metrics and are not bounded by -Xmx, so a Streams application sized purely by heap gets OOM-killed by the container with no Java error at all — the exit-code 137 problem from Java chapter 41, with a cause that is invisible in every heap dump you take.

Interactive queries

🧒 Simple

Because the state is right there, you can expose it directly — a REST endpoint that answers from the streaming state, with no database in between.

🎓 Professional

Interactive queries let you read a state store from your application, so a Streams job that maintains “current total per customer” can also serve it over HTTP. That removes a whole database from some architectures.

The catch is that state is partitioned across instances: any given key lives on exactly one of them. So an instance receiving a query must either hold that key or forward the request to the instance that does — Streams gives you the metadata to find out which (queryMetadataForKey), and you have to build the forwarding yourself. That extra hop is the reason many teams project to a database anyway, and knowing why is more useful than knowing the API.

Golden rules
  • Local RocksDB for speed, compacted changelog topic for durability.
  • A restore from an empty disk replays the whole changelog. Minutes to hours.
  • Persistent volumes, standby replicas, static membership. The three mitigations.
  • RocksDB memory is off-heap. Heap metrics will not show it, and the container will kill you.
  • Interactive queries can replace a read database — if you build the forwarding.
  • State is partitioned. A key lives on exactly one instance.

“Dove tiene lo stato un’applicazione Kafka Streams, e cosa succede se un’istanza muore?”

“Lo stato è locale, in RocksDB sul disco dell’istanza, e ogni modifica va anche su un changelog topic compattato. Quindi la lettura è un accesso locale, veloce, e la durabilità ce la mette Kafka. Se un’istanza muore, le sue partizioni vengono riassegnate e la nuova deve ricostruire lo stato leggendo il changelog: con stato di qualche gigabyte quello è un restore che può durare parecchio, ed è il vero problema operativo. Lo mitigo con volumi persistenti, con num.standby.replicas che tiene copie calde su altre istanze, e con la static membership, così un rolling restart non riassegna i task. E dimensiono la memoria tenendo conto che RocksDB è off-heap: non si vede nelle metriche della heap.”
