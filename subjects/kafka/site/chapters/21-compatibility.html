Compatibility modes, and the change that breaks consumers

Backward, forward, full — and the practical thing they decide, which is the order in which you are allowed to deploy your services. Teams usually discover this during an incident, having renamed a field on a Friday.

From the advert

Not in any advert. It is the setting that makes chapter 20’s registry useful rather than decorative.

The three modes, in terms of who reads what

🧒 Simple

Backward compatible means a new consumer can read old data. Forward means an old consumer can read new data. Full means both.

🎓 Professional

Define them precisely, because the names are easy to state backwards. BACKWARD (the default): a consumer using the new schema can read data written with the previous one. You may delete a field or add an optional field with a default. FORWARD: a consumer using the old schema can read data written with the new one. You may add a field or delete an optional one. FULL: both, so only fully optional changes are allowed.

Each has a _TRANSITIVE variant that checks against all previous versions rather than only the immediately preceding one. That matters more than it sounds: without it, three individually-compatible changes can leave you unable to read data from two versions ago, which is precisely the data still sitting in a topic with 30-day retention.

What it actually decides: deployment order

🧒 Simple

The mode tells you whether you must upgrade the consumers first or the producers first. Get it backwards and something breaks during the rollout.

🎓 Professional

This is the framing worth carrying into an interview, because it converts an abstract setting into an operational rule. BACKWARD means upgrade consumers first: they can read both old and new data, so producers can follow safely. FORWARD means upgrade producers first: old consumers can already read what the new producers write.

BACKWARD is the sensible default for event topics precisely because it matches how you want to deploy — and because retention means old data stays readable. If you get the order wrong under BACKWARD, the failure appears as consumers unable to deserialise records produced in the last few minutes, which is a confusing symptom for something caused by a deployment sequence.

⚠ Trap

Renaming a field is a delete plus an add, and under FULL it is simply rejected. Under BACKWARD it passes and breaks old consumers, which are still running. The safe rename is expand-and-contract: add the new field with a default, write both, migrate readers, remove the old field in a later release — the same discipline as a database column (Java chapter 29).

In practice

🧒 Simple

Add fields with defaults. Do not rename. Check compatibility in the build, not after the deploy.

🎓 Professional

Set the mode per subject, not globally — a topic consumed by three teams deserves FULL_TRANSITIVE; an internal topic with one consumer you deploy together can be more relaxed. Wire the Maven or Gradle schema-registry plugin into CI so an incompatible change fails the build with the offending field named, which is the entire point: the error belongs to the producer’s pipeline, not the consumer’s night.

And keep a habit of never reusing a field name for a different meaning. The registry cannot detect that — the schema is compatible, the data is now wrong — and it is the one evolution failure no tooling will catch for you.

Golden rules
  • BACKWARD: new consumer reads old data. FORWARD: old consumer reads new data.
  • The mode decides deployment order. BACKWARD means consumers first.
  • Use the _TRANSITIVE variants, or old retained data can become unreadable.
  • A rename is a delete plus an add. Expand and contract instead.
  • Set compatibility per subject, stricter the more consumers there are.
  • Check it in CI. The failure belongs to the producer’s build.

“Deve aggiungere un campo a un evento già in produzione. Come procede?”

“Aggiungo il campo come opzionale, con un default: sotto compatibilità BACKWARD è una modifica sicura, e i consumer che non conoscono ancora quel campo continuano a leggere. L’ordine di deploy lo detta la modalità: con BACKWARD aggiorno prima i consumer, poi i producer. Se invece dovessi rinominare un campo non lo farei in un colpo solo — per il registry è una cancellazione più un’aggiunta e romperebbe i consumer vecchi ancora in esecuzione: aggiungo il nuovo, scrivo su entrambi, sposto i lettori e tolgo il vecchio in una release successiva. E la verifica di compatibilità sta nella pipeline, così se sbaglio se ne accorge la build e non un consumer di notte.”
