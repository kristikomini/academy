Topics, partitions and keys

The unit of parallelism, the unit of ordering, and the one design decision you cannot cheaply undo. Almost every Kafka question in an interview eventually arrives here.

From the advert

“architetture applicative con competenze su REST, SQL e Apache Kafka”, from the Esprimo Milano posting — a role that is explicitly about design, which is what partitioning is.

A topic is partitions

🧒 Simple

A topic is a name for a stream of records — “orders placed”. It is split into partitions, and each partition is a separate append-only log.

Splitting is what lets several machines and several consumers work at once.

🎓 Professional

A topic is a logical name; a partition is the physical log, an ordered sequence of records each with a monotonically increasing offset. Partitions are distributed across brokers, which is how a topic scales beyond one machine.

Two rules to have ready, because they are the ones asked. Ordering is guaranteed within a partition and nowhere else — there is no global order across a topic, and expecting one is the most common design error. And the partition count is the ceiling on consumer parallelism in a group: with three partitions, a fourth consumer in the same group does nothing at all.

The key chooses the partition

🧒 Simple

Each record can carry a key. Records with the same key always go to the same partition, so they stay in order relative to each other.

Choosing that key is choosing what stays ordered.

🎓 Professional

The default partitioner hashes the key modulo the partition count. So key = orderId means every event for one order lands in one partition and is consumed in order; events for different orders are independent and may be processed in parallel and out of relative order — which is usually exactly right.

With a null key, records are distributed across partitions (in modern clients, sticky batching rather than strict round-robin) and you have no ordering guarantee at all. That is fine for independent telemetry and wrong for anything with a lifecycle. The key is the first question to ask about any topic design.

⚠ Trap

A key with poor distribution produces a hot partition: if 60 % of your traffic is one large customer and the key is customerId, one consumer does most of the work and adding consumers changes nothing. The symptom is lag on one partition while the others are idle — and the fix (a composite key, or more partitions) is a redistribution you would rather not do under load.

Choosing the count, which you cannot undo

🧒 Simple

You can add partitions to a topic later. You cannot remove them — and adding them changes which partition a key lands in, so ordering for existing keys breaks.

🎓 Professional

Increasing the partition count rehashes the key space: records for a given key that used to go to partition 2 may now go to partition 5, while the old ones sit in partition 2. Per-key ordering across that boundary is gone permanently, and there is no operation that repairs it short of reprocessing into a new topic.

So size with headroom: estimate target throughput and divide by what one consumer instance can handle, then leave room to grow. Too few is a ceiling you hit under load; too many costs memory, open file handles, and longer rebalances and leader elections (chapter 32). A few dozen is ordinary; thousands on one cluster is a decision that needs a reason.

Try it. Create a topic with three partitions, produce with and without a key, and look at where records land. The second command is the one that shows you ordering is per-partition.

# create with an explicit partition count
kafka-topics.sh --bootstrap-server localhost:9092 \
  --create --topic orders.placed --partitions 3 --replication-factor 1

# produce WITH a key: same key -> same partition, always
kafka-console-producer.sh --bootstrap-server localhost:9092 \
  --topic orders.placed --property "parse.key=true" --property "key.separator=:"
# > A-1:placed
# > A-1:paid          <- same partition as A-1:placed, so ordered after it
# > B-7:placed        <- may land anywhere

# read back, showing partition and offset
kafka-console-consumer.sh --bootstrap-server localhost:9092 \
  --topic orders.placed --from-beginning \
  --property print.partition=true --property print.offset=true \
  --property print.key=true
Golden rules
  • A partition is the log; a topic is a name for a set of them.
  • Ordering is per-partition. There is no global order, and assuming one is the classic bug.
  • Partition count caps consumer parallelism in a group.
  • The key chooses the partition, and therefore what stays ordered.
  • A null key means no ordering guarantee. Fine for telemetry, wrong for a lifecycle.
  • Adding partitions breaks per-key ordering for existing keys, and you cannot remove them.

“Come sceglierebbe la chiave e il numero di partizioni per un topic di ordini?”

“La chiave sarebbe l’orderId: così tutti gli eventi dello stesso ordine finiscono nella stessa partizione e li consumo in ordine, mentre ordini diversi restano indipendenti e possono essere elaborati in parallelo. Sul numero di partizioni parto dal throughput che mi aspetto diviso quello che regge un consumer, e lascio margine — perché aggiungerne dopo si può, ma cambia l’hashing e rompe l’ordinamento per le chiavi esistenti, e toglierne non si può affatto. E controllerei la distribuzione della chiave: se un cliente solo fa metà del traffico, con customerId avrei una partizione calda e aggiungere consumer non servirebbe a niente.”
