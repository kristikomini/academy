The producer API

send() returns immediately and has not sent anything yet. Understanding what happens between that call and the record reaching a broker explains batching, ordering, error handling and most of the surprises in producer code.

From the advert

“Sviluppatore Java e Kafka”, from the Sinergidea Milano posting — the most literal statement of the job this course exists for.

send() is asynchronous

🧒 Simple

Calling send() does not send anything. It puts the record into a buffer in memory and returns. A background thread does the actual sending, in batches.

So if your program exits right after, the record may never have left.

🎓 Professional

The producer appends the serialised record to a per-partition batch in an in-memory buffer (buffer.memory) and returns a Future. A single I/O thread drains batches to brokers. flush() blocks until the buffer is empty, and close() flushes first — which is why a producer left unclosed at JVM exit loses whatever was still buffered.

Handle the result. send(record, callback) gives you metadata (partition, offset) or an exception; ignoring it means silent loss on failure. Calling .get() on the future makes it synchronous and collapses throughput by an order of magnitude or more — correct only when you genuinely need per-record confirmation before continuing.

Try it. Run it, then delete the close() and add an immediate System.exit(0). The records vanish, with no error — which is the lesson.

var props = new Properties();
props.put(BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
props.put(KEY_SERIALIZER_CLASS_CONFIG, StringSerializer.class.getName());
props.put(VALUE_SERIALIZER_CLASS_CONFIG, StringSerializer.class.getName());
props.put(ENABLE_IDEMPOTENCE_CONFIG, true);          // acks=all, safe retries
props.put(LINGER_MS_CONFIG, 10);                      // wait 10ms to fill a batch

try (var producer = new KafkaProducer<String, String>(props)) {
    for (int i = 0; i < 1000; i++) {
        var record = new ProducerRecord<>("orders.placed", "order-" + i, "placed");
        producer.send(record, (metadata, exception) -> {
            if (exception != null) log.error("send failed", exception);   // do NOT ignore
            else log.debug("p{} @ {}", metadata.partition(), metadata.offset());
        });
    }
}   // close() flushes — without it, buffered records are lost

What a record carries

🧒 Simple

A record has a key, a value, a timestamp, and optional headers — small pieces of metadata alongside the payload.

🎓 Professional

Key and value are both byte[] as far as the broker is concerned; serialisers turn your objects into bytes (chapter 19). The key decides the partition (chapter 07) and is not a message id — a common confusion.

Headers are underused and worth adopting as a habit. They carry the trace context so a distributed trace survives the broker (Java chapter 35), the schema id, an event type, and a correlation id — all without polluting the payload schema. A consumer can route or filter on a header without deserialising the value at all.

Errors, retryable and not

🧒 Simple

Some failures are worth retrying — a broker was briefly unavailable. Others never will be: the record is too large, or the topic does not exist and cannot be created.

🎓 Professional

The client retries retryable errors itself (NotLeaderForPartition, NotEnoughReplicas, timeouts) up to delivery.timeout.ms, which is the setting that actually bounds how long a send can take — not retries. Non-retryable errors (RecordTooLargeException, serialisation failures, authorisation) surface to your callback immediately.

What you must decide is what your application does when delivery finally fails: drop, log, write to a local outbox (chapter 39), or fail the request that triggered it. That decision is the interesting part and the one most codebases never make explicitly.

⚠ Trap

send() can also block, despite being asynchronous: if the buffer is full it waits up to max.block.ms before throwing. So a slow or unreachable broker eventually blocks your request threads — the producer is not a fire-and-forget escape hatch from back-pressure, it just moves where the back-pressure appears.

Golden rules
  • send() buffers and returns. Nothing has been sent yet.
  • Always close the producer. Unflushed records disappear silently.
  • Handle the callback. Ignoring it turns a failure into silent loss.
  • .get() makes it synchronous and costs an order of magnitude.
  • Use headers for trace context, event type and correlation id.
  • delivery.timeout.ms bounds a send, not retries.
  • A full buffer blocks. Back-pressure moves; it does not vanish.

“Cosa succede esattamente quando chiama send()?”

“Il record viene serializzato, il partitioner decide la partizione, e finisce in un batch in memoria: send() ritorna subito un Future e non ha ancora inviato niente. Un thread di I/O separato svuota i batch verso i broker. Da qui due conseguenze pratiche: devo gestire la callback, altrimenti un errore di invio diventa una perdita silenziosa; e devo chiudere il producer, perché close() fa il flush — se il processo esce prima, quello che era ancora nel buffer è perso. E se il buffer si riempie, send() blocca fino a max.block.ms: l’asincronia non elimina la back-pressure, la sposta.”
