Serialisation: JSON, Avro and Protobuf

Serialisers turn your objects into the bytes the broker stores. The format decides message size, how schemas evolve, and whether one malformed record can stop a partition forever.

From the advert

Not in any advert. A poison-pill record that no consumer can deserialise blocks its partition indefinitely — a failure mode with no equivalent in a queue, and one worth meeting on paper rather than in production.

Serialisers and deserialisers

🧒 Simple

Kafka stores bytes. A serialiser turns your object into bytes on the way in, and a deserialiser turns them back on the way out.

The broker never looks inside — it does not know or care what the bytes mean.

🎓 Professional

Key and value each have their own serialiser. The broker is deliberately format-agnostic, which is why it is fast and why nothing validates your data: a producer can write anything, and the mismatch is discovered by the consumer, later, at deserialisation time.

That asymmetry is the whole argument for a schema registry (chapter 20). Without one, the contract between producer and consumer exists only in whatever both teams remember, and the first sign that it broke is a consumer that cannot start.

The three formats

🧒 Simple

JSON is readable and large. Avro and Protobuf are compact binary formats that carry a schema, so both sides agree on the shape.

🎓 Professional

JSON: human-readable, debuggable with any tool, and repeats every field name in every record. That verbosity compresses away reasonably well (chapter 08) but it never stops costing CPU. There is no schema unless you add one.

Avro: compact, schema-first, and designed for evolution — the reader resolves the writer’s schema against its own, so old consumers read new data. It is the default in the Confluent ecosystem. Protobuf: similarly compact, familiar to anyone from a gRPC background, with good cross-language tooling and slightly less elegant evolution semantics for defaults. Either is a defensible choice; JSON for a high-volume topic with many consumers is usually not.

The poison pill

🧒 Simple

If one record cannot be deserialised, the consumer throws every time it tries — and it cannot move past it, because moving past means committing an offset it never processed.

So one bad record stops that partition, permanently, until somebody intervenes.

🎓 Professional

This is the failure that has no queue equivalent, because in a queue the bad message can be rejected individually. Here the consumer crashes, restarts, reads the same offset, crashes again — a loop that also triggers rebalances (chapter 13) and takes the rest of the group with it.

The fix is an error-handling deserialiser: Spring Kafka’s ErrorHandlingDeserializer wraps yours, catches the failure, and hands the listener a null payload plus the exception in a header, so a DefaultErrorHandler can route the record to a dead-letter topic and continue. Configure that before you need it — the day you need it, the partition is already stopped.

Try it. Set this up, then produce a deliberately malformed record to the topic. Without the wrapper, the consumer loops forever; with it, the record lands in the DLT and processing continues.

# without this, one bad record stops the partition for good
spring:
  kafka:
    consumer:
      key-deserializer: org.springframework.kafka.support.serializer.ErrorHandlingDeserializer
      value-deserializer: org.springframework.kafka.support.serializer.ErrorHandlingDeserializer
      properties:
        spring.deserializer.key.delegate.class: org.apache.kafka.common.serialization.StringDeserializer
        spring.deserializer.value.delegate.class: io.confluent.kafka.serializers.KafkaAvroDeserializer

# and route the failures somewhere
@Bean
DefaultErrorHandler errorHandler(KafkaTemplate<String, Object> template) {
    var recoverer = new DeadLetterPublishingRecoverer(template);   // topic -> topic.DLT
    var handler = new DefaultErrorHandler(recoverer, new FixedBackOff(1_000L, 2));
    handler.addNotRetryableExceptions(DeserializationException.class);  // never retryable
    return handler;
}
Golden rules
  • The broker stores bytes and validates nothing. The contract is yours to keep.
  • JSON is readable and repeats every field name. Fine at low volume, costly at high.
  • Avro or Protobuf for anything high-volume or long-lived.
  • A poison pill blocks its partition forever. There is no per-record reject.
  • Wrap deserialisers in an error handler and route to a DLT before you need it.
  • Deserialisation failures are never retryable. Retrying is a loop, not a recovery.

“Cosa succede se arriva un messaggio malformato?”

“Senza precauzioni è il caso peggiore: il consumer non riesce a deserializzarlo, solleva un’eccezione, riparte dallo stesso offset e ricomincia — non può andare oltre, perché avanzare significherebbe committare un offset che non ha elaborato. Quindi quella partizione si ferma, e il loop di riavvii fa anche ribilanciare il gruppo. La soluzione è un ErrorHandlingDeserializer che incapsula quello vero: cattura l’errore, passa un payload nullo con l’eccezione negli header, e un error handler manda il record su un dead letter topic. Un errore di deserializzazione non è mai retryable: riprovare è solo un ciclo.”
