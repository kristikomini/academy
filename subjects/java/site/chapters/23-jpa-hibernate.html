JPA and Hibernate: the object-relational bargain

The persistence context is the single idea behind almost every Hibernate surprise: why an object you never saved was saved, why a change you made outside a transaction vanished, and why the same query returns the same instance twice. Learn it and the rest of Part 4 follows.

From the advert

“ottima conoscenza di Spring/Spring Boot (API REST, dependency injection, configurazioni, Spring Data JPA)”. Named in the senior Bologna advert and implied by every other one that mentions a database.

The persistence context

🧒 Simple

Within a transaction, Hibernate keeps track of every entity it has loaded. If you change one, you do not need to save it — at the end of the transaction Hibernate notices the change and writes it.

This is convenient and surprising in equal measure, because it means changing an object is enough to change the database.

🎓 Professional

The persistence context is a first-level cache and a unit of work, scoped to the transaction. Entities in it are managed: Hibernate holds a snapshot of their loaded state and, at flush, compares and issues UPDATEs for what differs. That is dirty checking, and it is why a setter call inside a transactional method is a database write.

It also guarantees identity: loading the same row twice in one context returns the same instance, so == holds within a context and not between contexts. The four states — transient, managed, detached, removed — are worth being able to name, because “why didn’t my change save?” is almost always “the entity was detached”.

⚠ Trap

Dirty checking cuts both ways. Modifying a managed entity for a temporary purpose — masking a field before returning it, say — writes that change to the database at flush. There is no save() to grep for. If you need a throwaway copy, map it to a DTO; never mutate a managed entity you did not intend to persist.

Lazy, eager and the transaction boundary

🧒 Simple

When you load an order, does Hibernate also load its customer and all its lines? If it did that every time, one query could pull in half the database.

So associations are usually lazy: fetched only when you touch them — and only while the transaction is still open.

🎓 Professional

@ManyToOne and @OneToOne default to EAGER, which is the wrong default; @OneToMany and @ManyToMany default to LAZY. Set fetch = FetchType.LAZY everywhere and fetch what you need explicitly per query (chapter 26).

Lazy loading works via a proxy that needs an open session. Touch it after the transaction has closed — typically while Jackson serialises the entity in the controller — and you get LazyInitializationException. The correct fix is to fetch what you need inside the transaction and return a DTO. open-in-view, which Boot enables by default and warns about, hides the problem by holding the session open for the whole request — and holds a database connection for the duration of serialisation, which is exactly the pool pressure chapter 22 described.

Writing an entity

🧒 Simple

An entity is a class mapped to a table. Give it an id, keep it simple, and be careful with equals.

🎓 Professional

Prefer IDENTITY or a SEQUENCE generator — on Oracle, sequences with an allocation size that matches the database, or Hibernate will produce ids with gaps you must not care about. Avoid @Data from Lombok on entities: it generates equals, hashCode and toString over every field, which triggers lazy loading and can recurse through bidirectional associations.

The equals/hashCode problem from chapter 03 is genuinely hard here, because the id is null before persist and identity therefore changes mid-life. The usual resolutions: use a business key if one exists, or return a constant hashCode and compare on id — correct, if unattractive, and far better than a hash that changes after insertion.

Golden rules
  • Dirty checking means mutation is persistence. There is no save() to look for.
  • Everything LAZY, and fetch explicitly per query.
  • LazyInitializationException means the entity outlived its transaction. Return a DTO.
  • open-in-view hides the problem and holds a connection for the whole request.
  • No Lombok @Data on entities. It walks your associations.
  • Never mutate a managed entity you did not intend to save.

“Cos’è il persistence context e perché dovrei saperlo?”

“È la cache di primo livello e l’unit of work della transazione: tiene le entità caricate in stato managed con uno snapshot dello stato iniziale. Al flush confronta e genera gli UPDATE per quello che è cambiato — il dirty checking. La conseguenza pratica è che modificare un’entità dentro una transazione è scriverla a database, anche senza chiamare save(): se modifico un’entità managed solo per restituirla mascherata, quella modifica finisce sul database. Per questo mappo su DTO invece di toccare l’entità.”
