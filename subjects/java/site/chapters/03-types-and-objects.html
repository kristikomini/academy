Types, objects and equality

Two objects that look the same and are not; a HashSet that contains your element and cannot find it; a cached Integer that compares equal at 127 and not at 128. All three come from the same place, and it is the most reliably asked area in a Java interview.

From the advert

Not in any advert. And in every interview, because the equals/hashCode contract is the cheapest way to find out whether someone has debugged a collection or only used one.

Primitives, wrappers and the cache

🧒 Simple

Java has two kinds of value. int is a plain number. Integer is an object that holds a number. Java converts between them automatically, which is convenient and occasionally a trap.

== on objects asks “are these the same object?”, not “are these equal?”. On small numbers it accidentally says yes, because Java reuses the same Integer objects for −128 to 127.

🎓 Professional

Autoboxing inserts Integer.valueOf(int), which is specified to return cached instances for −128…127. So Integer a = 127, b = 127; a == b is true, and the same code with 128 is false. Nothing is broken; you are comparing references, and the cache decides whether they coincide.

The practical rules: never use == on wrappers, and watch for unboxing a null Integer, which throws NullPointerException from a line containing no visible dereference — a classic in code that reads a nullable column into an int.

⚠ Trap

This shows up in real code most often as a Long id comparison: if (order.getId() == otherId) works in tests with small ids and fails in production at 128. Use equals, or compare primitives.

The equals / hashCode contract

🧒 Simple

If you decide two objects are equal, you must also give them the same hash code — a number used to file them in the right drawer.

Break that and a HashMap files the object in one drawer and looks for it in another. It will not find your object, and nothing will report an error.

🎓 Professional

The contract: equal objects must have equal hash codes; unequal objects may share one. equals must be reflexive, symmetric, transitive, consistent, and false for null. A HashMap uses the hash to pick a bucket and equals to scan it, so overriding one without the other produces a collection that silently loses elements.

Two follow-ups worth having ready. Mutating a field used in hashCode after insertion strands the entry in the wrong bucket — which is why keys should be immutable. And JPA entities are the hard case: an entity’s id is null before persist, so an id-based hashCode changes identity mid-life. Chapter 23 covers the usual resolution.

Try it. Run it. Then delete the hashCode method and run it again — the set will report that it does not contain an object it demonstrably holds.

import java.util.*;

final class Point {
    final int x, y;
    Point(int x, int y) { this.x = x; this.y = y; }

    @Override public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof Point p)) return false;   // pattern matching, Java 16+
        return x == p.x && y == p.y;
    }
    @Override public int hashCode() { return Objects.hash(x, y); }
}

public class Demo {
    public static void main(String[] args) {
        Set<Point> set = new HashSet<>();
        set.add(new Point(1, 2));
        System.out.println(set.contains(new Point(1, 2)));  // true — remove hashCode: false
    }
}

Immutability, and why it keeps coming up

🧒 Simple

An immutable object cannot change after it is built. That sounds like a restriction and is mostly a relief: nobody can modify it behind your back, two threads can read it safely, and it is always a valid key.

🎓 Professional

Immutability buys thread safety without synchronisation, safe publication, and usable hash keys. Build it with final fields, no setters, defensive copies of mutable components in and out, and no leaking of this from the constructor. Since Java 17, a record gives you most of this by default (chapter 07).

The caveat interviewers probe: immutability is shallow. A record holding a List is only as immutable as that list, because the reference is frozen and the object behind it is not. List.copyOf() in the compact constructor is the fix.

Golden rules
  • Never == on wrappers. The −128…127 cache makes it look correct in tests.
  • Override equals and hashCode together, or hash-based collections silently lose elements.
  • Keys must be immutable in the fields that feed hashCode.
  • Unboxing a null wrapper throws NPE on a line with no visible dereference.
  • Immutability is shallow. Copy mutable components in and out.

“Cosa succede se sovrascrivo equals ma non hashCode?”

Give the mechanism, then the symptom, because the symptom alone sounds memorised: “Le collezioni basate su hash usano hashCode per scegliere il bucket e equals solo per confrontare dentro quel bucket. Se due oggetti sono uguali ma hanno hash diversi finiscono in bucket diversi, quindi contains restituisce false per un oggetto che la collezione in realtà contiene. E non fallisce niente: è un bug silenzioso.” If they keep going, the natural next point is that a key must be immutable in those fields — and the JPA entity problem is an excellent thing to raise yourself.
