Java 8 → 17 → 21, version by version

The adverts say 8+, 11+ and 17. Those are not the same job. This chapter is what each long-term release actually added, which of it you will be expected to write, and how to answer the question underneath the question: do you write modern Java, or Java 8 that happens to compile on 17?

From the advert

“Java 17 (Spring Boot), OpenShift/Kubernetes, Apache Kafka/RabbitMQ, MongoDB e Oracle DB”, and separately “Solida esperienza con Java 8+” and “ottima conoscenza di Java 11+”. Three of the six adverts pin a version. It is worth knowing what they are pinning.

Why the number in the advert matters

🧒 Simple

A version number in an advert is a hint about the codebase. “Java 8” usually means something old and important that cannot easily be moved. “Java 17” usually means something built or rebuilt in the last few years.

Neither is better to work on. They are different jobs, and it is worth knowing which one you are interviewing for.

🎓 Professional

Java’s LTS releases are 8, 11, 17 and 21. Most Italian enterprise work sits on 8, 11 or 17, and a codebase’s version is a good proxy for its age, its build tooling and its appetite for change. An advert asking for 17 while describing a fifteen-year-old gestionale is telling you a migration is in progress, which is a useful thing to ask about.

The interview question underneath is almost never “list the features of Java 14”. It is whether you write the modern idiom. A candidate who writes a twenty-line class with getters where a record would do, on a Java 17 code test, has answered a question nobody asked out loud.

Java 8 — the one everyone still knows

🧒 Simple

Java 8 is the version that changed how Java looks. It added lambdas (short anonymous functions), streams (a pipeline for processing collections) and Optional (a box that may or may not contain a value).

🎓 Professional

Lambdas and method references, the Stream API, Optional, default methods on interfaces, and java.time — which finally replaced Date and Calendar. Default methods are the subtle one: they exist so that Collection could gain stream() without breaking every implementation in the world, and that motivation is a good interview answer.

Java 8 is still the floor for a large share of production code, and it is why java.util.Date keeps appearing in codebases written after it stopped being necessary. Chapter 06 covers streams properly.

Java 9–11 — modules, var, and the great renaming

🧒 Simple

Java 9 split the standard library into modules, so a program can declare which parts it needs. Java 10 added var, letting the compiler work out a local variable’s type. Java 11 became the next long-term version.

🎓 Professional

The Java Platform Module System (JPMS, “Jigsaw”) is the headline and the least used feature in the list — most applications never declare a module-info.java. Its real effect on working developers was strong encapsulation of internal APIs, which is why upgrading past 8 broke libraries that reached into sun.misc.Unsafe.

The migration pain from 8 to 11 was mostly this plus removals: JAXB, JAX-WS and CORBA left the JDK, so builds failed with missing classes that had always been there. If you are asked about a version migration you have done, that is the concrete detail to reach for.

⚠ Trap

var is not dynamic typing and it is not JavaScript’s var. The type is fixed at compile time and inferred from the initialiser; there is no runtime difference whatsoever. Saying “it makes Java dynamically typed” in an interview is a fast way to lose the room.

Java 17 — records, sealed types, and a better switch

🧒 Simple

Java 17 is the version that made small data classes short. A record is a class whose only job is to hold values — you write one line and get the constructor, the accessors, equals, hashCode and toString free.

🎓 Professional

Records, sealed classes and interfaces, switch expressions, text blocks, and pattern matching for instanceof. Together they aim at one thing: making it practical to model data as data, so that a closed set of alternatives can be expressed in the type system and checked exhaustively by the compiler.

This is the version most new Spring Boot work targets, and DTOs are where it shows first: a request or response body as a record is immutable, has correct equals by construction, and removes the Lombok dependency that used to be obligatory. Chapter 07 goes into all of it.

Try it. Write the same thing twice and count the lines. Then try to give the record a second field with the same name, or mutate one after construction — the compiler errors are the feature.

// The Java 8 way
public final class Money {
    private final long cents;
    private final String currency;
    public Money(long cents, String currency) { ... }
    public long cents() { return cents; }
    public String currency() { return currency; }
    // equals, hashCode, toString ... about 30 lines total
}

// The Java 17 way
public record Money(long cents, String currency) {
    // compact constructor: validation, no field assignment needed
    public Money {
        if (cents < 0) throw new IllegalArgumentException("negative money");
    }
    public Money plus(Money other) {
        return new Money(cents + other.cents, currency);
    }
}

Java 21 — virtual threads, and pattern matching finished

🧒 Simple

Java 21 added virtual threads: threads that are cheap enough to make millions of. Before this, a thread was an expensive operating-system resource and you had to share a small pool of them carefully.

🎓 Professional

Virtual threads (Project Loom) decouple the Java thread from the OS thread, so blocking a virtual thread parks a continuation instead of occupying a carrier. The practical effect for the sort of service in these adverts is large: the classic argument for reactive programming — that blocking a thread per request does not scale — largely evaporates, and you can write straightforward blocking code that scales like non-blocking code.

Also in 21: pattern matching for switch and record patterns, which complete the work 17 started. Spring Boot 3.2+ supports virtual threads with a single property. It is unlikely to be a requirement in these adverts yet and very likely to be a question, because it is the most interesting thing to have happened to Java in a decade.

Golden rules
  • The LTS line is 8, 11, 17, 21. The number in an advert is a hint about the codebase’s age.
  • Java 8 is lambdas, streams, Optional and java.time — and default methods, which existed so Collection could grow stream().
  • The 8→11 pain was removals and strong encapsulation, not modules you had to adopt.
  • var is compile-time inference. There is no runtime difference at all.
  • On Java 17, write Java 17. A record instead of a thirty-line DTO is the cheapest signal you have.
  • Virtual threads undercut the main argument for reactive. Know that, even if the job is on 17.

“Che differenza c’è tra Java 8 e Java 17? Cosa usa quando può?”

Do not recite a changelog. Name the shift and give one concrete example you have written: “La differenza pratica è che dalla 17 posso modellare i dati come dati. Un DTO che in Java 8 erano trenta righe con getter, equals e hashCode, adesso è un record di una riga — immutabile e con equals corretto per costruzione. Con sealed interface e switch con pattern matching il compilatore mi verifica anche di aver coperto tutti i casi.” If the codebase is on 8, say what you would miss and what you would not push for — that reads as someone who has migrated something, rather than someone who has only read about it.
