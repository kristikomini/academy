Validation and error responses

Two things a code test always shows and rarely marks explicitly: whether invalid input produces a clear 400 or a 500 with a stack trace, and whether your error bodies have one shape or five.

From the advert

Not in any advert. And in every code review. An API that returns a stack trace for a missing field fails a technical assessment faster than an inefficient algorithm.

Bean Validation

🧒 Simple

Instead of writing if checks at the top of every method, you annotate the fields with the rules they must satisfy and let the framework check them.

🎓 Professional

Jakarta Bean Validation: @NotNull, @NotBlank, @Size, @Email, @Positive, @Past, plus custom constraints. Put @Valid on the @RequestBody parameter and a violation becomes a MethodArgumentNotValidException before your method body runs; @Validated on the class enables it for path and request parameters too.

Validate the DTO, not the entity. Entity-level constraints run at flush time, deep inside a transaction, which turns a user input problem into a persistence exception at the wrong layer with a much worse message.

One place to turn exceptions into responses

🧒 Simple

Rather than each controller catching its own errors, one class handles them all and decides what the client sees.

🎓 Professional

@RestControllerAdvice with @ExceptionHandler methods centralises the mapping from exception type to status and body. Domain exceptions map to their statuses; everything unmapped becomes a 500 with a generic body and a logged stack trace — logged server-side, never returned, because a stack trace tells an attacker your framework versions and package layout.

Remember chapter 16: this runs inside the dispatcher, so it never sees authentication failures from the security filter chain. Those need an AuthenticationEntryPoint and an AccessDeniedHandler, and forgetting it is why an API returns tidy JSON errors for everything except a bad token.

⚠ Trap

A handler for Exception.class that returns 500 will also swallow Spring’s own meaningful exceptions — HttpMessageNotReadableException (malformed JSON) and MethodArgumentTypeMismatchException (a letter where an id belongs) should be 400, not 500. Handle those explicitly, or you turn every client mistake into an apparent server fault and lose the ability to alert on real ones.

RFC 7807 problem details

🧒 Simple

There is a standard shape for error responses. Using it means clients — and other teams — already know how to read yours.

🎓 Professional

application/problem+json with type, title, status, detail and instance, plus any extension members you need. Spring 6 / Boot 3 support it natively through ProblemDetail and ErrorResponseException.

For validation failures, add a errors array of field/message pairs so a form can highlight the offending inputs. Include a correlation id (chapter 35) in every error body: it costs nothing and turns “it failed this morning” into a log query.

Try it. Post an invalid body and read the response. Then remove @Valid and post it again — the difference between a 400 with field names and a 500 from deep inside persistence is the whole chapter.

public record CreateOrder(
        @NotBlank String customerRef,
        @NotEmpty List<@Valid LineDto> lines) {}

@PostMapping("/orders")
public ResponseEntity<OrderView> create(@Valid @RequestBody CreateOrder body) { ... }

@RestControllerAdvice
class ApiErrors {
    @ExceptionHandler(MethodArgumentNotValidException.class)
    ProblemDetail onInvalid(MethodArgumentNotValidException ex) {
        var pd = ProblemDetail.forStatus(HttpStatus.BAD_REQUEST);
        pd.setTitle("Validation failed");
        pd.setProperty("errors", ex.getBindingResult().getFieldErrors().stream()
            .map(f -> Map.of("field", f.getField(), "message", f.getDefaultMessage())).toList());
        return pd;
    }
    @ExceptionHandler(OrderNotFound.class)
    ProblemDetail onMissing(OrderNotFound ex) {
        return ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, ex.getMessage());
    }
}
Golden rules
  • Validate the DTO, not the entity. Entity constraints fire at flush, in the wrong layer.
  • @Valid on the request body turns bad input into a 400 before your code runs.
  • One @RestControllerAdvice, one error shape, stack traces logged and never returned.
  • Malformed JSON and type mismatches are 400s. A blanket Exception handler hides that.
  • RFC 7807, plus a correlation id. Standard shape, traceable incident.

“Come gestisce gli errori in una API REST?”

“Validazione con Bean Validation sui DTO, così l’input non valido diventa un 400 prima ancora di entrare nel metodo. Poi un solo @RestControllerAdvice che traduce le eccezioni di dominio negli status giusti e restituisce sempre la stessa forma, RFC 7807, con un correlation id. Lo stack trace va nei log, mai nella risposta. E tengo presente che gli errori di autenticazione non passano di lì: sono nella catena dei filtri, quindi servono un AuthenticationEntryPoint e un AccessDeniedHandler.”
