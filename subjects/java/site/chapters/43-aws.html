AWS: EC2, S3 and Route 53

Exactly the three services the advert names, plus the IAM model underneath them — which is the part that actually gets asked, because it is where the security mistakes are.

From the advert

“conoscenza dei principali servizi AWS (almeno EC2, S3, Route53)”, from the Bologna document-lifecycle posting.

The three, briefly

🧒 Simple

EC2 is a virtual machine you rent. S3 stores files and serves them. Route 53 is DNS — it turns your domain name into an address.

🎓 Professional

EC2: instances in a VPC, with security groups as stateful per-instance firewalls and subnets split public/private. The thing to know is that you rarely want bare EC2 for a Spring service any more — ECS, EKS or App Runner sit on top of it, and an advert naming EC2 usually means either older infrastructure or the underpinning of something managed.

S3: object storage, not a filesystem. Objects are immutable, there are no real directories (prefixes only), and listing is expensive relative to fetching a known key. Use presigned URLs so clients upload and download directly instead of streaming bytes through your JVM — that single decision removes most of the memory pressure document-heavy applications suffer. Route 53: DNS with health checks and alias records to AWS resources.

IAM, and the credentials you must not have

🧒 Simple

Every action in AWS is allowed or denied by a policy. The important rule: your application should never contain a password or key — it should be given an identity by the platform.

🎓 Professional

IAM roles are assumed, not logged into: an EC2 instance profile, or IRSA on EKS, gives the running process temporary rotating credentials that the SDK picks up from the default provider chain with no configuration. Long-lived access keys in environment variables are the thing to avoid, and they are the most common finding in any AWS review.

Grant least privilege and be specific with resource ARNs — s3:GetObject on one bucket prefix, not s3:* on *. If asked how you would store the database password, the answer is Secrets Manager or SSM Parameter Store, read at start-up through an assumed role (chapter 13), never a value baked into an image.

⚠ Trap

Committed AWS keys are found by scanners within minutes of reaching a public repository, and the usual outcome is a very large bill for someone else’s cryptocurrency mining. Roles exist precisely so there is no key to commit; if you find yourself putting one in a .env, that is the signal to reach for a role instead.

Regions, and the costs that surprise people

🧒 Simple

Your resources live in a region. Moving data out of AWS, or between zones, costs money — and it is the bill nobody predicts.

🎓 Professional

Pick a region for latency and data residency — eu-south-1 is Milan, which matters for Italian public-sector and GDPR-sensitive work. Availability zones within a region are the unit of redundancy.

On cost: inbound traffic is free, outbound is not, and cross-AZ traffic is charged too — which is how a chatty pair of services in different zones produces a surprising line on the bill. S3 storage is cheap and requests are not, so a job doing millions of small GETs can cost more than the storage it reads. Being able to mention data residency and egress unprompted is a small, senior-sounding thing.

Golden rules
  • S3 is object storage, not a filesystem. Presigned URLs keep bytes out of your JVM.
  • Roles, never long-lived keys. The SDK finds temporary credentials by itself.
  • Least privilege with specific ARNs. s3:* on * is a finding.
  • Secrets Manager or Parameter Store for the database password.
  • Egress and cross-AZ traffic cost money. Inbound does not.
  • eu-south-1 is Milan — relevant when data residency is a requirement.

“Come gestisce le credenziali AWS nell’applicazione?”

“Non le gestisco: uso un ruolo IAM. Su EC2 è l’instance profile, su EKS è IRSA — in entrambi i casi il processo riceve credenziali temporanee che l’SDK trova da solo nella default credentials chain, senza configurazione. Chiavi long-lived in variabili d’ambiente non ne metto, perché prima o poi finiscono in un repository. I segreti applicativi, tipo la password del database, li leggo da Secrets Manager all’avvio, sempre tramite il ruolo. E le policy le tengo specifiche: s3:GetObject su un prefisso preciso, non s3:*.”
