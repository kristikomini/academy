OpenAPI, contracts and generated clients

The unglamorous chapter that makes integration work tractable. Nobody lists it as a requirement; every integration project needs someone who insists the contract is written down before the code is.

From the advert

Not in any advert. But the industrial integration in advert 1 — REST and GraphQL against OPC UA, MQTT and Modbus systems — is only manageable when both sides agree on a document rather than on a phone call.

Generated from the code

🧒 Simple

OpenAPI is a machine-readable description of your API: the endpoints, what they accept, what they return. A library reads your controllers and writes it for you.

🎓 Professional

springdoc-openapi inspects controllers, DTOs and Bean Validation annotations to produce an OpenAPI document plus a Swagger UI. Because it is generated from the same code that serves the requests, it cannot drift — which is the entire argument against hand-written API documentation in a wiki.

Your Bean Validation annotations from chapter 18 become schema constraints for free, which is a small, real reason to prefer @NotBlank over a hand-written null check.

Contract-first, and generated clients

🧒 Simple

The other direction: write the API description first, agree it with whoever will call you, and generate code from it — for both sides.

🎓 Professional

Contract-first means the OpenAPI document is the source of truth and both the server interfaces and the client stubs are generated from it. In cross-team or cross-company integration this is worth the ceremony: the contract can be reviewed and agreed before anyone writes an implementation, and the client team is not blocked waiting for your service to exist.

Code-first is faster for a service with one internal consumer. Contract-first is better when the other side is a different company, a machine vendor, or a team on a different release cycle — which is exactly advert 1’s situation. Being able to name which you would pick and why the other exists is the answer.

⚠ Trap

A generated document is not a designed API. springdoc will faithfully publish an endpoint called /getOrdersList returning entities with lazy proxies, and the Swagger page will make it look official. Generation removes the drift problem, not the design problem (chapter 17).

Golden rules
  • Generate the document from the code and it cannot drift from the code.
  • Bean Validation annotations become schema constraints. One more reason to use them.
  • Contract-first when the consumer is another team or company; code-first for one internal client.
  • Generated clients unblock the caller before your service exists.
  • A published bad API is still a bad API. Swagger UI does not make it a design.

“Come documenta le sue API?”

“Con OpenAPI generato dal codice, usando springdoc: così la documentazione non può divergere dall’implementazione, e le annotazioni di validazione diventano vincoli nello schema. Quando l’integrazione è con un team o un’azienda esterna preferisco l’approccio contract-first: si concorda il documento OpenAPI prima, si genera lo stub per il server e il client per chi ci chiama, e nessuno resta bloccato ad aspettare che il servizio esista.”
