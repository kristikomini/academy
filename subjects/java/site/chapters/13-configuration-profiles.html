Configuration, profiles and properties

Where settings come from, which source wins, how to bind a whole block of them to a typed object, and the one rule about secrets that will be checked in any company subject to an audit.

From the advert

“ottima conoscenza di Spring/Spring Boot (API REST, dependency injection, configurazioni, Spring Data JPA)”. Named explicitly in the senior Bologna advert.

Where a property comes from

🧒 Simple

A setting can come from a file in the jar, a file next to the jar, an environment variable, or the command line. When several of them define the same thing, the more specific one wins.

🎓 Professional

Boot merges an ordered list of property sources into one Environment. Roughly, later beats earlier: application.yml inside the jar, then profile-specific files, then files outside the jar, then OS environment variables, then command-line arguments.

The practical consequence is the deployment story: the same artefact runs in every environment, and the environment supplies the differences. Baking environment values into the jar and building one artefact per environment is the anti-pattern this ordering exists to prevent. Note the relaxed binding — SPRING_DATASOURCE_URL as an env var maps to spring.datasource.url, which is what makes container deployment tidy.

Typed configuration

🧒 Simple

Instead of scattering @Value("${...}") across the codebase, you can bind a whole group of related settings to one object with real fields and real types.

🎓 Professional

@ConfigurationProperties(prefix = "billing") binds a tree of properties to a typed object, validated with Bean Validation if you add @Validated. Since Java 17 the binding target can be a record, which gives you immutable configuration for free.

The advantage over @Value is not tidiness: it is that a missing or malformed value fails at start-up, with a message naming the property, instead of producing a null that surfaces during the first request that happens to need it.

Try it. Bind a record, then start the app with the property missing. The failure message is the feature — compare it with what @Value would have given you.

@Validated
@ConfigurationProperties(prefix = "billing")
public record BillingProperties(
        @NotBlank String vatNumber,
        @Positive int retryAttempts,
        Duration timeout) {}

// application.yml
// billing:
//   vat-number: IT01234567890     <- relaxed binding: vat-number -> vatNumber
//   retry-attempts: 3
//   timeout: 5s                   <- parsed into Duration

@Service
class Invoicer {
    private final BillingProperties props;
    Invoicer(BillingProperties props) { this.props = props; }   // typed, validated, immutable
}

Profiles, and where secrets must not live

🧒 Simple

A profile is a named set of settings — dev, test, prod — and you choose one when you start the application.

Passwords do not go in these files. They come from the environment.

🎓 Professional

Profiles activate property files (application-prod.yml) and beans (@Profile("prod")). Use them for environment shape, not for business logic: a @Profile on a class that behaves differently for a customer is a maintenance problem in disguise.

Secrets belong in the environment or a secret manager, never committed — not even in application-dev.yml, because credentials leak through git history long after they are deleted from the working tree. In the Kubernetes deployments these adverts describe, that means a Secret mounted as an env var (chapter 42); on AWS, Secrets Manager or Parameter Store (chapter 43).

Golden rules
  • One artefact, many environments. The environment supplies the differences.
  • Later sources win: command line > env vars > external files > packaged files.
  • @ConfigurationProperties over @Value — it fails at start-up instead of at first use.
  • Bind to a record and add @Validated.
  • No secrets in the repository. Git history outlives the deletion.
