Designing a REST API people can use

Anyone can map a URL to a method. Designing an API that survives its second client, its first breaking change and a retry storm is a different skill, and it is the one an interviewer probes when they ask you to design an endpoint on a whiteboard.

From the advert

“progettazione e implementazione di API REST/GraphQL per l’integrazione con sistemi industriali (OPC UA, MQTT, Modbus)”. Note the word: progettazione. Integration work fails on contracts far more often than on code.

Resources, verbs and status codes

🧒 Simple

A REST API is organised around things, not actions. The thing is in the URL; what you are doing to it is the HTTP method.

So it is POST /orders, not POST /createOrder.

🎓 Professional

Nouns in paths, plural, hierarchical for genuine containment (/orders/42/lines). Verbs come from HTTP: GET reads, POST creates, PUT replaces, PATCH partially updates, DELETE removes.

Use status codes precisely, because clients branch on them: 201 with a Location header on creation, 204 for a successful delete, 400 for a malformed request, 401 not authenticated versus 403 authenticated but not allowed, 404 for a missing resource, 409 for a conflict with current state, 422 when the syntax is fine and the content is not. Returning 200 with {"error": ...} inside makes every client parse the body to find out whether it worked.

Idempotency, and the retry you did not send twice on purpose

🧒 Simple

Networks lose replies. The client asks once, gets nothing back, and asks again — but the first request may already have worked.

An operation is idempotent when doing it twice has the same effect as doing it once. That is what makes retrying safe.

🎓 Professional

GET, PUT and DELETE are specified as idempotent; POST is not, which is why “create” is the dangerous one. The standard remedy is an idempotency key: the client generates a unique id per logical operation and sends it as a header; the server stores the key with the result and replays the stored response if it sees the key again.

This matters more than it sounds in the integration work these adverts describe: a machine on a factory floor with a flaky link will retry, and “we created 40 duplicate production orders” is a real incident. It is also the same idea as chapter 16 of the Kafka course — at-least-once delivery is only safe if the consumer is idempotent.

⚠ Trap

“We’ll just check whether a row already exists” is not idempotency, it is a race: two retries arriving together both check, both find nothing, both insert. You need a unique constraint on a natural or supplied key, and to treat the constraint violation as success.

Pagination and versioning

🧒 Simple

Never return “all of them”. The collection is small in development and enormous in production.

And once someone else uses your API, you cannot change it freely — you need a way to introduce a new shape without breaking them.

🎓 Professional

Offset pagination (?page=&size=) is simple and drifts: rows inserted between requests shift the window, so items are skipped or repeated. Cursor (keyset) pagination — “give me the 20 after this id” — is stable and much faster deep into a large table, because the database seeks rather than counting past the offset. Always cap the page size server-side.

For versioning, the practical options are a URL segment (/v1/orders) or a media type. URL versioning wins in most enterprise settings for the unglamorous reason that it is visible in logs, proxies and browser address bars. Better still, avoid the new version: adding an optional field is not a breaking change, so design responses so clients ignore what they do not know.

Golden rules
  • Nouns in the path, verbs from HTTP. POST /orders, never /createOrder.
  • Status codes are the API. 200-with-an-error-body forces every client to parse to find out.
  • POST is not idempotent. Use an idempotency key and a unique constraint, not a pre-check.
  • Cap page size server-side, and prefer keyset pagination for large collections.
  • Adding an optional field is not a breaking change. Design so you rarely need v2.

“Come progetterebbe un endpoint per creare un ordine?”

Design out loud and reach idempotency before they ask: “POST /orders con il corpo dell’ordine; rispondo 201 con l’header Location e la rappresentazione creata. Validazione con Bean Validation, e in caso di errore un corpo strutturato secondo RFC 7807 invece di uno stack trace. Siccome POST non è idempotente, accetto un header Idempotency-Key: lo salvo con la risposta e se ricevo la stessa chiave restituisco la risposta già prodotta, con un vincolo di unicità a database che regge anche due retry simultanei.” Very few candidates raise idempotency unprompted, and in integration work it is the thing that actually goes wrong.
