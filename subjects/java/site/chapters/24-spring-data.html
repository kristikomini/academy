Spring Data repositories

You declare an interface and Spring provides the implementation. That is genuinely a large saving and it has a boundary, and knowing where the boundary is — where derived queries stop and you should write SQL — is what the advert means by ottima conoscenza.

From the advert

“ottima conoscenza di Spring/Spring Boot (API REST, dependency injection, configurazioni, Spring Data JPA)”.

Derived queries

🧒 Simple

Write a method called findByCustomerIdAndStatus on an interface, and Spring writes the query by reading the method name. There is no implementation to maintain.

🎓 Professional

The method name is parsed into a query at start-up — which means a name that cannot be parsed, or that references a property your entity does not have, fails the application at boot rather than at first call. That is a real benefit and worth saying out loud.

Extend JpaRepository<Order, Long> for the usual CRUD plus paging and sorting. Keep derived names short: past three conditions they become unreadable, and findByCustomerIdAndStatusAndCreatedAtBetweenOrderByCreatedAtDesc is a @Query wearing a disguise.

@Query, projections and Specifications

🧒 Simple

When the method name is not enough, write the query yourself — either in JPQL, which talks about your classes, or in native SQL, which talks about your tables.

🎓 Professional

@Query takes JPQL by default or SQL with nativeQuery = true. Use named parameters (:status) rather than positional ones. JPQL is validated at start-up; native SQL is not, which is a real trade for a real benefit — you get the database’s full dialect, which chapter 27 will need.

Projections are the underused feature. Declaring an interface or record with only the fields you need makes Spring Data select only those columns, which is usually a bigger win than any index. For dynamic filtering — the search screen where six filters are all optional — use Specification rather than writing eight query methods or concatenating a query string.

⚠ Trap

A @Modifying query bypasses the persistence context: it changes rows in the database while Hibernate’s first-level cache still holds the old values, so entities already loaded in this transaction are now stale. Use clearAutomatically = true, or be certain nothing downstream reads them.

Try it. Turn on SQL logging first, then run each of these and read what is actually sent. The projection query is the one to look at.

// application.yml
// logging.level.org.hibernate.SQL: DEBUG
// spring.jpa.properties.hibernate.format_sql: true

public interface OrderRepo extends JpaRepository<Order, Long> {

    // derived: parsed at start-up, fails fast if the property name is wrong
    List<Order> findByCustomerIdAndStatus(Long customerId, Status status);

    // projection: selects two columns, not the whole row
    record Summary(Long id, BigDecimal total) {}
    @Query("select new OrderRepo$Summary(o.id, o.total) from Order o where o.status = :s")
    List<Summary> summaries(@Param("s") Status s);

    // modifying: needs the transaction, and clears the context it would otherwise stale
    @Modifying(clearAutomatically = true)
    @Query("update Order o set o.status = :s where o.id = :id")
    int markStatus(@Param("id") Long id, @Param("s") Status s);
}

Where the abstraction ends

🧒 Simple

Spring Data is excellent for “fetch these rows by these fields”. It is a poor fit for a reporting query with five joins and an aggregate.

🎓 Professional

The abstraction earns its place for domain access and stops earning it for analytics. A report joining five tables with grouping and window functions is clearer as SQL, easier to tune with a query plan, and does not need to be expressed as objects at all — nobody wants an entity graph for a monthly total.

“Spring Data JPA for the domain, JdbcClient or a native query for reporting” is a mature answer to “how do you handle complex queries”, and much better than insisting one tool covers everything. It also protects you from the candidate’s classic mistake: pulling ten thousand entities into memory to compute a sum the database could have produced.

Golden rules
  • Derived queries are parsed at start-up. A wrong property name fails the boot, not the request.
  • Past three conditions, write @Query. The method name has stopped being documentation.
  • Projections select fewer columns. Often a bigger win than an index.
  • Specification for optional filters, never string concatenation.
  • @Modifying leaves the persistence context stale. Clear it.
  • JPA for the domain, SQL for reporting. Both, deliberately.

“Come gestisce una query complessa con Spring Data?”

“Finché è accesso al dominio uso i metodi derivati, che hanno il vantaggio di essere validati all’avvio. Quando le condizioni diventano più di tre il nome del metodo smette di essere leggibile e passo a @Query. Se i filtri sono opzionali e combinabili uso le Specification, non concateno stringhe. E per la reportistica — cinque join e delle aggregazioni — scrivo SQL nativo con JdbcClient: è più chiaro, lo posso analizzare con un execution plan, e non ha senso passare da oggetti per calcolare un totale.”
