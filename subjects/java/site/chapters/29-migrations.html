Schema migrations with Flyway and Liquibase

How the database schema changes, safely, in a system where several instances start at once and the previous version may still be serving traffic. The chapter exists because ddl-auto=update in production is a defect this course refuses to let you ship.

From the advert

Not in any advert. And it is the question that separates people who have deployed something from people who have only run it locally.

Why ddl-auto is not a strategy

🧒 Simple

Hibernate can create or alter your tables to match your entities. It is wonderful in development and dangerous in production, because it decides what to change — and it never removes anything, so the schema slowly fills with things nobody meant to keep.

🎓 Professional

ddl-auto=update compares entities to the schema and applies what it thinks is needed. It cannot rename (a rename looks like a drop plus an add), it will not delete, it applies no data migration, and the result is unreviewable: nobody can read a diff of what will happen to production before it happens.

Use validate in production — it fails fast when the schema and the entities disagree, which is exactly the check you want — and let a migration tool own the changes. create-drop belongs in tests and nowhere else.

⚠ Trap

The nastiest form is not data loss but silence: update adds a column with all nulls and no default, the application works in testing because the test data is new, and a report over historical rows is quietly wrong. Nothing failed. That is the argument for reviewable migrations in one sentence.

Flyway and Liquibase

🧒 Simple

A migration tool keeps a numbered list of change scripts and a table recording which ones have run. On start-up it applies the ones that have not.

🎓 Professional

Flyway is SQL-first: versioned files (V3__add_status_to_orders.sql), applied in order, recorded with a checksum in a history table. Change an applied file and it refuses to start — which is the feature, not an annoyance. Liquibase uses a database-agnostic changelog (XML, YAML or SQL) and can generate rollbacks; it is the better fit when you must support several database vendors.

For a team on one database, Flyway’s plain SQL is usually the right call: everyone can read it, it goes through code review like anything else, and it is the same language you would type into a client at three in the morning.

Migrations in the pipeline, and expand–contract

🧒 Simple

If two copies of your application start at the same time, both will try to migrate. And while you deploy, the old version is still running against the new schema.

So changes must be safe for both versions at once.

🎓 Professional

Running migrations at start-up races when instances scale out, and it forces the runtime database account to hold schema-altering rights it should not have. Run them as a separate, gated pipeline step before the new version is deployed.

And make every change backwards compatible for one release — expand and contract. To rename a column: add the new one, write to both, backfill, move readers across, and only drop the old one in a later release. It is more steps and it means a rollback never leaves you with a schema the previous version cannot read, which is the failure mode that turns a bad deploy into an outage.

Golden rules
  • validate in production, never update. create-drop is for tests.
  • Migrations are reviewed artefacts. A diff a human read before it touched production.
  • Flyway’s checksum refusal is a feature. Never edit an applied migration; add a new one.
  • Migrate in the pipeline, not at start-up. Instances race, and runtime accounts should not hold DDL rights.
  • Expand and contract. Every change survives one release of both versions.

“Come gestisce le modifiche allo schema del database?”

“Con Flyway, script SQL versionati e revisionati come qualsiasi altro codice, e ddl-auto impostato su validate in produzione: così se schema ed entità divergono l’applicazione non parte, invece di scoprirlo a runtime. Le migrazioni le eseguo come step della pipeline, non all’avvio dell’applicazione, perché con più istanze che partono insieme si crea una race e perché l’utenza runtime non dovrebbe avere permessi di DDL. E ogni modifica la faccio expand-and-contract: aggiungo la colonna nuova, scrivo su entrambe, faccio il backfill e tolgo la vecchia in una release successiva — così un rollback trova sempre uno schema che la versione precedente sa leggere.”
