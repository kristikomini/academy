Maven and Gradle

Every Java project is built by one of these, and most candidates have only ever pressed the button in the IDE. Reading a dependency tree is a five-minute skill with a very long tail — it is how you resolve the version conflict that only appears at runtime.

From the advert

Not in any advert. Assumed by all of them, and the source of the most frustrating class of bug: code that compiles and then throws NoSuchMethodError.

The lifecycle and the wrapper

🧒 Simple

A build tool runs a fixed sequence: compile, test, package, install. You ask for a late phase and it runs everything before it.

Always use the wrapper script in the repository, so everyone builds with the same version of the tool.

🎓 Professional

Maven’s lifecycle is fixed and declarative: validate → compile → test → package → verify → install → deploy. Plugins bind to phases. Gradle is a task graph with incremental builds and a build cache — considerably faster on large projects, and more flexible in ways that can become a bespoke build nobody understands.

./mvnw and ./gradlew are not optional niceties: the wrapper pins the build tool version in the repository, so CI and every developer use the same one. “It builds on my machine” caused by two Maven versions is a real and stupid way to lose an afternoon.

Transitive dependencies and conflicts

🧒 Simple

Your dependencies have their own dependencies. Two of them may want different versions of the same library, and only one version can be on the classpath.

🎓 Professional

Maven resolves conflicts by nearest wins — the shortest path in the tree, not the highest version — which is why adding an unrelated dependency can silently downgrade something. Gradle picks the highest version by default, which surprises people moving the other way.

The symptom of getting this wrong is not a compile error: it is NoSuchMethodError or NoClassDefFoundError at runtime, because you compiled against one version and are running against another. mvn dependency:tree (or gradle dependencies) shows you exactly which path won. Pin the version in dependencyManagement rather than excluding dependencies one at a time.

⚠ Trap

Scopes matter more than they look. provided means “something else supplies this at runtime” — correct for a servlet API in a WAR, and the cause of a NoClassDefFoundError when nothing actually provides it (chapter 01). test keeps a dependency out of the shipped artefact, which is where every test library belongs.

Try it. Run this on any real project. The omitted for conflict lines are the interesting ones — each is a version you are not getting.

# what is actually on the classpath, and why
./mvnw dependency:tree
./mvnw dependency:tree -Dincludes=com.fasterxml.jackson.core:jackson-databind

# gradle
./gradlew dependencies --configuration runtimeClasspath
./gradlew dependencyInsight --dependency jackson-databind

# pin it, rather than excluding it in five places (pom.xml)
# <dependencyManagement><dependencies><dependency>
#   <groupId>com.fasterxml.jackson.core</groupId>
#   <artifactId>jackson-databind</artifactId>
#   <version>2.17.2</version>
# </dependency></dependencies></dependencyManagement>

BOMs, and letting someone else choose

🧒 Simple

A BOM is a published list of versions that are known to work together. You import it and stop choosing versions yourself.

🎓 Professional

spring-boot-dependencies is the BOM behind the starters in chapter 14: it fixes the versions of several hundred libraries that Spring has tested together. Declaring a dependency without a version and letting the BOM decide is the correct default, and overriding one is a decision that should have a reason.

Multi-module projects put shared configuration in a parent pom and let each module declare only what it needs. That discipline is what stops a utility module from quietly depending on the web layer — and it makes the dependency graph a design document rather than an accident.

Golden rules
  • Always the wrapper. The build tool version belongs in the repository.
  • Maven: nearest wins. Gradle: highest wins. Neither is intuitive; know which you are in.
  • NoSuchMethodError at runtime is a version conflict, not a code bug.
  • Pin in dependencyManagement instead of scattering exclusions.
  • Let the Boot BOM choose versions. Overriding one needs a reason.
  • Scopes are load-bearing. provided means somebody else must actually provide it.

Guardo con dependency:tree quale percorso ha vinto — Maven risolve per vicinanza, non per versione più alta, quindi basta aggiungere una dipendenza non correlata per farsi downgradare qualcosa senza accorgersene. La correzione è fissare la versione in dependencyManagement, non mettere exclusion sparse.”
