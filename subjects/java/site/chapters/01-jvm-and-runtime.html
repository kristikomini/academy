The JVM, and what actually runs

Java’s reputation — slow to start, fast once warm, impossible to kill, hungry for memory — is not about the language. It is about the machine underneath it. This chapter is that machine: what javac produces, who loads it, when it becomes native code, and why a container gives a JVM so much trouble.

From the advert

“Solida esperienza con Java 8+”. Nobody asks “explain the JVM” directly. They ask why the first request is slow, why the container was OOM-killed, or what NoClassDefFoundError means — and all three are this chapter.

From .java to something that runs

🧒 Simple

Most languages either translate your code to machine code once, before you ship (C, Go), or read it line by line every time it runs (older PHP, Python).

Java does both, in that order. javac translates your source into bytecode — instructions for an imaginary computer. Then the JVM reads that bytecode and, for the parts you run often, translates them again into real machine code while the program is running.

🎓 Professional

javac performs a comparatively shallow compilation: type checking, generics erasure, syntactic desugaring, and emission of stack-based bytecode into .class files. Almost no optimisation happens here, which is deliberate — the compiler that matters runs later and knows things this one cannot.

The JVM interprets that bytecode at first, profiling as it goes, and hands hot methods to the JIT compiler. The consequence worth carrying into an interview: the same code gets faster the longer the process lives, which is why Java benchmarks are meaningless without a warm-up, and why a serverless Java function is a different performance problem from a long-running service.

Try it. Compile anything and disassemble it. The point is to see that the string concatenation you wrote is not the code that ships — on Java 9+ it becomes an invokedynamic to StringConcatFactory, resolved at runtime.

// Hello.java
public class Hello {
    public static void main(String[] args) {
        String who = args.length > 0 ? args[0] : "world";
        System.out.println("hello, " + who);
    }
}

// javac Hello.java
// javap -c Hello        <- the bytecode
// javap -v Hello        <- constant pool, versions, everything

The class loader, and the errors it produces

🧒 Simple

Classes are not all loaded when the program starts. Each one is fetched the first time it is actually needed, by a class loader — a piece of the JVM whose whole job is finding a class by name and reading it in.

This is why some Java errors appear minutes after start-up, on one particular code path, on one particular machine.

🎓 Professional

Loading is lazy and hierarchical: a loader delegates to its parent before trying itself, so the platform classes cannot be shadowed by something on your classpath. Linking then verifies the bytecode, prepares static fields and resolves symbolic references; initialisation runs static blocks, once, guarded.

Learn the difference between the two errors, because it is a common question and the answers point at different problems. ClassNotFoundException is thrown when something asked for a class by name at runtime and it was not there — reflection, a driver, a Spring bean. NoClassDefFoundError means it was there when you compiled and is not there now, which is a packaging or dependency-scope problem: a jar with provided scope that nothing provided.

⚠ Trap

NoClassDefFoundError is also thrown — confusingly — when a class loaded fine but its static initialiser threw. The stack trace then names a class that is on the classpath, and people go hunting for a missing jar that is not missing. Look for the ExceptionInInitializerError in the earlier log lines: that is the real failure, and it is usually a config value read in a static block.

JIT: why Java is slow, then fast

🧒 Simple

The JVM watches which methods you call a lot. Once a method is clearly popular, it stops interpreting it and compiles it properly — with optimisations it could only choose because it watched first.

That is why the first few hundred requests to a fresh Java service are slower than the ones after, and why a load test that runs for ten seconds tells you almost nothing.

🎓 Professional

HotSpot uses tiered compilation: interpreter, then C1 (fast to compile, lightly optimised), then C2 (slow to compile, aggressively optimised) for the genuinely hot paths. Because it profiles first, it can perform speculative optimisations an ahead-of-time compiler cannot — inlining a virtual call that has only ever seen one implementing type, for example — and it keeps a guard so it can deoptimise if a second type ever shows up.

This is the honest answer to “is Java slower than C++?”: in steady state it is competitive and occasionally faster for exactly this reason, and it pays for that with start-up time and memory. Which is precisely the trade GraalVM native images and Quarkus (chapter 15) reverse.

JDK, JRE, JVM — and what to install

🧒 Simple

The JVM runs your program. The JRE is the JVM plus the standard library. The JDK is the JRE plus the tools that build and inspect things — javac, jar, javap, jcmd.

Install a JDK. There is no good reason to install anything smaller on a machine you write code on.

🎓 Professional

Since Java 11 there is no separately-shipped JRE from most vendors; you ship a JDK, or you build a trimmed runtime with jlink containing only the modules you use, which is the modern way to get a small container image (chapter 41).

On distributions: Oracle’s JDK carries licence conditions that vary by version, and the builds almost everyone actually uses are Eclipse Temurin, Amazon Corretto, Azul Zulu or Red Hat’s. They are all builds of the same OpenJDK source. Being able to say that calmly is a small but real signal of having shipped something.

Golden rules
  • javac barely optimises. The compiler that matters is the JIT, and it runs later, with profile data.
  • Java gets faster as it runs. Any benchmark without a warm-up phase is measuring the interpreter.
  • ClassNotFoundException is a runtime lookup that failed; NoClassDefFoundError is a packaging problem — or a static initialiser that threw.
  • Install a JDK, not a JRE, and know which vendor’s build you are running.
  • Start-up cost is the price of the JIT. That is the trade Quarkus and native images reverse.

“Perché la prima richiesta a un servizio Java appena avviato è più lenta?”

Answer with the mechanism, not the symptom: “Perché all’inizio la JVM interpreta il bytecode. Mentre gira raccoglie un profilo, e solo quando un metodo diventa caldo il JIT lo compila in codice nativo — con ottimizzazioni che può scegliere proprio perché ha osservato l’esecuzione. Per questo un load test senza warm-up misura l’interprete, non il servizio.” If they push further, the natural continuation is class loading being lazy, and then the trade-off against native images — which shows you know why Quarkus exists without having to be asked.
