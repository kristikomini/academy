Java EE, Jakarta and the code you will inherit

A large share of Italian Java work is maintaining something written for an application server a decade ago. Nobody advertises this and everybody does it, so arriving able to read EJB and JSF without visible dismay is worth more than another framework on your CV.

From the advert

Not in any advert. Which is itself the point: adverts describe the work companies want to talk about, not the proportion of the week you will spend in a WAR file from 2013.

The shape of an older application

🧒 Simple

Before Spring Boot embedded a web server in your jar, you built a WAR file and deployed it into an application server that was already running — WebLogic, WildFly, WebSphere.

The server provided the database connections, the transactions and the security, and your code assumed they were there.

🎓 Professional

The container supplied resources through JNDI, transactions declaratively via EJB, and security via the server’s realm. That is the same set of concerns Spring later provided in-process — and recognising it as the same concerns makes an EJB codebase readable rather than alien: @Stateless is roughly @Service, container-managed transactions are roughly @Transactional, and JPA is JPA.

The parts that genuinely differ: JSF, a stateful server-side component model with a view tree kept in session, which is nothing like an SPA; and deployment as an artefact into a shared, long-lived server, which is why classloader leaks and redeploy problems (chapter 10’s Metaspace error) exist there and not in a container world.

The javax → jakarta rename

🧒 Simple

In 2019 Java EE moved to the Eclipse Foundation and had to give up the javax name. Every import changed to jakarta.

That single rename is why a lot of systems are still on old versions.

🎓 Professional

Oracle donated Java EE but not the trademark, so the namespace changed with Jakarta EE 9. Nothing else needed to change — and everything broke, because every library in the ecosystem had to be recompiled and no application could mix the two.

This is why Spring Boot 3 requires Java 17 and Jakarta EE 9+: the Boot 2 → 3 upgrade is mostly this rename plus the libraries that had not made it yet. If you are asked about a migration you have done, this is a concrete and very common one, and the honest difficulty is never your own code — it is a transitive dependency that never shipped a jakarta build.

⚠ Trap

Automated tools rewrite imports well and miss strings: class names in XML configuration, persistence.xml, reflection lookups, and property files still say javax. Those fail at runtime, not at compile time, which is the worst possible place to find them.

Working in it without being miserable

🧒 Simple

You will not be allowed to rewrite it. The useful contribution is making it safer to change — tests, then small improvements where you are already working.

🎓 Professional

The rewrite instinct is the main way people fail in these roles. A system that has run the business for ten years contains a great deal of undocumented correctness, and a rewrite discards it. The strangler pattern — put a facade in front, move one capability at a time into a new service, and let the old system shrink — is the answer interviewers want to hear, because it is the one that survives contact with a budget.

Practically: get characterisation tests around the behaviour before touching it, since there may be no specification other than what it does. Improve where you are already working rather than campaigning for a cleanup sprint. And keep in mind that a stable ten-year-old system may be the most valuable software the company owns.

Golden rules
  • EJB, CDI and container-managed transactions are the same concerns Spring later solved.
  • JSF is stateful, server-side and nothing like an SPA. Do not reason about it as one.
  • javax → jakarta is the reason many systems are stuck. Boot 3 requires the new namespace.
  • Rename tools miss strings — XML, persistence.xml, reflection.
  • Strangler, not rewrite. Facade in front, move one capability at a time.
  • Characterisation tests first. The behaviour is the specification.

“Le capiterebbe di lavorare su un’applicazione legacy. Come si troverebbe?”

This is a temperament question as much as a technical one: “Bene, perché è buona parte del lavoro vero. La prima cosa che non farei è proporre una riscrittura: un sistema che manda avanti l’azienda da dieci anni contiene un sacco di correttezza non documentata, e riscrivendo la si butta via. Comincerei mettendo dei test di caratterizzazione intorno al comportamento esistente, così da poter cambiare qualcosa in sicurezza, e poi migliorerei dove sto già lavorando. Se serve modernizzare, lo farei con lo strangler pattern — una facciata davanti e una funzionalità alla volta spostata fuori.”
