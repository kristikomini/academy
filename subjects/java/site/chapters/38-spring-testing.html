Testing a Spring application

Spring makes it easy to write an integration test by accident and pay for it on every build. The slices are the fix, almost nobody knows they exist, and context caching is why your suite takes four minutes instead of forty.

From the advert

Not in any advert. And the difference between a test suite that runs in twenty seconds and one people stop running.

What needs Spring at all

🧒 Simple

Most of your classes are plain Java. You can test them by constructing them with new — no framework, no context, milliseconds.

Only start Spring when the thing you are testing is the wiring.

🎓 Professional

A @Service with constructor injection is testable with new and two mocks. That is the bulk of your suite and it should stay that way, because a plain unit test runs in a millisecond and a context-loading test runs in seconds.

Start a context when the behaviour under test belongs to the framework: JSON serialisation, validation, security rules, transaction boundaries, repository queries. Those genuinely cannot be verified without Spring, and testing them without it is how a query that fails against the real database passes in CI.

Slices

🧒 Simple

Instead of starting the whole application, you can start just the web layer, or just the persistence layer. Much less to load, much faster.

🎓 Professional

@WebMvcTest loads controllers, converters and the security filter chain — no services, no database — and you supply collaborators with @MockitoBean. It is the right tool for status codes, validation responses and JSON shape. @DataJpaTest loads JPA and repositories, and is transactional and rolled back per test.

@SpringBootTest loads everything and is for the handful of genuine end-to-end paths. Reach for it last. The common failure is a suite where every test is annotated @SpringBootTest because it was copied from the one that needed to be — and then the build takes ten minutes and people stop running it locally.

⚠ Trap

Spring caches the application context per unique configuration. Every test that customises the context differently — a stray @TestPropertySource, a one-off @MockitoBean on a @SpringBootTest — creates another context to build and hold. That is usually the real reason a suite is slow, and the fix is to make configurations identical rather than to buy a faster machine.

Try it. Time the two. The slice loads a fraction of the context and tests exactly the thing you care about here — the status code and the error body.

@WebMvcTest(OrderController.class)
class OrderControllerTest {

    @Autowired MockMvc mvc;
    @MockitoBean OrderService orders;          // the service is NOT loaded, it is supplied

    @Test
    void returns404WhenMissing() throws Exception {
        when(orders.find(42L)).thenReturn(Optional.empty());

        mvc.perform(get("/orders/42"))
           .andExpect(status().isNotFound());
    }

    @Test
    void rejectsInvalidBody() throws Exception {
        mvc.perform(post("/orders").contentType(APPLICATION_JSON).content("{}"))
           .andExpect(status().isBadRequest())
           .andExpect(jsonPath("$.errors[0].field").value("customerRef"));
    }
}

Testing the persistence layer

🧒 Simple

Testing a query against a different database from the one you deploy on tests a database you do not ship.

🎓 Professional

@DataJpaTest defaults to an embedded database, and H2 is not Oracle: it accepts SQL Oracle rejects, and behaves differently on sequences, empty strings and dialect functions (chapter 27). A native query that works in H2 and fails in production is the standard outcome.

Point it at a real database with Testcontainers (chapter 39) — @AutoConfigureTestDatabase(replace = NONE) plus a container — and the whole class of “passed in CI, failed in production” defects disappears. This is the single highest-value testing change in a typical Spring codebase.

Golden rules
  • Most tests need no Spring at all. Constructor injection makes that true.
  • Slices over @SpringBootTest. @WebMvcTest, @DataJpaTest, then everything else.
  • Context caching is per configuration. Every variation is another context.
  • H2 is not Oracle. Testing against it tests a database you do not ship.
  • Slow suites stop being run. That is how the net disappears.

“Come testa un controller Spring?”

“Con @WebMvcTest, non con @SpringBootTest: carica solo il layer web — controller, converter, catena di sicurezza — e i collaboratori li fornisco con @MockitoBean. Così testo quello che il controller fa davvero: status code, validazione, forma del JSON. Il servizio sotto lo testo separatamente con un semplice new e due mock, senza contesto. @SpringBootTest lo tengo per pochi percorsi end-to-end, perché ogni configurazione diversa crea un contesto in più da costruire e tenere in cache, ed è lì che le suite diventano lente.”
