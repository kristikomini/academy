Messaging from inside a Spring application

Producers, consumers and the honest choice between Kafka and RabbitMQ — seen from inside a Spring application. This chapter deliberately stops at the client boundary: the broker’s own model belongs to the Kafka academy, and duplicating it here would create two copies to keep in step.

From the advert

“Java 17 (Spring Boot), OpenShift/Kubernetes, Apache Kafka/RabbitMQ, MongoDB e Oracle DB”. Note the slash: the advert wants someone who can work with either and, ideally, say why you would pick one.

Why go asynchronous at all

🧒 Simple

Some work does not need to happen before you answer the user. Sending the confirmation email, updating a search index, notifying another system — the user does not need to wait for any of it.

So you record that it needs doing, answer immediately, and do it shortly after.

🎓 Professional

Messaging buys three things: latency (the caller returns without waiting for downstream work), decoupling (the producer does not know who consumes, so a new consumer is added without touching it), and load levelling (a burst becomes a backlog rather than a failure).

It costs you eventual consistency and a much harder debugging story: the failure now happens somewhere else, later, on another thread. That is why chapter 35’s correlation ids stop being a nicety the moment you introduce a broker.

Kafka or RabbitMQ

🧒 Simple

RabbitMQ is a queue: a message is delivered to one consumer and then it is gone. Kafka is a log: messages stay for a set time and every consumer tracks its own position, so several can read the same stream and anyone can start again from the beginning.

🎓 Professional

RabbitMQ is a broker with rich routing (exchanges, bindings, per-message TTL, priorities, dead-letter queues) and per-message acknowledgement. Choose it for task distribution and complex routing — work queues where each job goes to exactly one worker.

Kafka is a partitioned, replicated log with retention. Choose it for event streams that several independent consumers read, for very high throughput, and when the ability to replay matters — rebuilding a projection by reprocessing history is something a queue simply cannot do. The trade is that per-message routing and per-message acknowledgement are not its model, and imitating them is painful.

⚠ Trap

Choosing Kafka because it is faster, and then using one topic per consumer with a single partition, gives you an expensive RabbitMQ with worse ergonomics. If what you need is “each job to exactly one worker, with retries and a dead-letter queue”, that is a queue — say so.

The Spring side

🧒 Simple

You send with a template and receive with an annotated method. The framework handles the connection, the threads and the deserialisation.

The part that needs your attention is what happens when the handler throws.

🎓 Professional

KafkaTemplate / RabbitTemplate to publish; @KafkaListener / @RabbitListener to consume. The decisions that matter are error handling and acknowledgement: configure a DefaultErrorHandler with backoff and a dead-letter topic, so a message that cannot be processed is set aside rather than retried forever.

Two things that catch people. A poison message blocks its partition in Kafka — the consumer cannot move past an offset it cannot process, so without a dead-letter route everything behind it stops. And the listener runs on the broker’s thread, not a request thread: there is no SecurityContext and no request-scoped bean, which surprises people who inject one.

Try it. Publish, consume, and then throw deliberately in the handler. Watch the retries, then watch it land in the DLT — that path is the one worth having seen once.

@Service
class OrderEvents {
    private final KafkaTemplate<String, OrderPlaced> template;
    OrderEvents(KafkaTemplate<String, OrderPlaced> template) { this.template = template; }

    // the KEY decides the partition, and therefore the ordering guarantee
    void publish(OrderPlaced event) {
        template.send("orders.placed", event.orderId(), event);
    }
}

@Component
class OrderListener {
    @KafkaListener(topics = "orders.placed", groupId = "billing")
    void on(OrderPlaced event) {
        // must be idempotent: delivery is at-least-once
        billing.chargeOnce(event.orderId(), event.total());
    }
}

@Bean
DefaultErrorHandler errorHandler(KafkaTemplate<String, Object> template) {
    var recoverer = new DeadLetterPublishingRecoverer(template);      // -> orders.placed.DLT
    return new DefaultErrorHandler(recoverer, new FixedBackOff(1000L, 3));
}
Golden rules
  • Async buys latency, decoupling and load levelling, and costs you eventual consistency.
  • Queue for work distribution, log for event streams. Replay is the deciding capability.
  • Delivery is at-least-once. Handlers must be idempotent.
  • A poison message blocks its partition. Configure a dead-letter route before you need one.
  • The listener thread has no SecurityContext and no request scope.
  • The message key chooses the partition, and therefore the ordering.

“Kafka o RabbitMQ, per questo caso?”

“Dipende se mi serve una coda o un log. RabbitMQ è una coda: routing ricco, ack per messaggio, il messaggio consumato sparisce — ottimo per distribuire lavoro dove ogni job va a un solo worker. Kafka è un log partizionato con retention: più consumer indipendenti leggono lo stesso stream, ognuno con il proprio offset, e posso rileggere dall’inizio per ricostruire una proiezione. Se la capacità di fare replay conta, è Kafka; se mi serve routing per messaggio e dead letter per singolo job, è Rabbit. In entrambi i casi il consumer lo scrivo idempotente, perché la consegna è at-least-once.”
