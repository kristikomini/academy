JDBC, connection pools and what leaks

The layer under every ORM. Read this before chapter 23 and Hibernate stops being magic; skip it and every performance conversation you have will bottom out in something you cannot explain.

From the advert

Not in any advert. And pool exhaustion under load is the classic Friday-afternoon incident — diagnosable in minutes if you know this layer exists, and mystifying if you do not.

JDBC, and why statements are prepared

🧒 Simple

JDBC is the standard way Java talks to a relational database: get a connection, send a statement, read the results, give the connection back.

Always send the query and the values separately. Gluing values into the SQL string is how SQL injection happens.

🎓 Professional

PreparedStatement sends the SQL and the parameters over separate channels, so the database parses the statement once and the values can never be interpreted as SQL. That is why parameterisation is a structural defence rather than an escaping trick — there is no escaping to get wrong.

It also lets the database cache the execution plan for the statement, which matters on Oracle (chapter 27), where a flood of textually distinct queries fills the shared pool and causes hard parses. Every layer above — JdbcTemplate, Hibernate, Spring Data — ends up here.

The pool, and why it is small

🧒 Simple

Opening a database connection is expensive, so the application opens a handful at start-up and lends them out. That set is the connection pool.

When every connection is lent out, the next request waits. If nobody gives one back, it waits forever.

🎓 Professional

HikariCP is Boot’s default. The counter-intuitive part is sizing: a bigger pool is usually slower. The database can only do so much concurrent work, and past that point extra connections add contention and context switching rather than throughput. Something near (2 × cores) + effective spindles is the classic starting point, and pools of 10–20 are normal for services people imagine need 200.

Set connectionTimeout so a request waiting for a connection fails fast instead of hanging; set maxLifetime shorter than any database or firewall idle timeout, or you will hand out connections the network has already dropped. And remember every pod has its own pool — ten replicas with a pool of 20 is 200 connections at the database, which is how a Kubernetes rollout takes down a shared Oracle instance.

⚠ Trap

The classic leak: a connection borrowed on a path that throws before it is returned. The symptom is not an error at the leak site — it is every other request timing out minutes later while waiting for the pool. Always try-with-resources (chapter 08), or let Spring manage the connection and never take one yourself.

JdbcTemplate and JdbcClient

🧒 Simple

Spring wraps JDBC so you do not write the same six lines of setup and cleanup every time. You give it the SQL and how to turn a row into an object.

🎓 Professional

JdbcTemplate (and the newer fluent JdbcClient) handles resource management and translates SQLException into Spring’s unchecked DataAccessException hierarchy — so a duplicate key becomes DuplicateKeyException regardless of vendor.

Do not assume the ORM everywhere. A reporting query with five joins and an aggregate is clearer, faster and easier to tune as SQL than as JPQL, and mixing the two in one codebase is normal and healthy. “JPA for the domain, plain SQL for reporting” is a good answer when asked how you handle complex queries.

Golden rules
  • Always parameterise. Separate channels for SQL and values; injection becomes structurally impossible.
  • Small pools are faster. 10–20 is normal; 200 is a misunderstanding.
  • Every replica has its own pool. Multiply before you deploy.
  • maxLifetime below the database and firewall idle timeouts, or you hand out dead connections.
  • A leaked connection breaks other requests, not the one that leaked it.
  • JPA for the domain, SQL for reporting. Mixing them is not a failure.

“L’applicazione sotto carico rallenta e poi va in timeout. Da dove parte?”

Reach for the pool early, because it is the most common cause and the fastest to check: “Prima cosa guardo le metriche del connection pool: connessioni attive, e soprattutto il tempo di attesa per ottenerne una. Se le richieste aspettano il pool, il problema non è il database ma il fatto che le connessioni non tornano indietro — o perché ci sono query lente che le tengono occupate, o perché c’è un leak su un path che solleva eccezione. Controllo anche che il pool non sia stato ingrandito per compensare: un pool più grande di solito peggiora le cose.”
