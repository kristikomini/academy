Mockito, test doubles and over-mocking

A suite that mocks everything passes forever and catches nothing. Knowing which collaborators deserve a double — and which should be real — is the difference between tests that help and tests that only cost.

From the advert

Not in any advert. Visible in every code test: the shape of your doubles says more about your judgement than the assertions do.

The kinds of double

🧒 Simple

A stub answers questions with canned data. A mock also checks that it was called the way you expected. A fake is a real, simple implementation — an in-memory version of the thing.

🎓 Professional

The distinction that matters is between state verification (assert on the result) and interaction verification (assert that a call happened). Prefer state. Interaction assertions couple the test to the implementation, so they break on refactoring even when behaviour is unchanged.

Use verify when the interaction is the behaviour — “an email was sent”, “the payment was charged exactly once”. Those are observable effects with no return value to assert on, so there is nothing else to check.

Mockito, and the argument captor

🧒 Simple

You create a fake version of a dependency, tell it what to return, run your code, and then check what your code did with it.

🎓 Professional

@Mock plus @InjectMocks with @ExtendWith(MockitoExtension.class), or simply construct the class under test with mocks — which constructor injection makes trivial and which reads better. when(...).thenReturn(...) for stubbing; ArgumentCaptor when you need to assert on what was passed, not merely that something was.

Mockito’s strict stubs will fail a test with an unused stub, which is a feature: it tells you the test is describing a path that no longer exists. And note you cannot mock final or static methods without the inline mock maker — needing to is usually a design signal, not a tooling problem.

⚠ Trap

Never mock a type you do not own. Mocking a third-party client encodes your assumption about how it behaves, and the test then keeps passing when that assumption is wrong — which is precisely the case you needed to catch. Wrap it in your own interface and mock that; verify the real thing with an integration test (chapter 39).

Over-mocking, and what to leave real

🧒 Simple

If a test mocks everything the code touches, it only proves that the mocks were configured the way the test expected. Change the code and the test still passes.

🎓 Professional

Mock at the edges: things that are slow, non-deterministic, or outside your process — network calls, the clock, the file system, message brokers. Leave your own value objects and domain logic real; mocking them tests nothing and makes refactoring expensive.

The clock is the underrated one. Injecting a java.time.Clock instead of calling Instant.now() makes anything time-dependent — expiry, retention, streaks — testable without waiting or sleeping. The accounts service in this repository injects a clock for exactly that reason: a test that must wait fifteen real minutes to prove a token expired is a test nobody runs.

Golden rules
  • Prefer state verification. verify only when the interaction is the behaviour.
  • Never mock a type you do not own. Wrap it and mock your wrapper.
  • Mock the edges — network, clock, filesystem, broker. Leave the domain real.
  • Inject a Clock. Time is a dependency like any other.
  • An unused stub is a message. The path it described is gone.
  • If everything is mocked, the test verifies the mocks.

“Quando usa un mock e quando no?”

“Mocko ai bordi: quello che è lento, non deterministico o fuori dal mio processo — chiamate di rete, il clock, il filesystem, il broker. Il dominio lo lascio vero, perché mockarlo non verifica niente e rende ogni refactoring costoso. Preferisco asserire sul risultato invece che sulle interazioni: verify lo uso quando l’interazione è il comportamento, tipo ‘è stata inviata una sola email’. E non mocko mai un tipo che non è mio: incapsulerei la mia assunzione su come si comporta una libreria, e il test continuerebbe a passare proprio quando quell’assunzione è sbagliata.”
