Generics and erasure

Generics look like a type system feature and are, at runtime, mostly absent. Understanding exactly what the compiler removes explains every “why can’t I do that” question in Java — and wildcards, which are the part almost nobody can explain under pressure.

From the advert

Not in any advert. Erasure is how interviewers separate people who have read the language from people who have copied from it, and wildcards appear the moment you write a method that takes a collection.

Erasure: what the compiler throws away

🧒 Simple

You write List<String>. The compiler checks that you only put strings in — then deletes the <String> part. At runtime it is just a List.

So the type safety is real, but it all happens before the program runs. Nothing is left to ask at runtime.

🎓 Professional

Generics are compile-time only: type parameters are erased to their bound (Object unless declared otherwise) and the compiler inserts casts. This was a backwards-compatibility decision — generic code had to interoperate with the pre-generic collections that already existed.

Everything that follows is a consequence: you cannot write new T[], you cannot ask x instanceof List<String>, you cannot overload on List<String> and List<Integer> because after erasure they are the same signature, and a ClassCastException can surface at a line that contains no cast — the compiler put it there.

⚠ Trap

Because erasure removes the check, an untyped legacy call can insert the wrong type into your List<String> and nothing complains until something reads it. That is heap pollution, and it is why @SuppressWarnings("unchecked") should make you look rather than reach for the keyboard.

Wildcards, and PECS

🧒 Simple

A List<Dog> is not a List<Animal>, even though a dog is an animal. If it were, someone could put a cat in your list of dogs.

Wildcards are how you say “a list of some kind of animal” when you only want to read from it.

🎓 Professional

Generics are invariant, which is what makes the assignment above illegal and correct. Wildcards reintroduce flexibility in one direction at a time: ? extends T is a producer — you can read T out and cannot put anything in (except null). ? super T is a consumer — you can put T in and only read Object out.

PECS: Producer Extends, Consumer Super. It is the mnemonic every interviewer is listening for, and Collections.copy(List<? super T> dest, List<? extends T> src) is the example that makes it obvious — the source produces, the destination consumes.

Try it. The commented lines are the ones that will not compile. Uncomment them one at a time and read the errors — each one is the rule stated back at you.

import java.util.*;

class Animal {} class Dog extends Animal {}

public class Pecs {
    // producer: we only read Animals out
    static void printAll(List<? extends Animal> src) {
        for (Animal a : src) System.out.println(a);
        // src.add(new Dog());   // won't compile: could be a List<Cat>
    }
    // consumer: we only put Dogs in
    static void addDogs(List<? super Dog> dest) {
        dest.add(new Dog());
        // Dog d = dest.get(0);  // won't compile: could be a List<Object>
    }
    public static void main(String[] args) {
        List<Dog> dogs = new ArrayList<>();
        addDogs(dogs);
        printAll(dogs);
        // List<Animal> as = dogs;  // won't compile: generics are invariant
    }
}

Bounded type parameters

🧒 Simple

You can require that a type parameter is at least something: “any type, as long as it can be compared”. Then you are allowed to call the comparison method on it.

🎓 Professional

<T extends Comparable<T>> bounds the parameter so the compiler permits compareTo and erases T to Comparable rather than Object. Multiple bounds are allowed (<T extends Number & Comparable<T>>), class first.

The distinction to keep straight: a type parameter <T> names a type you can use throughout the signature; a wildcard <?> does not. If the return type depends on the argument’s type, you need a parameter, not a wildcard.

Golden rules
  • Generics are erased. Compile-time safety, no runtime type argument.
  • No new T[], no instanceof List<String>, no overloading that differs only by type argument.
  • PECS. Producer extends, consumer super.
  • Generics are invariant — and that is what stops a cat entering your list of dogs.
  • @SuppressWarnings("unchecked") is a request to think, not a way to silence the compiler.

“Cos’è la type erasure e che conseguenze ha?”

Define it in one sentence and then spend your time on consequences, which is what they are really asking: “I generici esistono solo a compile time: il compilatore verifica i tipi e poi li cancella, sostituendoli col bound. La conseguenza è che a runtime il tipo parametrico non c’è, quindi non posso fare new T[], non posso testare instanceof List<String>, e due overload che differiscono solo per il parametro di tipo hanno la stessa firma dopo l’erasure.” Then add why — compatibility with pre-generics collections — because that turns a memorised fact into an understood design decision.
