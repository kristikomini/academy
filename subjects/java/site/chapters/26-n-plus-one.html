The N+1 problem and fetching strategies

One list page becomes four hundred queries and nobody notices until production. It is the most common Hibernate performance defect, it is invisible without SQL logging, and being able to name it, show it and fix it three ways is one of the strongest things you can do in a technical interview.

From the advert

Not in any advert. Visible in essentially every Hibernate codebase in the region, including ones that are otherwise well written.

What actually happens

🧒 Simple

You load 100 orders with one query. Then, for each one, you read its customer’s name — and each of those is another query.

One query became 101. In development, with three rows, nobody sees it.

🎓 Professional

The name is literal: 1 query for the collection, N more as each element’s lazy association is initialised. It is triggered by anything that touches the association — a loop, a mapping to DTOs, or Jackson serialising an entity in the controller (chapter 16).

It is invisible without instrumentation, which is why the first fix is to make it visible: turn on org.hibernate.SQL logging in development, and consider a query counter in tests that fails when an endpoint exceeds a threshold. A defect you can see is a defect that gets fixed.

⚠ Trap

The tempting fix — changing the association to FetchType.EAGER — makes it worse. Now every query that touches an order fetches the customer, even the ones that never look at it, and eager collections on the same entity multiply into a cartesian product. Eager is a global answer to a per-query question.

The four fixes

🧒 Simple

Tell Hibernate what you need with the first query, instead of letting it discover it one row at a time.

🎓 Professional

Join fetch — select o from Order o join fetch o.customer — one query, per query, which is the right granularity. Entity graph (@EntityGraph on the repository method) does the same declaratively. Batch size (@BatchSize, or hibernate.default_batch_fetch_size) turns N queries into N/size using an IN clause — the cheapest global mitigation and a very good default to set on any project. A projection avoids the problem entirely by never loading the entity graph.

One caveat to have ready: you cannot join fetch two collections in the same query without producing a cartesian product, and Hibernate 6 will refuse. Fetch one collection per query, or use batch fetching for the second.

Try it. Log the SQL, run the naive version, count the queries. Then run the fetched version and count again. The number is the argument.

// N+1: one query for orders, one per order for the customer
List<Order> orders = repo.findByStatus(Status.OPEN);
orders.forEach(o -> System.out.println(o.getCustomer().getName()));

// Fix 1 — join fetch, per query
@Query("select o from Order o join fetch o.customer where o.status = :s")
List<Order> findOpenWithCustomer(@Param("s") Status s);

// Fix 2 — entity graph, declarative
@EntityGraph(attributePaths = "customer")
List<Order> findByStatus(Status status);

// Fix 3 — batch fetching, global mitigation (application.yml)
// spring.jpa.properties.hibernate.default_batch_fetch_size: 50

// Fix 4 — never load the graph at all
@Query("select new com.x.OrderRow(o.id, o.customer.name, o.total) from Order o where o.status = :s")
List<OrderRow> rows(@Param("s") Status s);

Pagination and the in-memory trap

🧒 Simple

Asking for one page of orders and their lines in the same query does not work the way you expect. The join multiplies the rows, so “20” no longer means 20 orders.

🎓 Professional

When you combine join fetch on a collection with Pageable, Hibernate cannot apply the limit in SQL without cutting a collection in half — so it fetches everything and paginates in memory, warning HHH000104: firstResult/maxResults specified with collection fetch; applying in memory. On a large table that is an OutOfMemoryError waiting for enough rows.

The standard remedy is two queries: page the ids first, then fetch the full graph for that page with an IN clause. Recognising that warning line in a log is a genuinely senior-sounding moment, because almost everyone has ignored it at some point.

Golden rules
  • Turn on SQL logging in development. N+1 is invisible until you count queries.
  • Never fix it with EAGER. That answers a per-query question globally, and gets worse.
  • join fetch or @EntityGraph per query; default_batch_fetch_size as a safety net.
  • One collection fetch per query. Two is a cartesian product.
  • HHH000104 means it is paginating in memory. Page the ids, then fetch.
  • A projection sidesteps the whole problem.

“Cos’è il problema N+1 e come lo risolve?”

Show that you have actually seen it: “Faccio una query che carica N entità, e poi per ognuna Hibernate ne fa un’altra per inizializzare un’associazione lazy: una query diventa N+1. Non si vede finché non attivi il log dell’SQL, e in sviluppo con tre righe non te ne accorgi. Lo risolvo dicendo a Hibernate cosa mi serve nella prima query — join fetch o @EntityGraph — e imposto default_batch_fetch_size come rete di sicurezza. Quello che non faccio è mettere EAGER: risolve un problema di quella query peggiorando tutte le altre.”
