Spring Boot and auto-configuration

Boot’s promise is that a dependency on the classpath configures itself. That is genuinely useful and genuinely opaque, and the difference between a junior and a mid-level candidate is usually whether they can find out why a bean they never declared exists.

From the advert

“Esperienza consolidata in Java, Spring, Spring Boot”. Every one of the six adverts names Boot. None of them says what it does, which is the gap this chapter fills.

Starters and the classpath

🧒 Simple

A starter is a dependency that brings a whole capability with it. Add spring-boot-starter-web and you get a web server, JSON handling and the wiring — without choosing versions for any of it.

🎓 Professional

A starter is a pom with no code: it declares a coherent set of dependencies whose versions come from the Boot BOM, so you never pick a Jackson version that disagrees with your Spring version. That is most of what Boot is: an opinion about which library versions work together, maintained by someone else.

The other half is auto-configuration: classes registered in AutoConfiguration.imports that declare beans behind conditions — @ConditionalOnClass, @ConditionalOnMissingBean, @ConditionalOnProperty. “If Hibernate is on the classpath and the user has not defined an EntityManagerFactory, define one.”

Overriding, and finding out what happened

🧒 Simple

Because auto-configuration usually says “only if the user hasn’t defined one themselves”, the way to override anything is simply to declare your own bean.

🎓 Professional

@ConditionalOnMissingBean is what makes Boot overridable rather than magic: define the bean yourself and the auto-configuration steps aside. That is the whole mechanism, and it is a good answer to “what if I don’t want Boot’s default?”.

When something unexpected is wired, run with --debug and read the condition evaluation report: it lists every auto-configuration that matched, every one that did not, and the condition that decided. Being able to say that in an interview is worth more than any list of annotations, because it is the difference between debugging Boot and guessing at it.

⚠ Trap

@SpringBootApplication component-scans from its own package downwards. A bean in a sibling package is silently not found — no error, just a NoSuchBeanDefinitionException later, or worse, a working application missing a listener nobody noticed. Keep the main class at the root of your package tree.

Actuator: the built-in answers

🧒 Simple

Actuator adds endpoints that tell you about the running application — is it healthy, what is it configured with, how much memory is it using.

🎓 Professional

/actuator/health with its liveness and readiness groups is what Kubernetes probes (chapter 42); /actuator/metrics and /actuator/prometheus feed the monitoring in chapter 35; /actuator/env and /actuator/configprops answer “what is this instance actually configured with”.

Expose deliberately. The defaults are conservative for a reason: /actuator/env will happily print your configuration, and /actuator/heapdump hands over a file containing everything in memory. In production, expose the health and metrics endpoints and keep the rest behind authentication.

Golden rules
  • A starter is a version opinion, not code. That is most of Boot’s value.
  • Auto-configuration is conditional bean definition. Define your own bean and it backs off.
  • --debug prints the condition evaluation report. Use it instead of guessing.
  • Component scan starts at the main class’s package. Siblings are invisible.
  • Expose actuator endpoints deliberately. /env and /heapdump are not public information.

“Come fa Spring Boot a configurare le cose da solo? E se non mi piace il default?”

“L’auto-configuration è un insieme di classi che definiscono bean sotto condizione: @ConditionalOnClass guarda cosa c’è nel classpath, @ConditionalOnMissingBean guarda cosa ho già definito io. Quindi per sovrascrivere un default basta dichiarare il mio bean: la auto-configuration si fa da parte. E se non capisco perché esiste un bean, avvio con --debug e leggo il condition evaluation report, che mi dice quali configurazioni hanno fatto match e quali no.” That last sentence is the one that separates the answers.
