REST controllers and the request cycle

What happens between the socket and your method, and back. Filters, the dispatcher, argument resolution, JSON serialisation — each of them a place where requests fail in ways that look inexplicable until you know the order things run in.

From the advert

“ottima conoscenza di Spring/Spring Boot (API REST, dependency injection, configurazioni, Spring Data JPA)”. REST appears in five of the six adverts.

From socket to method

🧒 Simple

A request arrives at the embedded web server. It passes through a chain of filters, reaches a dispatcher that decides which of your methods should handle it, gets its parameters converted from text into objects, and your method finally runs.

Whatever you return goes back through the same machinery and becomes JSON.

🎓 Professional

Embedded Tomcat accepts the connection and hands it to the servlet filter chain — where Spring Security lives (chapter 20) — then to DispatcherServlet. That picks a handler by path and method, runs any interceptors, resolves arguments (@PathVariable, @RequestParam, @RequestBody via Jackson), invokes your controller, then converts the return value with an HttpMessageConverter.

The order is the useful part. Security runs in the filter chain, before the dispatcher, which is why an authentication failure never reaches your @ControllerAdvice and needs its own AuthenticationEntryPoint. It is also why CORS misconfiguration produces a rejection that no controller ever sees.

Writing the controller

🧒 Simple

A controller method maps a URL to code. Its job is to accept the request, hand off to a service, and turn the answer into a response — nothing else.

🎓 Professional

@RestController is @Controller plus @ResponseBody. Keep controllers thin: mapping, validation, status codes, and delegation. Business rules in a controller cannot be reused by a scheduled job or a message consumer, and cannot be tested without the web layer.

Never expose an entity directly. A JPA entity as a response body couples your API to your schema, drags lazy associations into serialisation (chapter 26), and leaks fields you did not mean to publish. Use a record DTO — which since Java 17 costs one line.

⚠ Trap

Returning a JPA entity from a controller is the single most common cause of the LazyInitializationException that appears only for some requests: the transaction closed when the service method returned, and Jackson then touched a lazy association while serialising. The error names Hibernate, and the cause is the controller.

Try it. Compare the two. The second one is longer to write and is the one that survives a schema change.

// Don't: the entity is the API contract now
@GetMapping("/orders/{id}")
public Order get(@PathVariable Long id) {
    return repo.findById(id).orElseThrow();
}

// Do: an explicit contract, mapped deliberately
public record OrderView(Long id, String customer, BigDecimal total, String status) {
    static OrderView of(Order o) {
        return new OrderView(o.getId(), o.getCustomer().getName(), o.getTotal(), o.getStatus().name());
    }
}

@GetMapping("/orders/{id}")
public ResponseEntity<OrderView> get(@PathVariable Long id) {
    return orders.find(id).map(OrderView::of)
                 .map(ResponseEntity::ok)
                 .orElseGet(() -> ResponseEntity.notFound().build());
}

Serialisation and content negotiation

🧒 Simple

Spring decides how to turn your object into a response by looking at what the client said it accepts. In practice that is almost always JSON, produced by a library called Jackson.

🎓 Professional

HttpMessageConverters handle both directions, selected by the Accept and Content-Type headers. Jackson maps by property name; @JsonProperty, @JsonIgnore and @JsonInclude(NON_NULL) adjust it.

Two things worth configuring once and forgetting: register JavaTimeModule (Boot does) and set spring.jackson.serialization.write-dates-as-timestamps=false so instants serialise as ISO-8601 rather than epoch numbers — and use BigDecimal for money, since a double will eventually publish 0.30000000000000004 to a client.

Golden rules
  • Security is a filter, before the dispatcher. That is why @ControllerAdvice never sees auth failures.
  • Thin controllers. Map, validate, delegate, set the status code.
  • Never return an entity. DTO records: one line, and the schema stops being the contract.
  • LazyInitializationException during serialisation means the entity escaped the transaction.
  • ISO-8601 dates, BigDecimal money. Configure once.

“Cosa succede da quando arriva la richiesta HTTP a quando risponde il controller?”

Walk the chain in order — the order is the answer: “Tomcat accetta la connessione e passa la richiesta alla catena di filtri, dove sta Spring Security. Poi arriva al DispatcherServlet, che sceglie l’handler in base a path e metodo, risolve gli argomenti — @RequestBody lo deserializza Jackson — e invoca il controller. Il valore di ritorno passa per un HttpMessageConverter che lo serializza in JSON.” Then add the consequence: “È per questo che un errore di autenticazione non arriva mai al mio @ControllerAdvice: succede prima del dispatcher.”
