Spring Security, JWT and OAuth2

The filter chain, the difference between proving who you are and being allowed to do something, and the token decisions that are hard to reverse. Spring Security is famously confusing for one reason: people meet it as configuration to copy rather than as a chain of filters.

From the advert

Not in any advert. Absent from all six, present in every application any of them would have you build — and it is the area where a wrong answer in an interview is remembered.

It is a filter chain

🧒 Simple

Spring Security is a queue of small checks that every request passes through before reaching your code. Each one looks at the request and either handles it, changes it, or passes it on.

🎓 Professional

A single servlet filter delegates to an ordered chain of security filters. One of them extracts credentials and produces an Authentication; on success it is stored in the SecurityContext for the rest of the request; another filter later checks authorisation rules for the URL.

Two consequences worth stating in an interview. First, this happens before the dispatcher, so security failures never reach your @RestControllerAdvice — they need an AuthenticationEntryPoint (401) and an AccessDeniedHandler (403). Second, the SecurityContext is thread-local by default, so it does not propagate to a @Async method or a new thread unless you configure the strategy to inherit — a classic cause of “works in the controller, anonymous in the background job”.

Authentication versus authorisation

🧒 Simple

Authentication is proving who you are. Authorisation is whether you are allowed to do this particular thing. They are different questions and they fail differently: 401 means “I don’t know you”, 403 means “I know you and no”.

🎓 Professional

Authorise in two places for different reasons: URL rules (requestMatchers("/admin/**").hasRole("ADMIN")) are coarse and cheap; method security (@PreAuthorize) is where the real rules live, because “the owner of this order, or an admin” is a statement about a domain object and not about a path.

Note that hasRole("ADMIN") checks for the authority ROLE_ADMIN — the prefix is added for you, and forgetting that is the single most common reason a correctly-configured rule denies everyone. Use hasAuthority if you would rather be explicit.

Sessions, JWT and OAuth2

🧒 Simple

There are two ways to remember that someone logged in. Keep a session on the server and give the browser a key to it, or give the client a signed token that contains the facts and check the signature each time.

The token is convenient because the server keeps nothing. That is also its problem: you cannot take it back.

🎓 Professional

A JWT is signed, not encrypted — anyone can read the payload, so it must never carry secrets. Because validation is local, a JWT cannot be revoked before it expires. The standard mitigation is the pair used by the accounts service in this repository: a short-lived access token (minutes) plus a long-lived, stateful, revocable refresh token.

Choose deliberately. Sessions are simpler, revocable instantly, and need shared storage (Redis) once you scale out — which the Milano advert’s OpenShift deployment implies. JWTs scale without shared state and cost you revocation. For a browser client, storing a JWT in localStorage exposes it to XSS; an HttpOnly cookie avoids that and reintroduces CSRF, which is why CSRF protection is enabled by default and why disabling it should be a decision, not a step in a tutorial.

⚠ Trap

csrf().disable() appears in nearly every Spring Security example on the internet. It is correct for a stateless API authenticated by an Authorization header, and wrong the moment authentication rides on a cookie — because then the browser attaches it automatically and any site can make requests as your user. Know which case you are in.

Try it. Set this up, call the endpoint without a token, then with an expired one. The two failures are 401 and 401 — and neither reaches your @RestControllerAdvice, which is the point of the exercise.

@Configuration
@EnableMethodSecurity                       // enables @PreAuthorize
class SecurityConfig {
    @Bean
    SecurityFilterChain api(HttpSecurity http) throws Exception {
        return http
            .csrf(csrf -> csrf.disable())               // stateless API, bearer token: correct here
            .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .authorizeHttpRequests(a -> a
                .requestMatchers("/api/auth/**", "/actuator/health").permitAll()
                .requestMatchers("/api/admin/**").hasRole("ADMIN")
                .anyRequest().authenticated())
            .oauth2ResourceServer(o -> o.jwt(Customizer.withDefaults()))
            .exceptionHandling(e -> e
                .authenticationEntryPoint(this::unauthorised)   // 401 — advice never sees this
                .accessDeniedHandler(this::forbidden))          // 403
            .build();
    }
}

@PreAuthorize("hasRole('ADMIN') or #id == authentication.principal.orderId")
public OrderView get(Long id) { ... }
Golden rules
  • It is a filter chain, before the dispatcher. Security errors need their own handlers.
  • 401 is “who are you”, 403 is “not allowed”. Clients branch on the difference.
  • hasRole("ADMIN") looks for ROLE_ADMIN. The prefix is implicit.
  • A JWT is signed, not secret, and cannot be revoked. Short access token, revocable refresh token.
  • Disable CSRF only for header-authenticated stateless APIs. Cookie auth needs it.
  • The SecurityContext is thread-local. It does not follow you into @Async.

“Come gestirebbe l’autenticazione in una API REST? Sessione o JWT?”

Show the trade, then choose: “Con JWT il server non tiene stato, quindi scala bene dietro più istanze; il prezzo è che un token firmato non lo posso revocare prima della scadenza. Per questo uso un access token di pochi minuti più un refresh token long-lived, che invece è stateful e revocabile. Con la sessione ho revoca immediata ma mi serve uno storage condiviso, tipo Redis, appena scalo su più pod. Se il client è un browser tengo il token in un cookie HttpOnly per l’XSS, e a quel punto il CSRF torna a essere un problema reale.” That last sentence is the one that shows you have actually deployed something.
