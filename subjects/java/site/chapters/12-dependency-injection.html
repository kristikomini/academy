Dependency injection, done properly

Constructor or field injection, what a circular dependency really means, and why @Autowired on a private field — still the most common style in Italian codebases — is the one Spring’s own documentation tells you not to use.

From the advert

“ottima conoscenza di Spring/Spring Boot (API REST, dependency injection, configurazioni, Spring Data JPA)”. The advert names DI explicitly, which means the interviewer will too.

Constructor, setter, field

🧒 Simple

There are three ways to give a bean what it needs: through its constructor, through a setter method, or by Spring reaching in and setting a private field directly.

Use the constructor. It is the only one where the object cannot exist in a half-built state.

🎓 Professional

Constructor injection makes dependencies explicit and mandatory, allows final fields, and yields an object that is fully valid the moment it exists. Since Spring 4.3, a single constructor needs no @Autowired at all.

Field injection is concise and worse in three specific ways: the fields cannot be final; the class cannot be constructed in a plain unit test without reflection; and it hides the dependency count, so a class quietly acquires nine collaborators and nobody notices the design has gone. That last point is the real argument — a constructor with nine parameters is visibly wrong.

⚠ Trap

@Autowired on a private field is still the dominant style in older Italian codebases, so you will read a lot of it. Being able to say why it is discouraged — untestable without reflection, no final, hides the dependency count — is a better interview answer than simply asserting that constructor injection is “best practice”.

When more than one bean fits

🧒 Simple

If two classes implement the same interface and you ask for the interface, Spring does not know which one you meant, and start-up fails.

🎓 Professional

Resolution is by type first, then by name. When several candidates match you get NoUniqueBeanDefinitionException at start-up — loudly, which is the right time. Fix it with @Primary for the usual default, @Qualifier("name") at the injection point for a specific one, or by injecting a List<PaymentGateway> when you genuinely want all of them.

That last pattern is worth knowing: injecting a list of every implementation of a strategy interface, then selecting by a method on each, is how you remove a long switch from a service — and it is a very good answer to “how would you make this extensible?”.

Circular dependencies

🧒 Simple

If A needs B and B needs A, neither can be built first. With constructor injection Spring detects this and refuses to start.

🎓 Professional

Field and setter injection can sometimes resolve a cycle through partial initialisation; constructor injection cannot, and since Boot 2.6 cycles fail by default. That is an improvement, because a cycle is almost always a design message: two beans that need each other are one concept, or there is a third concept trying to get out.

@Lazy and spring.main.allow-circular-references=true will silence it. Treat both as a note to come back, not a fix — and say so in an interview, because “I’d extract the shared logic into a third bean” is the answer they want.

Golden rules
  • Constructor injection — final fields, no half-built objects, no reflection needed to test.
  • A single constructor needs no @Autowired since Spring 4.3.
  • A long constructor is a visible design smell. Field injection hides it.
  • @Primary for the default, @Qualifier for the exception, a List<T> when you want all of them.
  • A circular dependency is a design signal. @Lazy silences the message.

“Constructor injection o field injection? Perché?”

“Constructor injection. Mi permette campi final, quindi l’oggetto è immutabile e completamente valido appena costruito; posso istanziarlo in un test senza Spring e senza reflection; e soprattutto rende visibili le dipendenze — se un costruttore arriva a otto parametri, il problema di design si vede. Con @Autowired sui campi quella stessa classe sembra pulita e non lo è.” Adding that you still read a lot of field injection in existing code, and would not rewrite it for its own sake, keeps the answer pragmatic rather than dogmatic.
