Oracle, and the SQL you will actually meet

One advert names Oracle explicitly, and in this region that usually means a database older than the application in front of it, full of packages nobody will let you rewrite. Enough dialect to be useful, and enough plan-reading to know whether the problem is your query or your index.

From the advert

“Java 17 (Spring Boot), OpenShift/Kubernetes, Apache Kafka/RabbitMQ, MongoDB e Oracle DB”, from the Milano backend posting.

The dialect differences that bite

🧒 Simple

SQL is standard until it is not. Oracle has its own way of generating ids, its own date handling, and one famous quirk: an empty string and NULL are the same thing.

🎓 Professional

The ones that cause real bugs: Oracle treats '' as NULL, so WHERE name = '' matches nothing ever and a @NotBlank field can arrive back as null. Identifiers are case-insensitive unless quoted, and quoting them makes them permanently case-sensitive — which is how a table ends up needing quotes forever. NUMBER without precision maps awkwardly to Java types; be explicit and use BigDecimal for money.

Ids come from sequences, not auto-increment. With JPA, use SEQUENCE generation and make Hibernate’s allocationSize match the sequence’s INCREMENT BY, or you get either wasted ranges or collisions. Gaps in ids are normal and not a bug; anyone treating an id as a count has already made a mistake.

⚠ Trap

Pagination is the other classic. Oracle 12c+ supports OFFSET ... FETCH FIRST n ROWS ONLY, but older code — and plenty of codebases you will inherit — wraps queries in a ROWNUM subquery. ROWNUM is assigned before ORDER BY, so WHERE ROWNUM <= 10 ORDER BY created_at DESC returns ten arbitrary rows sorted, not the ten most recent. It looks right and is wrong.

Reading a plan

🧒 Simple

The database decides how to run your query. You can ask it to show you that plan — which tables it reads, in which order, and whether it uses an index.

🎓 Professional

Look for three things. A full table scan on a large table where you expected an index — often because a function or an implicit type conversion on the column made the index unusable (WHERE TRUNC(created_at) = ... defeats the index on created_at). Wildly wrong row estimates, which mean the statistics are stale. Nested loops over a large driving set, where a hash join would be right.

Indexes follow query shape: a composite index is usable left-to-right, so an index on (status, created_at) serves a filter on status and a filter on both, but not one on created_at alone. That leftmost-prefix rule is the single most useful indexing fact and is regularly asked.

PL/SQL and the code you inherit

🧒 Simple

In a lot of Italian companies, business rules live in the database as PL/SQL packages written years ago. You will not get to move them into Java. You will have to call them.

🎓 Professional

Call stored procedures with @Procedure in Spring Data or SimpleJdbcCall. Expect refcursors as out parameters, and expect the procedure to commit internally — which quietly breaks the transaction boundary you thought you had (chapter 25) and is worth checking before you rely on rollback.

The professional stance, and a good thing to say in an interview: logic in the database is not automatically wrong. It is often there because several applications share the rule and the database is the only common point. The problems are testability and version control, so the useful contribution is usually getting the packages into git and under some test, not campaigning to rewrite them in Java.

Golden rules
  • Oracle: '' is NULL. Comparisons to empty string match nothing.
  • Sequences, not auto-increment. Match allocationSize to INCREMENT BY; expect gaps.
  • ROWNUM is applied before ORDER BY. The naive top-N query is wrong.
  • A function on an indexed column disables the index.
  • Composite indexes work left-to-right. Leftmost prefix.
  • Database logic is not automatically wrong. Get it into git and under test.

“Questa query è lenta. Come procede?”

Structure the answer as a method, not a guess: “Prima guardo il piano di esecuzione. Cerco tre cose: un full table scan dove mi aspettavo un indice, stime di righe molto diverse dalla realtà — che di solito vuol dire statistiche vecchie — e nested loop su un set grande. Il caso più frequente è un indice reso inutilizzabile da una funzione sulla colonna, tipo un TRUNC sulla data. Poi verifico che l’indice copra davvero la query: un composito si usa da sinistra, quindi un indice su (status, created_at) non aiuta un filtro solo su created_at.”
