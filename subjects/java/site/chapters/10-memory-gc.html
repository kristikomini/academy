Memory, garbage collection and the heap

Nobody advertises this and everybody hits it: a JVM in a container with a memory limit and no thought given to the heap is an OOMKill waiting to happen. Enough GC to reason about a restart loop, and the two commands that turn a memory leak into a diagnosis.

From the advert

Not in any advert. It becomes urgent the moment chapter 41 puts your application in a container and chapter 42 gives that container a memory limit.

Heap, stack and the generations

🧒 Simple

Objects live on the heap. Method calls and local variables live on the stack, one per thread.

Most objects die young, so the heap is split: new objects go in one area that is collected often and cheaply, and survivors are moved to another that is collected rarely.

🎓 Professional

The generational hypothesis — most objects die young — is why the heap is divided into young (eden and survivor spaces) and old generations. Minor collections are frequent and cheap because they only trace the small live set in eden; objects surviving enough of them are promoted.

Know the two errors apart. StackOverflowError is the stack — unbounded recursion. OutOfMemoryError: Java heap space is the heap — either a real leak or a heap too small for the working set. OutOfMemoryError: Metaspace is a third thing entirely, usually class loaders leaking in an application server that redeploys without restarting (chapter 45).

The collectors, briefly

🧒 Simple

The garbage collector finds objects nothing points at any more and reclaims their memory. To do part of that work it must briefly stop your program — a pause.

Different collectors trade shorter pauses against total throughput.

🎓 Professional

G1 is the default since Java 9: region-based, aims at a pause-time target, a good default for almost everything. ZGC and Shenandoah are concurrent collectors with sub-millisecond pauses that scale to very large heaps, at some throughput cost. Serial is right for a small single-core container, and Boot’s own container images sometimes pick it for that reason.

The honest answer to “which collector should we use” is the default, until a measurement says otherwise. Tuning GC before you have a heap dump or a GC log is guessing, and G1 with a sensible heap size beats a badly tuned exotic collector every time.

The JVM in a container

🧒 Simple

A container has a memory limit. If the JVM does not know about it, it will happily try to use more, and the system will kill the container without any Java error at all.

🎓 Professional

Modern JVMs are container-aware and size the heap from the cgroup limit, but the default (about 25 % of available memory via MaxRAMPercentage) is conservative, and the heap is not the whole story: metaspace, thread stacks, code cache and direct buffers all live outside it. A pod killed with exit code 137 and no Java stack trace is the OOMKiller, not the JVM.

So set -XX:MaxRAMPercentage deliberately (60–75 % is typical), leave headroom for non-heap memory, and make the Kubernetes memory limit larger than the heap by a real margin. This is the single most common Java-on-Kubernetes production problem, and being able to name exit code 137 in an interview is worth a lot.

Try it. Get the two artefacts that turn guessing into diagnosis. Run these against a live process; jcmd ships with the JDK, which is why chapter 01 said to install one.

# what is this JVM actually using?
jcmd <pid> VM.native_memory summary      # needs -XX:NativeMemoryTracking=summary
jcmd <pid> GC.heap_info

# a heap dump, to find what is retaining memory
jcmd <pid> GC.heap_dump /tmp/heap.hprof
# then open it in Eclipse MAT: "Leak Suspects" answers most cases in one click

# what the container thinks it has
java -XX:+PrintFlagsFinal -version | grep -i maxheap
Golden rules
  • Most objects die young. That is why the heap is generational.
  • Use the default collector until a measurement disagrees. G1 is a good default.
  • Exit code 137 with no stack trace is the OOMKiller, not a Java error.
  • The heap is not the whole footprint. Metaspace, stacks, code cache and direct buffers sit outside it.
  • Set MaxRAMPercentage and leave headroom under the container limit.
  • Heap dump first, opinions second.
