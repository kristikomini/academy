Containers, and a JVM image that is not 700 MB

Putting a Spring application in a container is easy and doing it well is a set of small decisions: which base image, how many layers, and the memory flags without which the JVM and the container disagree about how much memory exists.

From the advert

“Java 17 (Spring Boot), OpenShift/Kubernetes, Apache Kafka/RabbitMQ, MongoDB e Oracle DB”. You cannot deploy to that cluster without this chapter.

Layers, and why the fat jar is the wrong unit

🧒 Simple

A container image is built in layers, and layers are cached. If you copy your whole application as one file, any change means re-sending all of it.

Your dependencies change rarely and your code changes constantly — so they should be in different layers.

🎓 Professional

COPY app.jar puts 60 MB of unchanged dependencies and 200 KB of your classes into one layer, so every build invalidates the lot. Spring Boot’s layered jars split the artefact into dependencies, snapshot dependencies, loader and application; copy them as separate layers and a code-only change pushes kilobytes.

Use a multi-stage build so the JDK, the source and the build cache stay out of the final image, which ships only a JRE and the application. If you would rather not maintain a Dockerfile, ./mvnw spring-boot:build-image produces a sensibly layered image with buildpacks and no Dockerfile at all — a good answer when asked how you containerise.

Try it. Build both and compare. The layered one rebuilds in a fraction of the time after a one-line code change, which is the whole point.

# multi-stage, layered
FROM eclipse-temurin:21-jdk-alpine AS build
WORKDIR /src
COPY .mvn .mvn
COPY mvnw pom.xml ./
RUN ./mvnw -B dependency:go-offline          # cached unless the pom changes
COPY src ./src
RUN ./mvnw -B -DskipTests package
RUN java -Djarmode=layertools -jar target/app.jar extract --destination /layers

FROM eclipse-temurin:21-jre-alpine
WORKDIR /app
COPY --from=build /layers/dependencies/ ./
COPY --from=build /layers/spring-boot-loader/ ./
COPY --from=build /layers/snapshot-dependencies/ ./
COPY --from=build /layers/application/ ./     # <- the only layer that usually changes
USER 1000
ENTRYPOINT ["java", "-XX:MaxRAMPercentage=70", "org.springframework.boot.loader.launch.JarLauncher"]

The memory flags

🧒 Simple

The container has a memory limit. The JVM must be told to respect it — and to leave room for the memory it uses outside the heap.

🎓 Professional

Modern JVMs read the cgroup limit and size the heap as a percentage of it, but the default is conservative and the heap is not the whole footprint: metaspace, thread stacks, code cache and direct buffers live outside it (chapter 10). Set -XX:MaxRAMPercentage deliberately — 60–75 % is typical — and make the container limit comfortably larger than the heap.

Get this wrong and the pod is killed with exit code 137 and no Java error at all, which is why people spend a day looking for a leak that is not there. It is the most common Java-on-Kubernetes production problem and it is a one-line fix.

⚠ Trap

-Xmx hardcoded in the image is worse than a percentage: the same image then behaves differently on a node with a different limit, and someone will change the Kubernetes limit without changing the flag. Percentage-based sizing keeps the two in step.

Base images and what not to ship

🧒 Simple

Every extra thing in the image is something that can have a vulnerability. Ship the smallest thing that runs your application, and do not run it as root.

🎓 Professional

Prefer a JRE over a JDK in the final stage, or build a custom runtime with jlink containing only the modules you use. Alpine images are small but use musl, which occasionally matters for native libraries; distroless removes the shell entirely, which is excellent for security and inconvenient the day you want to exec into a pod.

Always set a non-root USER — and note that OpenShift enforces this: it runs containers with an arbitrary non-root UID by default, so an image that assumes root or writes to a fixed home directory simply fails there. That is a specific, checkable detail for the Milano advert, and very few candidates know it.

Golden rules
  • Layer the jar. Dependencies and application code do not change at the same rate.
  • Multi-stage builds keep the JDK and source out of the shipped image.
  • MaxRAMPercentage, not -Xmx. The flag must follow the limit.
  • Exit code 137 is the OOMKiller. Leave headroom outside the heap.
  • Non-root USER, always — and OpenShift will enforce it for you.
  • spring-boot:build-image if you would rather not own a Dockerfile.

“Come containerizza un’applicazione Spring Boot?”

“Multi-stage build, così nell’immagine finale c’è solo un JRE e l’applicazione, e uso i layered jar di Boot: dipendenze e codice applicativo in layer separati, perché cambiano con frequenze diverse e così una modifica al codice ricostruisce pochi kilobyte. Imposto MaxRAMPercentage invece di -Xmx, così la heap segue il limite del container, e lascio margine per la memoria fuori dalla heap — altrimenti il pod viene killato con exit code 137 senza nessun errore Java. E utente non root, che su OpenShift è obbligatorio comunque.”
