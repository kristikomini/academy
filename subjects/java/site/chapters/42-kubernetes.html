Kubernetes and OpenShift

Enough Kubernetes to deploy a Spring service, debug it when it will not start, and answer the questions the Milano advert implies — plus the specific things OpenShift does differently, which is where candidates who have only used vanilla Kubernetes get caught.

From the advert

“Java 17 (Spring Boot), OpenShift/Kubernetes, Apache Kafka/RabbitMQ, MongoDB e Oracle DB”.

The objects you actually touch

🧒 Simple

A Pod is one running copy of your application. A Deployment keeps a given number of them alive and replaces them when you release. A Service is a stable name and address in front of them, because pods come and go.

🎓 Professional

Deployment → ReplicaSet → Pods, with a rolling update strategy that starts new pods before removing old ones. A Service gives a stable ClusterIP and DNS name and load-balances across ready pods; an Ingress routes external HTTP to Services. Configuration comes from ConfigMaps and Secrets, mounted as environment variables — which is why chapter 13’s relaxed binding (SPRING_DATASOURCE_URL) matters.

Set requests and limits deliberately. Requests decide scheduling; limits decide when you are throttled (CPU) or killed (memory). A pod with no memory limit can be evicted when the node is under pressure; one with a limit below what the JVM will use gets exit code 137 (chapter 41).

Probes, and how a rollout goes wrong

🧒 Simple

Kubernetes asks your application two questions: are you alive, and are you ready to receive traffic? Getting them the wrong way round is how a deploy takes the service down.

🎓 Professional

Liveness failing restarts the pod. Readiness failing removes it from the Service — no restart, just no traffic. Startup gives a slow starter time to boot before liveness begins, which JVM applications frequently need.

Boot exposes /actuator/health/liveness and /actuator/health/readiness for exactly this. The classic mistake is pointing liveness at a check that includes the database: the database has a blip, every pod fails liveness, Kubernetes restarts all of them at once, and a recoverable dependency problem becomes a full outage. Liveness should ask only “is this process wedged?”; dependencies belong in readiness.

⚠ Trap

No preStop hook and no graceful shutdown means in-flight requests are cut off on every deploy. Set server.shutdown=graceful and a terminationGracePeriodSeconds longer than your longest request, and give the endpoints controller a moment to stop sending traffic before the process exits.

What OpenShift adds

🧒 Simple

OpenShift is Kubernetes with more rules. The one that will catch you is that it refuses to run containers as root.

🎓 Professional

Security Context Constraints are the big difference: by default OpenShift runs your container with an arbitrary non-root UID from a per-namespace range. An image that assumes root, writes to a fixed home directory, or chowns a path at start-up simply fails. Build images with a group-writable working directory and no assumption about the UID.

Otherwise: Routes instead of (or alongside) Ingress, an integrated registry, and BuildConfigs / Source-to-Image if the cluster builds your images for you. Naming SCCs in an interview for this advert is a strong, specific signal — it is the thing people only know if they have actually deployed to OpenShift.

Try it. A minimal, correct deployment. The probe split and the resource block are the two parts that decide whether a bad afternoon is an incident.

apiVersion: apps/v1
kind: Deployment
metadata: { name: orders }
spec:
  replicas: 2
  template:
    spec:
      containers:
        - name: orders
          image: registry.example/orders:1.4.2
          ports: [{ containerPort: 8080 }]
          env:
            - name: SPRING_DATASOURCE_PASSWORD
              valueFrom: { secretKeyRef: { name: orders-db, key: password } }
          resources:
            requests: { cpu: 200m, memory: 512Mi }
            limits:   { cpu: "1",  memory: 1Gi }      # heap ~70% of this
          startupProbe:                                # JVMs boot slowly
            httpGet: { path: /actuator/health/readiness, port: 8080 }
            failureThreshold: 30
            periodSeconds: 5
          livenessProbe:                               # NO database check here
            httpGet: { path: /actuator/health/liveness, port: 8080 }
          readinessProbe:
            httpGet: { path: /actuator/health/readiness, port: 8080 }
      terminationGracePeriodSeconds: 40
Golden rules
  • Deployment, Service, ConfigMap, Secret. That is most of what you touch.
  • Liveness restarts; readiness removes from traffic. Never put a dependency check in liveness.
  • Startup probes exist because JVMs boot slowly.
  • Memory limit above the heap, with headroom. Requests schedule, limits kill.
  • Graceful shutdown, or every deploy drops in-flight requests.
  • OpenShift runs you as a random non-root UID. Build the image for that.

“Che differenza c’è tra liveness e readiness probe?”

“La liveness dice se il processo è bloccato: se fallisce, Kubernetes riavvia il pod. La readiness dice se può ricevere traffico: se fallisce, il pod viene tolto dal Service ma non riavviato. La cosa importante è non mettere il controllo del database nella liveness: se il database ha un problema momentaneo, tutti i pod falliscono la liveness, Kubernetes li riavvia tutti insieme e un disservizio recuperabile diventa un’interruzione totale. Le dipendenze stanno nella readiness. E per la JVM aggiungo una startup probe, perché l’avvio è lento.”
