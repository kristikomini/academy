Transactions, propagation and isolation

The highest-value fifteen minutes in this course. @Transactional works by a proxy, and every surprising thing it does follows from that — including the self-invocation trap, which fails silently and is in a very large share of Italian Spring codebases right now.

From the advert

Not in any advert. Present in every one of these jobs, and the self-invocation trap produces data that is quietly wrong rather than an error anyone sees.

It is a proxy, and that explains everything

🧒 Simple

When you mark a method @Transactional, Spring does not change your class. It wraps it in another object that opens a transaction, calls your method, and commits or rolls back.

Everyone who gets your bean from Spring gets the wrapper. But your own code, calling its own method, does not go through the wrapper.

🎓 Professional

Spring creates a proxy (JDK dynamic proxy for interfaces, CGLIB subclass otherwise) and the transactional behaviour lives entirely in it. So the annotation only takes effect when the call arrives from outside the bean.

Three consequences follow immediately. Self-invocation does nothing — this.doWork() from another method in the same class bypasses the proxy and runs with no transaction at all. private and final methods cannot be advised, because a subclass proxy cannot override them; the annotation is silently ignored. And @Transactional in @PostConstruct does nothing, because proxying happens later in the lifecycle (chapter 11).

⚠ Trap

This is the one to remember. A public process() that loops and calls this.saveOne(), where saveOne is annotated @Transactional(propagation = REQUIRES_NEW), does not get one transaction per item. It gets none, silently. Nothing throws; the data is simply committed under whatever transaction happened to be open, or none. Move the method to another bean, or inject a self-reference.

Try it. Run both. The second logs a transaction name per item; the first logs nothing at all — which is the failure, and it produces no error.

// BROKEN: self-invocation, the proxy is bypassed
@Service
public class ImportService {
    public void importAll(List<Row> rows) {
        for (Row r : rows) saveOne(r);          // plain Java call — no proxy, no transaction
    }
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void saveOne(Row r) { repo.save(map(r)); }
}

// FIXED: the call crosses a bean boundary, so it goes through the proxy
@Service
public class ImportService {
    private final RowWriter writer;
    ImportService(RowWriter writer) { this.writer = writer; }
    public void importAll(List<Row> rows) {
        for (Row r : rows) writer.saveOne(r);   // through the proxy — one transaction each
    }
}
@Service
class RowWriter {
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void saveOne(Row r) { repo.save(map(r)); }
}

Propagation, and rollback rules

🧒 Simple

If a transactional method calls another one, does the second join the first, or start its own? That choice is propagation.

🎓 Professional

REQUIRED is the default: join the current transaction or start one. REQUIRES_NEW suspends the current one and starts an independent transaction — the right choice for an audit record that must survive the caller rolling back. MANDATORY insists there already is one; SUPPORTS and NEVER are rarer.

The rollback rule catches people: Spring rolls back on unchecked exceptions and Error, and commits on checked exceptions unless you say rollbackFor. So a method declaring throws IOException that throws one will commit the work it did. Also: catching an exception inside a transactional method and not rethrowing means no rollback — and if an inner REQUIRED call already marked the transaction rollback-only, you get UnexpectedRollbackException at commit with no obvious cause.

Isolation, and the read anomalies

🧒 Simple

Two transactions running at once can see each other’s half-finished work. Isolation levels decide how much.

🎓 Professional

READ_COMMITTED — the default on Oracle, PostgreSQL and SQL Server — prevents dirty reads but allows non-repeatable reads and phantoms. REPEATABLE_READ is MySQL/InnoDB’s default. SERIALIZABLE prevents all three and costs the most contention.

In practice, do not reach for a higher isolation level; reach for optimistic locking. A @Version column makes a concurrent overwrite throw OptimisticLockException instead of silently winning, and it scales far better than locking rows. That is also exactly the mechanism the accounts service in this repository uses to reject a profile write built on a stale revision.

Golden rules
  • It is a proxy. Self-invocation, private and final methods get no transaction, silently.
  • Rollback on unchecked only. A checked exception commits unless you set rollbackFor.
  • Catching without rethrowing means no rollback.
  • REQUIRES_NEW for work that must survive the caller’s failure — audit rows, outbox entries.
  • Keep transactions short. They hold a connection (chapter 22) for their whole life.
  • @Version beats a higher isolation level for concurrent updates.

“Ho annotato il metodo con @Transactional ma non fa rollback. Perché?”

There are three usual causes and naming all three is the strong answer: “Primo: se la chiamata è interna alla stessa classe, il proxy viene bypassato e la transazione non esiste proprio — e non dà nessun errore. Secondo: Spring fa rollback solo sulle eccezioni unchecked; se il metodo lancia una checked exception committa, a meno di specificare rollbackFor. Terzo: se dentro il metodo catturo l’eccezione e non la rilancio, per Spring è andato tutto bene. Nel primo caso sposto il metodo in un altro bean, così la chiamata attraversa il proxy.”
