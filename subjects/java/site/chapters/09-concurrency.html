Threads, executors and virtual threads

Every Spring application is concurrent whether you thought about it or not — the container hands each request its own thread and they all share your singleton beans. This chapter is the memory model that makes that safe or unsafe, the executor framework, and what Loom changed.

From the advert

Not in any advert. And unavoidable: chapter 11 explains that beans are singletons shared across request threads, which turns a mutable field into a data race. This is the chapter that says why.

The memory model, and why volatile exists

🧒 Simple

Each processor core keeps its own copy of recently used values. If one thread changes something, another thread may keep reading its old copy — possibly forever.

So “thread safety” is not only about two threads writing at once. It is also about one thread never seeing what another wrote.

🎓 Professional

The Java Memory Model defines a happens-before relation: without one, there is no guarantee that a write in one thread is visible to a read in another, and the compiler and CPU are both free to reorder. synchronized and volatile establish it; a plain field does not.

volatile gives visibility and ordering but not atomicity: count++ on a volatile field is still read-modify-write and still loses updates. For a counter use AtomicLong or LongAdder; for anything compound, a lock. The classic demonstration is a boolean running flag polled in a loop — without volatile, the loop can be hoisted and never terminates.

⚠ Trap

Double-checked locking without volatile is the famous broken idiom: another thread can observe a non-null reference to an object whose constructor has not finished. It “works” in testing and fails under load on a different CPU architecture, which is the worst possible failure profile.

Executors, not threads

🧒 Simple

Do not create threads yourself. Hand tasks to an executor, which owns a pool of threads and runs your work on them.

🎓 Professional

ExecutorService separates task submission from execution policy, so the pool size, queue and rejection behaviour are configuration rather than scattered new Thread() calls. submit returns a Future; CompletableFuture composes them without blocking.

Size by workload: CPU-bound work wants roughly one thread per core, because more only adds context switching; I/O-bound work wants many more, since threads spend their time waiting. Prefer a bounded queue with an explicit rejection policy — an unbounded queue turns overload into an OutOfMemoryError instead of a fast, visible failure, which is the difference between shedding load and falling over.

Virtual threads, and what they undo

🧒 Simple

Threads used to be expensive, so you kept a small pool and were careful never to block them. Java 21 made threads cheap enough to have a million, so blocking one costs almost nothing.

🎓 Professional

A virtual thread is scheduled by the JVM onto a small pool of carrier threads. Blocking operations park the continuation instead of occupying an OS thread, so a thread-per-request model scales to very high concurrency — and the main argument for reactive programming (that blocking does not scale) largely evaporates.

In Spring Boot 3.2+ this is spring.threads.virtual.enabled=true. Two caveats worth knowing: synchronized blocks could pin a virtual thread to its carrier in early versions (ReentrantLock did not), and pooling virtual threads is pointless — the whole idea is that creating one is cheap, so you create one per task.

Golden rules
  • Visibility is not atomicity. volatile gives the first, not the second.
  • count++ is read-modify-write. Use an atomic, or a lock.
  • Executors, not new Thread(). Execution policy belongs in one place.
  • Bounded queues with an explicit rejection policy. Unbounded turns overload into OOM.
  • Virtual threads: one per task, never pooled.
  • Singleton beans are shared across request threads. Keep them stateless.

“Un @Service in Spring è thread-safe?”

The question is a trap only if you answer yes or no: “Il bean di default è un singleton, quindi la stessa istanza è condivisa da tutti i thread delle richieste. È thread-safe se non ha stato mutabile: se tengo un campo che modifico durante la richiesta, quello è condiviso e diventa una race condition. Quindi tengo i bean stateless e passo lo stato come parametro; se proprio mi serve stato condiviso uso qualcosa di concorrente, tipo ConcurrentHashMap o un AtomicLong, non un campo normale.”
