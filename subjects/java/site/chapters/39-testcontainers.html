Testcontainers and integration tests worth trusting

The real Oracle, the real Kafka, in Docker, per test run — instead of H2 and hope. This is the single highest-value testing change in a typical Spring codebase, and it removes an entire class of defect rather than catching instances of it.

From the advert

Not in any advert. The advert that names Oracle, MongoDB and Kafka in one line is describing a system whose integration points are the risk — and those are exactly what an embedded database cannot exercise.

Why H2 is not enough

🧒 Simple

Tests usually run against a small in-memory database because it is fast. But you do not deploy on that database, so the test proves something about a system you never ship.

🎓 Professional

H2 in Oracle-compatibility mode is an approximation. It differs on empty-string-versus-null, sequence behaviour, locking, dialect functions, JSON support and error codes — and it cannot run a stored procedure your production schema depends on. The failures land in production, where they are expensive, having been green in CI, where they were cheap.

Testcontainers starts the actual image — Oracle, PostgreSQL, Kafka, MongoDB, Redis — in Docker for the test run, and gives Spring the connection details. The cost is seconds of start-up; the benefit is that “passed in CI, failed in production” stops being a category.

⚠ Trap

Do not point your tests at a shared development database instead. Tests then pass or fail depending on data somebody else left behind, cannot run in parallel, and cannot run at all on a laptop with no VPN. A container per run is isolated, reproducible, and disposable — which is the whole argument.

Using it

🧒 Simple

You declare which image you want, and the library starts it before the tests and stops it after. Spring is told where to find it automatically.

🎓 Professional

@Testcontainers plus a @Container field; a static container is started once per class rather than once per test. @ServiceConnection (Boot 3.1+) removes the boilerplate entirely — Spring derives the datasource or broker properties from the container without a @DynamicPropertySource block.

Two practical notes. Set reuse.enable=true locally so the container survives between runs and the feedback loop stays fast — but never in CI, where isolation matters more. And apply your real migrations (chapter 29) against the container rather than letting Hibernate create the schema: then the test also verifies that the migrations work, which is the second bug this catches for free.

Try it. Run it once and watch Docker pull the image; run it again and watch it start in seconds. Then write a query using a dialect feature H2 does not have — it will now pass here and would have failed before.

@SpringBootTest
@Testcontainers
@AutoConfigureTestDatabase(replace = AutoConfigureTestDatabase.Replace.NONE)
class OrderRepositoryIT {

    @Container
    @ServiceConnection                          // Boot wires the datasource itself
    static PostgreSQLContainer<?> db = new PostgreSQLContainer<>("postgres:16-alpine");

    @Autowired OrderRepository repo;

    @Test
    void findsByStatusUsingARealDialect() {
        repo.save(new Order("ACME", Status.OPEN));
        assertThat(repo.findByStatus(Status.OPEN)).hasSize(1);
    }
}

Where they fit in the suite

🧒 Simple

These tests are slower, so you want fewer of them — but the few you have should cover the places where two systems meet, because that is where things actually break.

🎓 Professional

Keep the shape: many fast unit tests, a layer of slice tests (chapter 38), and a small number of container-backed integration tests covering the boundaries — repository queries against the real dialect, the migration chain applying cleanly, a produce-and-consume round trip through a real broker.

Separate them by naming convention (*IT for integration) so the fast suite stays fast on every save and the slower one runs on push. That separation is what keeps both from being abandoned — and being able to describe it is a good answer to “how is your test suite organised?”

Golden rules
  • Test against the database you deploy on. H2 is a different product.
  • A container per run beats a shared dev database. Isolated, reproducible, disposable.
  • @ServiceConnection removes the property plumbing.
  • Run your real migrations against the container. Then they are tested too.
  • Reuse locally, never in CI.
  • Name them *IT and run them separately. Fast suite stays fast.

H2 è comodo ma è un altro prodotto: cambia sul comportamento delle sequenze, sulla stringa vuota, sulle funzioni di dialetto, e non esegue le stored procedure.
