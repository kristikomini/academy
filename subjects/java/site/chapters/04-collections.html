Collections, and choosing the right one

ArrayList or LinkedList; HashMap or TreeMap; why contains on a list is slow and on a set is not. Choosing a collection is choosing a performance profile, and the interview question is always really about whether you know that.

From the advert

Not in any advert. The most-used part of the standard library, and the one candidates explain worst. Knowing that a HashMap is a bucket array explains its speed and its surprises at the same time.

List: ArrayList, and when not to

🧒 Simple

An ArrayList is a row of numbered boxes. Getting box 400 is instant. Inserting at the front means shifting everything along.

A LinkedList is a chain: each item points at the next. Inserting is cheap once you are there, but getting item 400 means walking 400 links.

🎓 Professional

ArrayList is a backing array with amortised O(1) append, O(1) indexed access and O(n) insertion or removal in the middle. LinkedList is a doubly-linked list: O(1) insert/remove given a node, O(n) indexed access.

The honest modern answer is that ArrayList almost always wins, including for many workloads the complexity table says it should not. Contiguous memory is cache-friendly; a linked list is a pointer chase with an object header per element. Reach for ArrayDeque rather than LinkedList when you genuinely need queue behaviour at both ends.

Map: buckets, and what O(1) is hiding

🧒 Simple

A HashMap turns the key into a number and uses it to pick a drawer. Looking something up means going straight to one drawer instead of searching all of them.

If many keys land in the same drawer, it gets slow — you are back to searching.

🎓 Professional

HashMap is an array of buckets indexed by a spread function of hashCode. Average O(1); worst case O(n) when hashes collide, mitigated since Java 8 by converting a heavily-collided bucket into a red-black tree, giving O(log n) instead. Resizing doubles the table and rehashes, so sizing a large map up front is a real optimisation.

LinkedHashMap preserves insertion order (and can do access order, which makes it a two-line LRU cache). TreeMap keeps keys sorted at O(log n) and needs a Comparable key or a Comparator. ConcurrentHashMap is the one to use across threads — not Hashtable, and not a synchronizedMap wrapper, which serialises every operation.

⚠ Trap

A plain HashMap written from several threads can, in older versions, spin forever during a concurrent resize — a hang with no exception and no log line. Even now, concurrent mutation produces lost updates and corrupted state. If more than one thread touches it, it is ConcurrentHashMap.

Choosing, in practice

🧒 Simple

Ask two questions. Do I need to look things up by a key? Then a map. Do I need to know whether something is already in there? Then a set — not a list.

🎓 Professional

The decision that actually matters in review is list.contains() inside a loop: that is O(n²) and it is the most common accidental quadratic in business code. A HashSet turns it into O(n).

Beyond that: List for ordered, duplicate-tolerant sequences; Set for membership and uniqueness; Map for keyed access; Deque for stacks and queues. Return List.of() / Map.of() for genuinely immutable data, and note they reject null — which is a feature that will surprise you once.

Golden rules
  • ArrayList unless proven otherwise. Cache locality beats the complexity table more often than people expect.
  • ArrayDeque, not LinkedList, when you need both ends.
  • contains in a loop over a List is O(n²). Use a Set.
  • ConcurrentHashMap for shared maps — not Hashtable, not a synchronized wrapper.
  • Size large maps up front. Resizing rehashes everything.

“ArrayList o LinkedList?”

The expected answer is the complexity table; the better answer adds why the table misleads: “In teoria LinkedList conviene per inserimenti e rimozioni frequenti in mezzo, e ArrayList per l’accesso per indice. In pratica uso quasi sempre ArrayList: la memoria contigua è molto più efficiente per la cache, e LinkedList ha un overhead per nodo. Se mi serve una coda con inserimenti a entrambe le estremità uso ArrayDeque.” Ending on the case where you would choose differently shows judgement rather than a memorised rule.
