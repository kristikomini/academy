Exceptions, checked and otherwise

Java is the only mainstream language that made some exceptions mandatory to declare, and the argument about whether that was right is still running. What matters for the job is narrower: which to throw, what never to catch, and why the empty catch block is the most expensive two lines in most codebases.

From the advert

Not in any advert. And the single most common source of production mysteries in Java: a failure that was turned into a wrong answer years ago by a catch (Exception e) {} nobody has read since.

Checked versus unchecked

🧒 Simple

Some exceptions Java forces you to deal with: either catch them, or declare that your method throws them. Those are checked. Others you can ignore at compile time — unchecked.

🎓 Professional

Exception and its subclasses are checked, except RuntimeException and its subclasses. Error is unchecked and signals conditions you are not meant to handle — OutOfMemoryError, StackOverflowError.

The intended distinction was recoverable versus programming error. In practice the checked experiment is widely regarded as a mistake: it forced throws clauses up entire call stacks, and its most common effect was to teach people to wrap and swallow. Every framework in these adverts — Spring included — uses unchecked exceptions throughout, and Spring specifically translates JDBC’s checked SQLException into an unchecked DataAccessException hierarchy. That translation is a good thing to be able to name.

Catching, wrapping and the empty block

🧒 Simple

Only catch an exception if you can actually do something about it. If you cannot, let it travel — something further up may be able to.

Never catch and do nothing. That converts a loud failure into a quiet wrong answer.

🎓 Professional

Catch narrowly, at the level that can act. When wrapping, always pass the cause — throw new OrderFailed("...", e) — because a wrapped exception without a cause deletes the stack trace that would have told you what happened.

Never catch Throwable or Error. Never swallow InterruptedException: either propagate it or restore the flag with Thread.currentThread().interrupt(), or you break cancellation for everything above you — which matters more now that virtual threads make interruption the normal shutdown path.

⚠ Trap

catch (Exception e) { log.error("error", e); return null; } is the empty catch block with a costume on. The caller gets a null it did not expect, the NullPointerException surfaces three layers away, and the log line that explains it is somewhere else entirely.

try-with-resources

🧒 Simple

Anything you open — a file, a connection, a stream — must be closed, even when something goes wrong. try-with-resources closes it for you.

🎓 Professional

Any AutoCloseable declared in the try(...) header is closed in reverse order, before the catch or finally runs. It also fixes a bug the old finally idiom had: if the body threw and close() also threw, the close exception replaced the real one. Here the close exception is attached as a suppressed exception and the original survives.

This is the mechanism behind connection-pool leaks in chapter 22: a Connection not closed on the exception path is not returned to the pool, and enough of those exhaust it.

Golden rules
  • Unchecked for programming errors, checked only when the caller can genuinely recover — and modern frameworks use unchecked throughout.
  • Catch only what you can act on, at the level that can act on it.
  • Always pass the cause when wrapping. Otherwise you delete the evidence.
  • Never swallow InterruptedException. Propagate, or restore the flag.
  • try-with-resources always, and know that it preserves the original exception.

“Checked o unchecked — quali usa nelle sue eccezioni?”

State a position and justify it; interviewers are testing judgement, not recall: “Uso unchecked quasi sempre. Le checked costringono a propagare throws per tutto lo stack e nella pratica portano la gente a fare catch vuoti, che è il caso peggiore. Definisco eccezioni di dominio che estendono RuntimeException, e le lascio salire fino a un @ControllerAdvice che le traduce in una risposta HTTP sensata. Lo stesso Spring fa così: trasforma SQLException, che è checked, nella gerarchia unchecked DataAccessException.” Naming that translation shows you have noticed how the framework you are being hired for actually behaves.
