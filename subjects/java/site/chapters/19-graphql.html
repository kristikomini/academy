GraphQL, and when it beats REST

One advert asks for REST or GraphQL. The interesting question is not the syntax but when the trade is worth taking — and being able to name what GraphQL makes harder is a much stronger answer than enthusiasm.

From the advert

“progettazione e implementazione di API REST/GraphQL per l’integrazione con sistemi industriali”. The slash is doing a lot of work in that line; expect to be asked which you would choose.

What it actually changes

🧒 Simple

With REST the server decides what each endpoint returns. With GraphQL the client asks for exactly the fields it wants, in one request, and gets exactly those.

🎓 Professional

A single endpoint, a typed schema, and a query language that lets the client select the shape. It removes two REST annoyances: over-fetching (the endpoint returns forty fields, the screen uses three) and under-fetching (the screen needs three round trips to assemble one view). The schema is introspectable, so tooling and typed clients are generated rather than written.

In Spring, spring-boot-starter-graphql maps schema fields to @QueryMapping and @SchemaMapping methods. The mental shift is that you are implementing resolvers per field, not handlers per URL.

What it makes harder

🧒 Simple

Because the client can ask for anything, you lose the things REST got for free: simple caching, easy rate limiting, and knowing in advance how expensive a request will be.

🎓 Professional

Four real costs. HTTP caching stops working — everything is one POST to one URL, so CDN and browser caching need replacing with application-level caching. Rate limiting by endpoint is meaningless; you need query cost analysis and depth limiting, or one client can request a deeply nested query that walks your whole database. N+1 gets worse, because resolvers are called per field per item — the fix is a DataLoader that batches within a request. Errors are 200s with an errors array, so monitoring built on status codes goes blind.

The honest rule: GraphQL pays off with many heterogeneous clients whose data needs differ and change — mobile plus web plus partners. For one front end talking to one backend, or for machine-to-machine integration with a fixed contract, REST is simpler and the operational tooling already exists.

⚠ Trap

Exposing your entity graph directly as the GraphQL schema recreates the coupling REST DTOs were meant to break, and hands clients the ability to traverse relationships you never meant to publish. The schema is a contract you design, not a projection of your tables.

Golden rules
  • GraphQL moves shape selection to the client. That is the whole idea.
  • It costs you HTTP caching, endpoint rate limiting and status-code monitoring.
  • N+1 is worse, not better. DataLoader batching is mandatory, not optional.
  • Worth it for many differing clients; overkill for one front end or a fixed integration contract.
  • Design the schema. Do not expose the entity graph.

“REST o GraphQL, per questo progetto?”

Ask what the clients look like, then commit: “Dipende da quanti client diversi ci sono. GraphQL conviene quando ho più client con esigenze di dati diverse — mobile, web, partner — perché ognuno chiede esattamente i campi che gli servono in una sola chiamata. Il prezzo è concreto: perdo il caching HTTP, il rate limiting per endpoint non ha più senso, e il problema N+1 peggiora, quindi serve un DataLoader che fa batching. Per una integrazione macchina-a-macchina con un contratto fisso resto su REST.” Naming the costs is what makes the recommendation credible.
