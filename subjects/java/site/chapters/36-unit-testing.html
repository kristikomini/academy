JUnit 5 and what a unit test is for

No advert asks for tests. Every technical assessment counts them, and a submission without any is read as a statement about how you work. This chapter is what a test is for, which decides everything about how you write it.

From the advert

Not in any advert. And the cheapest signal you control on a take-home exercise.

What a test is for

🧒 Simple

A test is not there to prove the code works today. You already know that — you just wrote it. It is there so that when someone changes it in eight months, they find out immediately if they broke something.

🎓 Professional

Tests are a regression net and a design pressure. The design pressure is the underrated half: code that is hard to test is usually hard to use, and the difficulty is almost always the same thing — hidden dependencies, static state, or a class doing three jobs. Constructor injection (chapter 12) exists partly for this reason.

The consequence for how you write them: a test should fail for exactly one reason, name that reason in its title, and read as a specification of behaviour rather than a transcript of implementation. throwsWhenQuantityIsZero is a sentence; test1 is not.

JUnit 5 in practice

🧒 Simple

Arrange the situation, do the thing, check the result. Three parts, in that order, with a blank line between them so the reader can see which is which.

🎓 Professional

@Test, @BeforeEach, @DisplayName for readable output, @ParameterizedTest with @CsvSource for the same assertion over many inputs, @Nested to group cases that share a setup. Use AssertJ — assertThat(x).isEqualTo(y) reads better than the JUnit assertions and produces far better failure messages, which is where the real time saving is.

Test behaviour, not implementation. A test that asserts a private method was called breaks every time you refactor and never once catches a bug — it is coupled to how, not to what. And test the edges: empty, null, zero, negative, boundary, duplicate. That is where the defects are, and where reviewers look.

⚠ Trap

Tests that share mutable state through a static field or a field on the test class pass alone and fail when the suite runs in a different order — or, worse, in parallel. JUnit 5 creates a new test instance per method precisely to discourage this; do not defeat it with static.

Try it. Write the parameterised version first, then try to express the same coverage as four separate tests. The first is the one you can extend in one line.

class MoneyTest {

    @Test
    @DisplayName("rejects a negative amount")
    void rejectsNegative() {
        assertThatThrownBy(() -> new Money(-1, "EUR"))
            .isInstanceOf(IllegalArgumentException.class);
    }

    @ParameterizedTest(name = "{0} cents formats as {1}")
    @CsvSource({ "0, 0.00", "5, 0.05", "1999, 19.99", "100000, 1000.00" })
    void formats(long cents, String expected) {
        assertThat(new Money(cents, "EUR").format()).isEqualTo(expected);
    }
}

Coverage, and what it does not tell you

🧒 Simple

Coverage measures which lines ran during the tests. It does not measure whether you checked that they did the right thing.

🎓 Professional

A test that executes a method and asserts nothing produces full coverage and zero information. Coverage is a floor detector: 20 % tells you something is wrong, 90 % tells you very little, and chasing 100 % produces tests written for the metric.

If you want to know whether the suite is any good, use mutation testing — PIT changes the code deliberately and checks that a test fails. A surviving mutant is a line nothing actually verifies. Mentioning that in an interview is unusual and lands well, because it shows you have thought about what the tests are worth rather than how many there are.

Golden rules
  • Tests are for the person who changes this in eight months.
  • Hard to test usually means hard to use. Listen to that.
  • One reason to fail, and say it in the name.
  • Test behaviour, not implementation. Asserting on private calls breaks on refactor and catches nothing.
  • Edges: empty, null, zero, negative, boundary, duplicate.
  • Coverage is a floor detector. Mutation testing is the real measure.

“La copertura la guardo per capire dove non c’è niente: sotto una certa soglia è un segnale, sopra dice poco, perché un test che esegue il metodo senza asserire nulla copre le righe e non verifica niente. Quello che mi interessa è se i test falliscono quando il comportamento cambia — per questo, dove ha senso, uso il mutation testing con PIT: modifica il codice apposta e controlla che qualche test si rompa. I mutanti sopravvissuti sono le righe che nessuno sta davvero verificando.”
