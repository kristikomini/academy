Spring Cloud: config, discovery, gateway

The advert names Spring Cloud alongside Spring Boot. Much of what it was built for has since been absorbed by Kubernetes, and knowing which parts is more useful than knowing all the annotations — because you will meet codebases that still use both.

From the advert

“Sviluppare microservizi in Java 11+ utilizzando Spring Boot e Spring Cloud”.

Config server and service discovery

🧒 Simple

With many services you need two things: one place to keep configuration, and a way for each service to find the others without hard-coded addresses.

🎓 Professional

Config Server centralises configuration in a git repository, so settings are versioned and auditable, and services fetch theirs at start-up. Eureka is a service registry: instances register themselves, clients ask the registry where a service is, and a client-side load balancer picks an instance.

Both solve problems Kubernetes also solves — ConfigMaps and Secrets for the first, DNS plus Services for the second (chapter 42). On Kubernetes, adding Eureka is usually duplicated machinery. The exception worth naming: Config Server’s git-backed history and refresh are genuinely nicer than ConfigMaps for audited environments, which is why banks and public administration keep it.

The gateway

🧒 Simple

Rather than exposing ten services to the outside world, you put one service in front that routes requests to the right one.

🎓 Professional

Spring Cloud Gateway handles routing, and the cross-cutting concerns you do not want repeated ten times: authentication, rate limiting, request logging, CORS, and response aggregation. It is reactive (built on WebFlux), which is worth knowing before you block a thread inside a filter.

This is the Spring Cloud component that survives on Kubernetes, because an Ingress routes but does not do token validation or per-client rate limiting. The trap is the gateway that starts making business decisions — once it knows which customers get which discount, it is a distributed monolith’s single point of coordination.

Calling another service

🧒 Simple

One service calls another over HTTP. The important part is not how you write the call — it is what happens when the other side is slow.

🎓 Professional

RestTemplate is in maintenance; the current choices are WebClient (reactive, works fine blocking) and Spring 6’s declarative @HttpExchange interfaces. OpenFeign remains common in existing Spring Cloud codebases — you declare an interface and it generates the client.

Always set timeouts. The default for several of these clients is effectively infinite, and a call with no timeout converts a slow dependency into an exhausted thread pool in your service, which is how one team’s incident becomes four teams’ incident. That is chapter 32, and it is the thing to say if you are only allowed one sentence about inter-service calls.

Try it. Two ways to call a service. Note that the timeouts are the only lines that matter for reliability — and the only ones people forget.

// Declarative, Spring 6+
@HttpExchange("/api/customers")
interface CustomerClient {
    @GetExchange("/{id}")
    CustomerDto byId(@PathVariable Long id);
}

@Bean
CustomerClient customerClient(WebClient.Builder builder) {
    var http = HttpClient.create()
        .responseTimeout(Duration.ofSeconds(2))                       // <- not optional
        .option(ChannelOption.CONNECT_TIMEOUT_MILLIS, 1000);
    var wc = builder.baseUrl("http://customers")
        .clientConnector(new ReactorClientHttpConnector(http)).build();
    return HttpServiceProxyFactory.builderFor(WebClientAdapter.create(wc))
        .build().createClient(CustomerClient.class);
}
Golden rules
  • Kubernetes has absorbed config and discovery. Do not add Eureka to a cluster that already does it.
  • Config Server’s git history still earns its place in audited environments.
  • The gateway is the piece that survives — auth, rate limiting, aggregation.
  • A gateway making business decisions is a coordination point. Keep it dumb.
  • Every inter-service call needs a timeout. The default is effectively forever.

“Usa Spring Cloud? Serve ancora, con Kubernetes?”

“In parte. Service discovery e configurazione distribuita le fa già Kubernetes, con i Service e le ConfigMap, quindi mettere Eureka sopra un cluster è duplicare la stessa cosa. Quello che resta utile è il gateway — validazione dei token, rate limiting, aggregazione — perché un Ingress instrada ma non fa quelle cose. E il Config Server ha ancora senso dove serve la storia in git delle configurazioni per motivi di audit. La cosa su cui non transigo, comunque, sono i timeout su ogni chiamata tra servizi.”
