The container: beans, scopes, lifecycle

Spring is often taught as a set of annotations to memorise. It is one idea with a lot of surface: an object that builds your objects and hands them to each other. Once the container is concrete, auto-configuration, proxies, transactions and the self-invocation trap all stop being magic and become consequences.

From the advert

“ottima conoscenza di Spring/Spring Boot (API REST, dependency injection, configurazioni, Spring Data JPA)”. Four of the six adverts name Spring. This chapter is the part underneath all four of those words.

What the container actually is

🧒 Simple

Normally your code creates the things it needs with new. In Spring you do not. You describe what exists, and a container builds everything at start-up and passes each object the things it asked for.

So by the time your code runs, all its collaborators are already there.

🎓 Professional

The ApplicationContext is a registry of bean definitions — recipes, not objects — which it uses to instantiate, wire, configure and manage a graph of singletons at start-up. Inversion of control: the framework calls you, and object construction is the framework’s job.

The consequence that matters for everything later: Spring does not usually hand you your own object. It hands you a proxy wrapping it, which is how @Transactional, @Cacheable, @Async and security annotations work at all. Chapter 25 is where forgetting that produces a silent bug.

Scopes, and the singleton trap

🧒 Simple

By default there is exactly one of each bean for the whole application, and every request shares it.

So if you store something about the current user in a field on a service, the next user gets it too.

🎓 Professional

The default scope is singleton — one instance per container, not per JVM and not per request. prototype creates a new instance per lookup; request and session exist in web contexts.

Because a singleton is shared across every request thread, mutable state in a @Service field is a data race, not a style question. This is the biggest single difference from the PHP model, where every request starts from nothing, and it is the bug most often introduced by developers arriving from that world. Keep beans stateless; pass state as arguments.

⚠ Trap

Injecting a prototype bean into a singleton does not do what people expect: the prototype is resolved once, at wiring time, and the singleton then holds that one instance forever. If you genuinely need a fresh one per call, inject an ObjectProvider and ask it each time.

The lifecycle, and where to hook it

🧒 Simple

A bean is built, then configured, then told “you are ready”, and much later told “we are shutting down”. You can run code at those last two moments.

🎓 Professional

Instantiate → populate dependencies → *Aware callbacks → BeanPostProcessor before-init → @PostConstruct → post-init (where proxies are usually created) → in service → @PreDestroy.

Two practical points. Do not do work in a constructor that needs other beans to be fully initialised — that is what @PostConstruct is for. And note that proxying happens after @PostConstruct, which is why calling a @Transactional method from inside @PostConstruct runs without a transaction. For application-ready work, prefer ApplicationReadyEvent.

Golden rules
  • The container owns construction. You describe beans; Spring builds the graph.
  • What you get injected is usually a proxy, not your object. Everything AOP-based depends on that.
  • Singleton is the default scope. Mutable fields on a service are shared across every request.
  • Prototype injected into a singleton is resolved once. Use ObjectProvider for per-call instances.
  • @PostConstruct runs before proxying. Transactions there do not exist.

“Cos’è lo scope di default di un bean, e perché è importante saperlo?”

Give the answer and immediately the consequence, because the consequence is what they are testing: “Singleton: una sola istanza per container, condivisa da tutte le richieste. La conseguenza pratica è che i bean devono essere stateless — se tengo stato mutabile in un campo di un @Service, quello stato è condiviso tra thread di richieste diverse, e diventa una race condition, non un problema di stile.” If they push, the prototype-in-singleton trap is the natural follow-up and few candidates raise it unprompted.
