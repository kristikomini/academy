MongoDB, and when a document store earns its place

The same advert asks for MongoDB and Oracle in one line, which is the honest state of most systems: a relational database for the things with invariants, and a document store for the things with none. The interesting part is the modelling decision, because it is the one you cannot undo cheaply.

From the advert

“Java 17 (Spring Boot), OpenShift/Kubernetes, Apache Kafka/RabbitMQ, MongoDB e Oracle DB”.

Documents, and the modelling decision

🧒 Simple

Instead of splitting an order across several tables, you store the whole thing as one document — the order and its lines together, in one place.

That makes reading it fast. It makes changing something shared between many documents slow.

🎓 Professional

The decision is embed or reference, and it follows the access pattern, not the domain. Embed when the child is owned by the parent, read with it, and bounded in size — order lines. Reference when the thing is shared, large, or independently updated — a customer referenced by ten thousand orders.

Get it wrong in the embedding direction and you get unbounded document growth (Mongo caps a document at 16 MB) plus duplicated data to update in many places. Get it wrong in the referencing direction and you have reinvented joins in application code, at which point you wanted a relational database. Model for the query you run most.

⚠ Trap

“Schemaless” means the database does not enforce a schema, not that your data has none. Two years of drift produces documents in four shapes, and the code that reads them accumulates a null check per shape. Use schema validation, or a strict mapping layer, and version your documents from the start.

Spring Data MongoDB

🧒 Simple

The repository style is the same as for JPA: declare an interface, get an implementation. The difference is what happens underneath.

🎓 Professional

MongoRepository gives derived queries and @Query with JSON filters; MongoTemplate is the lower-level API and where aggregation pipelines live. The important difference from JPA is that there is no persistence context and no dirty checking — changing an object does nothing until you explicitly save it, which is the opposite of chapter 23 and a genuine source of bugs when developers move between the two in one codebase.

Transactions exist (multi-document, since 4.0, on a replica set) but are not free and are not the default assumption. If your design needs multi-document transactions routinely, that is evidence the aggregate boundaries are wrong — or that this data belonged in Oracle.

When to use which

🧒 Simple

Use the relational database for things that must be consistent — money, stock, anything with rules that must always hold. Use the document store for things that are read as a whole and have no such rules.

🎓 Professional

A useful framing for an interview: relational databases are for invariants — foreign keys, unique constraints, transactions across tables. Document stores are for aggregates read as a unit with a flexible or evolving shape: event payloads, audit trails, product catalogues with per-category attributes, session and preference data.

The polyglot answer the advert implies is normal and worth stating plainly: orders and invoices in Oracle because they have invariants and an accountant; documents, telemetry and catalogue data in Mongo because they do not. What you should not claim is that one replaces the other.

Golden rules
  • Embed what is owned and bounded; reference what is shared. Model for the query you run most.
  • Schemaless is not schema-free. Validate, and version your documents.
  • No persistence context, no dirty checking. Nothing saves until you save it.
  • Needing multi-document transactions routinely is a modelling signal.
  • Relational for invariants, documents for aggregates. Both, on purpose.

“Quando userebbe MongoDB invece di un database relazionale?”

“Quando i dati si leggono come un blocco unico e non hanno invarianti forti da far rispettare al database: payload di eventi, log di audit, cataloghi con attributi diversi per categoria. Il relazionale lo tengo per le cose con vincoli — ordini, fatture, movimenti — dove mi servono chiavi esterne, unicità e transazioni. La decisione difficile in Mongo è embed o reference: incorporo quello che è posseduto dal documento e ha dimensione limitata, referenzio quello che è condiviso. Se mi accorgo di aver bisogno di transazioni su più documenti in continuazione, vuol dire che ho sbagliato i confini degli aggregati.”
