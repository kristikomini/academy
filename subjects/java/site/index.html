The shape of the job, in one picture

Almost every requirement in that list is one layer of a single request travelling through a system. Learning them in isolation is what makes them feel like a dozen unrelated subjects. They are not. They are floors of one building.

🧒 Simple

Think of an office building. Someone arrives at reception with a form. Reception (the ingress and Tomcat) checks they are allowed in and gives them to a clerk. Security (the filter chain) checks their badge before they get any further. The clerk (your @Service) knows the rules and decides what to do. The archive (Hibernate and the database) is where the paper actually lives, and the clerk never goes in personally — they fill in a request slip.

The one difference from a real office: the building has a fixed number of clerks (the connection pool). If every clerk is busy waiting on the archive, the queue at reception grows and nobody is doing anything wrong. That is most Java performance problems, in one sentence.

🎓 Professional

The adverts describe a standard layered Spring application: a client over an HTTP boundary, a servlet container with a security filter chain, a controller layer that does mapping and validation and nothing else, a service layer holding the business rules and the transaction boundary, and a persistence layer where an ORM turns objects into SQL.

Two properties of the JVM shape everything above. First, the process is long-lived and shared — unlike PHP, state in a singleton bean survives between requests, which is why a mutable field on a @Service is a data race rather than a style question. Second, requests are served by a bounded thread pool over a bounded connection pool, so the system does not degrade gracefully under load; it queues, and then it times out.

Chapters 09, 22 and 25 are the three that make the rest of the stack predictable. Read them before the framework chapters if you have the choice.

Beyond the advert

The requirements above are what companies write down. These twenty-five chapters are not in them — they are here because the same skills turn up again and again in Java work across Modena, Bologna and Milano, and because interviewers ask about them whether the posting mentioned them or not. Three of them — the transaction self-invocation trap, the N+1 problem and inheriting a Java EE application server — are large, unglamorous parts of the actual regional job that almost no course prepares anyone for, and four more are the rounds you have to pass before anyone reads your code at all.

Where this fits in the repository

This site is the tutorial layer. Underneath it sits the real thing: the deep course in course/ and a working reference application in src/, with the accounts service that backs the sign-in on this site in api/ — all written in Java, heavily commented, and meant to be read as much as run.

Real. Every chapter has questions, the viva deck is generated from the chapters’ own Golden rules, and all twenty-eight course modules are written. src/ is a Maven build that passes 89 tests: a framework-free domain with the order state machine and money as a value object, and a Spring Boot application over PostgreSQL with Flyway migrations, optimistic concurrency and a transactional outbox. api/ is the accounts service behind the sign-in above — fourteen endpoints, 27 tests, JWT with refresh-token rotation and a recovery code instead of an email address. It runs with no configuration at all. docs/BUILD-STATUS-java.md records exactly which parts are real, including what is deliberately missing.
