## 1. The idea

Java gives you two notions of sameness and does not make you choose between them
carefully. `==` compares references for objects and values for primitives. `equals`
compares whatever the class decided. Everything painful about equality in Java comes
from those two sentences being one keystroke apart.

### The contract, and why it is a contract

`Object.equals` has requirements the compiler does not enforce: reflexive, symmetric,
transitive, consistent, and `x.equals(null)` is false. `hashCode` has one more, and it
is the one that matters in practice:

> **Equal objects must have equal hash codes.**

Not the converse — unequal objects may share a hash code, and that is just a
collision. But breaking this direction breaks `HashMap`, `HashSet`, `distinct()`,
`groupingBy` and every library that hashes, and it breaks them *silently*. No
exception. The value goes into bucket A, the lookup goes to bucket B, and you get
`null`.

That is why the rule is "override them together". It is not tidiness. It is that one
without the other is a working object that loses data.

### The three wrapper traps

**`==` on wrappers.** `Integer` caches −128 to 127, so `Integer.valueOf(100) ==
Integer.valueOf(100)` is `true` and `Integer.valueOf(1000) == Integer.valueOf(1000)`
is `false`. Test data is small; production ids are not. This is the single most
reliable "looks right until it doesn't" bug in Java.

**Unboxing a null.** `int total = map.get(missingKey);` throws
`NullPointerException` on a line with no visible dereference. `Integer` → `int`
inserts an `intValue()` call you never wrote.

**Mutable keys.** If a field that feeds `hashCode` changes after the object is in a
`HashMap`, the entry is still in the old bucket. The map now contains something it
cannot find, including via `containsKey`. Keys must be immutable in the fields that
hash — which is not the same as "keys must be immutable", and knowing the difference
is worth saying.

### The one the JDK itself gets wrong for you

`BigDecimal.equals` compares **scale as well as value**. `10.0` and `10.00` are equal
numbers and unequal `BigDecimal`s. `compareTo` disagrees with `equals`, which
technically violates `Comparable`'s recommendation and definitely violates your
expectations.

This is not trivia — it reaches you through `record`. A record's generated `equals`
delegates to its components', so a naïve money record inherits the problem, and
`Money` in this codebase normalises scale in its compact constructor specifically to
fix it. One line, and `compareTo` and `equals` agree again.

### Value or entity — decide before you write `equals`

- **A value** has no identity. Ten euro is ten euro. Equality is by contents, and
  mutation makes no sense.
- **An entity** has identity and history. An order is the same order after it ships.
  Equality is by id, *never* by contents.

Getting this backwards produces two specific bugs. An entity with value equality
means two different orders that happen to match look like one. A value with identity
equality means the same amount of money fails to equal itself.

## 3. Do it

**Lab A — watch the cache boundary.**

```bash
jshell -q --execution local <<'EOF'
Integer a = 127, b = 127, c = 128, d = 128;
System.out.println((a == b) + " " + (c == d));        // true false
System.out.println(a.equals(b) + " " + c.equals(d));  // true true
EOF
```

Then ask the question that matters: which of those two lines would your test suite
have used? Small fixtures live inside the cache. Real ids do not.

**Lab B — break `hashCode` and lose an object.**

In a scratch class, write a mutable key whose `hashCode` uses a field, put it in a
`HashSet`, mutate the field, then call `contains`. It returns `false` for an object
the set is still holding — and iterating the set will show it there. A collection that
contains something it cannot find is the shape of this bug.

**Lab C — give `Order` value equality.**

Replace `Order.equals` with a contents comparison:

```java
return other instanceof Order that && id.equals(that.id)
    && status == that.status && lines.equals(that.lines);
```

Predict which of the two `Identity` tests fails before you run it. Most people say
`contentsDoNotMakeIdentity` — it is the one with "contents" in the name. It **passes**,
because the two orders it builds have different ids, so a contents comparison that
includes the id still separates them.

The one that fails is `identityIsTheIdNotTheState`: an order compared against the same
order after it was delivered. Same id, different status, no lines. That is the whole
point of an entity, and it is the assertion that a contents-based `equals` destroys.

Then find the second consequence, which no test catches: the order's hash now depends
on mutable state, so an order in a `HashSet` moves bucket every time it is modified and
the set stops being able to find it. Revert, and say out loud why an entity's `equals`
must depend only on immutable identity.

**Lab D — the `Set` that separates the two rules.**

Put two `Money.euro("10")` values and two `Order.draft(...)` orders into two `HashSet`s.
The money set has one element; the order set has two. Same collection, opposite
behaviour, both correct — because the objects are different kinds of thing.

1. **Never `==` on wrappers.** The −128…127 cache makes it look correct in tests.
2. **Override `equals` and `hashCode` together,** or hash-based collections silently lose elements.
3. **Keys must be immutable** in the fields that feed `hashCode`.
4. **Unboxing a null wrapper throws NPE** on a line with no visible dereference.
5. **Immutability is shallow.** Copy mutable components in and out.

## 5. Interview questions

**"Differenza fra `==` e `equals`?"** — `==` is reference identity for objects, value
comparison for primitives; `equals` is whatever the class defines, and `Object`'s
default is reference identity. Lead with the wrapper trap, because that is what they
are really asking: the `Integer` cache makes `==` appear to work for small numbers.

**"Se sovrascrivo `equals` devo sovrascrivere `hashCode`?"** — Yes. Equal objects must
have equal hash codes, or hash-based collections put them in different buckets and lose
them with no error. Then give the harder version: even when you write both, delegating
to a component whose `equals` is stricter than you expected — `BigDecimal` and its
scale — reintroduces the bug.

**"Cosa può andare storto con una chiave di una `HashMap`?"** — Mutating a field that
feeds `hashCode` after insertion. The entry stays in the old bucket, so the map holds
an object it cannot find. The precise rule is that keys must be immutable *in the
fields that hash*, which is weaker than "immutable" and worth stating precisely.

**"Perché `NullPointerException` su una riga senza `.`?"** — Auto-unboxing. `int x =
map.get(k)` inserts an `intValue()` call on a `null`. It is the reason to prefer
`Integer` in the signature when absence is possible, or `getOrDefault`.

**"Come implementa `equals` per un'entità?"** — By id only, never by contents, because
an entity is the same entity after its fields change. And by contents for a value
object, where there is no id to speak of. If the interviewer only asked for the code,
answer with the code and then say which of the two kinds you were writing — that is the
part that shows you have thought about it.
