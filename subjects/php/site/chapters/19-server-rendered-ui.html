Blade, Twig, Livewire and Inertia

Between "server renders HTML" and "we built an SPA and an API" there is a middle ground that most Italian PHP work actually lives in, and Laravel has invested heavily in it. Blade and Twig for the rendering, Livewire and Inertia for interactivity without a second application. Knowing why you would choose each is a more useful answer than knowing the syntax of all four.

From the advert

"Consolidata esperienza con il framework Laravel". Blade is not optional in that sentence — and the escaping rule below is the security half of the chapter, which is why this material shows up in a technical round more often than the templating.

Escaping by default, and the one that is not

🧒 Simple

Anything a user typed must be printed as text, never as markup. Blade and Twig do that for you automatically — except for one syntax that deliberately does not, and that syntax is where the security holes are.

🎓 Professional

{{ $x }} in Blade compiles to htmlspecialchars($x, ENT_QUOTES); {!! $x !!} does not escape at all. In Twig, {{ x }} escapes and {{ x|raw }} does not. Every stored XSS in a Laravel application is {!! !!} around something a user supplied — usually a rich-text field or an admin-editable block, added by someone who wanted their <br> to work (ch. 15).

The two rules that matter beyond the basic case. HTML escaping is not enough inside a <script> tag or a JavaScript attribute — the context is different, and the correct tool is @json($data) (which uses JSON_HEX_TAG and friends) rather than interpolating into JavaScript by hand. And never build a URL attribute from user input without validating the scheme: href="{{ $url }}" is escaped and still executes when $url starts with javascript:.

If you genuinely must render user HTML, sanitise it with an allow-list library such as HTML Purifier — server side, on the way in or the way out, never by regex.

⚠ Trap

A grep for {!! is a one-minute security audit of any Laravel codebase, and it almost always finds something. Do it on your own project before an interview: being able to say "ho fatto un grep di {!! !!} e ne ho tolti tre" is a concrete story about security that costs you a minute and sounds like experience, because it is.

Blade and Twig: inheritance, components, and the N+1 you cannot see

🧒 Simple

A template engine gives you a page skeleton that every page fills in, and small reusable pieces you can drop anywhere. It is the same idea as functions, applied to HTML.

🎓 Professional

Blade compiles to plain PHP and caches it, so the engine costs essentially nothing at run time. The modern style is components (<x-card>) rather than @include: they have an explicit prop contract and slots, which makes them composable in the way an include never was. @extends/@section is the older layout style you will still meet everywhere.

Twig, from Symfony, is stricter: a sandboxed syntax with no PHP in the template at all, which is an advantage when non-developers edit templates and a mild friction otherwise. Its inheritance and macros map one-to-one onto Blade’s ideas.

The performance trap is specific to templates and easy to miss: a lazy relation accessed inside a loop in the view is an N+1 (ch. 12). It does not appear in the controller, where you were looking, and Debugbar shows 400 queries on a page whose controller contains one. The fix is with() in the controller; the discipline is that a view should not be able to trigger a query at all — passing a view model rather than an Eloquent collection enforces that structurally.

Livewire: interactivity without leaving PHP

🧒 Simple

Livewire lets you write a component in PHP with a Blade template, and it keeps the page in sync by quietly sending the interaction to the server and swapping in the new HTML. It feels like an SPA and it is written like a controller.

🎓 Professional

A Livewire component is a PHP class with public properties and methods. Interactions trigger a small AJAX round trip; the component re-renders server-side and Livewire morphs the DOM difference into the page. Validation, authorisation and the model layer are the ones you already have — no duplicated rules, no API to build, no token handling.

The trade is a network round trip per interaction. That is fine for a form, a filtered table or a wizard; it is wrong for anything that must respond instantly, like drag-and-drop or a canvas. The usual pairing is Livewire for state and Alpine.js for purely local behaviour — opening a dropdown should not ask the server for permission. Livewire ships Alpine for exactly this reason.

Two things to know before using it in anger: public properties are serialised into the page and sent back, so putting a large collection or anything secret in one is both a payload and a security problem; and wire:model.live on a text input fires a request per keystroke unless you use .blur or .live.debounce.500ms, which is the most common cause of "Livewire is slow".

Try it. The whole component — search, filter, paginate — with no JavaScript, no API endpoint and no client-side state. Compare it with what the SPA version of the same feature would require.

<?php declare(strict_types=1);
// app/Livewire/OrderTable.php

namespace App\Livewire;

use App\Models\Order;
use Livewire\Component;
use Livewire\WithPagination;

final class OrderTable extends Component
{
    use WithPagination;

    public string $search = '';
    public string $status = '';

    // Reset to page 1 when the filter changes, or page 7 of the new filter is empty.
    public function updatingSearch(): void { $this->resetPage(); }
    public function updatingStatus(): void { $this->resetPage(); }

    public function render()
    {
        return view('livewire.order-table', [
            'orders' => Order::query()
                ->with('customer')                        // the N+1 fix lives here, not in the view
                ->when($this->search, fn ($q) => $q->where('reference', 'like', "%{$this->search}%"))
                ->when($this->status, fn ($q) => $q->where('status', $this->status))
                ->latest()
                ->paginate(20),
        ]);
    }
}

{{-- resources/views/livewire/order-table.blade.php --}}
<div>
  {{-- .live.debounce, not .live: one request per keystroke is the classic mistake --}}
  <input type="search" wire:model.live.debounce.400ms="search" placeholder="Cerca riferimento">

  <select wire:model.live="status">
    <option value="">Tutti gli stati</option>
    <option value="submitted">Da confermare</option>
    <option value="shipped">Spediti</option>
  </select>

  <table>
    <tbody>
      @forelse ($orders as $order)
        <tr wire:key="order-{{ $order->id }}">
          <td>{{ $order->reference }}</td>
          <td>{{ $order->customer->name }}</td>
          <td>{{ $order->status }}</td>
        </tr>
      @empty
        <tr><td colspan="3">Nessun ordine trovato.</td></tr>
      @endforelse
    </tbody>
  </table>

  {{ $orders->links() }}
</div>

Inertia: real Vue, no API

🧒 Simple

Inertia lets you write proper Vue or React components while your Laravel controllers keep returning pages. You get the SPA feel and the client-side framework, but you never build a separate API.

🎓 Professional

The controller returns Inertia::render('Orders/Index', [...]); the adapter delivers props to a Vue or React page component and swaps pages client-side without a full reload. Routing, authentication, authorisation and validation all stay in Laravel — session cookies, no tokens, and validation errors are handed back to the page as errors.

So the choice between the three, stated as a trade:

  • Blade when the page is mostly content and forms. Fastest to write, nothing to maintain.
  • Livewire when you want interactivity and your team is a PHP team. One language, one set of rules; costs a round trip per interaction.
  • Inertia when you genuinely want Vue or React components but do not need a public API. Full client-side power, no second application.
  • A real SPA plus an API when a mobile client or a third party consumes the same API, or the interaction is continuous and stateful (ch. 18).

The one thing Inertia does not give you by default is SEO, since the first paint is client-side unless you add SSR. For a gestionale behind a login that is irrelevant; for a public catalogue it is decisive.

Golden rules
  • {{ }} escapes, {!! !!} does not. Grep for the second one.
  • HTML escaping is not JavaScript escaping. @json() for data in a script.
  • Validate the scheme of any user-supplied URL. javascript: survives escaping.
  • A lazy relation in a loop in a view is an N+1 the controller does not show.
  • Livewire public properties travel to the browser and back. Nothing big, nothing secret.
  • .live.debounce, not .live, on a text input.
  • Build the API when someone else consumes it, not to make a web page interactive.

"Livewire, Inertia o una SPA? Come sceglie?"

Choose on consumers and interaction, not on taste: "Parto da due domande: c’è un altro consumatore dell’API — una app mobile, un partner — e quanto è continua l’interazione. Se l’API serve comunque a qualcun altro, faccio SPA più API. Se no, non costruisco una seconda applicazione solo per rendere interattiva una pagina: per tabelle, filtri e form uso Livewire, così validazione e autorizzazione restano una volta sola in PHP, e metto Alpine per le cose puramente locali come aprire un dropdown, che non devono fare un giro sul server. Se il team vuole davvero componenti Vue, Inertia dà quello senza l’API. L’unica cosa su cui sto attento è la SEO: con Inertia senza SSR il primo paint è lato client."
