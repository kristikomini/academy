Composer, autoloading and Docker

Two questions decide whether a new developer is productive on day one or day four: how does the code find its classes, and how do I start this project. Composer answers the first and Docker answers the second — and both are asked in interviews as small factual questions (install or update? what is the lock file for?) that reveal immediately whether you have operated them or only run them.

From the advert

"Gradita conoscenza di Docker". Gradita, so this is a differentiator. The practical version of the requirement is: can you get the project running without occupying a senior developer for a day.

PSR-4 autoloading, and the optimisation for production

🧒 Simple

You never write require any more. When PHP meets a class it does not know, it asks the autoloader, which turns the class name into a file path and includes it. The rule is simply that the namespace mirrors the folders.

🎓 Professional

PSR-4 maps a namespace prefix to a directory: "App\\": "src/" means App\Domain\Order lives at src/Domain/Order.php. It is case-sensitive on Linux and not on Windows or macOS, which is the origin of the classic "works locally, class not found in production" — a file named order.php for a class named Order.

Underneath, spl_autoload_register() is the mechanism; Composer generates the registered closure. Three flags matter at deploy time:

  • --optimize-autoloader (-o) — converts PSR-4 lookups into a static class map, removing a filesystem check per class. Always in production.
  • --classmap-authoritative — the map is the truth; anything not in it is not found, with no filesystem fallback. Fastest, and it breaks if anything generates classes at runtime.
  • --no-dev — leaves PHPUnit and friends off the server entirely.

Also know autoload.files (loaded unconditionally — for helper functions, which cannot be autoloaded) and autoload-dev for test-only namespaces, which is what stops your factories shipping to production.

Semver, the lock file, and install versus update

🧒 Simple

composer.json says what you want, roughly. composer.lock records exactly what you got. On your machine you may change your mind; on a server you install exactly what the lock file says, so everyone runs identical code.

🎓 Professional

Semantic versioning: MAJOR.MINOR.PATCH — breaking, feature, fix. The constraint operators are worth being exact about, because guessing here causes real incidents: ^1.2.3 allows anything below 2.0.0 (the sane default); ~1.2.3 allows below 1.3.0 (patch only); 1.2.* the same idea; >=1.0 is an open invitation to a breaking change and should almost never appear.

install reads the lock file; update rewrites it. So: update on your machine, deliberately, reviewing the diff; install in CI and on every server. A server running composer update is a server that can silently deploy a different dependency tree from the one you tested — this is a genuine outage cause and a favourite interview question.

Commit the lock file. Always for an application. For a library, do not — the library must be resolvable against many dependency trees, and its lock file is meaningless to consumers.

Two more worth naming: composer audit for known vulnerabilities, and --no-scripts when you want an install that cannot execute arbitrary code from a package — supply chain is a real risk vector, and PHP has had incidents.

⚠ Trap

composer update as a fix for "it does not work". It resolves everything to the newest versions the constraints allow, changes fifty packages, and now the problem is different and much larger — and it happens most often under time pressure, when you can least afford it. To update one package: composer update vendor/package --with-dependencies. To debug a resolution problem: composer why-not vendor/package 2.0, which tells you exactly what is holding it back.

Docker: images, layers and the one that matters for PHP

🧒 Simple

An image is a frozen filesystem with your application and everything it needs. A container is a running copy of it. The point is that it runs the same on your laptop, on your colleague’s, and on the server.

🎓 Professional

An image is built in layers, one per instruction, and each is cached. The ordering rule that follows is the single most useful Docker fact for PHP: copy composer.json and composer.lock and install dependencies before copying your source. Application code changes on every commit; dependencies change rarely. Get the order wrong and every build reinstalls the vendor directory from scratch, turning a 20-second build into three minutes — on every push, for everyone.

Multi-stage builds keep the toolchain out of the final image: one stage with Composer and Node to build, one runtime stage that copies only the result. Smaller image, faster deploys, and a much smaller attack surface, because a compiler in a production container is a gift to anyone who gets a shell.

Other things that are specifically PHP problems:

  • Extensions. Use the docker-php-ext-install helpers (and install-php-extensions from mlocati, which handles the system libraries). A missing pdo_mysql or intl is the classic first failure.
  • Bind-mount performance on macOS and Windows is poor, and a Laravel application doing thousands of file stats per request feels it. :cached, or a native volume for vendor/, or use the WSL2 filesystem on Windows rather than mounting from /mnt/c.
  • Permissions on Linux. The container writes as its own uid and your host user cannot delete storage/logs. Pass your uid at build time.
  • Logs to stdout, one process per container, config from environment variables (ch. 25, 29).
  • Never bake secrets into an image. They persist in the layer history even if a later layer deletes them.

Try it. A multi-stage Dockerfile with the layer order that matters. Build it twice, changing one line of PHP in between, and watch the second build skip the whole Composer step.

# ---------- stage 1: build ----------
FROM composer:2 AS vendor

WORKDIR /app
# Only the manifests first. This layer is cached until a DEPENDENCY changes,
# not every time you edit a controller — the whole point of the ordering.
COPY composer.json composer.lock ./
RUN composer install \
      --no-dev --no-scripts --no-autoloader \
      --prefer-dist --no-interaction

# Now the source, and only now generate the optimised autoloader.
COPY . .
RUN composer dump-autoload --optimize --classmap-authoritative

# ---------- stage 2: runtime ----------
FROM php:8.3-fpm-alpine

# Extensions the application actually needs — a missing one is the classic first failure.
RUN apk add --no-cache icu-dev libzip-dev \
 && docker-php-ext-install pdo_mysql intl zip opcache

# Production OPcache: validate_timestamps=0 means a deploy MUST reload FPM (ch. 01, 30).
COPY docker/php/opcache.ini /usr/local/etc/php/conf.d/opcache.ini

WORKDIR /var/www/html
COPY --from=vendor /app .

# Do not run as root. One process per container; logs go to stdout.
RUN chown -R www-data:www-data storage bootstrap/cache
USER www-data

EXPOSE 9000
CMD ["php-fpm"]

Compose, and the alternatives worth knowing

🧒 Simple

A real project is not one container: PHP, a web server, a database, Redis, a queue worker. Compose describes all of them in one file so that docker compose up starts the whole thing.

🎓 Professional

Containers reach each other by service name on the compose network, which is the detail that confuses newcomers: the database host is mysql, not 127.0.0.1, because localhost inside a container is that container. Named volumes for database data (a bind mount for MySQL data is slow and fragile); depends_on with a healthcheck, because "started" is not "ready to accept connections" and a migration that runs too early fails intermittently in CI.

In the Laravel world know the three: Sail (an opinionated Compose wrapper, excellent for getting started), DDEV (widely used in Italian agencies, especially for WordPress and Drupal work, and it handles TLS and multiple projects gracefully), and Lando. All of them are Docker with the sharp edges filed off.

The thing worth being able to say in an interview: the goal is a README whose setup section is two commands. If a new colleague can clone and run in ten minutes, the containerisation did its job; if it takes a day and a call with a senior developer, it did not, whatever the technology.

Golden rules
  • PSR-4 is case-sensitive where it matters. Filename equals class name.
  • update locally, install everywhere else.
  • Commit the lock file for an application, never for a library.
  • ^ for constraints; >= is an invitation to a breaking change.
  • Update one package with --with-dependencies, not the world.
  • Manifests before source in the Dockerfile. That is the build cache.
  • Multi-stage: no compiler in the runtime image.
  • No secrets in layers. They survive deletion.
  • Two commands in the README, or it is not really containerised.

"Perché si committa il composer.lock?"

A small question that is really about deployment discipline: "Perché il composer.json dice cosa voglio, ma il lock dice esattamente cosa ho testato: versioni precise di tutto l’albero delle dipendenze. Committandolo, in CI e in produzione giro composer install e ottengo esattamente quelle versioni, quindi il codice che va in produzione è quello provato. Se sul server girasse update, potrebbe risolvere una minor version diversa da quella testata e mi troverei un bug che in locale non esiste. update lo faccio solo io, di proposito, guardando il diff. Per una libreria invece il lock non si committa, perché deve poter essere risolta dentro alberi di dipendenze diversi."
