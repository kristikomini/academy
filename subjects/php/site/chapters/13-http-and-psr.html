HTTP, REST, PSR-7 and PSR-15

HTTP is the one protocol every web developer is assumed to know and almost nobody is taught. The questions that separate candidates are not "what is GET" — they are which methods are idempotent, which status code you return when validation fails, and why that distinction matters to the client.

From the advert

"Sviluppo e integrazione di API REST". Note integrazione: you will be consuming other people's APIs as often as writing your own, and their retry behaviour becomes your problem.

Methods, safety and idempotency

🧒 Simple

Some requests only look at things — asking twice changes nothing. Some replace a thing with an exact copy of what you sent — doing that twice also changes nothing. But "add a new one" done twice gives you two.

🎓 Professional

Safe means it does not change state: GET, HEAD, OPTIONS. Idempotent means doing it N times has the same effect as doing it once: the safe methods plus PUT and DELETE. POST and PATCH are neither.

This is not trivia. It decides what a client, a proxy or a mobile app on a flaky connection may safely retry. A retried PUT is harmless; a retried POST creates a second order. That is why payment and order-creation endpoints take an idempotency key — the client supplies a unique id, you store it, and a repeat with the same key returns the original result instead of doing the work again.

⚠ Trap

A GET that changes state — /orders/5/delete — is broken in a way that bites later, not now. Crawlers, browser prefetch and link previews follow GETs. Somebody's antivirus or mail scanner will eventually walk your admin panel and delete everything, and the logs will show it came from the user.

Status codes that actually differ

🧒 Simple

The number tells the caller whose fault it is and what to do next. 2xx: fine. 3xx: look somewhere else. 4xx: you got it wrong, do not just try again. 5xx: we got it wrong, trying again might work.

🎓 Professional

The ones that get confused, and the distinction that matters to a client:

  • 200 vs 201 — 201 for a created resource, with a Location header pointing at it. 204 for success with no body.
  • 400 vs 422 — 400 means the request was malformed (broken JSON). 422 means it parsed fine but failed your business rules. Laravel returns 422 for validation, and clients rely on it to know they can render field errors.
  • 401 vs 403 — 401 is "I do not know who you are" (log in). 403 is "I know exactly who you are and the answer is no" (do not retry with the same credentials).
  • 404 vs 410 — 404 might come back; 410 is permanently gone.
  • 409 — a conflict with current state. The correct answer to a stale optimistic-concurrency version.
  • 429 — rate limited, and send Retry-After so the client knows how long to wait.

Errors are a payload too. RFC 9457 (formerly 7807) gives you a standard shape, so clients parse errors the same way across every service instead of guessing.

HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json

{
  "type":     "https://bottega.example/problems/validation",
  "title":    "The request could not be processed.",
  "status":   422,
  "detail":   "One or more fields failed validation.",
  "instance": "/api/orders",
  "traceId":  "01J9ZC7Q3K2M8V",
  "errors": {
    "lines":            ["At least one line is required."],
    "lines.0.quantity": ["Quantity must be at least 1."]
  }
}

The traceId is the detail that pays for itself: a customer sends you that string and you find their exact request in the logs, without asking what time it was.

What REST actually asks of you

🧒 Simple

Name things, not actions. The address says what you are talking about; the method says what you want done to it. So it is "orders, number five" plus "delete", not "delete-order-five".

🎓 Professional

Resources are nouns and URLs identify them; the method carries the verb. Plural collections, ids as path segments, filtering and pagination as query parameters. So GET /orders?status=shipped&page=2, and POST /orders/5/cancel when an operation genuinely is not CRUD — which is allowed, and better than contorting the model to pretend it is.

Statelessness is the load-bearing constraint: every request carries everything needed to understand it, so any server can answer any request. That is what lets you put three PHP-FPM boxes behind a load balancer without sticky sessions — and it happens to be exactly how PHP already works.

PSR-7 and PSR-15

🧒 Simple

Everyone agreed on one shape for "a request" and "a response", so a piece of code written for one framework can be dropped into another without translation.

🎓 Professional

PSR-7 standardises HTTP message objects, and makes them immutable: withHeader() returns a new instance rather than mutating. That is the detail people get wrong — calling $response->withHeader(...) and discarding the result changes nothing, and it fails silently.

PSR-15 defines the middleware interface on top of it: process(Request, RequestHandlerInterface): Response. Because both are standards, a rate limiter written for Slim works in Mezzio unchanged. Laravel uses its own Illuminate objects rather than PSR-7, which is worth knowing when you are choosing a package. 

<?php declare(strict_types=1);

use Psr\Http\Message\{ResponseInterface, ServerRequestInterface};
use Psr\Http\Server\{MiddlewareInterface, RequestHandlerInterface};

final class CorrelationId implements MiddlewareInterface
{
    public function process(ServerRequestInterface $request, RequestHandlerInterface $handler): ResponseInterface
    {
        $id = $request->getHeaderLine('X-Correlation-Id') ?: bin2hex(random_bytes(8));

        // Immutable: withAttribute() RETURNS a new request. Reassign, or it is lost.
        $request = $request->withAttribute('correlationId', $id);

        $response = $handler->handle($request);

        return $response->withHeader('X-Correlation-Id', $id);   // also returns a new object
    }
}
Golden rules
  • Safe means no state change; idempotent means repeating is harmless. It decides what may be retried.
  • POST is not idempotent — use an idempotency key on anything that takes money or creates an order.
  • Never change state on a GET. Something will crawl it.
  • 400 is malformed, 422 is invalid; 401 is who are you, 403 is no.
  • 409 for a stale version, and return the current state with it.
  • Errors need a schema too. RFC 9457 plus a trace id.
  • PSR-7 messages are immutable. with*() returns a new object; reassign it.

"Che differenza c'è tra PUT e PATCH? E tra 401 e 403?"

Two pairs, one sentence each, with the consequence attached: "PUT sostituisce la risorsa per intero ed è idempotente: ripeterlo lascia lo stesso stato. PATCH applica una modifica parziale e in generale non lo è. La conseguenza pratica è che un client può ritentare una PUT dopo un timeout, una POST no — per quella serve una idempotency key. Sul 401 e 403: 401 significa che non so chi sei, quindi autenticati; 403 significa che so chi sei e la risposta è no, quindi non ritentare con le stesse credenziali."
