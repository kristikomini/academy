Arrays, SPL and the array_* family

PHP has one collection type and calls it an array, which is a lie that explains most of its behaviour. It is an ordered hash map: that single fact accounts for why keys survive array_filter, why in_array on 100 000 items is slow and isset on the same data is instant, and why passing a big array to a function costs nothing until you write to it.

From the advert

Not in any advert. It is the most-used data structure in PHP and the one candidates explain worst. Knowing it is a hash map explains its performance and its surprises in the same sentence — and "ottimizzazione di strutture dati" (ch. 11) is a line that does appear.

The ordered hash map

🧒 Simple

A PHP array is really a dictionary that also remembers the order you put things in. A "list" is just a dictionary whose keys happen to be 0, 1, 2 — which is why deleting an item leaves a gap where a real list would close up.

🎓 Professional

One type, two roles. Keys are int or string only; anything else is coerced, and the coercions matter: "8" becomes 8, true becomes 1, null becomes "", and 1.9 is truncated to 1. Insertion order is preserved and is part of the contract.

Since PHP 8.1 array_is_list() asks the question directly: are the keys exactly 0..n-1 in order? It matters because json_encode() emits a JSON array for a list and a JSON object for anything else — so an array_filter that removed the second element silently turns your API response from [...] into {"0":...,"2":...} and the front end breaks. That is the single most common PHP-to-JSON bug in existence.

⚠ Trap

array_filter and unset() preserve keys. array_map preserves them too (with one callback and one array). If the result is going to json_encode, wrap it in array_values() — every time, as a reflex. 

<?php
$refs = ['ORD-1', 'ORD-2', 'ORD-3'];
$kept = array_filter($refs, fn ($r) => $r !== 'ORD-2');

echo json_encode($kept), PHP_EOL;                  // {"0":"ORD-1","2":"ORD-3"}  ← an object
echo json_encode(array_values($kept)), PHP_EOL;    // ["ORD-1","ORD-3"]          ← what you meant
var_dump(array_is_list($kept));                    // bool(false)

Copy-on-write, and the & that undoes it

🧒 Simple

Passing a huge array to a function does not copy it. PHP hands over the same array and only makes a real copy at the moment somebody writes to it. So reading is free; writing is where the cost lives.

🎓 Professional

Arrays are value types with copy-on-write. Assignment and by-value parameter passing bump a refcount; the duplication happens on the first write while the count is above one. So function f(array $rows) on a million-row array is cheap unless f modifies it.

This is why &$array for "performance" is usually a mistake — it buys nothing over copy-on-write for read-only use and costs you a function that can now mutate its caller’s data. There is one real exception: modifying a large array in place inside a loop, where you want to avoid a copy per iteration.

⚠ Trap

The dangling reference after foreach ($a as &$v). The reference outlives the loop, so the next foreach reusing $v writes into the last element — producing an array whose final item is a duplicate of the second-to-last. It has been catching people for twenty years. unset($v) immediately after the loop, or do not take the reference. 

<?php
$a = [1, 2, 3];
foreach ($a as &$v) { $v *= 10; }
// unset($v);   ← the fix
foreach ($a as $v) { }
print_r($a);    // [10, 20, 20]  — not [10, 20, 30]

in_array versus isset: the O(n) you can see

🧒 Simple

Looking for a value means checking every item one by one. Looking for a key is instant, however big the array is. If you are searching a lot, make the thing you search for into the key.

🎓 Professional

in_array() and array_search() are O(n) linear scans. isset($h[$k]) and array_key_exists() are O(1) hash lookups. Inside a loop over m items that is O(n×m) versus O(m) — the difference between 40 seconds and instant on a reconciliation job, and it is the most common self-inflicted performance bug in import code.

Flip the array once with array_flip() or build a keyed index with array_column($rows, null, 'id'), then look up by key. Also: in_array() without the third argument uses loose comparison, so in_array(0, ['a','b']) was true before PHP 8 — always pass strict: true.

isset() versus array_key_exists(): isset returns false for a key that exists with a null value. When "present but null" is meaningful — a nullable column, a deliberately unset config — you need array_key_exists().

Try it. The two loops do the same work. Time them and the hash map argument stops being theoretical.

<?php declare(strict_types=1);

$haystack = range(1, 50_000);
$needles  = range(1, 5_000);

$t = microtime(true);
$found = 0;
foreach ($needles as $n) { if (in_array($n, $haystack, strict: true)) { $found++; } }
printf("in_array   %6.3fs (%d)%s", microtime(true) - $t, $found, PHP_EOL);

$index = array_flip($haystack);        // pay O(n) once
$t = microtime(true);
$found = 0;
foreach ($needles as $n) { if (isset($index[$n])) { $found++; } }
printf("isset      %6.3fs (%d)%s", microtime(true) - $t, $found, PHP_EOL);

The array_* family worth memorising

🧒 Simple

There are hundreds of array functions and you need about twelve. The awkward part is that they do not agree on argument order or on what they do with keys, so the ones you use daily are worth learning properly rather than guessing.

🎓 Professional
  • array_map — callback first. Pass several arrays and it zips them, and then keys are discarded. Pass null as the callback and it zips into tuples.
  • array_filter — array first. With no callback it drops every falsy value, which quietly removes 0 and ''. Third argument ARRAY_FILTER_USE_KEY or USE_BOTH.
  • array_reduce — the one people avoid; ideal for summing money or folding into an index.
  • array_column — pluck a field from rows; the third argument re-keys them, which is how you build a lookup in one line.
  • usort / uasort / uksort — usort discards keys, uasort keeps them. The spaceship operator makes the comparator a one-liner: fn ($a, $b) => $a->total <=> $b->total.
  • array_merge versus + — array_merge renumbers integer keys and later values win; + keeps the left-hand value and never renumbers. For config defaults you almost always want + or array_replace.
  • Spread and unpacking — [...$a, ...$b], with string keys allowed since 8.1; [$first, , $third] = $row for destructuring.

SPL, and when an array is the wrong answer

🧒 Simple

PHP also ships a small set of purpose-built structures — queues, stacks, heaps, an object set. You will rarely need them, but knowing they exist is the difference between "I would use an array" and "I would use an array, unless it is a priority queue".

🎓 Professional

The ones that earn their place: SplObjectStorage (a set keyed by object identity — the only clean way to attach data to objects without a spl_object_id dance), SplPriorityQueue and SplMinHeap (ordering on insert instead of sorting at the end), SplFixedArray (lower memory for a large, known-size integer-indexed set) and ArrayIterator/ArrayObject when you need an array that is also an object.

Be honest about the trade in an interview: SPL classes are objects, so they carry object overhead and lose the array functions. For most application code the plain array plus a good index is faster to write, faster to read, and fast enough. Naming SplObjectStorage for object identity and SplPriorityQueue for scheduling shows range without pretending you rewrite everything in SPL.

Golden rules
  • An array is an ordered hash map. Every surprise follows from that.
  • array_values() before json_encode() whenever you filtered.
  • Searching by value is O(n). Flip it and search by key.
  • in_array always with strict: true.
  • unset($v) after foreach by reference. Always.
  • Copy-on-write means passing is cheap. & for speed is a myth with a mutation bug attached.
  • array_key_exists when null is a real value; isset otherwise.

Answer with the implementation and then immediately spend it on a consequence: "È una hash map ordinata: mantiene l’ordine di inserimento, le chiavi sono solo int o string, e liste e dizionari sono lo stesso tipo. La conseguenza pratica è che cercare per chiave è O(1) mentre in_array è O(n) — in un import ho sostituito un in_array dentro un ciclo con un array_flip fatto una volta sola e il job è passato da minuti a secondi. E gli array si copiano copy-on-write, quindi passarli è economico finché non li modifichi."
