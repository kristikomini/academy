Security: OWASP, injection, XSS, CSRF and auth

PHP powers a large share of the public web, which means PHP applications are attacked constantly and mostly through four or five well-understood holes. Nothing in this chapter is advanced. All of it is asked in interviews, and the answers people give are usually one level shallower than the answer that shows understanding.

From the advert

"Attenzione alla sicurezza applicativa". In a first technical round this almost always means: explain SQL injection, explain XSS, and tell me how you store a password.

SQL injection

🧒 Simple

You write a sentence and leave a blank for the user to fill in. If they write a whole new sentence into the blank, and you read the result aloud as one sentence, you have just obeyed their instructions instead of yours.

🎓 Professional

A prepared statement sends the query structure to the server, where it is parsed and planned, and then sends the values separately. A value can therefore never be parsed as SQL — not because it was cleaned, but because it never reaches the parser.

That distinction is the whole answer. "It escapes the input" describes a filter, and filters can be wrong; parameterisation removes the category of bug. Interviewers listen for exactly this difference.

⚠ Trap

You cannot parameterise an identifier. Table names, column names and ORDER BY directions are structure, not values, so ORDER BY ? does not work. When those must be dynamic, validate against an allowlist you wrote — never interpolate user input, however well you think you escaped it. 

<?php declare(strict_types=1);

// Injectable. "1 OR 1=1" returns every row; a semicolon returns worse.
$sql = "SELECT * FROM orders WHERE customer_id = " . $_GET['id'];

// Safe: structure and values travel separately.
$stmt = $pdo->prepare('SELECT * FROM orders WHERE customer_id = :id');
$stmt->execute(['id' => $_GET['id']]);

// Identifiers cannot be bound — allowlist them.
$allowed = ['created_at', 'total_cents', 'status'];
$sort = in_array($_GET['sort'] ?? '', $allowed, true) ? $_GET['sort'] : 'created_at';
$dir  = ($_GET['dir'] ?? '') === 'asc' ? 'ASC' : 'DESC';
$pdo->query("SELECT * FROM orders ORDER BY {$sort} {$dir}");

One PDO setting matters: connect with PDO::ATTR_EMULATE_PREPARES => false. With emulation on, PDO interpolates the values itself before sending, which is exactly the thing you were trying to avoid.

XSS: escape on output

🧒 Simple

You let people pin notes on your noticeboard. Someone pins one saying “everyone hand your keys to reception”. The problem is not the pen — it is that you displayed their note as though you had written it yourself.

🎓 Professional

Cross-site scripting is user data being interpreted as code by the browser. The defence is to escape on output, for the context the value lands in — HTML body, an attribute, inside a <script>, a URL. They need different escaping, and only at render time do you know which one applies.

Sanitising on input is the tempting wrong answer: it destroys the user's real data (an address containing &) and still gets it wrong, because you cannot know at write time how the value will later be rendered.

Blade's {{ $x }} escapes by default and {!! $x !!} does not. Every XSS hole in a Laravel codebase is either the second form or a @json in an attribute.

Passwords

🧒 Simple

Never keep the password itself. Keep a scrambled version that cannot be unscrambled, and check new attempts by scrambling them the same way. And make the scrambling deliberately slow, so someone with a stolen copy cannot try billions of guesses a second.

🎓 Professional

password_hash($p, PASSWORD_ARGON2ID). It is deliberately slow and memory-hard, generates its own salt, and stores the algorithm and cost parameters inside the resulting string — so you never manage a salt column and you can raise the cost later without invalidating existing accounts.

MD5 and SHA-256 are wrong here, and the reason is worth saying precisely: they are strong and fast, and fast is the wrong property when the attacker has your database and a GPU. Slowness is the feature. 

<?php declare(strict_types=1);

$hash = password_hash($plain, PASSWORD_ARGON2ID);   // store this string, nothing else

if (password_verify($plain, $hash)) {
    // Cost raised since this account was created? Upgrade it transparently.
    if (password_needs_rehash($hash, PASSWORD_ARGON2ID)) {
        $hash = password_hash($plain, PASSWORD_ARGON2ID);
        // persist the new hash
    }
}

// Comparing secrets you already have: constant time, never ===
hash_equals($expectedToken, $providedToken);
⚠ Trap

"Invalid username" and "Invalid password" as separate messages turn your login form into an account-enumeration oracle. Use one message for both. And on the unknown-user path, verify against a dummy hash anyway — otherwise the response time tells the attacker which accounts exist, and you have leaked the same information through a side channel.

CSRF, and what a token proves

🧒 Simple

Your browser carries your ID card everywhere and shows it automatically. So a stranger's website can shout an instruction at your bank, and your browser politely presents your card with it.

The token is a secret handshake that only pages from your bank know. The stranger's site cannot say it.

🎓 Professional

The attack works because the browser attaches your session cookie to any request to that domain, including one triggered by a form on someone else's site. The token defends against it because it is the one thing a cross-site page cannot know.

So a CSRF token proves origin, not identity. Which is also why it is unnecessary for a stateless API authenticated with an Authorization header: no cookie is sent automatically, so there is nothing to ride on.

Sessions, JWTs, and where to keep them

🧒 Simple

A session id is a cloakroom ticket: meaningless by itself, and the cloakroom can tear it up whenever it likes.

A JWT is a signed letter stating who you are. Anyone can check the signature without phoning the office — but once you have handed it over, you cannot take it back until it expires.

🎓 Professional

A session id is a meaningless key into server-side state, so revoking it is a delete. A JWT carries its claims and is validated by signature alone, with no server lookup — which is the feature (it scales, it needs no shared session store) and the cost: you cannot revoke it before it expires.

Hence the standard shape, which is what the accounts service in this repository implements: a short-lived access token (minutes) plus a long-lived, stateful, revocable refresh token that rotates on every use.

Storage is a trade between two attacks, and saying so is the strong answer. localStorage is readable by JavaScript, so any XSS exfiltrates the token. An httpOnly cookie is not readable by JavaScript, but is sent automatically, so it needs CSRF protection. Neither is free.

Golden rules
  • Prepared statements because values never reach the parser — not because they escape.
  • Identifiers cannot be bound. Allowlist them.
  • Escape on output, for the context. Sanitising on input loses data and still fails.
  • password_hash with Argon2id. Slow is the point.
  • One error message for bad user and bad password, and burn equivalent time on the unknown path.
  • A CSRF token proves origin, not identity — and is redundant for header-authenticated APIs.
  • A JWT cannot be revoked. Short access token, revocable refresh token.
  • hash_equals() for secrets, never ===.

"Come previene la SQL injection?"

The one-level-deeper answer: "Con le prepared statement. La differenza importante è che la struttura della query viene inviata e analizzata separatamente dai valori, quindi un valore non può mai diventare sintassi SQL — non è che venga 'pulito', proprio non arriva al parser. Per gli identificatori, come il nome di una colonna in un ORDER BY, il binding non è possibile, quindi uso una allowlist. E disattivo ATTR_EMULATE_PREPARES, altrimenti PDO interpola i valori lui stesso."
