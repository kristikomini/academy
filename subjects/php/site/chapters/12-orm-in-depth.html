The ORM in depth: Eloquent and Doctrine

An ORM turns rows into objects, and the whole craft is knowing what it is doing on your behalf. Almost every "Laravel is slow" complaint is one specific thing — the N+1 problem — and it is invisible on a development database with ten rows in it.

From the advert

"Esperienza con Laravel e il suo ORM". Expect N+1 to come up by name. It is the question that separates someone who has used Eloquent from someone who has debugged a slow page in production.

The N+1 problem

🧒 Simple

You need the address of a hundred customers. You could ask the office once for all hundred addresses — or you could walk to the office a hundred times and ask for one each time. Both work. One takes all afternoon.

🎓 Professional

One query fetches N parents. Then touching a relation inside a loop issues one more query per parent: 1 + N. With 100 orders that is 101 round trips, each with its own network latency and parse cost.

It is invisible locally because ten rows and no network latency make 11 queries feel instant. It appears the week you go live. The fix is eager loading: tell the ORM up front which relations you need, and it fetches them in one extra query using an IN over the collected keys.

Try it. Enable the query log and count. This is the demonstration to have ready in an interview.

<?php
// 1 + 100 queries
$orders = Order::limit(100)->get();
foreach ($orders as $o) {
    echo $o->customer->name;      // a query, every single iteration
}

// 2 queries total
$orders = Order::with('customer')->limit(100)->get();
foreach ($orders as $o) {
    echo $o->customer->name;      // already in memory
}

// Already have the collection? Load afterwards.
$orders->load('customer');

// Nested and conditional
Order::with(['customer', 'lines.product'])->get();
Order::withCount('lines')->get();   // no need to load lines just to count them
⚠ Trap

Do not wait to discover this in production. Laravel can be told to throw when a relation is lazy-loaded, which turns a silent production problem into a loud local one. Put this in AppServiceProvider::boot(): 

Model::preventLazyLoading(! app()->isProduction());

Saying this sentence in an interview is worth more than knowing what N+1 stands for.

Active Record versus Data Mapper

🧒 Simple

Eloquent: the object knows how to save itself. $order->save(). Doctrine: the object is just data, and a separate manager knows how to store it.

🎓 Professional

Eloquent is Active Record. The model is the table row and carries persistence behaviour. Fast to write, excellent for CRUD, and it couples your domain object to the database schema — the object cannot exist without a connection behind it.

Doctrine is a Data Mapper. Entities are plain objects that know nothing about persistence; an EntityManager maps them to tables. More ceremony, and it keeps a complex domain model free of the database, which is what makes it dominant where the business rules are the hard part.

That is the entire trade-off, and stating it that way — as a trade, not as one being better — is the answer that lands.

The unit of work

🧒 Simple

You do not walk to the filing cabinet after every single note. You make all your changes at your desk, then go once and file everything together.

🎓 Professional

Doctrine's EntityManager tracks every managed entity, and on flush() computes what changed and writes it as one transaction. This is why you do not call save per entity: you modify objects, then flush once.

The consequence that catches people: an entity you fetched and modified will be written on flush even if you never called persist(), because it is already managed. persist() is for new entities only.

Migrations are append-only

⚠ Trap

Never edit a migration that has run anywhere but your own machine. The migrations table records which have run, so an environment that already applied it will not re-run it — it simply stays in the old shape, silently, with no error anywhere. Add a new migration instead.

This is the same discipline as the append-only quiz ids in this repository, and for the same reason: the failure produces no symptom, so only the rule protects you.

Large result sets

🧒 Simple

Do not tip the entire warehouse onto your desk in order to count it. Bring one shelf at a time.

🎓 Professional

Order::all() hydrates every row into an object. On a nightly export that is how you get Allowed memory size exhausted. Three tools, in increasing laziness: chunk() pages in fixed batches, cursor() yields one hydrated model at a time via a generator, and a plain query builder ->toBase() skips hydration altogether when you only need values. 

<?php
// Dies on a large table
foreach (Order::all() as $o) { /* ... */ }

// Batches of 500 — bounded memory
Order::chunk(500, function ($orders) {
    foreach ($orders as $o) { /* ... */ }
});

// One at a time, generator-backed
foreach (Order::lazy() as $o) { /* ... */ }

// chunkById is safer when you are MODIFYING rows as you go:
// chunk() paginates with OFFSET, so updating rows shifts the pages under you.
Order::where('status', 'draft')->chunkById(500, function ($orders) {
    foreach ($orders as $o) { $o->update(['status' => 'expired']); }
});
Golden rules
  • N+1 is the default failure mode of an ORM. Eager-load with with(), and turn on preventLazyLoading() in development.
  • Active Record couples the model to the schema; Data Mapper does not. Choose on how complex the domain is.
  • In Doctrine, a managed entity is saved on flush whether you persisted it or not.
  • Migrations are append-only once they have run outside your machine.
  • all() is a memory bomb. chunkById() when you are also writing.
  • An ORM is a convenience, not a replacement for SQL. Read the generated query when it matters.

"Che cos'è il problema N+1 e come lo risolve?"

Define it, fix it, then prevent it — the third part is what sounds senior: "È quando una query carica N record e poi, accedendo a una relazione dentro il ciclo, parte una query per ogni record: 1 + N. Si risolve con l'eager loading, in Laravel with(), che fa una sola query aggiuntiva con una IN. In sviluppo attivo preventLazyLoading(), così il problema diventa un errore in locale invece di una pagina lenta in produzione."
