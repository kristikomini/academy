SPAs, Vue and TypeScript

Vue is disproportionately common in Italian PHP shops, and the reason is historical rather than technical: it could be added to one page of an existing Laravel application without a build step or a rewrite, which is exactly the situation every agency was in. This chapter is the reactivity model, the component contract, where state should live, and the honest case for not building an SPA at all.

From the advert

"Gradita conoscenza di framework JavaScript (Vue, React)". Gradita — so this is a differentiator, not a filter. One clear paragraph about reactivity and where you put shared state is worth more than a half-finished portfolio SPA.

Reactivity: what actually happens when a value changes

🧒 Simple

You change a variable and the screen updates. The framework arranges that by watching which variables each piece of the page read while it was drawing, so when one of them changes it knows exactly what to redraw.

🎓 Professional

Vue 3 wraps state in a Proxy and tracks dependencies at run time: while a component renders, every reactive property it reads registers that component as a subscriber. On write, only the subscribers are invalidated and re-render is queued to the microtask queue (ch. 17b) — which is why several changes in the same tick produce one render, and why you need await nextTick() to see the DOM after a change.

ref() holds any value and needs .value in script (never in the template); reactive() takes an object and returns a proxy, and destructuring it loses reactivity — the extracted variable is a plain value with no proxy around it. computed() is cached and re-evaluates only when a dependency changes; watch() is for side effects, not for deriving values, and reaching for a watch to keep two pieces of state in sync is nearly always a computed that was not spotted.

Contrast worth being able to state: React re-runs the whole component function on a state change and diffs the result, with memoisation as an opt-in; Vue tracks fine-grained dependencies and re-renders only what read them. Different trade, same goal.

Try it. No build step — save as vue.html and open it. That this works at all from a plain file is exactly why Vue took hold in PHP shops.

<!doctype html>
<meta charset="utf-8">
<div id="app">
  <h1>Carrello</h1>
  <ul>
    <li v-for="riga in righe" :key="riga.id">
      {{ riga.nome }} —
      <input type="number" v-model.number="riga.qta" min="0" style="width:4rem">
      × {{ euro(riga.prezzoCents) }}
    </li>
  </ul>
  <p><strong>Totale: {{ euro(totaleCents) }}</strong></p>
  <p v-if="totaleCents === 0">Il carrello è vuoto.</p>
</div>

<script type="module">
import { createApp, ref, computed } from 'https://unpkg.com/vue@3/dist/vue.esm-browser.js';

createApp({
  setup() {
    const righe = ref([
      { id: 1, nome: 'Espresso',  qta: 2, prezzoCents: 120 },
      { id: 2, nome: 'Cornetto',  qta: 1, prezzoCents: 150 },
    ]);

    // computed: cached, recalculated only when righe changes.
    const totaleCents = computed(() =>
      righe.value.reduce((sum, r) => sum + r.qta * r.prezzoCents, 0));

    // Integer minor units all the way, formatted only at the edge — same rule as PHP.
    const euro = (cents) =>
      new Intl.NumberFormat('it-IT', { style: 'currency', currency: 'EUR' }).format(cents / 100);

    return { righe, totaleCents, euro };
  },
}).mount('#app');
</script>

Components: props down, events up

🧒 Simple

A component receives data from its parent and is not allowed to change it. When something happens, it tells the parent, and the parent decides. Data flows one way, which is what keeps a large page understandable.

🎓 Professional

Props are read-only; mutating one is an error in Vue and a bug in React. The child emits, the parent owns. v-model on a component is sugar over exactly that pair — a prop plus an update:modelValue event — and knowing that is what lets you write a custom input component instead of only consuming them.

Two details that come up in review: :key in a list must be a stable identity, not the array index, or state attaches to the wrong row when the list reorders — the classic symptom is a checkbox that appears to tick the wrong item. And slots are the composition mechanism: a component that takes markup from its parent is far more reusable than one with fourteen boolean props.

On the two Vue APIs: Composition API (setup, ref, composables) is the current default and composes logic far better than Options API, which you will still meet in every project written before 2022. Being able to read both is worth more than an opinion about which is nicer.

⚠ Trap

Prop drilling and its overcorrection. Passing a value through five components that do not use it is a smell — but replacing it with a global store for every piece of state is worse, and produces an application where nothing can be reasoned about locally. Most state is component state. Promote to a store only what genuinely more than one branch of the tree needs: the authenticated user, the cart, a toast queue.

State, the API boundary, and TypeScript

🧒 Simple

There are two kinds of state: things the server owns, which you are only borrowing, and things only the screen cares about. Confusing them is the source of most complexity in a front end.

🎓 Professional

Server state (the order list) is a cache of something remote: it can be stale, it needs loading and error states, and it belongs in a query library — TanStack Query, Pinia Colada — that handles caching, deduplication and invalidation. Client state (which tab is open) is genuinely yours and belongs in a component or a small store (Pinia).

Half of the "Vuex was complicated" experience was people putting server state in a global store and hand-writing cache invalidation. Being able to say that distinction out loud is a strong signal in an interview.

TypeScript earns its place at the boundary. The high-value move is generating types from your API rather than hand-writing them — OpenAPI to TypeScript — so a renamed PHP field becomes a compile error instead of undefined in production. Without that, TypeScript is confidently describing a response shape that nothing checks: as OrderResponse on a fetch is an assertion, not a validation, and that is the honest limit worth knowing.

Do you need an SPA at all?

🧒 Simple

A single-page application is a second application, with its own build, its own routing, its own authentication and its own deployment. Sometimes that is worth it. For a gestionale with forms and tables, it very often is not.

🎓 Professional

An SPA is right when the interaction is genuinely stateful and continuous: a drag-and-drop planner, a live dashboard, a collaborative editor, or a front end shared with a mobile app that needs the API to exist anyway.

It is the wrong default for CRUD. You take on JSON serialisation, client-side validation duplicating server-side validation, token handling, SEO work, a build pipeline and a second deployment — to reproduce what a server-rendered form did for free. For that shape, Livewire, Inertia or plain Blade with a sprinkle of Alpine (ch. 19) deliver the same result with one application instead of two.

Saying this in an interview is a maturity signal, provided you say it as a trade and not as a dislike: name the cases where you would build the SPA, and the answer reads as judgement rather than avoidance.

Golden rules
  • Reactivity tracks what the render read. Re-render is queued, so nextTick before touching the DOM.
  • Destructuring a reactive() loses reactivity.
  • computed to derive, watch for side effects. A syncing watch is a missed computed.
  • Props down, events up. Never mutate a prop.
  • :key is an identity, never the array index.
  • Server state is a cache, not global state. Keep them apart.
  • Generate types from the API, or TypeScript is describing a shape nothing verifies.
  • CRUD does not need an SPA. Know when it does.

"Per questo gestionale useremmo Vue. Come organizzerebbe lo stato?"

The distinction is the whole answer: "Separerei subito due cose. Lo stato del server — la lista ordini, il cliente — è una cache di qualcosa che sta altrove: lo gestisco con una libreria di query, che mi dà loading, errori, deduplica e invalidazione, e non lo metto in uno store globale. Lo stato del client — quale tab è aperto, il contenuto di una form — sta nel componente, e passa in Pinia solo quello che serve davvero a più rami dell’albero, tipo l’utente autenticato. Metà della complessità che si vede negli store è stato del server messo nel posto sbagliato, con l’invalidazione scritta a mano."
