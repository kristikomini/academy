PHP the platform

Before the language, the machine that runs it. Which PHP version you are on decides which half of Stack Overflow applies to you; whether you are behind PHP-FPM or the CLI decides how your code ends and what a "memory leak" even means. This chapter is the layer candidates skip and interviewers use to tell a developer from someone who has only written PHP.

From the advert

"Consolidata esperienza nello sviluppo PHP". The word doing the work is consolidata: they are checking whether you have run PHP in production, and the fastest probe for that is asking what happens between nginx and your index.php.

Versions, and why 8.x is a different language

🧒 Simple

PHP got a big engine rebuild at version 7 and a long series of language upgrades through 8. Code written for PHP 5 often still runs, which is why so much of it is still out there — and why so much advice you find online is answering a question nobody has any more.

🎓 Professional

PHP 7.0 replaced the value representation in the engine and roughly doubled throughput for typical web workloads. PHP 8.0 added the JIT, named arguments, union types, match, constructor promotion, nullsafe ?-> and attributes. 8.1 brought enums, readonly, fibers and pure intersection types; 8.2 readonly classes and DNF types; 8.3 typed class constants and json_validate(); 8.4 property hooks, asymmetric visibility and a new DOM API.

The practical point for an interview: know which version you are speaking about. Say "on 8.1 or later I would use an enum here; on 7.4 that has to be class constants plus a guard" and you have demonstrated more than the feature list — you have shown you work in codebases that have a version constraint, which every real one does.

⚠ Trap

Security support is shorter than people assume. Each release gets roughly two years of active support plus two of security fixes. A shop still on 7.4 is running code that stopped receiving security patches years ago, and "we’ll upgrade next quarter" has been true for eight quarters. If you are asked what you would do first in such a codebase, the answer is not "rewrite it": it is get it onto a supported version with Rector and a test harness (ch. 16b), because everything else you might want to do is blocked behind that.

SAPI: the same code, four different worlds

🧒 Simple

The SAPI is the doorway PHP was entered through. A script run from the terminal and the same script run by a web server behave differently — different limits, different output, a different idea of when it is finished.

🎓 Professional

php_sapi_name() tells you which: cli, fpm-fcgi, apache2handler, cli-server. What changes with it:

  • max_execution_time is 0 on CLI and typically 30 on FPM. A cron import that works from the terminal and dies from the browser is this, every time.
  • memory_limit is usually looser on CLI (often -1 from Composer’s own wrapper), which is why composer update works and the same job in a web request does not.
  • Output buffering and headers only mean something under a web SAPI.
  • A separate php.ini is common: /etc/php/8.3/cli/php.ini and /etc/php/8.3/fpm/php.ini are different files, and the number of hours lost to editing the wrong one is enormous.

Try it. Run this from the terminal, then put it in your web root and load it in a browser. Two different answers from one file is the entire point of this section.

<?php declare(strict_types=1);

printf("sapi:        %s%s", PHP_SAPI, PHP_EOL);
printf("version:     %s%s", PHP_VERSION, PHP_EOL);
printf("memory:      %s%s", ini_get('memory_limit'), PHP_EOL);
printf("max_exec:    %s%s", ini_get('max_execution_time'), PHP_EOL);
printf("ini file:    %s%s", php_ini_loaded_file() ?: '(none)', PHP_EOL);
printf("opcache:     %s%s",
    function_exists('opcache_get_status') && opcache_get_status() ? 'on' : 'off', PHP_EOL);

PHP-FPM and the process model

🧒 Simple

PHP-FPM keeps a pool of worker processes waiting. A request arrives, a free worker picks it up, runs your code from scratch, sends the answer, throws everything away, and goes back to the pool. Nothing survives between requests — that is the whole design.

🎓 Professional

nginx does not run PHP. It passes the request over FastCGI to a PHP-FPM master, which hands it to a worker. The pool is configured by pm (dynamic, static, ondemand) and pm.max_children, and that number is a concurrency limit, not a performance setting. It is why a site "goes down" under load with no error in the PHP log: every child is busy waiting on a slow external API, nginx queues, and the queue times out into 502/504.

Size it by memory, not by hope: max_children ≈ available RAM / average process size. Setting it to 200 on a 2 GB box does not serve 200 requests, it invites the OOM killer. And because each request is a fresh interpreter, shared-nothing is the consequence that matters — no application state between requests, so anything that has to persist goes in Redis, the session store or the database (ch. 08, 20).

⚠ Trap

"PHP is slow" is nearly always "one PHP request is waiting". Under FPM a worker blocked on a third-party HTTP call with no timeout is a worker that serves nobody for 30 seconds. Two dozen of those and the site is down. Always set a timeout on an outbound call, and move anything genuinely slow onto a queue (ch. 22) — that single habit prevents more outages than any amount of micro-optimisation.

OPcache, and the JIT question

🧒 Simple

Without OPcache, PHP reads and re-compiles every one of your files on every single request. OPcache keeps the compiled version in memory, so it only pays that cost once. It is the single largest performance setting on the platform, and it is one line of config.

🎓 Professional

OPcache stores compiled opcodes in shared memory. In production: opcache.enable=1, generous opcache.memory_consumption, opcache.max_accelerated_files above your real file count (a Laravel app easily passes 10 000), and opcache.validate_timestamps=0 so it never even stats the files.

That last one is the deployment coupling worth knowing: with timestamp validation off, deploying new code changes nothing until the opcode cache is cleared — reload PHP-FPM as part of the deploy, or you have shipped a version nobody is running (ch. 30).

The JIT, added in 8.0, is the question people over-answer. The honest response: for typical web request/response code it gains almost nothing, because the bottleneck is I/O and not opcode dispatch; it helps CPU-bound numeric work. Saying that is a stronger answer than claiming a speed-up you have never measured.

Composer, extensions and the four settings that bite

🧒 Simple

Composer downloads the libraries your project depends on and writes the file that teaches PHP where to find every class. Extensions are the extra abilities PHP is compiled with — talking to MySQL, handling images, reading ZIPs — and a missing one is a very confusing error.

🎓 Professional

Composer resolves dependencies, writes composer.lock and generates a PSR-4 autoloader (ch. 28). Two habits mark experience: composer install in CI and on servers, never update; and composer install --no-dev --optimize-autoloader for a production build.

The php.ini values that account for most "it works locally" tickets:

  • memory_limit — the exhausted-memory fatal, usually an unbounded query result.
  • upload_max_filesize and post_max_size — two settings; the smaller wins, and exceeding post_max_size silently empties $_POST rather than raising an error.
  • max_input_vars — default 1000, and a large gestionale form simply loses fields past it with no warning at all.
  • display_errors — Off in production, always, with log_errors=On. Displaying a stack trace to a visitor is a security finding (ch. 15), not an inconvenience.
Golden rules
  • Name the version you are speaking about. "On 8.1+" is a senior habit.
  • CLI and FPM are different worlds — different ini file, different limits.
  • pm.max_children is a concurrency ceiling, sized by RAM, not optimism.
  • Every outbound call gets a timeout. A blocked worker is a worker serving nobody.
  • Reload FPM on deploy when validate_timestamps=0, or you shipped nothing.
  • install on servers, update on your machine. The lock file is the point.
  • display_errors=Off in production. Log it, never show it.

"Cosa succede, passo per passo, da quando arriva una richiesta a quando il browser riceve la risposta?"

This is the platform question, and the answer should walk the path rather than list nouns: "nginx riceve la richiesta, vede che è PHP e la passa via FastCGI a PHP-FPM. Il master la assegna a un worker libero — se sono tutti occupati la richiesta si mette in coda, ed è lì che nascono i 502. Il worker carica il codice, che normalmente è già compilato in OPcache, esegue, restituisce la risposta e poi butta via tutto: shared-nothing, quindi niente stato tra una richiesta e l’altra. Per questo sessioni e cache stanno in Redis o nel database." Finish on shared-nothing — it is the sentence that shows you understand the model and not just the diagram.
