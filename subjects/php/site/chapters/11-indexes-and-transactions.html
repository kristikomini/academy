Indexes, EXPLAIN, transactions and deadlocks

Everything in this chapter becomes urgent on the same day: the one where a page that was fine with two hundred rows takes eleven seconds with two hundred thousand. Indexes are how you fix it, EXPLAIN is how you find out whether you actually did, and transactions are how you stop two users corrupting each other while you are at it.

From the advert

"Ottimizzazione di query e strutture dati". This line is the difference between a junior who writes queries and one who is trusted with the database. It is also the most common live-coding topic in Italian technical interviews after plain SQL.

What an index actually is

🧒 Simple

An index is the alphabetical list at the back of a book. Without it, finding every mention of "Bologna" means reading all 900 pages. With it, you look up B, and it tells you the page numbers.

And like a real index, it is not free: every time you add a page to the book you have to update it.

🎓 Professional

An InnoDB index is a B-tree keeping the indexed columns in sorted order, with a pointer back to the row. Lookups become a tree descent instead of a full scan. The cost is on write — every INSERT, UPDATE and DELETE maintains every index on that table — plus the disk space.

Which is the answer to "why not index everything?": you would make reads slightly faster and every write meaningfully slower, on a table that is probably written more than you think.

Composite indexes and the leftmost rule

🧒 Simple

A phone book is sorted by surname, then first name. You can find every "Rossi" instantly, and every "Rossi, Marco" instantly. But you cannot find every "Marco" — they are scattered across the whole book.

🎓 Professional

A composite index on (a, b, c) is usable for the leftmost prefixes: a, (a, b), and (a, b, c). It is not usable for b alone or c alone. This is the single most-tested index fact in interviews, and the most common reason a "we already have an index" query is still slow.

Ordering heuristic: equality columns first, then the range or sort column. An index on (customer_id, created_at) serves WHERE customer_id = ? ORDER BY created_at perfectly — the rows for that customer are already in date order, so there is no sort to do.

Why your index is being ignored

⚠ Trap

Wrap a column in a function and the index dies. The index is sorted by created_at, not by YEAR(created_at), so the engine has to compute the function for every row to find out. The predicate has become non-sargable.

The same applies to an implicit cast — comparing a VARCHAR column to an integer makes MySQL convert the column, row by row.

Try it. Both queries return the same rows. Run EXPLAIN on each and compare type and key.

-- non-sargable: index on created_at cannot be used
EXPLAIN SELECT * FROM orders
WHERE YEAR(created_at) = 2026;

-- sargable rewrite: a range the B-tree can walk
EXPLAIN SELECT * FROM orders
WHERE created_at >= '2026-01-01'
  AND created_at <  '2027-01-01';

-- implicit cast, same problem, harder to spot
EXPLAIN SELECT * FROM orders WHERE order_ref = 12345;   -- order_ref is VARCHAR
EXPLAIN SELECT * FROM orders WHERE order_ref = '12345'; -- quoted: index used

Reading an EXPLAIN plan

🧒 Simple

EXPLAIN is asking the database: before you run this, tell me how you plan to do it. It answers with the plan, and you read it to find out whether it intends to look at ten rows or ten million.

🎓 Professional

Four columns carry most of the meaning:

  • type — the access method. const and eq_ref are ideal, ref and range are healthy, index is a full index scan, and ALL is a full table scan.
  • key — which index was actually chosen. NULL means none.
  • rows — the optimiser's estimate of rows examined. An estimate, not a count, but a large number here is where you look first.
  • Extra — Using index is excellent: the query was answered from the index alone. Using filesort or Using temporary mean work you may be able to design away.

type: ALL is not automatically bad. On a 40-row lookup table a full scan is the right plan and an index would be ignored. It is bad when the table is large and the WHERE is selective.

Covering indexes

🧒 Simple

If the index at the back of the book already tells you what you wanted to know, you never turn to the page at all. That is a covering index.

🎓 Professional

If an index contains every column the query needs — those in SELECT as well as WHERE — the engine answers from the index and never reads the row. EXPLAIN shows Using index. It is usually the cheapest large win available on a hot read path, because it removes an entire I/O per row.

Transactions, isolation and the anomalies

🧒 Simple

A transaction is "all of this, or none of it". Take money from one account and put it in another: if the second step fails, the first must be undone, or money vanishes.

🎓 Professional

ACID, and the three anomalies that isolation levels remove in order:

  • Dirty read — seeing another transaction's uncommitted data. Removed by READ COMMITTED.
  • Non-repeatable read — reading the same row twice and getting different values. Removed by REPEATABLE READ.
  • Phantom read — the same WHERE returning new rows on a second run. Removed by SERIALIZABLE (and largely by InnoDB's gap locks).

InnoDB defaults to REPEATABLE READ, unlike PostgreSQL and SQL Server which default to READ COMMITTED. Know this one: it means that inside a MySQL transaction, re-reading a row will not show another transaction's committed change, which surprises people arriving from other engines.

Optimistic and pessimistic locking

🧒 Simple

Two ways to stop two people editing the same thing at once. Pessimistic: lock the door while you work. Optimistic: leave it open, but note what the page looked like when you started, and refuse to save if somebody changed it meanwhile.

🎓 Professional

Pessimistic: SELECT ... FOR UPDATE takes an exclusive lock on the matched rows for the rest of the transaction. Correct when a conflict is likely and must not happen — reserving the last unit of stock.

Optimistic: carry a version column, and make the update conditional on it. If zero rows were affected, somebody else got there first, and you return a 409 rather than silently overwriting their work. Correct when conflicts are rare, and it holds no locks between reading and writing — which matters over an HTTP request, where the user might take four minutes to press Save. 

-- Pessimistic: nobody else touches this row until COMMIT.
START TRANSACTION;
SELECT quantity FROM stock WHERE product_id = 42 FOR UPDATE;
UPDATE stock SET quantity = quantity - 1 WHERE product_id = 42;
COMMIT;

-- Optimistic: no lock held while the user thinks.
UPDATE orders
   SET status = 'confirmed', version = version + 1
 WHERE id = 114 AND version = 7;
-- 0 rows affected => somebody else changed it. Reload and tell the user.
⚠ Trap

A deadlock needs a cycle: A holds row 1 and wants row 2, B holds row 2 and wants row 1. The fix is not a longer timeout and not a higher isolation level — it is acquiring locks in a consistent order everywhere, which makes a cycle impossible. Then retry on failure anyway, because under real load deadlocks are normal and MySQL will pick a victim and roll it back.

Golden rules
  • Composite indexes work left to right. (a, b) cannot serve a query filtering only on b.
  • A function on a column kills the index. Rewrite it as a range.
  • Measure with EXPLAIN, not intuition — read type, key, rows, Extra.
  • Every index makes writes slower. That is the answer to "why not index everything".
  • InnoDB defaults to REPEATABLE READ. Most other engines do not.
  • Consistent lock ordering prevents deadlocks; retries survive them. You need both.
  • Never hold a database lock across user think-time. That is what a version column is for.
