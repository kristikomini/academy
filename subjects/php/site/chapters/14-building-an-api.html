Building an API

Chapter 13 was the protocol. This one is the thing you build on it: routes, validation that happens before your code does anything, a serialisation layer that does not leak your database schema to the world, pagination that still works at page 4000, versioning you can actually retire, and an error body a client developer can program against instead of screenshotting.

From the advert

"Sviluppo e integrazione di API REST". Note both halves — you will build them and consume them (ch. 14b). The build half is judged almost entirely on two things: what happens with invalid input, and what the error looks like.

Validation at the boundary

🧒 Simple

Everything arriving from outside is a lie until checked. Check it once, at the door, and turn it into something trustworthy — then the rest of your code never has to wonder.

🎓 Professional

Validation belongs at the edge, and its output should be a typed object, not an array that is now merely "probably fine". A Laravel FormRequest or a Symfony DTO with constraints gives you one place where the rules live, and a controller that receives something already valid.

The distinction that matters in an interview: validation is not authorisation and neither is a domain invariant. "quantity must be an integer ≥ 1" is validation; "this user may modify this order" is authorisation; "an order cannot be confirmed twice" is a domain rule that must hold no matter which entry point was used, so it lives on the model (ch. 03, 23) — not in the request class, which the queue worker never runs.

Return 422 for a well-formed request whose contents fail the rules, and 400 for a body that is not parseable at all. Report all the field errors at once, keyed by field — a client that has to submit five times to discover five problems will be re-implemented by an angry front-end developer.

⚠ Trap

Mass assignment. Order::create($request->all()) hands the attacker every column you forgot to think about — is_admin, total_cents, user_id. Use $request->validated(), which returns only the keys you declared rules for, and keep $fillable honest as the second line of defence. This is a genuine OWASP category (ch. 15), not a style preference, and it is one of the most common findings in a Laravel security review.

Serialisation: the response is a contract

🧒 Simple

Do not hand your database rows straight to the client. Decide deliberately what the outside world sees, because from the moment somebody uses it, you cannot change it without breaking them.

🎓 Professional

return Order::all(); works and is a trap: it publishes your column names, ships password_hash the day somebody adds it to the wrong model, and makes a column rename a breaking API change. An explicit resource layer — Laravel API Resources, Symfony Serializer groups, Fractal — makes the payload a decision.

Decide these once and apply them everywhere: money as integer minor units with the currency beside it, never a float (ch. 03); dates as ISO-8601 with an offset, not d/m/Y; enums as their backing string; identifiers as strings, because a JavaScript client silently loses precision on integers past 253.

On null versus absent: pick one convention and document it. A field that is sometimes missing and sometimes null forces every client into defensive code.

Try it. Framework-free on purpose — the shape is the point, and it is the same shape underneath Laravel or Symfony.

<?php declare(strict_types=1);

final readonly class OrderResource
{
    public function __construct(private array $row) {}

    public function toArray(): array
    {
        return [
            'id'         => (string) $this->row['id'],        // string: JS loses big ints
            'reference'  => $this->row['reference'],
            'status'     => $this->row['status'],             // backed enum value
            'total'      => [
                'amount'   => (int) $this->row['total_cents'], // minor units, never a float
                'currency' => 'EUR',
            ],
            'placed_at'  => (new DateTimeImmutable($this->row['placed_at']))
                                ->format(DateTimeInterface::ATOM),
            // deliberately NOT exposed: internal_note, cost_cents, customer_id
        ];
    }
}

header('Content-Type: application/json');
echo json_encode(
    (new OrderResource([
        'id' => 9007199254740993, 'reference' => 'ORD-2026-114', 'status' => 'confirmed',
        'total_cents' => 2499, 'placed_at' => '2026-09-06 11:20:00',
    ]))->toArray(),
    JSON_THROW_ON_ERROR | JSON_UNESCAPED_UNICODE | JSON_UNESCAPED_SLASHES
), PHP_EOL;

Pagination that survives page 4000

🧒 Simple

Never return every row. Return a page — but be aware that the obvious way of doing it gets slower the deeper the client goes, and shows duplicates when new rows arrive while they are paging.

🎓 Professional

Offset pagination (LIMIT 20 OFFSET 80000) is what everyone ships. The database must walk and discard 80 000 rows to give you 20, so cost grows with depth; and because the window is positional, an insert at the top shifts everything and the client sees an item twice.

Cursor (keyset) pagination asks for "the next 20 after this key": WHERE (created_at, id) < (:ts, :id) ORDER BY created_at DESC, id DESC LIMIT 20. It is index-friendly, constant cost at any depth, and stable under inserts. The tie-breaker column is not optional — two rows with the same timestamp will skip or repeat without it. The trade is that you cannot jump to page 47, which is fine for feeds and mobile clients and wrong for an admin table with page numbers.

Whichever you choose, make the total count optional. COUNT(*) over a large filtered set is frequently more expensive than the page itself, and most clients never display it.

Versioning, and an error body clients can use

🧒 Simple

Once someone depends on your API you cannot change its shape under them. And when something goes wrong, the answer should be a small structured document that a program can read — not an HTML error page and not a bare string.

🎓 Professional

Versioning. URI versioning (/api/v1/orders) wins in practice for the kind of API this market builds: it is visible in logs, trivially routable, and every client developer understands it without reading documentation. Header and media-type versioning are more correct and more expensive; choose them when you have a real reason. What actually matters is the additive rule — adding a field is not breaking, removing or renaming one is — and having a retirement plan, because a v1 nobody can turn off is a v1 forever.

Errors. Use RFC 9457 Problem Details: type, title, status, detail, instance, plus your own members such as errors keyed by field. Serve it as application/problem+json. It costs nothing, it is a standard you can name in an interview, and it stops every project from inventing its own error envelope.

Include a correlation id in the body and in the log line (ch. 25). When a client reports "it failed at 14:32", that id is the difference between finding the request in seconds and grepping an afternoon.

Try it. A Problem Details response with per-field errors. This is the exact shape to reach for whenever you are asked how you report a validation failure.

<?php declare(strict_types=1);

http_response_code(422);
header('Content-Type: application/problem+json');

echo json_encode([
    'type'     => 'https://api.bottega.test/problems/validation',
    'title'    => 'The request body failed validation.',
    'status'   => 422,
    'detail'   => 'Two fields could not be accepted.',
    'instance' => '/api/v1/orders',
    'traceId'  => 'c0ffee-114',            // matches the log line
    'errors'   => [                         // keyed by field, all at once
        'quantity'    => ['Must be an integer of at least 1.'],
        'customer_id' => ['No customer exists with this identifier.'],
    ],
], JSON_THROW_ON_ERROR | JSON_PRETTY_PRINT), PHP_EOL;
Golden rules
  • Validate at the boundary into a typed object, and never trust an array again.
  • Domain invariants live on the model, not in the request class the worker never runs.
  • Never create($request->all()). validated(), always.
  • 422 for invalid content, 400 for unparseable, and report every field at once.
  • Resources, not models, in responses. Money in minor units, dates ISO-8601, ids as strings.
  • Keyset pagination for feeds, offset only where a page number is genuinely needed.
  • Problem Details plus a correlation id. Adding a field is safe; removing one is not.

"Come gestisce gli errori di validazione in una API?"

Give the status code, the shape and the reason for the shape: "Valido al bordo, con una FormRequest, e restituisco 422 con un corpo in formato Problem Details: application/problem+json con title, status e un oggetto errors con tutti i campi che non vanno, non solo il primo — altrimenti il client deve fare cinque tentativi per scoprire cinque errori. Ci metto anche un traceId che finisce nel log, così se il cliente mi segnala un errore lo trovo subito. Le regole di dominio, tipo 'un ordine non si conferma due volte', non stanno nella validazione ma sul modello, perché devono valere anche quando l’ordine arriva da un job in coda."
