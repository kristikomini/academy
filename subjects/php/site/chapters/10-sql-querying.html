SQL: querying

This is the chapter most likely to be tested live, with a whiteboard or a shared editor. Not because SQL is hard, but because it is the one skill an ORM cannot hide: the moment a report gets complicated, you are writing it by hand, and the interviewer knows it.

From the advert

"Conoscenza di database relazionali (MySQL/MariaDB)". In a technical round this usually becomes one join question, one aggregation question, and — if they are thorough — "give me the top three per category", which is a window function.

Joins, and the LEFT JOIN that quietly is not one

🧒 Simple

You have a list of customers and a list of orders. An inner join gives you only customers who ordered something. A left join gives you every customer, with blanks where they never ordered.

🎓 Professional

INNER keeps rows matching on both sides. LEFT keeps every row from the left table, filling the right side with NULL where there is no match. RIGHT is the mirror and is rare in practice — people reorder the tables instead. FULL OUTER does not exist in MySQL; you emulate it with a UNION.

⚠ Trap

Filter the right-hand table in WHERE and your LEFT JOIN silently becomes an INNER JOIN. The unmatched rows have NULL there, and NULL > 100 is not true, so WHERE throws them away — undoing exactly what you asked for.

The fix is to put the condition in ON, which filters during the join, rather than in WHERE, which filters after it. This is the most common SQL bug in interviews and in real reports. 

-- Looks like "all customers", behaves like INNER JOIN
SELECT c.name, o.total
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.total > 100;

-- Actually all customers, with only their large orders attached
SELECT c.name, o.total
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id AND o.total > 100;

-- "Customers who have never ordered" — the anti-join
SELECT c.name
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.id IS NULL;

GROUP BY, HAVING and the counting trap

🧒 Simple

GROUP BY is sorting things into buckets and then asking one question per bucket: how many, how much, the largest. WHERE decides what goes into the buckets; HAVING decides which buckets you keep.

🎓 Professional

WHERE runs before grouping and therefore cannot see aggregates; HAVING runs after and can. Filter as early as possible in WHERE — it reduces the rows that ever reach the grouping step, so it is both correct and faster.

COUNT(*) counts rows. COUNT(col) counts rows where col IS NOT NULL. After a LEFT JOIN, COUNT(*) gives 1 for a customer with no orders, because the outer row still exists — you want COUNT(o.id), which gives 0. 

-- Wrong: customers with no orders show a count of 1
SELECT c.name, COUNT(*) AS orders
FROM customers c LEFT JOIN orders o ON o.customer_id = c.id
GROUP BY c.id, c.name;

-- Right: COUNT over a column from the joined table
SELECT c.name, COUNT(o.id) AS orders, COALESCE(SUM(o.total), 0) AS spent
FROM customers c LEFT JOIN orders o ON o.customer_id = c.id
GROUP BY c.id, c.name
HAVING COUNT(o.id) >= 3        -- filters the buckets
ORDER BY spent DESC;

Window functions

🧒 Simple

GROUP BY squashes each bucket down to a single row. A window function lets you keep all the rows and ask a question about the bucket each one sits in — like writing each pupil's rank next to their name without collapsing the class into one line.

🎓 Professional

OVER (PARTITION BY ... ORDER BY ...) computes across a set of rows related to the current row, without collapsing them. ROW_NUMBER() numbers them uniquely, RANK() leaves gaps after ties, DENSE_RANK() does not, and LAG/LEAD reach into the previous or next row — which is how you compute month-on-month change without a self-join.

Available in MySQL from 8.0 and MariaDB from 10.2. On an older gestionale you will still meet the correlated-subquery workaround, which is worth being able to read.

Try it. "The three biggest orders per customer" is the classic live-coding question. GROUP BY cannot do it — it would collapse each customer to one row.

WITH ranked AS (
  SELECT
    o.*,
    ROW_NUMBER() OVER (PARTITION BY o.customer_id ORDER BY o.total DESC) AS rn
  FROM orders o
)
SELECT customer_id, id, total
FROM ranked
WHERE rn <= 3;

-- Month-on-month change, no self-join
SELECT
  month,
  revenue,
  revenue - LAG(revenue) OVER (ORDER BY month) AS delta
FROM monthly_revenue;

You cannot filter on a window function in WHERE — it is computed after WHERE runs. That is why the ranking goes in a CTE or subquery and the filter goes outside it.

EXISTS, IN, and the NULL that eats your result set

🧒 Simple

EXISTS asks "is there at least one?" and stops looking as soon as it finds one. IN builds the whole list first and then checks membership.

🎓 Professional

For the positive case modern optimisers usually treat them alike. The difference that bites is NOT IN with a NULL anywhere in the subquery: comparing to NULL yields unknown, never true, so NOT IN (1, 2, NULL) matches nothing at all and your query silently returns an empty set.

NOT EXISTS does not have this problem. Prefer it, or the LEFT JOIN ... IS NULL anti-join, whenever the column could be nullable. 

-- Returns NOTHING if any customer_id in orders is NULL
SELECT * FROM customers
WHERE id NOT IN (SELECT customer_id FROM orders);

-- Safe
SELECT * FROM customers c
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id);

CTEs, and reading a query top to bottom

🧒 Simple

A WITH block lets you name a step. Instead of one enormous sentence with brackets inside brackets, you write "first work this out, call it X; then use X".

🎓 Professional

A common table expression is a named subquery scoped to the statement. The main win is readability — a three-level nested subquery becomes three named steps read in order — and it lets you reference the same intermediate result twice.

Do not assume a performance gain: MySQL may materialise a CTE into a temporary table. WITH RECURSIVE is the real capability jump, and it is how you query a category tree or an org chart of unknown depth.

Golden rules
  • Filtering the right table in WHERE turns a LEFT JOIN into an INNER JOIN. Put the condition in ON.
  • WHERE before grouping, HAVING after. Filter as early as you can.
  • COUNT(*) counts rows; COUNT(col) skips NULLs. After a LEFT JOIN you almost always want the second.
  • Top-N-per-group is a window function. GROUP BY cannot express it.
  • You cannot filter a window function in WHERE — wrap it in a CTE and filter outside.
  • NOT IN with a NULL returns nothing. Use NOT EXISTS.
  • Name your steps with CTEs. The query you can read in six months is the one you can fix.

"Mi scriva una query che restituisce i primi 3 ordini per ogni cliente."

Say why the obvious answer fails before writing anything — that is what is being tested: "Con GROUP BY non si può, perché collasserebbe ogni cliente su una riga sola: LIMIT 3 mi darebbe tre clienti, non tre ordini a testa. Serve una window function: ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY total DESC), in una CTE, e poi filtro rn <= 3 fuori — perché nella WHERE la window function non è ancora stata calcolata."
