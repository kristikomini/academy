HTML, CSS and the DOM

In a software house of eight people there is no front-end team, so "conoscenza di HTML e CSS" means you can finish your own ticket. This chapter is the part of the front end that a back-end developer is genuinely expected to know: markup that means something, the two ways the cascade actually resolves a conflict, flex versus grid decided in one sentence, and the accessibility minimum that is a legal requirement for a public-sector client.

From the advert

"Conoscenza di HTML, CSS e JavaScript". Nobody expects a designer. They expect that your feature arrives looking like the rest of the application without a second person touching it.

Semantic markup, and why it is not decoration

🧒 Simple

Use the tag that says what the thing is. A button is a <button>, a list is a <ul>. You get keyboard support, screen-reader support and correct behaviour for free — and a <div onclick> gives you none of it.

🎓 Professional

The element is an accessibility contract, not a style hook. <button> is focusable, fires on Enter and Space, and is announced as a button; reproducing that on a div takes tabindex, a role, and two keyboard handlers people always forget. Same for <a href>, which must be a real link if it navigates — middle-click and "open in new tab" are behaviours users notice losing.

The rest that matters: one <h1> per page and heading levels that do not skip, because that outline is how a screen-reader user navigates; <label for> on every input, which also makes the label a click target; <table> for tabular data with real <th scope>; and landmarks (header, nav, main, footer) so "skip to content" works.

Forms specifically: a <form> with a submit button submits on Enter, which users expect and JavaScript handlers routinely break. Use the right type and autocomplete — type="email" changes the mobile keyboard, and autocomplete="current-password" is what lets a password manager work.

The cascade: specificity, and the modern escape from it

🧒 Simple

When two rules both apply, the more specific one wins — an id beats a class beats a tag. If they are equally specific, the one written last wins. Almost every "why is my CSS not applying" is one of those two sentences.

🎓 Professional

Specificity is counted as three numbers: (ids, classes/attributes/pseudo-classes, elements). #nav .item a is (1,1,1) and beats .sidebar .item a.active at (0,3,1) — one id outranks any number of classes, which is why id selectors in a stylesheet cause trouble later. Inline styles sit above all of it, and !important above that; both are the escalation that ends in a second !important.

Useful modern tools: :is() takes the specificity of its most specific argument, :where() has zero specificity — which makes it the right way to write defaults that are trivially overridable. Cascade layers (@layer) let you declare that everything in components beats everything in reset, regardless of selector complexity. That is the real fix for specificity wars.

Inheritance is a separate mechanism from the cascade and is a frequent confusion: colour and font inherit, box properties do not.

⚠ Trap

Margin collapsing. Two vertical margins that touch merge into one — the larger, not the sum. Worse, a child’s top margin can escape its parent and push the parent down instead of the child, which produces the "there is a mysterious gap above my box" bug. It stops at any padding, border, or a new formatting context (display: flow-root, flex, grid). It only ever affects vertical margins, and it does not happen in flex or grid containers at all, which is one more reason those layouts feel more predictable.

Flex or grid, decided in one sentence

🧒 Simple

Flexbox arranges things in one direction — a row or a column. Grid arranges them in rows and columns at once. A toolbar is flex; a page layout is grid.

🎓 Professional

One dimension versus two, and the difference is who decides: with flex the content largely determines the sizing; with grid the container defines the tracks and the items are placed into them.

The flex properties worth knowing properly are the ones inside the shorthand: flex: 1 1 auto is grow, shrink, basis. Most "my flex item will not shrink" bugs are min-width: auto, whose default prevents an item shrinking below its content — min-width: 0 is the fix, and it is the single most useful flex debugging fact.

For grid, two things carry most of the value: repeat(auto-fill, minmax(240px, 1fr)) gives a responsive card layout with no media queries at all, and named template areas make a page skeleton readable at a glance. Then gap — which works in both — replaces the entire era of margin hacks.

Modern responsive work is increasingly not media queries: clamp() for fluid type, container queries for a component that must adapt to its own width rather than the viewport’s, and logical properties (margin-inline) for writing directions.

Try it. Save as layout.html and open it. Resize the window: the cards reflow with no media query, and the toolbar stays one row. Then delete min-width: 0 and watch the long reference stop shrinking — that is the bug you will otherwise spend an hour on one day.

<!doctype html>
<meta charset="utf-8">
<style>
  body { font: 16px/1.5 system-ui, sans-serif; margin: 2rem; }

  /* One dimension: a toolbar. */
  .bar   { display: flex; gap: .75rem; align-items: center; }
  .bar .grow { flex: 1 1 auto; min-width: 0; }        /* ← the shrink fix */
  .bar .grow span { display: block; overflow: hidden; text-overflow: ellipsis; white-space: nowrap; }

  /* Two dimensions: responsive cards, no media query anywhere. */
  .cards { display: grid; gap: 1rem; margin-top: 1.5rem;
           grid-template-columns: repeat(auto-fill, minmax(240px, 1fr)); }
  .card  { border: 1px solid #ccc; border-radius: 8px; padding: 1rem; }
</style>

<div class="bar">
  <strong>Ordini</strong>
  <div class="grow"><span>ORD-2026-000114 — Ferramenta Bolognese S.r.l. — in attesa di conferma</span></div>
  <button type="button">Conferma</button>
</div>

<div class="cards">
  <div class="card"><h2>Bozze</h2><p>4</p></div>
  <div class="card"><h2>Da spedire</h2><p>11</p></div>
  <div class="card"><h2>Consegnati</h2><p>231</p></div>
</div>

Accessibility: the minimum, and why it is contractual

🧒 Simple

Can someone use it with only a keyboard? Can they read it with a screen reader? Is the text dark enough against its background? Those three questions catch most of what matters, and all three come free if the markup was honest.

🎓 Professional

In Italy this is not only good practice: the Legge Stanca and the European Accessibility Act make WCAG conformance a requirement for public-sector work and, increasingly, for large private services. Any agency that touches a comune, an ASL or a university has this in the contract, and knowing that is a differentiator in an interview at a Bologna agency.

The checks that catch most real failures:

  • Keyboard. Tab through the whole feature. If focus disappears or a modal does not trap it, the feature is unusable. Never set outline: none without a visible replacement.
  • Contrast. 4.5:1 for body text. Grey-on-grey placeholder text fails almost universally.
  • Names. Every control needs an accessible name — a <label>, or aria-label for an icon-only button. "Bottone" announced with no name is a dead end.
  • Images. Meaningful alt, or alt="" when decorative. An alt of "immagine" is worse than nothing.
  • Errors. Announce them: link the message to the field with aria-describedby, and do not rely on colour alone to say which field failed.
  • The first rule of ARIA is not to use ARIA — a native element beats role="button" every time, and bad ARIA is worse than none.
Golden rules
  • The tag is a contract. <button> for actions, <a href> for navigation.
  • Specificity is (ids, classes, elements), then source order. One id outranks ten classes.
  • :where() for defaults, @layer for order. That is the end of !important.
  • A mystery gap is a collapsed margin. Vertical only, never in flex or grid.
  • Flex is one dimension, grid is two. min-width: 0 when a flex item will not shrink.
  • auto-fill + minmax + gap is a responsive layout with no media query.
  • Tab through it before you call it done. Contrast, labels, focus.

"Quanto se la cava con il front-end? Da noi non c’è un team dedicato."

Do not oversell it — claim the honest, useful level: "Non sono un designer, ma chiudo il mio ticket da solo: scrivo markup semantico, uso flexbox e grid senza dover chiedere aiuto, e so debuggare la cascata quando una regola non si applica. Faccio attenzione all’accessibilità di base — navigazione da tastiera, label sui campi, contrasto — anche perché per i clienti pubblici è un requisito di legge, non un extra. Se serve un lavoro di design vero preferisco lavorarci insieme a chi lo sa fare." That last sentence is not weakness; it is the answer of someone who has shipped with a team.
