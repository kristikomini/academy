The framework: Laravel and Symfony

Laravel is the most-quoted requirement in Italian PHP adverts, and the one most candidates answer at the level of "I've used it". What gets tested is whether you know what happens between the request arriving and your controller method running — the container, the middleware pipeline, and where things get resolved.

From the advert

"Consolidata esperienza con il framework Laravel". It appeared in every posting this course was built from. The three things actually probed: the service container, middleware order, and what a facade really is.

The request lifecycle

🧒 Simple

A letter arrives at a building. Reception logs it, security checks the sender is allowed in, someone verifies the form is filled correctly, and only then does it reach the person who actually does the work. On the way out it goes back past the same desks in reverse.

🎓 Professional

public/index.php is the single entry point. It loads Composer's autoloader, bootstraps the application container, and hands the Request to the HTTP kernel. The kernel runs global middleware, matches a route, runs that route's middleware group, then resolves and calls the controller. The Response travels back out through the same middleware in reverse order.

That last detail is the one to say out loud: middleware is an onion, not a queue. Code before $next($request) runs on the way in; code after it runs on the way out, once the response exists. 

<?php declare(strict_types=1);

final class MeasureDuration
{
    public function handle(Request $request, Closure $next): Response
    {
        $start = microtime(true);          // ── on the way IN

        $response = $next($request);       // ── everything deeper happens here

        $ms = (microtime(true) - $start) * 1000;   // ── on the way OUT
        return $response->header('X-Duration-Ms', (string) round($ms, 1));
    }
}

Run php artisan route:list on any project and read the middleware column. That list, in that order, is the pipeline for each route.

The service container

🧒 Simple

Instead of every class building its own tools, it writes down what it needs, and someone hands them over at the door. When you want to swap a real tool for a fake one in a test, you change what is handed over — not the class.

🎓 Professional

The container resolves dependencies from constructor type hints, recursively. Type-hint a concrete class and it just builds it. Type-hint an interface and it needs a binding telling it which implementation to use — and that binding is the seam that makes the code testable and swappable.

bind() gives a fresh instance every resolution; singleton() gives the same one for the life of the request. Remember that "the life of the request" is the ceiling: PHP is shared-nothing, so a Laravel singleton is not a cross-request singleton the way it would be in Java or .NET. That difference catches people arriving from those languages. 

<?php declare(strict_types=1);

// In a service provider's register() method:
$this->app->bind(PaymentGateway::class, StripeGateway::class);
$this->app->singleton(InvoiceNumbering::class, fn ($app) =>
    new InvoiceNumbering($app->make(Connection::class), prefix: 'FT'));

// Anywhere: the container reads the type hints and builds the graph.
final class ConfirmOrder
{
    public function __construct(
        private readonly PaymentGateway $gateway,      // resolved from the binding
        private readonly InvoiceNumbering $numbering,  // the shared instance
    ) {}
}

// Contextual binding — same interface, different implementation per consumer.
$this->app->when(RefundOrder::class)
          ->needs(PaymentGateway::class)
          ->give(SandboxGateway::class);

Facades, and what they hide

🧒 Simple

It looks like you are calling a shortcut, and you are. Behind the shortcut, somebody quietly fetches the real tool and passes your request along to it.

🎓 Professional

Cache::get() looks static and is not. A facade is a static proxy that resolves the real object out of the container and forwards the call to it. That is why Cache::shouldReceive() can mock it in a test — the facade swaps what the container returns.

The trade-off worth stating: facades hide dependencies. A class using five facades has a constructor that declares nothing, so its real dependencies are invisible to a reader and to static analysis. In domain code, prefer constructor injection; keep facades for glue.

Validation and form requests

🧒 Simple

Check the form at the door, not at the desk. By the time it reaches the person who does the work, it is already known to be correct.

🎓 Professional

A form request moves validation out of the controller and runs it before the controller method is entered — so by the time your code runs, the input is already known-good. On failure Laravel returns 422 with the field errors, or redirects back for a web request, without you writing either branch.

authorize() on the same object is where "may this user do this at all?" belongs, and returning false there produces a 403. Two different questions, two different methods, both answered before the business logic starts. 

<?php declare(strict_types=1);

final class StoreOrderRequest extends FormRequest
{
    public function authorize(): bool
    {
        return $this->user()->can('create', Order::class);   // 403 if false
    }

    /** @return array<string, mixed> */
    public function rules(): array
    {
        return [
            'customer_id'      => ['required', 'integer', 'exists:customers,id'],
            'lines'            => ['required', 'array', 'min:1'],
            'lines.*.sku'      => ['required', 'string', 'max:32'],
            'lines.*.quantity' => ['required', 'integer', 'min:1'],
        ];
    }
}

// The controller now only ever sees valid input.
public function store(StoreOrderRequest $request): JsonResponse
{
    $order = $this->orders->create($request->validated());
    return response()->json(new OrderResource($order), 201);
}

Where Symfony differs

🧒 Simple

The same kind of toolbox, arranged differently. Laravel puts the common tools within reach and decides a lot on your behalf; Symfony makes you say where everything goes, and then never surprises you.

🎓 Professional

Symfony is the same ideas with different defaults: explicit configuration over convention, Doctrine (Data Mapper) instead of Eloquent, and a compiled container configured in YAML or PHP attributes rather than resolved at runtime. Laravel optimises for how quickly you can build; Symfony for how much the framework enforces.

Worth knowing: Laravel is built on Symfony components — HttpFoundation, Console, Routing. Saying that in an interview shows you have looked below the surface, and it is also why moving between them is much less work than it appears.

Golden rules
  • Middleware is an onion. Before $next() on the way in, after it on the way out; order is behaviour, not style.
  • The container resolves from type hints. Bind an interface and you have a seam.
  • A Laravel singleton lasts one request. Shared-nothing means there is no longer scope.
  • A facade is a container lookup wearing static syntax — convenient, and it hides dependencies.
  • Validate in a form request, so the controller only ever sees valid input. authorize() is a separate question from rules().
  • Laravel is built on Symfony components. They are not opposite worlds.
  • Learn what the framework does, not just how to call it. That is the entire difference the interview is measuring.

"Mi spieghi il ciclo di vita di una richiesta in Laravel."

Walk it in order and land the onion detail: "Tutto entra da public/index.php, che carica l'autoloader di Composer e crea il container. Il kernel HTTP esegue i middleware globali, poi il router individua la rotta ed esegue i middleware di quel gruppo, infine il container risolve il controller leggendo i type hint del costruttore. La risposta ripercorre i middleware in ordine inverso: quello che scrivo prima di $next($request) gira in entrata, quello che scrivo dopo gira in uscita, quando la response esiste già."
