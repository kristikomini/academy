The toolchain and the debugger nobody sets up

Two developers with identical knowledge of PHP can differ by a factor of several in daily output, and the difference is usually this chapter. One of them sets a breakpoint and inspects the actual state; the other adds var_dump, reloads, adds another, reloads, and does it eleven times. Xdebug takes twenty minutes to configure once, and most candidates never have.

From the advert

Not in any advert. Nobody writes "must be able to use a debugger". But every technical interviewer asks how you would investigate something, and "aggiungo dei var_dump" is a visibly weaker answer than "metto un breakpoint e guardo lo stack".

Xdebug: step debugging, actually configured

🧒 Simple

A debugger lets you stop the program on a chosen line and look at everything: every variable, the whole chain of calls that got you there, and what happens next as you step through it one line at a time. It is the difference between reading about the crime and being there.

🎓 Professional

Xdebug 3 simplified the configuration into one setting, xdebug.mode, and the remaining friction is entirely about networking: PHP connects out to your editor, not the other way round, which is why it fails inside Docker until you tell it where the host is.

Once it is running, the capabilities worth knowing beyond the breakpoint: conditional breakpoints ($order->id === 4471), which is how you debug the one record out of fifty thousand that misbehaves; break on exception, which stops at the throw rather than at the log line, so you see the state that caused it; watch expressions; and step into the framework’s own code, which is by far the fastest way to understand what Laravel is really doing.

Two more Xdebug modes that are separate tools in the same extension: profile produces a cachegrind file you open in KCachegrind or PhpStorm and shows you where time actually went; coverage is what PHPUnit uses to compute coverage (ch. 24).

Never enable Xdebug in production. Even in develop mode it costs real performance, and debug mode with an open port is a remote code execution risk. Local and CI only.

Try it. The Docker configuration is the one that defeats people. This is the whole thing: three lines of ini, one host mapping, one editor mapping.

# docker/php/xdebug.ini
zend_extension=xdebug

xdebug.mode=debug,develop
xdebug.start_with_request=yes
xdebug.client_port=9003

# THE line everyone gets wrong: PHP dials OUT to your editor, so it needs the
# address of the host from inside the container.
#   Docker Desktop (Mac/Windows):  host.docker.internal
#   Linux:                         add extra_hosts below and use the same name
xdebug.client_host=host.docker.internal

xdebug.idekey=PHPSTORM
xdebug.log=/tmp/xdebug.log          # when it does not connect, the answer is in here

# compose.yaml
services:
  php:
    build: ./docker/php
    volumes:
      - .:/var/www/html
    extra_hosts:
      - "host.docker.internal:host-gateway"   # required on Linux
    environment:
      PHP_IDE_CONFIG: "serverName=bottega"    # must match the server name in the IDE

# In PhpStorm: Settings → PHP → Servers → name it "bottega", tick "Use path mappings",
# map the project root to /var/www/html. Without that mapping the breakpoint is set on
# a file path the container does not recognise, and it silently never triggers —
# which is the failure people give up on.
⚠ Trap

A breakpoint that never fires is nearly always path mapping, not Xdebug being broken. Your editor says /home/kristi/progetto/app/Http/Controller.php; PHP inside the container says /var/www/html/app/Http/Controller.php. Without the mapping the two never match. Check xdebug.log — it will show the connection succeeding, which is exactly what makes this so confusing.

Static analysis: PHPStan and the baseline

🧒 Simple

A static analyser reads your code without running it and tells you about mistakes that would only show up later — a method that does not exist, a variable that might be null, an argument of the wrong type. It is a reviewer that never gets tired.

🎓 Professional

PHPStan (or Psalm) has levels 0 to 10. The strategy that works on a real codebase: start at level 0, fix what it finds, raise one level at a time. On a legacy project, generate a baseline — a file listing every current error — so the build passes today and fails only on new problems. That single move makes static analysis adoptable in a codebase where a clean run is years away (ch. 16b).

Add larastan on Laravel, because Eloquent’s magic defeats a generic analyser. And use the annotations that give it something to work with: generics in docblocks (@return list<Order>) turn "array" into a type the analyser can check, which is where most of the real value on a typed codebase comes from.

The other three in the standard toolchain:

  • PHP-CS-Fixer or Laravel Pint — formatting, decided once and enforced automatically. The point is not beauty; it is that formatting disappears from code review, which is where it wastes the most time (ch. 35).
  • Rector — automated refactoring by rule set: version upgrades, dead code, type declarations. Read the diff; it is a tool, not an authority.
  • Composer audit — checks your dependencies against known vulnerabilities. One command, run it in CI (ch. 30).

The editor, and the shortcuts that compound

🧒 Simple

Whichever editor you use, learn to jump to a definition, find every usage, and rename a symbol everywhere. Those three cover most of what you do all day, and doing them by hand is a tax you pay hourly.

🎓 Professional

PhpStorm is the standard in Italian PHP shops and worth the licence: real static understanding of the code, first-class Xdebug integration, database tools, and refactorings that are safe rather than textual. VS Code with Intelephense plus the PHP Debug extension is a capable free alternative, and increasingly common.

The habits that compound: go to definition and find usages; safe rename across the project; extract method; the HTTP client file (.http) checked into the repository so API requests are shared and versioned instead of living in someone’s Postman account; and the debugger bound to a key you press without thinking.

Also learn the terminal tools you will need on a server where there is no editor at all: tail -f, grep -r, jq for JSON logs (ch. 25), and php -a or php artisan tinker for a REPL against the real application — which is frequently the fastest way to answer "what does this actually return".

⚠ Trap

dd() left in production code. It is not merely embarrassing: dd() and var_dump() of an object print connection details, environment values and tokens straight to the page, and search engines index them. Add a CI grep for dd(, dump(, var_dump( and console.log(, or a pre-commit hook (ch. 30). Every team that has been bitten by this has one.

Golden rules
  • Configure Xdebug once. It repays the twenty minutes in the first week.
  • A silent breakpoint is a path mapping, not a broken extension.
  • Conditional breakpoints and break-on-exception are where the real speed is.
  • Never Xdebug in production. Cost and remote-execution risk.
  • PHPStan with a baseline: freeze old debt, fail on new.
  • Automate formatting so review is about design, not spacing.
  • Profile before optimising. Measured, not guessed.
  • Grep for dd( in CI. It leaks more than it embarrasses.

"Come fa il debug di un problema che non riesce a riprodurre facilmente?"

The answer that separates the two developers in the lede: "Uso il debugger, non i var_dump. Se il problema riguarda un record specifico metto un breakpoint condizionale sull’id, così si ferma solo su quello e vedo lo stato vero: variabili, stack, cosa è arrivato in ingresso. Se è un’eccezione uso il break on exception, che si ferma dove viene lanciata e non dove la logghiamo. Se non riesco proprio a riprodurlo in locale, parto dai log strutturati e dal request id per ricostruire la sequenza, e se serve profilo con Xdebug per capire dove va il tempo invece di indovinare. In un caso così la prima cosa che faccio comunque è scrivere il test che fallisce: se non riesco a farlo fallire, non ho ancora capito il problema."
