Cloud hosting and deployment

Not usually a junior requirement, and it is what turns a project you wrote into a URL somebody can open — which is exactly what gets discussed in an interview. "L’ho messo online io" invites twenty minutes of good questions about environment configuration, secrets, backups and what happens during a deploy, and every one of those answers is a chance to sound like somebody who has run something real.

From the advert

Not in any advert. The adverts ask for Docker (ch. 28) and stop there. But a portfolio project with a working URL and a sentence about how it deploys is worth more than one more framework on the CV (ch. 36).

Where to host it, and what each choice costs

🧒 Simple

You can rent a whole machine and set it up yourself, or pay someone to do the setting up. The first is cheaper and you own the problems; the second costs more and removes most of them.

🎓 Professional
  • A VPS — Hetzner, Contabo, OVH, DigitalOcean. A few euro a month for something that comfortably runs a real application. You own nginx, PHP-FPM, MySQL, TLS, backups, updates and the firewall. Best value and the best learning; also genuinely yours to keep patched.
  • A managed control plane — Laravel Forge, Ploi, RunCloud. They provision and configure your VPS: nginx, PHP, certificates, deploy scripts, queue workers, scheduled tasks. Roughly the cost of a coffee a week, and it removes about eighty per cent of the ways a first deployment goes wrong. This is what most Italian agencies actually use.
  • Platform as a service — Laravel Cloud, Platform.sh, Render, Fly.io. You push, they build and run it. Most expensive per unit of compute, least operational burden.
  • Serverless (Bref on Lambda, Laravel Vapor) — genuine scale-to-zero and per-request billing. The trade is cold starts, a 15-minute execution ceiling, an ephemeral filesystem and a different mental model for queues and sessions. Excellent for spiky workloads, unnecessary for a gestionale with 40 users.
  • Shared cPanel hosting — its own chapter, because a large share of Italian PHP runs there and its constraints are severe (ch. 29b).

Latency is a real consideration for Italian clients: a server in Falkenstein or Milano behaves noticeably better for users in Emilia-Romagna than one in Virginia. And for public-sector or health-adjacent clients, where the data physically sits is a contractual question — EU region, and be able to say so.

Environment configuration and secrets

🧒 Simple

The same code has to run on your laptop, on staging and in production with different databases and different keys. So nothing that differs between them may be written in the code — it comes from the environment.

🎓 Professional

Config from the environment, one artefact for every stage. In PHP that means .env locally and real environment variables (or a secret manager) on the server — never a .env committed to the repository, and never one readable from the web root, which is a finding that shows up in scans constantly.

The rules that matter:

  • Commit .env.example with every key present and no value. It is the documentation of what the application needs, and it is what makes onboarding possible.
  • Never call env() outside a config file in Laravel. With config:cache enabled — which you want in production — env() returns null everywhere else. This is the single most common Laravel deployment bug and a very good interview question.
  • Secrets belong in a manager — the platform’s, or Vault, or at minimum a file with restrictive permissions outside the document root. Not in Git, not in the image (ch. 28), not in the CI log.
  • Rotate on exposure. If a key reached a log, a screenshot or a repository, it is compromised (ch. 26).
  • APP_DEBUG=false in production. Laravel’s debug page prints environment variables — database password included — to anyone who triggers an exception. This is a real breach, not a tidiness issue (ch. 15).
⚠ Trap

The document root. Point the web server at public/, never at the project root. Getting this wrong exposes .env, composer.json, storage/ and your entire source tree to anyone who guesses a path — and /.env is the first thing every automated scanner tries, within minutes of a new host appearing. It is the most consequential single line in an nginx config.

Zero-downtime deploys, and the migration problem

🧒 Simple

Deploying by copying files over a running site means visitors get a mix of old and new for a few seconds. The fix is to build the new version beside the old one and switch between them in one instant.

🎓 Professional

Atomic deploys: build into releases/<timestamp>, run composer install and the asset build there, then repoint a current symlink. The switch is one atomic operation. shared/ holds what must survive a release — .env, storage/, uploads — symlinked into each release. Deployer is the PHP-native tool for this; Forge and Envoyer do it for you.

Three PHP-specific steps that are forgotten and cause confusing bugs:

  1. Reload PHP-FPM, or OPcache keeps serving the previous code when validate_timestamps=0 (ch. 01). Also invalidate the realpath cache, which the symlink swap otherwise defeats.
  2. queue:restart, or workers continue running the old release indefinitely (ch. 22).
  3. Rebuild the caches: config:cache, route:cache, view:cache. And remember a closure in a route file makes route:cache fail (ch. 19).

Migrations are the part that breaks rollback and deserves the most thought. During a deploy there is always a moment when old code meets the new schema, so a migration that drops or renames a column takes the site down for that moment and makes rollback impossible. Expand/contract: add the new column and write to both (release 1), migrate the reads and backfill (release 2), drop the old column (release 3). Slower, and it keeps rollback available at every step — which is what you want at 18:00 on a Friday (ch. 25b). Also beware that a large ALTER TABLE on MySQL can lock a table for minutes; know pt-online-schema-change exists.

Try it. An atomic deploy in plain shell — what Deployer and Envoyer do underneath. Reading it once makes the tools obvious rather than magical.

#!/usr/bin/env bash
set -euo pipefail          # fail loudly: a half-finished deploy is worse than none

APP=/var/www/bottega
REL="$APP/releases/$(date +%Y%m%d%H%M%S)"

# 1. Build the new release BESIDE the live one. Nothing is live yet.
git clone --depth 1 --branch main git@github.com:acme/bottega.git "$REL"
cd "$REL"
composer install --no-dev --optimize-autoloader --no-interaction --prefer-dist

# 2. Link the things that must survive a release.
ln -sfn "$APP/shared/.env"     "$REL/.env"
rm -rf "$REL/storage"
ln -sfn "$APP/shared/storage"  "$REL/storage"

# 3. Migrations run BEFORE the switch — and only additive ones, so the currently
#    live old code keeps working against the new schema (expand/contract).
php artisan migrate --force

php artisan config:cache
php artisan route:cache
php artisan view:cache

# 4. The switch: one atomic symlink swap. No visitor sees a half-deployed tree.
ln -sfn "$REL" "$APP/current.new" && mv -Tf "$APP/current.new" "$APP/current"

# 5. The three forgotten steps.
sudo systemctl reload php8.3-fpm     # OPcache still holds the old code without this
php artisan queue:restart            # workers hold the old code too
php artisan up

# 6. Keep the last five releases — rollback is `ln -sfn` to the previous one.
ls -1dt "$APP"/releases/* | tail -n +6 | xargs -r rm -rf

Backups, TLS and the boring things that save you

🧒 Simple

A backup you have never restored is not a backup, it is a hope. Test it once and you will know something almost nobody knows about their own system.

🎓 Professional

3-2-1: three copies, two media, one off-site. For a PHP application that means a nightly database dump plus the uploads directory, shipped somewhere that is not the same server — a backup on the machine that dies is not a backup. Encrypt it, because it contains personal data and GDPR applies to it exactly as it applies to the database.

Restore-test it on a schedule. Actually restoring into a scratch database is the only way to discover that the dump has been failing since March, or that it silently omits the routines (ch. 10b). Then know your two numbers: RPO (how much data you can afford to lose — the backup interval) and RTO (how long a restore takes). Being able to state both for a system you have run is a strong senior signal.

The rest of the checklist, briefly: TLS via Let’s Encrypt with automatic renewal (an expired certificate is a self-inflicted outage, and it always happens on a Sunday); a firewall with only 80, 443 and SSH open, and the database not listening on a public interface; SSH keys with password authentication disabled; unattended security upgrades; log rotation, because a full disk breaks everything at once and in confusing ways; and monitoring that tells you before the client does (ch. 25).

Golden rules
  • Document root is public/. The single most consequential line.
  • APP_DEBUG=false in production. The debug page prints your secrets.
  • Never env() outside config. Caching makes it null.
  • Commit .env.example, never .env.
  • Atomic deploys via symlink, with shared storage outside the release.
  • Reload FPM and restart queues on every deploy.
  • Expand/contract for migrations, so rollback stays possible.
  • An untested backup is not a backup. Know your RPO and RTO.

"Come deployerebbe questa applicazione senza downtime?"

Walk the sequence and name the three PHP-specific steps — that is what shows experience: "Deploy atomico: costruisco la nuova release in una cartella a parte, ci faccio composer install e i cache di config e route, e solo alla fine sposto un symlink — così nessuno vede un albero mezzo aggiornato. Poi tre cose che si dimenticano sempre: ricarico PHP-FPM, altrimenti OPcache continua a servire il codice vecchio; faccio queue:restart, perché i worker tengono in memoria la release precedente; e tengo storage e .env in una cartella condivisa fuori dalla release. La parte delicata sono le migration: durante il deploy il codice vecchio gira contro lo schema nuovo, quindi uso expand/contract — prima aggiungo la colonna e scrivo su entrambe, poi sposto le letture, e solo in una release successiva tolgo la vecchia. Così il rollback resta sempre possibile."
