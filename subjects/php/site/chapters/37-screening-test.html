The screening test

Almost every Italian software house screens before the technical interview, and candidates lose here for reasons that have nothing to do with their code: a submission with no README, a solution that does not run on the reviewer’s machine, forty hours spent on a four-hour exercise, or a live session spent silently staring at an editor. All four are avoidable, and knowing what is actually being measured is most of the fix.

From the advert

Not in any advert. It appears in the email after the advert: "le inviamo un piccolo esercizio, ci faccia sapere entro una settimana". That message is a filter, and most people treat it as a formality.

What they are actually measuring

🧒 Simple

They are not checking whether you can make it work — they assume you can. They are looking at how you work: how you organise it, whether you tested it, and whether they would enjoy reviewing your code every week.

🎓 Professional

A take-home is read in about fifteen minutes, and in that time the reviewer is answering:

  • Does it run? Clone, follow the README, run it. If it fails here, nothing else is read. This is the single most common elimination and it is entirely mechanical.
  • Is it structured? Not "is it hexagonal" — is it obvious where things are, and is the logic separated from the framework glue (ch. 23)?
  • Did you test the part that matters? Three meaningful tests beat forty trivial ones, and beat zero by an enormous margin (ch. 24).
  • Did you handle the edge cases? Empty input, a duplicate, a value out of range. Most submissions handle only the happy path, so this is where you separate yourself cheaply.
  • Can you explain your decisions? The README is where this happens, and it is the part almost nobody writes.

Note what is not on the list: cleverness. A concise, obvious solution scores better than an ingenious one, because the reviewer is imagining maintaining it.

⚠ Trap

Over-engineering the small exercise. A CSV-parsing task returned with six layers, an event bus, a Docker Compose stack and a dependency-injection container reads as poor judgement, not as seniority — the reviewer concludes you will do this to their codebase too. The opposite mistake is one 200-line file with the logic in a controller. Aim at the middle and say in the README where you deliberately stopped: "non ho aggiunto un layer di repository: con una sola implementazione sarebbe stato solo cerimonia". That sentence demonstrates the judgement the structure alone cannot.

The take-home: scope, time and the README

🧒 Simple

Do what was asked, in roughly the time they suggested, and write a short document explaining what you did and why. The document is worth more than the last two hours of polishing.

🎓 Professional

Respect the timebox, and be honest about it. If they say four hours, spend four. Spending twenty is unfair to other candidates, and it misrepresents your speed — you will be measured against that pace afterwards. If you run out of time, ship what you have and write "con altre due ore avrei aggiunto X e Y, in questo ordine". That is a strong answer; a reviewer reads it as prioritisation.

Ask one clarifying question by email if the specification is genuinely ambiguous. It is not a weakness — it is the behaviour they claim to want in the advert (ch. 35). If you would rather not, state your assumption in the README instead; either is fine, and silently guessing is not.

Use Git properly. A handful of meaningful commits with real messages, not one commit called "solution". Some reviewers read the history specifically to see how you work (ch. 26).

The README is the highest-value artefact in the submission, and it takes twenty minutes. Most candidates send code with no explanation, so this alone puts you in a different group.

Try it. The README template. Twenty minutes, and it is the part the reviewer actually reads before deciding whether to read your code carefully.

# Ordini — esercizio per [Azienda]

## Come eseguirlo
    cp .env.example .env
    docker compose up -d
    docker compose exec app php artisan migrate --seed
    docker compose exec app php artisan test

App su http://localhost:8080 · PHP 8.3 · MySQL 8 · nessun altro requisito.

## Cosa fa
Importa un CSV di ordini, valida ogni riga, e restituisce un report
con le righe accettate e quelle rifiutate con il motivo.

## Decisioni e perché
- **Generator per la lettura del CSV.** Il file di esempio è piccolo, ma un
  import è la cosa che cresce per prima: la memoria resta costante.
- **Importi in centesimi (int), mai float.** `0.1 + 0.2 !== 0.3`, e qui si
  parla di totali fatturabili.
- **Validazione in una classe separata dal comando.** È la parte che ha
  davvero delle regole, ed è quella che ho voluto poter testare da sola.
- **Niente repository pattern.** Con una sola implementazione e nessun test
  double necessario sarebbe stata cerimonia. Con una seconda sorgente dati
  lo aggiungerei.
- **Errori raccolti, non fatali.** Una riga sbagliata non deve far fallire
  l'import di 9.999 righe buone: l'utente vuole il report.

## Test
    php artisan test         # 11 test, 24 asserzioni

Ho testato la validazione riga per riga (compresi i casi limite: file vuoto,
intestazione mancante, importo negativo, codice duplicato) e l'import
end-to-end. Non ho testato il rendering della vista: è markup senza logica.

## Cosa farei con più tempo
1. Import idempotente su una chiave del file, così un doppio invio non duplica.
2. Spostare l'import su una coda con notifica via email a fine elaborazione.
3. Un indice su `(cliente_id, data)` — con volumi veri quella query non regge.

## Assunzioni
- Il separatore decimale nel CSV è la virgola (formato italiano).
- Le righe duplicate nello stesso file sono un errore, non un aggiornamento:
  non era specificato e ho scelto l'interpretazione più prudente.

Tempo impiegato: ~4 ore, come indicato.

Live coding and pair-programming sessions

🧒 Simple

In a live session the thing being tested is how you think, and the only way they can see that is if you say it out loud. Silence is the failure mode, not a wrong first idea.

🎓 Professional

Narrate. "Prima chiarisco un paio di cose sull’input… parto dal caso semplice e poi lo generalizzo… questa è O(n²), per ora va bene e poi la sistemo." A candidate who thinks out loud is being interviewed; a silent one is being watched.

The sequence that works:

  1. Restate the problem and ask about the edges: empty input, duplicates, size, what to do on an invalid value. Two minutes here prevents solving the wrong problem, and it is itself part of the assessment.
  2. Say your approach before typing. If it is wrong, they will redirect you now rather than after fifteen minutes.
  3. Make it work, then make it good. A working naive solution plus "ora la ottimizzo" is far better than a half-finished clever one.
  4. Test it out loud with a concrete example, including an edge case. Walking through your own code with real values catches bugs and shows discipline.
  5. Say what you would change. Naming your own solution’s weakness before they do is one of the strongest moves available.

If you get stuck, say so and say where. "Sto cercando di ricordare la firma esatta di array_column" is normal and human; five minutes of silent scrolling is not. Asking a question in a pairing session is the behaviour they want on the team — that is why it is a pairing session.

On tools: ask what is allowed. Many companies now permit documentation and an AI assistant, because it reflects the actual job; using one well — and reviewing what it produces rather than pasting it — can itself be a positive signal (ch. 33b). Never use one covertly.

Timed platform tests, and when to decline

🧒 Simple

Some companies use automated timed tests with puzzle-style problems. They reward practice more than skill, so if you are going to face one, practise the format for a few evenings rather than trusting your experience.

🎓 Professional

HackerRank, Codility and similar are common at consultancies and larger groups. They test algorithmic pattern-matching under a clock — a specific and learnable skill that has little to do with maintaining a gestionale. A few evenings on arrays, hash maps, sorting and string handling covers most of what appears, and knowing that isset() on a hash is O(1) while in_array() is O(n) (ch. 06) resolves a surprising share of the time-limit failures. Read the constraints: n ≤ 105 is telling you the O(n²) solution will time out.

When to push back. An unpaid exercise of eight hours or more, or one that is transparently production work — "build us an integration with this API" — is reasonable to decline or to negotiate. Do it politely and offer an alternative: "posso dedicarci volentieri tre o quattro ore; in alternativa possiamo fare una sessione insieme, o posso illustrarvi un progetto che ho già scritto". A company that reacts badly to that has told you something useful about how it treats people’s time.

And whatever the format, follow up: a short message when you submit, saying what you built and what you would add next, keeps you in mind and reads as engagement rather than pestering.

Golden rules
  • It must run from a clean clone. Test that yourself, in a fresh directory.
  • Respect the timebox, and say what you would do with more.
  • The README is the highest-value twenty minutes. Decisions, not features.
  • Say where you deliberately stopped. Restraint reads as judgement.
  • A few real tests, on the part with actual rules.
  • Handle the edge cases. Most submissions do not.
  • Narrate in live sessions. Silence is the only real failure.
  • Working first, clever never.

"Ha domande sull’esercizio?" — the email you should always answer

Reply, briefly, and use it to set expectations: "Grazie, un paio di cose per non fare assunzioni sbagliate: le righe duplicate nello stesso file vanno considerate un errore o un aggiornamento? E c’è un ordine di grandezza atteso per il file — migliaia o milioni di righe? Cambia l’approccio. Nel frattempo procedo: conto di dedicarci le quattro ore indicate e vi mando un repository con un README che spiega le scelte." Two precise questions, a stated assumption about effort, and a commitment — before writing a line of code you have already demonstrated the analysis skill the advert asked for (ch. 35).
