Legacy PHP and how to migrate it

Nobody advertises it and almost everybody does it. A large share of Italian PHP work is keeping alive something written between 2008 and 2015: procedural, no tests, mysql_query in the templates, business rules in the HTML. Being good at this is a genuine speciality, it is rarer than being good at Laravel, and it is worth saying out loud in an interview.

From the advert

Not in any advert. But "disponibilità ad attività di manutenzione ed assistenza" is in several, and this is what that line means when you arrive. A candidate who is visibly unbothered by legacy code is unusual and memorable.

The first week: characterise before you change

🧒 Simple

Do not start by improving anything. Start by making the thing runnable on your machine and writing down what it does, because right now the only description of its behaviour is the behaviour itself.

🎓 Professional

The order that works:

  1. Get it running locally, with a copy of real-shaped data. Until this is true you are editing blind, and this step alone often takes three days in an old project.
  2. Put it in Git if it is not already, including the schema and any stored routines (ch. 10b). Some of these codebases are still versioned by index_old_2.php.
  3. Turn on the errors you have been spared. error_reporting(E_ALL) in the local environment reveals the notices production has been swallowing for a decade. Do not fix them yet; read them.
  4. Write characterisation tests. Not tests of what it should do — tests of what it does, including the bugs. Hit the URL, capture the output, assert it does not change. That is your safety net, and it is the difference between refactoring and gambling.
  5. Only now change something, and make the first change small enough to deploy on a Tuesday morning.
⚠ Trap

The rewrite. Every developer meeting a legacy codebase proposes one in the first fortnight, and it is nearly always the wrong call: you would be rebuilding fifteen years of undocumented business rules discovered by the business the hard way, while the old system keeps changing underneath you. The famous failures were all rewrites. If you say anything about this in an interview, say you would strangle it incrementally — that answer is both more correct and far more reassuring to the person who has to pay for it.

PHP 5 to 8, with Rector doing the boring half

🧒 Simple

Upgrading the PHP version is usually the highest-value thing you can do, and much of it is mechanical. There is a tool that performs the mechanical part for you, so your attention goes to the handful of changes that genuinely need thinking.

🎓 Professional

Go one version at a time, deploying between each. The breaks that actually bite:

  • ext-mysql is gone (removed in 7.0). mysql_query → PDO, and that is also where SQL injection gets fixed (ch. 15).
  • PHP 7: uncaught Errors where fatals used to be, list() ordering, changed constructor rules.
  • PHP 8.0: the big one. Many notices became Errors, and string-to-number comparison changed — 0 == "foo" was true and is now false. That is a semantic change in code nobody will flag, and it is the reason an upgrade needs tests rather than a smoke check (ch. 02).
  • PHP 8.1: null passed to a non-nullable internal parameter is deprecated — and in a legacy codebase htmlspecialchars($maybeNull) appears several thousand times.
  • Implicit float-to-int conversions with precision loss now warn.

Rector automates the mechanical transformations by version set; run it one set at a time and read the diff, because it is a refactoring tool and not an oracle. PHPStan at level 0 or 1 on a legacy codebase finds real bugs immediately — undefined variables, wrong argument counts, methods that do not exist — and the baseline file lets you freeze the existing debt and fail the build only on new problems, which is the single most practical static-analysis move there is (ch. 27).

The strangler pattern in practice

🧒 Simple

Put the new application in front of the old one. Route one page at a time to the new code, and let everything you have not done yet fall through to the old system. Eventually there is nothing left to fall through to.

🎓 Professional

Named for the strangler fig. A reverse proxy — or plain nginx location blocks, or a front controller with a fallback — sends known routes to the new stack and everything else to the old. The system is in both states at once, in production, for months, and that is the feature: every step is small, deployable and reversible.

The hard parts are not the routing:

  • Shared session. A user logged into the old application must be logged into the new one. Move sessions to Redis or the database with a shared cookie domain, and do this first — it blocks everything else.
  • One database, two writers. Both applications write the same tables, so an invariant enforced only in the new code is not enforced. This is the argument for a database-level constraint or, briefly, a trigger (ch. 10b).
  • Duplicated logic during the overlap. A VAT rule now lives in two places. Accept it, write it down, and keep the list of duplicates short and visible.
  • Pick the first route deliberately. Something visible enough to prove the approach and unimportant enough to fail safely — never the checkout.

Try it. The whole pattern, in a front controller. Everything the new router does not recognise falls through to the legacy application, untouched.

<?php declare(strict_types=1);
// public/index.php — the strangler seam.

$path = parse_url($_SERVER['REQUEST_URI'], PHP_URL_PATH) ?? '/';

/* Routes already migrated. The list only ever grows, and every entry is a
   deployment that can be reverted by deleting one line. */
$migrated = [
    '#^/api/v1/orders#'   => __DIR__ . '/../new/bootstrap.php',
    '#^/clienti/nuovo$#'  => __DIR__ . '/../new/bootstrap.php',
];

foreach ($migrated as $pattern => $bootstrap) {
    if (preg_match($pattern, $path) === 1) {
        require $bootstrap;
        return;
    }
}

// Not migrated yet: the 2011 application, exactly as it was.
require __DIR__ . '/../legacy/index.php';

Changing code you do not trust

🧒 Simple

In a codebase with no tests, the risk is not writing the wrong code — it is not knowing what else you touched. Work in small, separately deployable steps, and never mix a refactor with a behaviour change in the same commit.

🎓 Professional

The techniques that repay themselves in a week:

  • Sprout method / sprout class. Do not untangle the 600-line function. Write the new behaviour in a clean, tested class and call it from one line inside the mess. The new code is good; the old code shrinks by attrition.
  • Seams. To test something calling date() or a global, extract the dependency into a parameter with a default. Minimal change, and suddenly testable (ch. 24).
  • The boy scout rule, bounded. Improve the function you touched, not the file, and never the directory. An 800-line diff cannot be reviewed and will not be reverted cleanly when something breaks at 18:00 on Friday.
  • Separate the commits. "Refactor, no behaviour change" and "fix the VAT rounding" as two commits means git bisect can tell you which one broke production (ch. 26).
  • Read the blame before judging. That strange condition is usually a customer requirement nobody wrote down. git log -S on the odd line frequently produces the explanation and, occasionally, the ticket.
Golden rules
  • Runnable locally, then Git, then tests, then changes. In that order.
  • Characterisation tests capture what it does, bugs included.
  • Never propose the rewrite. Strangle it, one route at a time.
  • Upgrade one version at a time, with Rector for the mechanical part.
  • PHPStan with a baseline: freeze old debt, fail on new.
  • Sprout new code beside the old; do not untangle it first.
  • Refactor and behaviour change are two commits. Always.

"Si trova davanti a un’applicazione in PHP 5.6, senza test. Da dove parte?"

The answer that reassures the person paying: "Non da una riscrittura. Prima la faccio girare in locale con dati realistici e la metto sotto Git, schema e stored procedure comprese. Poi scrivo test di caratterizzazione — non quello che dovrebbe fare, quello che fa oggi, bug inclusi — perché senza quelli ogni modifica è una scommessa. A quel punto porto la versione di PHP su, una alla volta, con Rector per la parte meccanica e PHPStan con un baseline per congelare il debito esistente. Le funzionalità nuove le scrivo in codice pulito accanto al vecchio e le richiamo da una riga, e se serve un rifacimento uso lo strangler pattern: una rotta alla volta, sempre deployabile."
