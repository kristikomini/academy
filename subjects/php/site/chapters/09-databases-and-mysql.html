Databases and MySQL/MariaDB

Before the queries, the shape. Choosing a column type, a charset and an engine takes thirty seconds and is nearly permanent — changing them later means an ALTER TABLE on a live system, which is the kind of evening nobody enjoys. Most of the decisions have one right answer, and knowing why is the interview.

From the advert

"Conoscenza di database relazionali (MySQL/MariaDB)". MySQL and MariaDB are where Italian PHP lives — behind WordPress, PrestaShop, Magento and nearly every gestionale.

InnoDB, and why the choice is already made

🧒 Simple

MySQL can store tables in more than one way. One of the old ways is faster at reading but cannot undo a half-finished job and locks the whole table while it writes. You want the other one.

🎓 Professional

InnoDB for everything. It gives you transactions, foreign keys, row-level locking and crash recovery. MyISAM has none of those — it locks the whole table on write and a crash can leave it corrupt — and it is the default only in very old installations.

You still meet MyISAM in inherited codebases, and now you know what to check first when a legacy gestionale "randomly loses data" or grinds to a halt under concurrent writes.

utf8 is not UTF-8

🧒 Simple

MySQL has something called utf8 that is not actually the whole of UTF-8. It can store most letters but not emoji or some rarer characters. The complete one is called utf8mb4. Always use that one.

🎓 Professional

MySQL's utf8 is an alias for utf8mb3: at most three bytes per character, so anything outside the Basic Multilingual Plane — emoji, some CJK extensions — cannot be stored. Inserting one either throws or silently truncates the string, depending on your SQL mode.

Use utf8mb4 with utf8mb4_unicode_ci (or utf8mb4_0900_ai_ci on MySQL 8), and set it in three places: the column, the connection, and PHP's DSN. A mismatch anywhere produces mojibake, and it is always the connection people forget. 

<?php declare(strict_types=1);

$pdo = new PDO(
    'mysql:host=localhost;dbname=bottega;charset=utf8mb4',   // ← the connection charset
    $user, $pass,
    [
        PDO::ATTR_ERRMODE            => PDO::ERRMODE_EXCEPTION, // fail loudly
        PDO::ATTR_DEFAULT_FETCH_MODE => PDO::FETCH_ASSOC,
        PDO::ATTR_EMULATE_PREPARES   => false,                  // real prepared statements
    ],
);

Those three options are the standard opening move. Without the first, PDO fails silently and you debug a false return value instead of reading an exception.

Column types, and the two that matter

🧒 Simple

Pick the smallest box that definitely fits. And never keep money in the box designed for approximate measurements — use the one designed for exact counting.

🎓 Professional

Money: DECIMAL(10,2), or an integer of minor units. Never FLOAT or DOUBLE — they are binary approximations, so totals drift by a cent and an accountant notices before you do.

Time: DATETIME stores what you wrote; TIMESTAMP converts to UTC on write and back to the session timezone on read, and tops out in 2038. For an Italian business with one timezone, DATETIME and storing UTC explicitly is the least surprising choice.

VARCHAR(255) is a habit, not a rule — it comes from an old index-length limit. Size to the data. And prefer NOT NULL with a sensible default: every nullable column is a branch in every query that touches it.

⚠ Trap

Storing an Italian partita IVA or CAP as an integer loses leading zeros — a Bologna CAP of 40100 survives, an Aosta one of 11100 does too, but a codice destinatario like 0000000 does not. They are identifiers, not numbers: you never do arithmetic on them, so they are CHAR or VARCHAR.

Keys and relationships

🧒 Simple

Every row needs a name that is only ever used once — that is the primary key. When one table points at another, the pointer is a foreign key, and the database refuses to let it point at nothing.

🎓 Professional

An auto-increment BIGINT primary key is the default answer, and it is right most of the time: small, sequential, and it does not fragment the clustered index. In InnoDB the primary key is the physical row order, which is why a random UUIDv4 primary key hurts — every insert lands in the middle. If you need a non-guessable id, keep the integer key internally and expose a UUID (or a v7, which is time-ordered) alongside it.

Declare foreign keys. They cost a little on write and they make orphan rows impossible, which is worth far more. Choose the ON DELETE behaviour deliberately: CASCADE for things that cannot exist alone (order lines), RESTRICT for things that should block the delete (a customer with orders). 

CREATE TABLE orders (
  id           BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  public_ref   CHAR(26)        NOT NULL,             -- what the customer sees
  customer_id  BIGINT UNSIGNED NOT NULL,
  status       ENUM('draft','submitted','confirmed','shipped','delivered','cancelled')
                               NOT NULL DEFAULT 'draft',
  total_cents  INT UNSIGNED    NOT NULL DEFAULT 0,   -- minor units, never FLOAT
  version      INT UNSIGNED    NOT NULL DEFAULT 0,   -- optimistic concurrency
  created_at   DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY uq_orders_public_ref (public_ref),
  KEY idx_orders_customer_created (customer_id, created_at),
  CONSTRAINT fk_orders_customer FOREIGN KEY (customer_id)
    REFERENCES customers (id) ON DELETE RESTRICT
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

Normalisation, and when to stop

🧒 Simple

Write each fact down once. If a customer's address is copied into every order, then changing it means finding every copy — and you will miss one.

🎓 Professional

Third normal form is the working target: every non-key column depends on the key, the whole key, and nothing but the key. It removes update anomalies, which are the expensive kind of bug because they produce data that disagrees with itself.

The deliberate exception is a historical record. An order line stores the price and the customer's address as they were at the time, not a foreign key to the current values — otherwise repricing a product silently rewrites last year's invoices. That is not denormalisation for speed; it is modelling a fact that was true at a moment.

Golden rules
  • InnoDB, always. Transactions, foreign keys, row-level locking.
  • utf8mb4, never utf8 — and set it on the column, the connection and the DSN.
  • Money is DECIMAL or integer cents. Never a float, in the database or in PHP.
  • Identifiers are strings. Partita IVA, CAP, codice destinatario — you never add them up.
  • Sequential primary keys. In InnoDB the primary key is the physical row order.
  • Declare foreign keys, and choose ON DELETE on purpose.
  • Prefer NOT NULL. Every nullable column is a branch in every query.
  • Copy the price onto the order line. History is a fact, not a duplicate.

"Come memorizza un importo in euro?"

Short, certain, with the reason: "Mai in floating point. Uso DECIMAL(10,2), oppure un intero in centesimi, e lo stesso lato PHP. I float sono approssimazioni binarie: 0.1 + 0.2 non fa esattamente 0.3, e su una fattura questo diventa un centesimo di differenza che il cliente nota subito." If they follow up on why cents rather than DECIMAL: integer arithmetic is exact everywhere, including in JavaScript on the way to the browser.
