Views, functions and stored procedures

Somewhere in the gestionale you are about to be hired onto there is a stored procedure written in 2009 that nobody understands and everybody depends on. You will not get to redesign it. You will have to read it, work out what it changes, and add a feature next to it without breaking the invoice run — and that is a genuinely different skill from writing clean new code.

From the advert

Not in any advert. Italian gestionali are full of routines written when the database was the application. The advert says "conoscenza di database relazionali"; the job says "here is sp_ricalcola_giacenze, good luck".

Views: a saved query, with a performance catch

🧒 Simple

A view is a query you gave a name to. You then use that name as if it were a table. It stores no data of its own — every time you select from it, the query underneath runs again.

🎓 Professional

In MySQL a view is resolved one of two ways. MERGE folds the view’s definition into your query, so your WHERE reaches the base tables and indexes are used normally. TEMPTABLE materialises the view first and then filters the result — which means a view over ten million rows builds ten million rows in a temporary table before applying your WHERE id = 42.

MySQL is forced into TEMPTABLE by aggregation, DISTINCT, UNION, a subquery in the select list, or a window function. So the useful mental rule: a view that aggregates cannot be filtered efficiently from outside. That single fact explains most "the view is slow" tickets. Check with EXPLAIN (ch. 11) — a DERIVED line in the plan is the materialisation.

MySQL and MariaDB have no materialised views. When somebody says "we have a materialised view", they mean a summary table refreshed by a job, and it is your responsibility to know how stale it is.

⚠ Trap

Views nested inside views. Three levels deep, each aggregating, is a query plan nobody can read and an optimiser that has given up. It is common in old gestionali because each level was added by a different person solving one report. If you find one at the bottom of a slow page, do not try to optimise the outer view — write the flat query you actually need and compare plans. It is usually ten times faster and shorter than the view stack.

Stored procedures and functions

🧒 Simple

A stored procedure is a small program that lives inside the database instead of in your application. You call it by name and it does several things at once, right next to the data.

🎓 Professional

A procedure is invoked with CALL, can take IN, OUT and INOUT parameters and may return result sets. A function returns one value and can be used inside a query — which is where the danger is, because a function in a WHERE clause runs per row and prevents index use, turning a fast query into a full scan.

The real arguments for them, stated fairly: a set-based bulk update inside the database avoids shipping a million rows to PHP and back; a routine can be the single enforcement point when several applications write to the same schema, which is the common situation in a company where a desktop gestionale and a web front end share one database.

The arguments against are mostly about the surrounding practice: routines are hard to version (they live in the database, not obviously in Git), hard to test, hard to debug — there is no step debugger — and they scatter business logic across two languages so that understanding one rule means reading both. DEFINER semantics are also a security consideration: a routine can execute with its creator’s privileges.

Try it. The shape you will meet in a gestionale, reduced to something you can actually run. Note the DELIMITER dance and the explicit transaction with an exit handler — both are the parts people get wrong when they write their first one.

-- Run this in the mysql client, not through PDO: DELIMITER is a client directive.
DROP PROCEDURE IF EXISTS sp_conferma_ordine;
DELIMITER $$

CREATE PROCEDURE sp_conferma_ordine(IN p_order_id INT, OUT p_esito VARCHAR(32))
BEGIN
    DECLARE v_stato VARCHAR(20);

    -- Without this, a failure mid-way leaves the transaction open and the row locked.
    DECLARE EXIT HANDLER FOR SQLEXCEPTION
    BEGIN
        ROLLBACK;
        SET p_esito = 'errore';
    END;

    START TRANSACTION;

    SELECT stato INTO v_stato FROM ordini WHERE id = p_order_id FOR UPDATE;

    IF v_stato <> 'submitted' THEN
        SET p_esito = 'stato_non_valido';
        ROLLBACK;
    ELSE
        UPDATE ordini SET stato = 'confirmed', confermato_il = NOW() WHERE id = p_order_id;
        UPDATE giacenze g
          JOIN righe_ordine r ON r.articolo_id = g.articolo_id
           SET g.quantita = g.quantita - r.quantita
         WHERE r.ordine_id = p_order_id;
        SET p_esito = 'ok';
        COMMIT;
    END IF;
END$$

DELIMITER ;

CALL sp_conferma_ordine(114, @esito);
SELECT @esito;

Triggers, and why they are the worst of the three

🧒 Simple

A trigger is code that runs automatically whenever a row is inserted, updated or deleted. You do not call it and you cannot see it in your code — which is exactly what makes it hard to live with.

🎓 Professional

Triggers are invisible action at a distance. Your UPDATE touches one row and four other tables change; nothing in the application says so. In MySQL they are per-row (not statement-level), they run inside your transaction, and they add latency to every write on the table forever.

They also break the ORM’s picture of the world: an entity written through Doctrine or Eloquent will hold stale values for anything the trigger changed, because the object in memory was never told. That is the source of the classic "I saved it, then read it back, and it was different" bug.

The defensible uses are narrow: an audit trail that must not be bypassable, or maintaining a denormalised column when several applications write the same table. Both are the "many writers" case again. When there is exactly one application, put it in the application.

Living with a codebase that chose wrong

🧒 Simple

You cannot rewrite it and you should not pretend it is not there. The job is to find out what exists, write it down, and stop adding to it — new logic goes in the application, and the old routines get replaced only when you have to touch them anyway.

🎓 Professional

A working method, in order:

  1. Inventory it. information_schema.ROUTINES and .TRIGGERS tell you what exists and when it was last altered. Do this on day one, because nobody will otherwise tell you the trigger is there.
  2. Get it into Git. mysqldump --routines --triggers --no-data gives you a schema file to commit. Now a change is visible in a diff, which is the single biggest improvement available.
  3. Test the boundary, not the routine. You cannot unit-test a procedure, but you can write an integration test that sets up rows, calls it, and asserts the resulting state (ch. 24). That test is what lets you change anything at all.
  4. Freeze and strangle. New rules go in PHP. When a routine must change, port it and leave the old one in place calling nothing, then delete it a release later (ch. 16b).
  5. Never migrate silently. Moving a rule from a trigger into the application while another application still writes that table removes an invariant for everybody. Find the other writers first — that is the whole reason the logic was in the database.
Golden rules
  • A view that aggregates materialises. Filtering it from outside is too late.
  • MySQL has no materialised views. A "materialised view" is a summary table with a staleness question.
  • A function in a WHERE clause kills the index.
  • Routines need an EXIT HANDLER, or a failure leaves the transaction open.
  • Triggers are invisible, per-row, and lie to your ORM.
  • Dump routines into Git before doing anything else.
  • Find the other writers before moving a rule out of the database.

"Cosa ne pensa delle stored procedure? Da noi ce ne sono parecchie."

This is a loyalty test as much as a technical one — criticising their codebase in the interview is how candidates lose it. Be balanced, then practical: "Non le userei per logica nuova: sono difficili da versionare e da testare, e la logica finisce divisa fra due linguaggi. Però capisco perché ci sono — se più applicazioni scrivono sullo stesso database, la procedura è l’unico punto dove la regola vale per tutti. In un codebase così la prima cosa che farei è metterle sotto Git con un dump e coprirle con test di integrazione, così almeno diventano modificabili; poi la logica nuova la scrivo in PHP e le vecchie le porto fuori solo quando devo già metterci mano."
