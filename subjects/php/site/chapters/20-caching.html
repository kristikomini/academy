Caching: Redis, OPcache and HTTP

"Ottimizzazione delle prestazioni" almost always cashes out as two things: cache it, or move it to a queue. This chapter is the first. It is also the chapter where the famous joke about the two hard problems stops being a joke — getting a value into a cache is trivial, and knowing when it is no longer true is the entire job.

From the advert

"Ottimizzazione delle prestazioni applicative". The interview version is usually "questa pagina è lenta, cosa fa?" — and answering "metto una cache" before measuring is the wrong first move, which is what they are checking.

Measure first, then the three caches you already have

🧒 Simple

Caching hides a slow thing instead of fixing it. Sometimes that is exactly right — but find out what is slow first, because a cache over a missing database index just means you are wrong quickly instead of slowly.

🎓 Professional

Order of operations, and this is the part interviewers listen for: measure, fix the query, then cache. A page doing 400 queries is an N+1 (ch. 12); a page doing one query that takes 4 seconds needs an index (ch. 11). Caching either of those buys a fast page that breaks confusingly the moment the cache misses — and it will miss, at the worst possible moment, which is the deploy.

Before adding anything, know the three caches already present:

  • OPcache — compiled PHP in shared memory. Free, enormous, one config line (ch. 01).
  • The database buffer pool — InnoDB keeps hot pages in RAM. A "slow query" that is fast the second time is this, and it is why benchmarking a query twice is the minimum honest measurement (ch. 09).
  • The browser and any CDN in front — HTTP caching, which costs you nothing per request because the request never arrives.

Only then application caching, which almost always means Redis.

Cache-aside, TTL and what the key must contain

🧒 Simple

The usual pattern: look in the cache; if it is there use it; if not, do the work, put it in the cache, and return it. The hard part is the name you file it under, and how long you keep it.

🎓 Professional

Cache-aside (lazy loading) is the default and it is what Cache::remember() implements. The alternatives are worth naming: write-through updates the cache on every write (consistent, slower writes), write-behind defers the database write (fast, and it loses data on a crash).

The key is a contract. It must contain every input that changes the output — the tenant, the locale, the user’s permissions if the content varies by them, and a version prefix so a change in the cached structure does not have to be manually purged. A key missing the locale is how a French customer is served the Italian page; a key missing the tenant is a data leak between clients, and that is the version of this bug that ends up in an incident report.

Choose the TTL by asking how wrong you can afford to be. A catalogue page: ten minutes, nobody dies. A stock level: seconds, or not at all. A permission check: never cache it for longer than you would take to revoke access. Stating the TTL as a business decision rather than a technical one is what a senior answer sounds like.

⚠ Trap

Caching a null. The lookup misses, you cache the result, and the result was "not found" — so the record that appears a second later stays invisible for the whole TTL. Conversely, not caching the miss leaves you open to cache penetration, where requests for a non-existent id go straight to the database every time. Both are real; the fix is to cache the negative deliberately, with a short TTL, and to be aware you did it. Laravel’s remember() stores null, so the behaviour is already chosen for you — know which way.

Invalidation, tags and the stampede

🧒 Simple

Two problems. First: when the data changes, the cache is now lying. Second: when a popular cached thing expires, everybody asks for it at the same moment and they all do the expensive work at once.

🎓 Professional

Invalidation strategies, in increasing order of how much they can go wrong: TTL only (simple, always eventually correct, briefly stale); explicit deletion on write (correct, and you will forget one of the three places that writes); tags (Cache::tags(['orders'])->flush(), which requires Redis or Memcached, not the file driver); and key versioning, which is the one to reach for — include a version number or an updated_at in the key, bump it on write, and the old entries simply become unreachable and expire on their own. No delete to forget, and it is safe under concurrency.

The stampede (dogpiling): a key with a 60-minute TTL on a busy site expires, and 500 requests simultaneously find a miss and all run the 4-second query. The site falls over at the exact moment the cache was supposed to be helping, which is why this is a favourite interview scenario. Fixes: a lock so one process recomputes while the others wait or serve stale (Cache::lock()); probabilistic early expiry, where a request near the end of the TTL refreshes voluntarily; or recomputing from a scheduled job so the value is never absent.

Related and worth naming: cache avalanche, where many keys warmed at the same time expire at the same time. Jitter the TTLs.

Try it. Cache-aside with a stampede lock and a versioned key, framework-free so the mechanism is visible. This is what Cache::remember plus Cache::lock is doing underneath.

<?php declare(strict_types=1);

final class OrderStats
{
    private const TTL  = 600;              // 10 minutes
    private const WAIT = 5;                // how long a loser waits for the winner

    public function __construct(private readonly Redis $redis, private readonly PDO $db) {}

    public function forCustomer(int $customerId): array
    {
        // Everything that changes the answer is in the key: version, tenant, entity.
        $version = (int) ($this->redis->get('v:order-stats') ?: 1);
        $key     = "order-stats:v{$version}:customer:{$customerId}";

        if (($hit = $this->redis->get($key)) !== false) {
            return json_decode($hit, true, flags: JSON_THROW_ON_ERROR);
        }

        // Exactly one process recomputes; the others wait for it rather than piling on.
        $lock = $key . ':lock';
        if (!$this->redis->set($lock, '1', ['nx', 'ex' => 30])) {
            for ($i = 0; $i < self::WAIT * 10; $i++) {
                usleep(100_000);
                if (($hit = $this->redis->get($key)) !== false) {
                    return json_decode($hit, true, flags: JSON_THROW_ON_ERROR);
                }
            }
            return $this->compute($customerId);        // gave up waiting: compute anyway
        }

        try {
            $value = $this->compute($customerId);
            // Jitter the TTL so a warmed set of keys does not all expire together.
            $this->redis->setex($key, self::TTL + random_int(0, 60), json_encode($value));
            return $value;
        } finally {
            $this->redis->del($lock);
        }
    }

    private function compute(int $customerId): array
    {
        $st = $this->db->prepare(
            'SELECT COUNT(*) AS orders, COALESCE(SUM(total_cents), 0) AS cents
               FROM orders WHERE customer_id = ?');
        $st->execute([$customerId]);
        return $st->fetch(PDO::FETCH_ASSOC);
    }

    /** Invalidation without a single delete: make the old keys unreachable. */
    public function invalidateAll(): void { $this->redis->incr('v:order-stats'); }
}

Redis in practice, and the free cache in HTTP

🧒 Simple

Redis is a very fast store that keeps everything in memory. It is also where your sessions, queues and locks usually live — which means it is a single point of failure worth thinking about.

🎓 Professional

Redis. Single-threaded for commands, so one KEYS * on a large database blocks every other client — use SCAN. Set maxmemory and an eviction policy deliberately: allkeys-lru for a pure cache, noeviction when the same instance also holds your queue, because evicting a queued job loses work. That is the strongest practical argument for separate Redis databases or instances for cache and queue, and it is a detail that marks real operational experience. Persistence (RDB/AOF) matters for the queue and not for the cache.

HTTP caching is the cheapest layer and the most neglected in PHP applications. Cache-Control: public, max-age=… for genuinely public content; private for anything user-specific (getting this wrong caches one user’s page for another at the CDN — a serious incident); ETag or Last-Modified so a repeat request returns 304 Not Modified with an empty body. For assets, use fingerprinted filenames with an immutable long max-age — the file never changes, its name does, so invalidation is free (ch. 13, 28).

Golden rules
  • Measure, fix the query, then cache. Never in the other order.
  • The key contains everything that changes the answer — tenant, locale, version.
  • TTL is a business decision: how stale can you afford to be?
  • Prefer key versioning to deletion. There is no delete to forget.
  • Lock or serve stale on recompute. Expiry on a busy key is a stampede.
  • Jitter TTLs so warmed keys do not expire together.
  • Separate Redis for cache and queue. Eviction must not eat a job.
  • private on anything user-specific. A CDN takes public literally.

"Una pagina è diventata lenta. Come procede?"

Resist naming a cache in the first sentence — that is the trap: "Prima misuro: guardo quante query fa e quanto durano, con Debugbar o il log delle slow query. Nove volte su dieci è un N+1 o un indice mancante, e la cache lì non serve — nasconderebbe il problema fino al primo miss. Sistemata la query, se resta qualcosa di costoso e non deve essere in tempo reale, allora metto una cache: chiave che contiene tenant, lingua e una versione, TTL scelto in base a quanto posso permettermi di essere vecchio, e invalidazione per versione invece che per delete. E metto un lock sul ricalcolo, perché se scade una chiave molto richiesta partono tutte insieme e il sito cade proprio nel momento in cui la cache doveva aiutare."
