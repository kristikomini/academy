Errors, exceptions and async

PHP 7 turned most fatal errors into throwable objects, and a lot of code — and a lot of candidates — never caught up. This chapter is the Throwable hierarchy you must be able to draw, the handlers every production app needs and most do not have, and the honest answer to "PHP è asincrono?", which is: rarely, and when you need concurrency you almost always want a queue.

From the advert

"Consolidata esperienza nello sviluppo PHP". The interview probe is usually catch (Exception $e) versus catch (Throwable $e) — a one-word difference that decides whether your error handling catches a TypeError.

Throwable: Error and Exception are siblings

🧒 Simple

There are two families of things that can go wrong: mistakes in the program (calling a method on null, passing the wrong type) and problems in the world (the file is missing, the API is down). Both can be caught — but only if you catch the right word.

🎓 Professional

Throwable is the interface at the top. Under it sit two unrelated branches: Error (TypeError, ValueError, ArgumentCountError, DivisionByZeroError, ArithmeticError) and Exception (RuntimeException, LogicException, InvalidArgumentException, PDOException, JsonException…).

Error does not extend Exception. So catch (Exception $e) — the reflex every PHP 5 tutorial taught — does not catch a TypeError. In a top-level handler you want Throwable. Deeper in the code you want the narrowest type that you can actually do something about.

The convention worth stating: LogicException and its children mean a bug in the code (fix it, do not catch it); RuntimeException means the world misbehaved (catch it, retry it, report it).

⚠ Trap

Not everything is throwable. Warnings and notices are not exceptions — fopen() on a missing file emits a warning and returns false, and try/catch around it catches nothing. Either check the return value, or install set_error_handler() to convert warnings into ErrorException so one mechanism covers everything. PHP 8 promoted many old warnings to Error, but plenty remain.

The three handlers a production app needs

🧒 Simple

Somewhere at the very edge of your application there must be something that catches everything nobody else caught, writes it down properly, and shows the visitor a polite page instead of a stack trace.

🎓 Professional

A framework installs these for you; know what they are, because when you write a script or a worker outside the framework, nothing does.

  • set_exception_handler() — last stop for an uncaught throwable. Log with context, return a 500, exit non-zero on CLI.
  • set_error_handler() — turn warnings and notices into ErrorException so they cannot be ignored.
  • register_shutdown_function() plus error_get_last() — the only way to observe a genuine fatal (memory exhausted, timeout). The exception handler never runs for those, so without this the log shows the request starting and nothing else.

Try it. Run it as-is, then uncomment the last line and run again. The second run is the case that catches nobody by surprise only because of the shutdown function.

<?php declare(strict_types=1);

set_error_handler(static function (int $no, string $msg, string $file, int $line): bool {
    throw new ErrorException($msg, 0, $no, $file, $line);   // warnings become exceptions
});

set_exception_handler(static function (Throwable $e): void {
    // Throwable, not Exception — a TypeError must land here too.
    fwrite(STDERR, sprintf("[uncaught] %s: %s @ %s:%d%s",
        $e::class, $e->getMessage(), $e->getFile(), $e->getLine(), PHP_EOL));
    exit(1);
});

register_shutdown_function(static function (): void {
    $e = error_get_last();
    if ($e !== null && ($e['type'] & (E_ERROR | E_PARSE | E_CORE_ERROR)) !== 0) {
        fwrite(STDERR, "[fatal] {$e['message']} @ {$e['file']}:{$e['line']}" . PHP_EOL);
    }
});

try {
    fopen('/definitely/not/here', 'r');      // a warning — now an ErrorException
} catch (ErrorException $e) {
    echo 'caught the warning: ', $e->getMessage(), PHP_EOL;
}

// ini_set('memory_limit', '2M'); $x = str_repeat('a', 50_000_000);   // ← only the shutdown handler sees this

Throwing well: custom types, context and chaining

🧒 Simple

An exception should say what went wrong in words the person reading the log can act on, and it should carry the original problem with it rather than replacing it. Losing the original cause is how a five-minute bug becomes an afternoon.

🎓 Professional

Define exceptions per domain concept, not per class that throws them, and give them named constructors so the message is written once: OrderNotFound::withReference($ref) reads better at the call site than a string literal, and it puts the wording under test.

Always chain. The third constructor argument is $previous, and dropping it is the single most damaging habit in PHP error handling: you catch a PDOException that says deadlock found when trying to get lock, rethrow new RuntimeException('Could not save order'), and the actual cause is gone from the log forever.

And finally runs whether or not something was thrown — the place for releasing a lock, closing a handle or ending a transaction span.

⚠ Trap

catch (Throwable $e) { } with an empty body, or one that only calls return null, is worse than no error handling at all: the failure still happened, the system now behaves as if it did not, and nothing anywhere records it. If you genuinely must swallow one — a best-effort cache write, say — log it at warning with the exception attached and write the reason in a comment. "Swallowed deliberately, here is why" is a design decision; a bare empty catch is a hole.

Async in PHP: fibers, and why the answer is usually a queue

🧒 Simple

PHP normally does one thing at a time and finishes the request. If work is slow, the usual fix is not to make PHP do two things at once — it is to hand the slow work to a background worker and answer the user immediately.

🎓 Professional

Fibers (8.1) give you a full suspendable call stack: Fiber::suspend() pauses, ->resume() continues. They are cooperative, single-threaded, and they are plumbing — you use them through ReactPHP, Amp or Swoole, not directly. They are not threads and they do not make blocking I/O non-blocking by themselves.

Genuine parallelism exists: ext-parallel, pcntl_fork() on CLI, Swoole’s coroutines, or simply several worker processes. Under PHP-FPM none of it applies — each request is its own process and the concurrency unit is the worker (ch. 01).

The pragmatic middle ground that is nearly always the right answer for a web app: run outbound HTTP calls concurrently with Guzzle’s promise pool when you need several at once, and move anything genuinely slow — PDFs, emails, imports, LLM calls — to a queue (ch. 22). Saying "in una richiesta web sposto il lavoro lento su una coda, non provo a renderlo asincrono dentro la richiesta" is the answer of someone who has run this in production.

Golden rules
  • Error is not an Exception. Catch Throwable at the edge.
  • Warnings are not exceptions until you make them so with an error handler.
  • Only a shutdown function sees a real fatal. Without one, the log just stops.
  • Always pass $previous. An unchained rethrow destroys the evidence.
  • Catch the narrowest type you can act on; catch broadly only at the boundary.
  • No empty catch. Log it, or do not catch it.
  • Slow work goes on a queue, not into an async experiment inside the request.

"Che differenza c’è tra Error ed Exception?"

Short, then immediately practical: "Da PHP 7 entrambi implementano Throwable, ma Error non estende Exception: sono due rami separati. Error sono i problemi del programma — TypeError, DivisionByZeroError — mentre Exception sono le condizioni applicative. La conseguenza pratica è che catch (Exception $e) non prende un TypeError: nell’handler globale catturo Throwable, mentre nel codice catturo il tipo più stretto su cui so davvero agire." If they push further, add the shutdown function: fatals reach neither branch.
