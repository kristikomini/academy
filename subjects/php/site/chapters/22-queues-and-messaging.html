Queues, workers and messaging

The second half of "ottimizzazione delle prestazioni", and usually the more valuable one: do not make it faster, do it later. A PDF, an email, an import, a call to somebody else’s API — none of them belong in the thirty seconds a user is staring at a spinner. This chapter is the queue, the worker that drains it, and the four failure modes that turn a queue from an improvement into an outage.

From the advert

"Ottimizzazione delle prestazioni applicative". Together with caching (ch. 20) this is what that line means in practice. The interview version is "l’invio delle email blocca il salvataggio dell’ordine" — and the answer is a queue, plus what happens when the job fails.

What belongs on a queue

🧒 Simple

If the user does not need the result to continue, do not make them wait for it. Write down what needs doing, answer immediately, and let a background worker pick the note up a second later.

🎓 Professional

The test is not "is it slow" but "does the user need the outcome to proceed?". Sending the order confirmation email: no. Charging the card: yes, they need to know it worked.

The usual list: email and notifications, PDF and report generation, image and video processing, imports and exports, search indexing (ch. 21), webhook delivery, calls to third-party APIs, and anything involving an LLM (ch. 33b). Two secondary benefits people undersell: the queue is a natural retry boundary, so a transient failure in a third-party API becomes an automatic retry rather than a 500 shown to a customer; and it is a load buffer, so a spike becomes a longer queue instead of a fallen-over site.

What must not go on a queue: anything the response depends on, and anything that must happen exactly once with no compensation available. A queue is at-least-once, and pretending otherwise is the source of the duplicate invoice.

⚠ Trap

Dispatching inside a transaction. You save() the order and dispatch a job in the same transaction; the worker — a different process, on another machine — picks it up in milliseconds, before your transaction commits, and cannot find the record. It fails with "no query results for model", it retries, and by then the row exists, so it works on the second attempt and nobody investigates. Then one day the transaction rolls back and you have sent an email about an order that does not exist. Laravel’s after_commit option (or DB::afterCommit()) exists precisely for this, and knowing why is a strong interview signal.

Redis or RabbitMQ, and the database driver

🧒 Simple

A queue needs somewhere to keep the notes. Your database can do it, Redis does it faster, and RabbitMQ or Kafka do it with more guarantees and more moving parts.

🎓 Professional
  • Database driver. Zero new infrastructure, transactional with your data, and visible in a table you can query — genuinely fine for a few thousand jobs a day, which describes most gestionali. It contends with your application workload and polls, so it does not scale far.
  • Redis. The default for Laravel and the right answer for the overwhelming majority of projects here. Fast, simple, well supported by Horizon. Remember the eviction warning from chapter 20: noeviction, and ideally an instance separate from the cache.
  • RabbitMQ. Real message broker semantics: exchanges, routing keys, per-message acknowledgement, dead-letter queues as a first-class feature. Worth it when several services consume the same events with different routing, which is a distribution question (ch. 22b), not a performance one.
  • SQS when you are on AWS and want no operational burden at all — at the cost of latency and visibility-timeout semantics you must understand.

Do not use the sync driver in production. It runs the job inline, which means it silently is not a queue — and it is the default in a fresh .env, so this is a real deployment mistake rather than a hypothetical one.

Idempotency, retries and the poison job

🧒 Simple

A job can run twice. The worker might be killed after doing the work but before saying "done", and then somebody else picks the same note up. So every job must be safe to run again.

🎓 Professional

At-least-once delivery is the guarantee you actually have. Exactly-once is mostly marketing: the far end of any operation can succeed while the acknowledgement is lost. So the job must be idempotent — running it twice must produce the same state as running it once.

Practical mechanisms: a unique constraint on a natural key (the database wins the race for you); a state check before acting (if ($order->status !== Submitted) return;); an idempotency key sent to the third party (ch. 14b); or Laravel’s ShouldBeUnique, which prevents a duplicate being queued but does not help once two copies are already in flight.

Retries need backoff and a ceiling. $tries and a backoff() that grows — an immediate infinite retry against a service that is down is a denial-of-service attack you wrote yourself. Distinguish a transient failure (retry) from a permanent one (fail immediately): a 422 from an API will fail identically forever, so catch it and call $this->fail($e) rather than burning three attempts.

The poison job is the one that fails, retries, and fails again forever, consuming the workers so that nothing else runs. A dead-letter queue — Laravel’s failed_jobs table — is the containment. A failed_jobs table nobody monitors is the most common silent failure in a PHP production system: the work was accepted, the user was told it succeeded, and it is sitting in a table nobody has opened since March (ch. 25).

Try it. A job with all four defences: idempotent by state check, bounded retries with backoff, a permanent failure that does not retry, and a timeout below the broker’s visibility window.

<?php declare(strict_types=1);

namespace App\Jobs;

use App\Models\Order;
use Illuminate\Contracts\Queue\ShouldQueue;
use Illuminate\Foundation\Queue\Queueable;

final class SendOrderConfirmation implements ShouldQueue
{
    use Queueable;

    public int $tries   = 5;
    public int $timeout = 30;      // must be BELOW the broker's visibility timeout,
                                   // or a second worker picks it up while this one is still running

    /** 10s, 30s, 2m, 10m — exponential-ish, with room for a provider to recover. */
    public function backoff(): array { return [10, 30, 120, 600]; }

    public function __construct(public readonly int $orderId) {}

    public function handle(Mailer $mailer): void
    {
        $order = Order::find($this->orderId);

        // Idempotency by state: a second run is a no-op, not a second email.
        if ($order === null || $order->confirmation_sent_at !== null) {
            return;
        }

        try {
            $mailer->sendConfirmation($order);
        } catch (PermanentMailException $e) {
            // A rejected address will be rejected identically five times. Do not spend the retries.
            $this->fail($e);
            return;
        }

        $order->forceFill(['confirmation_sent_at' => now()])->save();
    }

    /** Runs after the last attempt. This is where the alert goes. */
    public function failed(\Throwable $e): void
    {
        logger()->error('order confirmation failed permanently', [
            'order_id' => $this->orderId,
            'exception' => $e->getMessage(),
        ]);
    }
}

// Dispatch AFTER the transaction commits, or the worker will not find the row:
// DB::transaction(fn () => $order->save());
// SendOrderConfirmation::dispatch($order->id)->afterCommit();

Running workers: supervisor, Horizon and deployment

🧒 Simple

A worker is a PHP process that runs forever, taking jobs one at a time. Something has to keep it alive, something has to restart it when you deploy new code, and something has to tell you when the queue is getting longer instead of shorter.

🎓 Professional

Keep it running. Supervisor or a systemd unit, configured to restart on exit. A worker that died at 03:00 and was never restarted is a queue that has silently stopped, and the application shows no error anywhere — it just quietly stops sending email.

queue:work, not queue:listen: work bootstraps the framework once and is far cheaper. The consequence is that it holds your code in memory, so every deploy must run queue:restart or workers keep executing the previous release — a genuinely confusing bug where the site is fixed and the emails are still wrong (ch. 30).

Long-running process rules apply. This is the shared-nothing exception from chapter 08: static caches accumulate, and the container is not rebuilt between jobs. Use --max-jobs and --max-time so workers recycle. Horizon does this by default.

Horizon (Redis only) gives you a dashboard, per-queue worker balancing, metrics and failed-job retry from a UI. Use separate queues by latency requirement — emails, reports, default — and give them different workers, otherwise one 20-minute export blocks every confirmation email behind it. That priority argument is the practical answer to "how do you stop a slow job from starving the others".

Monitor queue depth, not just failures. A growing backlog is the early warning; failed_jobs is the post-mortem. Alert on both, and on worker count reaching zero.

Golden rules
  • Queue what the response does not depend on. Not merely what is slow.
  • Dispatch after commit. The worker is faster than your transaction.
  • Every job is idempotent, because delivery is at-least-once.
  • Bounded retries with backoff; fail permanent errors immediately.
  • Job timeout below the broker's visibility timeout, or it runs twice concurrently.
  • queue:restart on every deploy. Workers hold the old code.
  • Separate queues by latency so a report cannot block an email.
  • Alert on failed_jobs and on queue depth. An unwatched failed table is silent data loss.

"Un job in coda è fallito a metà. Cosa succede?"

They are testing whether you have actually operated a queue: "Dipende da quanto il job è scritto bene. La consegna è at-least-once, quindi parto dal presupposto che possa girare due volte: rendo il job idempotente con un controllo di stato o un vincolo unique, così il secondo tentativo non manda una seconda email. Configuro tries con un backoff crescente, e distinguo gli errori transitori da quelli permanenti — un 422 dall’API fallirà uguale altre quattro volte, quindi lo faccio fallire subito. Dopo l’ultimo tentativo finisce in failed_jobs, e la cosa importante è che qualcuno lo guardi: una tabella di job falliti che nessuno monitora è perdita di dati silenziosa, perché all’utente avevamo detto che era andato tutto bene."
