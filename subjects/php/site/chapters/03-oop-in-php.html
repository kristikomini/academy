OOP in PHP

Every Italian PHP advert carries the line "buona conoscenza della programmazione ad oggetti", and almost every interview tests it with the same three or four questions. This chapter is those questions, plus the PHP 8 features that changed the answers — enums, readonly and constructor promotion — which a lot of candidates have not caught up with.

From the advert

"Buona conoscenza della programmazione ad oggetti". In practice this gets tested three ways: interface versus abstract class, what a trait is actually for, and whether you can model something small without reaching for inheritance.

Interface or abstract class

🧒 Simple

An interface is a job advert: "must be able to send a message". It says what you have to be able to do, and nothing about how. You can answer many job adverts at once.

An abstract class is a half-built machine you inherit. It arrives with some parts already fitted and you finish the missing ones. You only get to inherit one machine.

🎓 Professional

An interface declares a contract with no state and no implementation, and a class may implement any number of them. An abstract class may hold properties, a constructor and concrete methods — but PHP has single inheritance, so a class extends exactly one.

That asymmetry is the whole decision. Reach for an interface when you need a type: something to type-hint against and swap implementations of. Reach for an abstract class only when there is real shared state or behaviour to hand down, and accept that you have just spent the one inheritance slot the class had.

⚠ Trap

"An abstract class is just an interface with code in it" is the answer that sounds right and scores badly. The examiner is listening for single inheritance. If you do not say it, you have not answered the question — that constraint is the only reason the choice is ever hard.

Traits: reuse without a parent

🧒 Simple

A trait is a block of methods you can paste into any class. The compiler does the pasting, so you only write it once — but the class does not become a "kind of" anything by using it.

🎓 Professional

Traits are horizontal reuse: compiler-assisted copy-paste, for classes that cannot share a parent. Crucially, a trait is not a type — you cannot type-hint against one. It gives you code sharing without polymorphism.

The cost is locality. A class using five traits has its behaviour defined across six files, and the conflict-resolution syntax (insteadof, as) exists precisely because two traits can define the same method. Needing that syntax is the smell that composition was the right answer.

Try it. Save this and run php trait.php. Then add a second trait that also defines describe(), use both, and read the fatal error carefully — it names the exact conflict and the two ways out.

<?php declare(strict_types=1);

trait Describable
{
    public function describe(): string
    {
        // static::class, not self::class — late static binding gives us the
        // class that actually used the trait, not the trait's own context.
        return static::class . ': ' . $this->label();
    }

    abstract protected function label(): string;   // a trait may demand a method
}

final class Order
{
    use Describable;

    public function __construct(private readonly string $ref) {}

    protected function label(): string { return $this->ref; }
}

echo (new Order('ORD-2026-114'))->describe(), PHP_EOL;
// Order: ORD-2026-114

Enums, and the constants they replaced

🧒 Simple

An enum is the list of the only values something is allowed to be. An order can be draft, paid or shipped — and now it is impossible to write "shipepd" by accident, because that is not on the list and the code refuses to run.

🎓 Professional

PHP 8.1 enums are real types. A pure enum has only cases; a backed enum gives each case a string or int value plus from() and tryFrom(), which is what makes it storable in a database column. Both kinds can implement interfaces and carry methods, so behaviour that used to live in a match somewhere else can live on the enum itself.

The one to have ready under pressure: from() throws on an unknown value, tryFrom() returns null. For anything arriving from a request or a legacy table, tryFrom() is almost always the one you want.

Try it. This is the order state machine from the reference system in src/, cut down to fit a screen. Note where the rule lives: putting the allowed transitions on the enum means they cannot drift out of step with the states.

<?php declare(strict_types=1);

enum OrderStatus: string
{
    case Draft     = 'draft';
    case Submitted = 'submitted';
    case Confirmed = 'confirmed';
    case Shipped   = 'shipped';
    case Delivered = 'delivered';
    case Cancelled = 'cancelled';

    /** @return list<self> */
    public function allowedNext(): array
    {
        return match ($this) {
            self::Draft     => [self::Submitted, self::Cancelled],
            self::Submitted => [self::Confirmed, self::Cancelled],
            self::Confirmed => [self::Shipped, self::Cancelled],
            // Deliberately NOT cancellable: once it is on a lorry, "cancel"
            // is a returns process, not a status change.
            self::Shipped   => [self::Delivered],
            self::Delivered,
            self::Cancelled => [],
        };
    }

    public function canMoveTo(self $next): bool
    {
        return in_array($next, $this->allowedNext(), strict: true);
    }
}

var_dump(OrderStatus::Shipped->canMoveTo(OrderStatus::Cancelled)); // bool(false)
var_dump(OrderStatus::from('draft')->canMoveTo(OrderStatus::Submitted)); // bool(true)
var_dump(OrderStatus::tryFrom('shipepd'));  // NULL — not an exception

readonly, promotion and value objects

🧒 Simple

readonly means: you may fill this in once, when the object is born, and never change it afterwards. Like the date of birth printed in a passport.

🎓 Professional

A readonly property is initialised once from inside the declaring class scope and throws on any later write. Combined with constructor property promotion, a value object is now three lines instead of twelve — which is why PHP 8.1 changed how much domain modelling is worth doing in the first place.

It is shallow. A readonly property holding an object still lets you mutate that object's own properties: the reference is frozen, not the thing it points at. Say that unprompted in an interview, because it is the follow-up question.

⚠ Trap

Never model money as a float. 0.1 + 0.2 !== 0.3 in every language using IEEE-754 floats, and in an e-commerce or gestionale context that becomes an invoice total one cent out and a client who stops trusting the system. Store integer minor units — cents — or use BCMath. 

<?php
var_dump(0.1 + 0.2 === 0.3);   // bool(false)
var_dump(0.1 + 0.2);           // float(0.30000000000000004)

Try it. A complete value object in PHP 8.2, with the two invariants that actually matter enforced in the constructor.

<?php declare(strict_types=1);

final readonly class Money
{
    public function __construct(
        public int $cents,                 // minor units — never a float
        public string $currency = 'EUR',
    ) {
        if ($cents < 0) {
            throw new InvalidArgumentException('Money cannot be negative.');
        }
    }

    public function add(self $other): self
    {
        if ($other->currency !== $this->currency) {
            throw new InvalidArgumentException('Cannot add different currencies.');
        }
        return new self($this->cents + $other->cents, $this->currency);
    }

    public function format(): string
    {
        return number_format($this->cents / 100, 2, ',', '.') . ' ' . $this->currency;
    }
}

echo (new Money(1999))->add(new Money(500))->format(), PHP_EOL;   // 24,99 EUR

self:: versus static::

🧒 Simple

self:: means "the class where this line is written". static:: means "the class that was actually called". When a child inherits the method, those are two different classes.

🎓 Professional

This is late static binding. In a parent's factory method, new self() always builds the parent even when invoked as Child::make(), while new static() builds the child. It is why fluent base classes and Eloquent's static query methods work at all, and it is a favourite question because the wrong choice produces a bug that only shows up the day somebody subclasses.

Golden rules
  • Interface for a contract, abstract class for shared state — and you only get one parent.
  • A trait is not a type. It buys reuse and no polymorphism, so you cannot type-hint it.
  • tryFrom() for anything from outside; from() only when an unknown value genuinely is a bug.
  • readonly is shallow. The reference is frozen; the object behind it is not.
  • Money is never a float. Integer minor units, or BCMath.
  • Put the transition rule on the enum. Then the state machine cannot drift out of step with the states.
  • static:: when a subclass should get itself back, self:: when it genuinely must be this class.

"Interfaccia o classe astratta — quando usa l'una e quando l'altra?"

Lead with single inheritance, because that is the constraint that decides it: "Uso un'interfaccia quando mi serve solo un contratto, perché una classe può implementarne molte ma può estenderne una sola. Uso una classe astratta quando c'è stato o comportamento condiviso da ereditare — e a quel punto ho speso l'unica ereditarietà che avevo." Then give an example from your own code. An interface for a payment gateway with two implementations is the one every interviewer recognises immediately.
