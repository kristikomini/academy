CI/CD pipelines

A pipeline is a written-down answer to "how do we know this is safe to ship". Most PHP teams in this market have a partial one — tests run somewhere, deployment is a script somebody maintains — and being the person who can finish it is a disproportionately visible contribution. It is also one of the easiest things to demonstrate in a portfolio: a green badge on a public repository is evidence, not a claim.

From the advert

"Gradita conoscenza di Docker" is usually the closest an advert gets, and CI is where Docker actually earns its keep for a team: the same image runs the tests and runs in production, so "it passed on my machine" stops being a category of excuse.

What the pipeline runs, and in what order

🧒 Simple

On every push, a machine you do not control checks out the code, installs it from scratch, and runs the checks. Because it starts clean every time, it catches everything that only worked because of something on your laptop.

🎓 Professional

Order the stages by how fast they fail, so feedback is quick and expensive jobs only run on code that already passed the cheap ones:

  1. Lint and format check (Pint or CS-Fixer in dry-run) — seconds.
  2. Static analysis (PHPStan with the baseline) — under a minute, catches real bugs (ch. 27).
  3. Unit tests — fast, no database.
  4. Integration and feature tests — needs MySQL and Redis as services (ch. 24).
  5. Architecture tests — deptrac, if you claim to have boundaries (ch. 23).
  6. Security — composer audit, and a grep for dd( and committed secrets.
  7. Build the artefact — the Docker image or the release archive, once, tagged with the commit sha.
  8. Deploy — automatic to staging, and to production on a tag or with a manual approval.

Build once, deploy many. The artefact that passed the tests is the artefact that reaches production — not a fresh composer install on the server that may resolve differently (ch. 28). Configuration comes from the environment, so the same image runs in staging and production (ch. 29).

Test the matrix you actually support. If clients run 8.1 and 8.3, run both; a matrix of six versions nobody uses is cost without information.

Try it. A complete GitHub Actions workflow for a Laravel application: service containers, dependency caching, the stages in fail-fast order, and deployment gated on everything above it.

# .github/workflows/ci.yml
name: CI

on:
  push:
    branches: [main]
  pull_request:

jobs:
  quality:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: shivammathur/setup-php@v2
        with:
          php-version: '8.3'
          extensions: pdo_mysql, intl, zip, bcmath
          coverage: none                      # no Xdebug here: it is slow and unused
      - run: composer install --no-interaction --prefer-dist --no-progress
      - run: vendor/bin/pint --test           # formatting, seconds
      - run: vendor/bin/phpstan analyse --no-progress
      - run: composer audit
      # Catch what a reviewer misses at 18:00 on a Friday.
      - name: No leftover debug calls
        run: |
          ! grep -rnE '\b(dd|dump|var_dump|ray)\(' app/ routes/ --include='*.php'

  tests:
    runs-on: ubuntu-latest
    needs: quality                            # do not spend a database on unformatted code
    strategy:
      fail-fast: false
      matrix:
        php: ['8.2', '8.3']                   # the versions actually supported

    services:
      mysql:
        image: mysql:8.0
        env:
          MYSQL_DATABASE: testing
          MYSQL_ALLOW_EMPTY_PASSWORD: 'yes'
        ports: ['3306:3306']
        # Without this, migrations race the database and fail intermittently.
        options: >-
          --health-cmd="mysqladmin ping" --health-interval=10s
          --health-timeout=5s --health-retries=5
      redis:
        image: redis:7
        ports: ['6379:6379']

    steps:
      - uses: actions/checkout@v4
      - uses: shivammathur/setup-php@v2
        with:
          php-version: ${{ matrix.php }}
          extensions: pdo_mysql, intl, zip, bcmath
      - uses: actions/cache@v4
        with:
          path: ~/.composer/cache
          key: composer-${{ matrix.php }}-${{ hashFiles('composer.lock') }}
      - run: composer install --no-interaction --prefer-dist --no-progress
      - run: cp .env.example .env && php artisan key:generate
      - run: php artisan migrate --force
        env:
          DB_HOST: 127.0.0.1
          DB_DATABASE: testing
          DB_USERNAME: root
          DB_PASSWORD: ''
      - run: php artisan test --parallel
        env:
          DB_HOST: 127.0.0.1
          DB_DATABASE: testing
          DB_USERNAME: root
          DB_PASSWORD: ''
          REDIS_HOST: 127.0.0.1

  deploy:
    runs-on: ubuntu-latest
    needs: tests
    if: github.ref == 'refs/heads/main'      # never from a pull request
    environment: production                   # a GitHub environment can require approval
    steps:
      - uses: actions/checkout@v4
      - name: Deploy
        env:
          DEPLOY_KEY: ${{ secrets.DEPLOY_KEY }}   # a secret, never a literal
        run: ./bin/deploy.sh                       # the atomic-symlink script from ch. 29

Continuous delivery, environments and gates

🧒 Simple

Continuous integration means the checks run automatically. Continuous delivery means the result is always ready to ship. Whether it ships by itself, or waits for someone to press a button, is a separate decision.

🎓 Professional

Distinguish them cleanly in an interview: delivery means every green build produces a deployable artefact; deployment means it goes out without a human. Most teams in this market want the first and choose the second only for staging — and that is a sound position, not a lack of ambition.

Environments. Staging should differ from production in data and scale, not in shape: same PHP version, same extensions, same web server, same deploy path. A staging box that is subtly different is a machine that produces false confidence, which is worse than no staging at all.

Secrets live in the CI provider’s secret store, are masked in logs, and are scoped to the environment that needs them. Remember that a pull request from a fork must not receive them — that is a real exfiltration path and the reason the deploy job above is gated on the branch.

Deployment strategies worth naming: rolling (replace instances gradually), blue-green (two full environments, switch traffic — instant rollback), canary (a small percentage first, watch the error rate, then proceed). The symlink deploy from chapter 29 is the small-scale version of blue-green, and saying so shows you understand what the fancy words are describing.

And feature flags again: they decouple deploying from releasing, which is what lets you merge to main continuously without shipping half a feature to customers.

⚠ Trap

The flaky test that everyone re-runs. One test that fails randomly and passes on retry teaches the whole team that red does not mean broken — and from then on nobody reads the pipeline. The cost is not the test; it is that your gate has stopped working, exactly as in chapter 25 with alerts that fire constantly. Quarantine it the same day, open a ticket, and fix the cause: usually shared state between tests, real time in an assertion, or a database not reset between runs (ch. 24).

Migrations in the pipeline, and rolling back

🧒 Simple

Code can be put back. A database change usually cannot. So the pipeline has to treat schema changes differently from everything else it deploys.

🎓 Professional

Migrations run automatically as part of the deploy — but only additive ones, because for a moment the old code is running against the new schema (ch. 29). Destructive changes go in a later, separate release. This is the expand/contract discipline enforced by the pipeline rather than by memory.

migrate --force is required non-interactively; a long ALTER TABLE should not be in the deploy path at all, because a five-minute lock during a deploy is an outage. Take a backup before a migration that transforms data, and know that "we can restore" means "we have restored, recently, and it worked" (ch. 29).

Rollback must be one command and it must have been tested. A rollback path that has never been exercised is not a rollback path — the same argument this whole course keeps making about gates and backups. Rehearse it on staging on a calm afternoon, not on production during an incident (ch. 25b).

Golden rules
  • Order stages fail-fast. Lint, analyse, unit, integration, deploy.
  • Build once, deploy many. The tested artefact is the shipped artefact.
  • Cache Composer on the lock file hash. Cheapest speed-up available.
  • Service containers need health checks, or migrations race the database.
  • Secrets never reach a fork's pull request. Gate the deploy on the branch.
  • Only additive migrations in the deploy. Destructive ones ship later.
  • Fix a flaky test the same day. It disables the whole gate.
  • Rehearse the rollback before you need it.

"Avete una pipeline? Cosa ci metterebbe?"

Give the order and the reason for the order, then the deployment nuance: "La ordinerei per velocità di fallimento: prima lint e PHPStan, che costano secondi e trovano errori veri, poi i test unitari, poi quelli di integrazione con MySQL e Redis come service container — con health check, altrimenti le migration partono prima che il database accetti connessioni e i test falliscono a caso. Poi composer audit e un grep per i dd() dimenticati. L’artefatto lo costruisco una volta sola e deployo quello, non rifaccio composer install sul server: così quello che è passato dai test è esattamente quello che va in produzione. Le migration nel deploy le tengo solo additive, perché per qualche secondo il codice vecchio gira sullo schema nuovo; le rimozioni vanno in una release successiva, così il rollback resta possibile."
