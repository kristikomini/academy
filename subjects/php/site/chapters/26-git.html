Git

Everyone puts Git on the CV and a surprising number of interviews find the limit within two questions. The limit is almost always the same: the candidate knows the four commands they use daily and has never had to undo anything. This chapter is the model that makes the commands obvious, the merge-versus-rebase answer that is actually a policy question, and the recovery moves that turn a panic into two minutes.

From the advert

"Utilizzo di sistemi di versionamento (Git)". Nobody is impressed that you can commit. The differentiators are: can you resolve a conflict without fear, can you undo a mistake, and do your commits help the next person.

The model: commits, refs, and the three trees

🧒 Simple

A commit is a complete snapshot of the project plus a pointer to the one before it. A branch is just a sticky note on one commit that moves forward as you work. Almost every confusing Git situation becomes obvious once you picture that.

🎓 Professional

A commit is an immutable object: a tree (the content), one or more parents, author, message. Its id is the hash of all of that — which is why changing history creates new commits rather than editing old ones, and why a rebase rewrites every commit after the point it touched.

A branch is a movable pointer to a commit; HEAD points at the current branch. A tag is the same idea, fixed. That is the whole data model.

The three trees explain the commands: the working directory (your files), the index/staging area (what the next commit will contain), and HEAD (the last commit). git add moves working → index; git commit moves index → HEAD; git reset moves things backwards and its three modes are exactly which trees it touches: --soft moves HEAD only, --mixed (the default) also resets the index, --hard also overwrites your files — which is the only one that can lose work.

Merge or rebase: a policy, not a preference

🧒 Simple

Merge keeps the true story: two lines of work joined at a point. Rebase rewrites your commits as if you had started from the latest code, giving a straight line. One preserves history, the other tidies it.

🎓 Professional

merge creates a commit with two parents; history is accurate and the graph branches. rebase replays your commits onto a new base, producing new commits with new hashes and a linear history that is easier to read and to bisect.

The golden rule: never rebase a branch other people have pulled. The commits they have are gone, replaced by new ones, and their next pull produces duplicated commits and a mess that someone has to untangle by hand. Rebase your own unpushed work freely; leave shared history alone.

The workflow most teams settle on, and a good answer to give: rebase to update your feature branch onto main while you work, and merge (or squash) the pull request at the end. You get a readable linear-ish history and a preserved record of what was merged when. Squash-merge is worth naming too: one commit per PR keeps main clean and makes revert trivial, at the cost of losing the intermediate steps — which for most teams is a good trade.

git pull is fetch + merge, and it is what produces those "Merge branch 'main' into 'main'" commits that clutter a history. Configure pull.rebase = true, or use git pull --rebase by habit.

⚠ Trap

git push --force on a shared branch overwrites whatever your colleague pushed while you were rebasing, and it is gone from the remote with no warning. Use --force-with-lease, which refuses if the remote has moved since you last fetched. It is a one-word change that converts a destructive command into a safe one, and knowing it is a reliable interview signal.

Conflicts, and undoing anything

🧒 Simple

A conflict just means two people changed the same lines and Git will not guess. You open the file, decide what the result should be, delete the markers, and tell Git you are done. Nothing is broken and nothing is lost.

🎓 Professional

Read the markers correctly, because during a rebase they are counter-intuitive: <<<<<<< HEAD is the branch you are replaying onto (usually main), and the lower section is your commit. In a merge it is the other way round. Resolve, git add, then git rebase --continue or git commit. --abort always returns you to where you started, which is the fact that removes the fear.

The recovery kit, worth having memorised:

  • git reflog — the safety net for everything. It records where HEAD has been, including commits orphaned by a bad reset or rebase; git reset --hard HEAD@{3} brings them back. Nothing committed is truly lost for about ninety days, and this single command has rescued more work than any other.
  • git restore --staged <file> to unstage; git restore <file> to discard working changes (the modern, clearer split of what checkout used to do).
  • git commit --amend for the last commit — only if unpushed.
  • git revert <sha> to undo a commit that is already public: it makes a new commit that reverses it, which is the safe way and the right answer for production (ch. 25b).
  • git stash for "I need to look at something else right now"; git stash pop to come back. Remember stashes are easy to forget about — git stash list.
  • git cherry-pick to take one commit onto another branch, which is exactly how a hotfix gets back into main.
  • git bisect — binary search over history to find the commit that introduced a bug. It feels magical the first time and it is the strongest argument for small, self-contained commits.

Try it. Manufacture a disaster in a throwaway repository and recover from it. Doing this once removes the fear permanently — and the fear is what actually costs people time.

# A scratch repo with three commits.
mkdir /tmp/git-lab && cd /tmp/git-lab && git init -q
echo uno   > f.txt && git add . && git commit -qm "primo"
echo due  >> f.txt && git commit -qam "secondo"
echo tre  >> f.txt && git commit -qam "terzo"

# Destroy the last two commits, the way a bad reset does.
git reset --hard HEAD~2
git log --oneline          # only "primo" — the work looks gone

# It is not gone. The reflog remembers every position HEAD has held.
git reflog                 # find the sha of "terzo"
git reset --hard HEAD@{1}  # back, completely
git log --oneline          # primo, secondo, terzo

# The safe way to undo a commit that others already have:
git revert --no-edit HEAD  # a NEW commit that reverses "terzo"
git log --oneline

Branching, commits and the pull request

🧒 Simple

Small branches, short-lived, with commit messages that say why. The person reading them is usually you in eight months with no memory of the ticket.

🎓 Professional

Branching strategy — know the two and when each fits. GitHub Flow: one long-lived main that is always deployable, short feature branches, deploy on merge. Simple, and right for a web application or an agency shipping continuously. Git Flow: develop, release/*, hotfix/*. Heavier, and genuinely appropriate when you ship versioned releases to clients who upgrade on their own schedule — which describes a fair number of gestionale vendors, so do not dismiss it.

Commit messages. Imperative subject under about 50 characters, blank line, then why in the body. The diff already says what changed; it cannot say what you were trying to achieve or what you ruled out. Reference the ticket. Conventional Commits (feat:, fix:) are worth adopting if the team generates changelogs or versions from them, and are ceremony otherwise.

Keep it out of the repository: .env, vendor/, node_modules/, anything with a credential. And if a secret does get committed, rotate it immediately — rewriting history does not un-leak it, because it is already in clones, forks and CI caches. That answer is the correct one and is not the one most candidates give.

Pull requests: small enough to review properly. A 40-file PR gets "LGTM" and a 4-file PR gets read (ch. 35). Write the description for the reviewer — what changed, why, how you tested it, what you are unsure about. That last item invites the review you actually want.

Golden rules
  • A commit is a snapshot; a branch is a pointer. Everything follows.
  • Rebase your own work, never shared history.
  • --force-with-lease, never bare --force.
  • revert in public, reset in private.
  • reflog first when something looks lost. It usually is not.
  • --abort always exists. A conflict is never a trap.
  • The message explains why; the diff already shows what.
  • A committed secret is a leaked secret. Rotate it, do not just rewrite.

"Che differenza c’è tra merge e rebase, e quando usa l’uno o l’altro?"

Give the mechanism, the rule, and the workflow: "Il merge crea un commit con due genitori e mantiene la storia reale; il rebase riscrive i miei commit come se fossero partiti dall’ultimo main, quindi genera commit nuovi con hash diversi e una storia lineare. La regola che seguo è non fare mai rebase su un ramo che altri hanno già scaricato: i loro commit sparirebbero e al pull si ritroverebbero i duplicati. In pratica uso rebase per aggiornare il mio branch di feature mentre lavoro, e poi merge o squash della pull request: storia leggibile e traccia di cosa è stato integrato. E quando devo forzare uso --force-with-lease, che si rifiuta se qualcuno ha pushato nel frattempo."
