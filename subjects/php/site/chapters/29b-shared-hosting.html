Shared hosting, cPanel and FTP

Unglamorous and extremely real. Aruba, Register.it, Netsons and shared cPanel host an enormous amount of Italian PHP — every small client site, most WordPress installations, a surprising number of gestionali. A developer who has only ever deployed to Docker is stuck on day one, and a developer who can ship competently into these constraints is quietly valuable, because most cannot.

From the advert

Not in any advert. Nobody advertises "must be able to work with FTP and no SSH access". Then you are handed the credentials for the client’s Aruba account and asked to fix the contact form by Thursday.

The constraints, and which ones are fatal

🧒 Simple

On shared hosting your site is one of hundreds on the same machine, so you get a folder, a database, and almost no control. Many of the tools you are used to are simply not available.

🎓 Professional

What you typically lose, in order of how much it hurts:

  • No root, often no SSH at all. On the cheapest Aruba plans you have FTP and a web file manager. No composer install on the server, no artisan, no tail -f.
  • You cannot choose the document root on some plans — the web root is fixed at httpdocs/ or public_html/. This is the one that decides how you deploy a framework at all (below).
  • No long-running processes. No queue worker, no supervisor. Cron is the only background mechanism, often with a minimum interval of five or fifteen minutes.
  • The PHP version is chosen from a dropdown, extensions are a checkbox list, and some (intl, imagick, bcmath) may be unavailable entirely.
  • Hard limits on max_execution_time, memory, database connections and inodes — the inode limit is real and a node_modules uploaded by accident can exhaust it.
  • No Redis, usually. Cache and sessions go to files or the database.
  • Shared everything: a noisy neighbour on the same machine is your performance problem and there is nothing you can do about it.

Which are fatal? Almost none, individually. The combination that genuinely rules out a project is no SSH plus a fixed document root plus a real queue requirement — at that point a €5 VPS is the honest recommendation, and being able to make that case to a client with reasons rather than disdain is part of the skill.

Deploying a framework where you cannot move the web root

🧒 Simple

A framework expects the web server to point at its public folder, with the rest of the code above it and unreachable. When you cannot move the web root, you have to arrange that yourself — and the wrong way to do it exposes your entire source code.

🎓 Professional

Three approaches, best first:

  1. A subdomain or add-on domain pointed at public/. cPanel and Plesk both allow this, and it is the correct solution. Always ask — it is often available on a plan the client already has.
  2. Application above the web root, contents of public/ inside it. Put the project in ~/bottega and copy public/* into public_html/, then edit index.php to require ../bottega/vendor/autoload.php and ../bottega/bootstrap/app.php. Two paths to change, and the source stays unreachable.
  3. Everything inside the web root with .htaccess protection. The common shortcut and the one to be suspicious of: it works until a server-configuration change stops honouring .htaccess, or somebody restores a backup without it, and then /.env is world-readable. If you must, deny by directory and verify by requesting the paths yourself.

Then: run composer install locally and upload vendor/, since there is no Composer on the server. Upload as a single archive and extract with the file manager if you can — uploading twelve thousand small files over FTP takes an hour and fails halfway. Build the assets locally too.

Verify with a request, not with a belief. After every deploy, fetch https://sito.it/.env, /composer.json, /storage/logs/laravel.log and /vendor/. Scanners try these within minutes of a host appearing; you should try them first.

⚠ Trap

Backups and .git. Two of the most common real-world exposures on shared hosting are an uploaded backup.sql or sito.zip sitting in the web root, and a .git directory deployed by an FTP sync — from which the whole repository, including history and any credential ever committed, can be reconstructed by a public tool. Both are downloaded routinely by automated scanners. Never deploy by copying your working directory, and never leave a dump in public_html.

Cron instead of workers, and the rest of the workarounds

🧒 Simple

With no background process, the trick is to have cron wake PHP up every few minutes, do a bounded amount of work, and exit. It is not as good as a real worker, and it is usually enough.

🎓 Professional

Queues. Use the database driver (ch. 22) and a cron entry running queue:work --stop-when-empty --max-time=280 every five minutes. The --max-time must be comfortably under the host’s process limit, and --stop-when-empty means it exits cleanly instead of being killed mid-job. Add flock so two cron runs cannot overlap. Latency becomes minutes rather than milliseconds — tell the client that, because "the email arrives within five minutes" is a perfectly acceptable requirement when it is stated in advance and a nasty surprise when it is not.

Scheduling. One cron entry running the scheduler every minute if minute-level cron is available; if the minimum is fifteen minutes, design the tasks around it rather than pretending.

Cache and sessions on the file driver, or the database if the filesystem is slow — and it often is, because it is network storage shared with everyone else on the machine.

Email. Do not use the host’s mail(): shared IPs have poor reputation and messages land in spam. SMTP through a real provider, and make sure SPF, DKIM and DMARC are configured on the domain — this is frequently the actual fix for "le nostre email non arrivano", and it is a five-minute DNS answer that clients find impressive.

Debugging without SSH. Log to a file inside storage/ (outside the web root) and read it through the file manager; Sentry (ch. 25) is even more valuable here than elsewhere, because it is the only thing that tells you an error happened at all. Keep display_errors off regardless of how tempting it is.

Try it. The cron lines that replace supervisor. The flock and the --max-time are the difference between this working and it being killed halfway through a job every five minutes.

# crontab on shared hosting — set these in cPanel's "Cron Jobs" panel.

# The scheduler, every minute where the host allows it.
* * * * * /usr/local/bin/php8.3 /home/utente/bottega/artisan schedule:run >> /dev/null 2>&1

# The queue, every five minutes. flock prevents two runs overlapping;
# --stop-when-empty exits cleanly; --max-time stays under the host's process limit.
*/5 * * * * /usr/bin/flock -n /home/utente/queue.lock \
    /usr/local/bin/php8.3 /home/utente/bottega/artisan queue:work \
      --stop-when-empty --max-time=280 --tries=3 >> /home/utente/bottega/storage/logs/queue.log 2>&1

# Nightly database backup, kept OUTSIDE public_html and rotated.
30 3 * * * mysqldump -u utente -p'...' db_bottega | gzip > /home/utente/backups/db-$(date +\%F).sql.gz \
    && find /home/utente/backups -name 'db-*.sql.gz' -mtime +14 -delete

# Note the absolute path to the PHP binary: the CLI default on shared hosting is
# often an older version than the one the website is configured to use.

Recommending a VPS without sounding dismissive

🧒 Simple

Sometimes shared hosting genuinely is not enough. The way to say so is in terms of what the client wants and what it costs, not in terms of what you would prefer to work on.

🎓 Professional

Make the case with their requirements: "Il gestionale deve mandare le fatture allo SDI entro pochi secondi e generare PDF da cento pagine. Su hosting condiviso i job partono ogni cinque minuti e c’è un limite di trenta secondi per processo, quindi non è una questione di preferenza: alcune cose non si possono fare. Un VPS costa cinque euro al mese in più e li toglie tutti e due i limiti." Numbers and consequences, not architecture opinions.

And know when shared hosting is the right answer, because saying so builds the credibility you will need later: a WordPress brochure site, a small catalogue, anything with modest traffic and no background processing. Recommending a Kubernetes cluster for a five-page site is the same error in the opposite direction, and clients remember it.

A middle option worth knowing: managed WordPress hosting or a small managed VPS (ch. 29) gives the client most of the reliability with none of the administration, at a price between the two.

Golden rules
  • Ask for a subdomain pointed at public/ before anything else.
  • Application above the web root, public/ contents inside it.
  • Fetch /.env yourself after every deploy. Scanners will.
  • Never deploy .git or leave a dump in the web root.
  • vendor/ is built locally and uploaded as an archive.
  • Cron plus flock plus --stop-when-empty replaces the worker.
  • SMTP with SPF, DKIM and DMARC, never the host's mail().
  • Argue for a VPS with limits and euros, never with taste.

"Il cliente ha un hosting Aruba condiviso. Riesce a metterci Laravel?"

Say yes, then show you know exactly where the sharp edges are: "Sì, con qualche accortezza. La cosa più importante è la document root: chiedo se posso puntare un sottodominio su public/, altrimenti metto l’applicazione sopra la web root e dentro public_html ci lascio solo il contenuto di public, cambiando i due path in index.php — se lascio tutto dentro, /.env è scaricabile e lo provano i bot nel giro di minuti. vendor lo costruisco in locale e lo carico come archivio, perché sul server non c’è Composer. Le code le faccio con il driver database più un cron ogni cinque minuti con flock e --stop-when-empty, e lo dico al cliente: le email arrivano entro cinque minuti, non subito. Se invece servono davvero job in tempo reale o processi lunghi, gli spiego con i numeri che un VPS da cinque euro toglie quei limiti."
