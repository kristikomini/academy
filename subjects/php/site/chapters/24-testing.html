Testing: PHPUnit, Pest and test doubles

Italian adverts usually say gradita for testing — nice to have. Treat it as the opposite: it is the cheapest way to look like someone who has worked on a system that outlived its first release, and in a junior interview a candidate who can explain what they test and what they deliberately do not stands out immediately.

From the advert

"Gradita esperienza con test automatici". Rarely a hard requirement, frequently the question that decides between two otherwise equal candidates — because it reveals whether you have ever had to change code you were afraid of.

Unit, integration, end-to-end

🧒 Simple

Three sizes of check. Does this one small part work on its own? Do two parts work together? Does the whole thing work the way a customer would use it? The small ones are fast and there should be lots; the big ones are slow and there should be a few.

🎓 Professional

Unit tests one class with its collaborators replaced — milliseconds, and they tell you precisely what broke. Integration tests real components together, above all your code against a real database, where most PHP bugs actually live. End-to-end drives the application as a user, catching wiring failures nothing else sees, at the cost of being slow and flaky.

Where PHP differs from the classic pyramid advice: a great deal of a PHP application is its SQL and its framework wiring, so a thin layer of unit tests over a solid band of integration tests usually buys more confidence than the reverse.

The test doubles, precisely

🧒 Simple

Stand-ins for the real thing. A stub just reads its lines. A mock also checks you said the right thing to it. A fake is a small working version. A spy quietly writes down what happened.

🎓 Professional

A stub returns canned values — state verification. A mock carries expectations about how it was called and fails the test if they are not met — behaviour verification. A fake is a real implementation with a shortcut, like an in-memory repository. A spy records calls for you to assert on afterwards.

The judgement worth having: mock at the boundaries you do not own — the payment gateway, the SDI, the mail transport — and use real objects inside your own domain. Over-mocking produces tests that assert your code called the methods you wrote, which still pass after you have broken the behaviour. 

<?php declare(strict_types=1);

use PHPUnit\Framework\TestCase;

final class ConfirmOrderTest extends TestCase
{
    public function test_it_charges_the_customer_once(): void
    {
        // MOCK — an external boundary, and "exactly once" is the thing that matters.
        $gateway = $this->createMock(PaymentGateway::class);
        $gateway->expects($this->once())
                ->method('charge')
                ->with($this->equalTo(new Money(2499)))
                ->willReturn(PaymentResult::approved('ch_123'));

        // FAKE — a real, in-memory implementation we own.
        $orders = new InMemoryOrderRepository([Order::draft(id: 1, total: new Money(2499))]);

        (new ConfirmOrder($gateway, $orders))->handle(orderId: 1);

        self::assertSame(OrderStatus::Confirmed, $orders->find(1)->status);
    }

    public function test_a_shipped_order_cannot_be_cancelled(): void
    {
        $this->expectException(InvalidTransition::class);
        Order::shipped()->cancel();
    }
}

Testing against a real database

🧒 Simple

If your code talks to MySQL, test it against MySQL. Practising on a pretend database proves you can pass a pretend test.

🎓 Professional

Substituting SQLite for MySQL is the tempting shortcut and it hides exactly the bugs you wanted to catch: different type handling, different date functions, no strict mode, different behaviour on invalid values. Your tests pass and production does not.

Testcontainers starts a real MySQL in Docker for the test run and throws it away afterwards, so CI matches production. Wrap each test in a transaction and roll it back — far faster than re-migrating, and it keeps tests independent of one another, which is the property that stops a suite becoming order-dependent and unfixable.

What coverage does and does not tell you

🧒 Simple

Coverage counts which lines ran while the tests were running. A line can run without anybody checking that it did the right thing — so a high number does not mean the tests are good.

🎓 Professional

Coverage measures execution, not verification. A test with no assertions covers plenty of lines and proves nothing, which is why coverage targets get gamed the moment they become a number someone is judged on.

Mutation testing is the honest counterpart: infection/infection changes your code deliberately — flips a > to >=, removes a line — and re-runs the suite. Every mutant that survives is a change your tests did not notice. It is slow, so run it nightly rather than per-commit, and publish the score next to the coverage number: it usually undercuts it, which is the point.

⚠ Trap

A test that asserts the implementation rather than the behaviour — "the service called save() twice" — breaks on every refactor while catching no real bugs. Those tests get deleted, and with them goes the team's belief that testing is worth it. Assert what the caller can observe.

Golden rules
  • Mock the boundaries you do not own. Use real objects inside your own domain.
  • Test against the database you deploy. SQLite-instead-of-MySQL hides the bugs you were hunting.
  • Transaction per test, rolled back. Fast, and it keeps tests independent.
  • Coverage measures execution, not verification. Mutation score is the honest number.
  • Assert behaviour, not implementation, or every refactor breaks the suite.
  • A bug fix starts with a failing test. It proves the bug and stops it returning.
  • Test names are documentation. test_a_shipped_order_cannot_be_cancelled tells you the rule.

"Che tipo di test scrive, e cosa non testa?"

The second half is what they are really asking — anyone can list test types: "Test unitari sulla logica di dominio, dove le regole sono vere e le dipendenze le sostituisco. Test di integrazione sul database reale, perché gran parte dei bug in PHP stanno nelle query e un database finto non li mostra. Qualche test end-to-end solo sui percorsi critici, tipo il checkout. Non testo i getter, non testo il framework, e non testo il codice di configurazione: sono test che si rompono a ogni refactoring senza trovare niente."
