JavaScript as a language

The interview question is almost always the event loop, because it is the one thing that is genuinely different from PHP and it separates people who have debugged asynchronous code from people who have copied async until the error stopped. This chapter is that model, the promise semantics that follow from it, and the handful of language details — this, ==, closures in loops — that produce the classic bugs.

From the advert

"Conoscenza di HTML, CSS e JavaScript". The JavaScript half is tested more seriously than the other two, because it is where a back-end developer's habits actually break: PHP finishes everything before it answers, and JavaScript does not.

The event loop, microtasks and why order surprises you

🧒 Simple

JavaScript does one thing at a time, like PHP. The difference is that when something is slow it does not wait — it books the rest for later and carries on. "Later" is a queue, and the queue only gets a turn when the current work has completely finished.

🎓 Professional

One thread, one call stack. Asynchronous work is handed to the host (browser or Node), which puts a callback on a queue when it completes. The loop runs the stack to empty, then drains queues.

The part that decides interview answers: there are two queues. Microtasks — promise callbacks, queueMicrotask, await continuations — are drained completely after the current task and before the next macrotask. Macrotasks — setTimeout, events, I/O — get one per loop turn. So a resolved promise’s .then always runs before a setTimeout(..., 0) queued earlier, and an infinite chain of microtasks starves the page forever.

The consequence developers actually hit: setTimeout(fn, 0) does not mean "now", it means "after the current work and after every pending microtask". And because there is one thread, a long synchronous loop freezes rendering, input and everything else — the UI is not "slow", it is blocked.

Try it. Predict the order before running it in a browser console. Getting this right is the whole of the event-loop question.

console.log('1 sync');

setTimeout(() => console.log('5 macrotask (setTimeout 0)'), 0);

Promise.resolve().then(() => console.log('3 microtask'));

queueMicrotask(() => console.log('4 microtask'));

console.log('2 sync');

// 1 sync · 2 sync · 3 microtask · 4 microtask · 5 macrotask
// Every microtask drains before the timeout, even though the timeout was queued first.

(async () => {
  console.log('a: runs synchronously up to the first await');
  await null;                       // await always yields, even on a non-promise
  console.log('c: continuation — a microtask');
})();
console.log('b: after the async call');
// a · b · c

Promises and async/await

🧒 Simple

A promise is a receipt for a value that has not arrived yet. async/await lets you write code that reads top-to-bottom while still waiting properly — but the waiting is real, and forgetting the await is the most common bug in the language.

🎓 Professional

An async function always returns a promise; await unwraps one and suspends the rest of the function as a microtask. Two rules do most of the work:

  • await in a loop is sequential. Ten requests at 200 ms take two seconds. If they are independent, start them all and await Promise.all() — 200 ms. This is the most valuable single optimisation in front-end code and a favourite interview follow-up.
  • An un-awaited promise swallows its error. Calling an async function without await or .catch() produces an unhandled rejection: the operation failed, nothing was logged, and the UI shows a spinner forever.

Know the combinators, because they are the follow-up question: Promise.all rejects as soon as any input rejects; allSettled waits for all and reports each outcome; race settles with the first to settle, however it settled; any resolves with the first success.

And fetch’s trap: it only rejects on a network failure. A 404 or a 500 resolves normally with ok === false. Code that only has .catch() treats every server error as a success.

⚠ Trap

try/catch around a call you forgot to await catches nothing — the function returned a pending promise successfully, and the rejection happens after your catch block is long gone. The same applies to forEach: it ignores the promises its callback returns, so items.forEach(async i => await save(i)) finishes instantly having saved nothing yet. Use for...of with await, or Promise.all(items.map(save)).

this, closures and the two loop bugs

🧒 Simple

In a normal function, this depends on how the function was called, not where it was written. Arrow functions do not have their own this at all — they use the one from around them, which is almost always what you wanted.

🎓 Professional

this is determined at call time: the object before the dot, the argument to call/apply/bind, the new instance under new, or undefined in strict mode (which modules are). Passing a method as a callback detaches it — setTimeout(obj.method, 0) loses this. Arrow functions close over the enclosing this lexically, which is why class fields defined as arrows are the standard fix for event handlers.

var versus let in a loop is the other classic: var is function-scoped, so every closure shares one variable and all of them see the final value; let creates a fresh binding per iteration and each closure gets its own. It is the same shape as the PHP use (&$i) bug in chapter 04, arrived at from the opposite direction.

Equality: == coerces with rules nobody remembers, === does not. Use === always, with one idiomatic exception — x == null is a deliberate way to test for null-or-undefined together. And know that typeof null === 'object', NaN !== NaN (use Number.isNaN), and 0.1 + 0.2 !== 0.3, which is the same IEEE-754 fact that makes money an integer in PHP (ch. 03).

Modern JavaScript worth having in your fingers

🧒 Simple

The language got a lot nicer after 2015. A small set of features covers most day-to-day code, and using them makes your JavaScript look current rather than like jQuery with the jQuery removed.

🎓 Professional
  • Destructuring and spread — const { id, total = 0 } = order, { ...order, status: 'paid' }. Note that spread is a shallow copy, exactly like clone in PHP.
  • ?. and ?? — optional chaining, and nullish coalescing which falls through only on null/undefined. That is the difference from ||, and it matters the moment a legitimate 0 or '' is a value.
  • Array methods — map, filter, reduce, find, some, every, flatMap, and at(-1) for the last element.
  • Map and Set — real collections. A Map takes any key type and preserves insertion order; a plain object does neither properly.
  • Modules — import/export, and await import() for code splitting. In a browser this needs <script type="module">, which is also deferred and strict by default.
  • structuredClone() for a real deep copy, replacing the JSON.parse(JSON.stringify(x)) hack that silently destroys dates and undefined.
  • Intl — Intl.NumberFormat('it-IT', { style: 'currency', currency: 'EUR' }). Formatting money by hand in an Italian application is how you end up with 1.234,56 written as 1,234.56.
Golden rules
  • Microtasks drain before the next macrotask. .then beats setTimeout(0).
  • One thread: a long loop freezes the page. Not slow — blocked.
  • await in a loop is sequential. Independent work goes in Promise.all.
  • Never async inside forEach. It ignores the promise.
  • fetch does not reject on 404 or 500. Check res.ok.
  • Arrow functions for callbacks, because this is lexical.
  • === always; ?? when 0 and '' are real values.

"Mi spiega l’event loop?"

Do not recite a diagram — give the model and then a consequence you have hit: "JavaScript ha un solo thread e uno stack. Il lavoro asincrono viene affidato all’ambiente, che rimette una callback in coda quando finisce. Le code sono due: i microtask — le promise e le continuazioni degli await — vengono svuotati tutti dopo il codice sincrono corrente, e solo dopo passa un macrotask come un setTimeout. Per questo un .then già risolto parte prima di un setTimeout(0) messo in coda prima. La conseguenza pratica che mi è capitata: dieci await dentro un ciclo erano dieci chiamate in sequenza, due secondi; erano indipendenti, le ho messe in Promise.all ed è diventato duecento millisecondi."
