Architecture: layers, hexagonal, CQRS, DDD

"Codice manutenibile e riutilizzabile" is the same advert line that produced the SOLID chapter, asked at a larger scale: where do the rules of the business live, and what stops them leaking into controllers, Blade templates and Eloquent models until changing a VAT rate means touching eleven files. This chapter is the vocabulary interviewers expect — layers, hexagonal, CQRS, DDD — used at the size of project you will actually be working on.

From the advert

"Capacità di scrivere codice manutenibile e riutilizzabile". At junior level this is tested as SOLID (ch. 05). From mid level it becomes "dove metteresti questa logica?" and the answer is judged on whether you have a consistent place for it.

Layers, and the dependency rule

🧒 Simple

Sort the code into rings. The rules of the business go in the middle. The web, the database and the outside world go on the outside. Then the only law is: the outside may know about the middle, never the other way round.

🎓 Professional

The names vary — Clean, Onion, Hexagonal, Ports and Adapters — and the substance is one idea: dependencies point inward. Typically four layers:

  • Domain. Entities, value objects, domain services, and the interfaces the domain needs. No framework, no ORM, no HTTP. This layer should compile with the vendor directory deleted.
  • Application. Use cases: ConfermaOrdine. Orchestrates the domain, owns the transaction boundary, knows nothing about HTTP.
  • Infrastructure. The implementations — Doctrine or Eloquent repositories, the mail client, the SDI adapter.
  • Presentation. Controllers, console commands, queue jobs. Thin: parse input, call a use case, format the result.
  • Ports and adapters restates the same thing usefully: the domain defines ports (interfaces), the outside supplies adapters. HTTP is an adapter and so is the database, which is why the domain does not care that one is "in front" and one "behind".

The payoff is testability without a database, and a business rule that has exactly one home. The cost is indirection — a change touches more files — which is why the size question below is not optional.

⚠ Trap

The anaemic domain model. Entities that are nothing but getters and setters, with every rule in a Service class. It looks like layering and it is procedural code with objects for data — nothing prevents an invalid state, because anyone can call setStatus('shipped') on a cancelled order. The fix is behaviour on the entity: $order->ship() that checks the transition (ch. 03) and refuses. If your OrderService is 900 lines and Order is 40 getters, that is the diagnosis.

DDD: the parts that pay, and the parts that do not

🧒 Simple

Domain-Driven Design is mostly the idea that the code should use the same words as the people who do the work, and that you should draw lines around parts of the business where those words mean different things.

🎓 Professional

The high-value, low-cost parts — use these everywhere:

  • Ubiquitous language. If the warehouse says impegnare la merce, the method is impegna(), not reserveStock(). Translating vocabulary at the boundary of a conversation is where requirements get lost.
  • Value objects. Money, PartitaIva, CodiceDestinatario. Immutable, self-validating, impossible to mix up with a plain string. This is the single highest return-per-hour idea in the whole list (ch. 03).
  • Aggregates. A consistency boundary with one root: you load, change and save an Order with its lines as one unit, and nothing outside reaches a line directly. The practical rule that follows: one transaction, one aggregate — needing two in a transaction is a sign the boundary is wrong.
  • Bounded contexts. "Cliente" in sales and "Cliente" in accounting are different models with different fields. Forcing one shared class to serve both is how a model becomes unusable for everyone.
  • Domain events. OrdineConfermato as a first-class object decouples what happened from what should follow.

The expensive parts — event sourcing, full tactical DDD across every module, a separate persistence model with hand-written mappers — are worth it in a genuinely complex core domain and are overhead in a CRUD application. Being able to draw that line out loud is the answer that sounds experienced rather than enthusiastic.

Try it. The same use case twice. The second version is not longer because of ceremony — it is longer because the rule is now impossible to bypass, and testable without a database.

<?php declare(strict_types=1);
/* ---------- Before: the rule lives in the controller, and only there ---------- */

public function confirm(Request $request, int $id)
{
    $order = Order::findOrFail($id);
    if ($order->status !== 'submitted') {              // the rule, in the HTTP layer
        return response()->json(['error' => 'stato non valido'], 422);
    }
    $order->status = 'confirmed';                       // anyone can write any value
    $order->save();
    Mail::to($order->email)->send(new Confirmation($order));
    return response()->json($order);
}
/* The queue worker, the console command and the SDI import each need a copy of
   that check — and one of them will not have it. */


/* ---------- After: domain owns the rule, application owns the transaction ---------- */

// Domain — no framework, no ORM. Testable with `new`.
final class Order
{
    private function __construct(
        public readonly OrderId $id,
        private OrderStatus $status,          // the enum state machine from ch. 03
        private array $events = [],
    ) {}

    public function confirm(): void
    {
        if (!$this->status->canMoveTo(OrderStatus::Confirmed)) {
            throw new InvalidTransition($this->status, OrderStatus::Confirmed);
        }
        $this->status   = OrderStatus::Confirmed;
        $this->events[] = new OrderConfirmed($this->id);   // what happened, not what to do
    }

    /** @return list<object> */
    public function releaseEvents(): array
    {
        $e = $this->events; $this->events = []; return $e;
    }
}

// Application — the use case. Owns the transaction, depends on interfaces only.
final readonly class ConfermaOrdine
{
    public function __construct(
        private OrderRepository $orders,      // a port; Eloquent implements it in infrastructure
        private EventDispatcher $events,
        private TransactionManager $tx,
    ) {}

    public function __invoke(OrderId $id): void
    {
        $this->tx->transactional(function () use ($id): void {
            $order = $this->orders->get($id);
            $order->confirm();
            $this->orders->save($order);
            // Dispatched after commit — the ch. 22 trap.
            $this->events->dispatchAll($order->releaseEvents());
        });
    }
}

// Presentation — thin, and now there is nothing here to duplicate.
public function confirm(int $id, ConfermaOrdine $confermaOrdine)
{
    $confermaOrdine(new OrderId($id));
    return response()->noContent();
}

CQRS, without the event sourcing

🧒 Simple

Reading and writing are different jobs with different needs. Writing needs rules and safety; reading needs speed and exactly the shape the screen wants. CQRS just means letting them have different models instead of forcing one to serve both.

🎓 Professional

Command Query Responsibility Segregation, in its cheap and useful form: commands go through the domain, queries do not. A dashboard reads through a hand-written SQL query into a DTO, bypassing the aggregate entirely — because hydrating five hundred rich entities to render a table is slow and buys nothing, since you are not going to change them.

This resolves the tension people feel with the repository pattern: a repository is for loading an aggregate to change it; a read model is for the screen. Trying to serve both from one interface is what produces repositories with forty methods.

The expensive form — separate write and read databases, synchronised by events, with eventual consistency visible to the user — is a different commitment, and the honest caveat to give in an interview: the moment the read model is asynchronous, the user can save a change and not see it. That must be a product decision.

Event sourcing is not CQRS and they are constantly conflated. Event sourcing stores the sequence of events as the source of truth and derives current state. It gives a perfect audit trail — genuinely valuable for accounting or regulated domains — and it costs you versioning of events, replay tooling, and a team that has done it before. Not a first-project decision.

How much architecture this project deserves

🧒 Simple

All of this is a cost paid up front for a benefit that arrives later. On a small project the benefit never arrives, and you are left with the cost. Match the structure to the size and the lifetime.

🎓 Professional

A defensible scale:

  • A brochure site or a small CRUD tool. Framework conventions, fat models, thin controllers. Adding a domain layer here is a cost with no payer.
  • A gestionale with real rules — stock, invoicing, state machines. Value objects and behaviour on the entities, form requests, a service layer for the multi-step use cases. This is where most of this market lives, and it is where the return is highest.
  • A core domain with genuine complexity and a long life. Full layering, ports and adapters, enforced boundaries, CQRS on the read side.

Whatever the scale, two things are cheap enough to always do: put behaviour on the entity rather than in a setter, and enforce whatever boundaries you claim to have in CI with deptrac (ch. 22b, 30). An architecture that exists only in a diagram on Confluence has already eroded.

Golden rules
  • Dependencies point inward. The domain compiles without the framework.
  • Getters and setters plus a 900-line service is an anaemic model.
  • Value objects first. Highest return of anything in this chapter.
  • One transaction, one aggregate. Needing two means the boundary is wrong.
  • Speak the business's words in the code, untranslated.
  • Commands through the domain, queries straight to SQL.
  • Event sourcing is not CQRS, and it is not a first-project decision.
  • Enforce boundaries in CI, or they are decoration.

"Dove mette la logica di business?"

Answer with a place and a reason it cannot be bypassed: "Il più vicino possibile ai dati che protegge: sull’entità, non nel controller. Se la regola è 'un ordine si conferma solo da submitted', quella regola sta dentro $order->confirm(), che tira un’eccezione se la transizione non è valida — così vale anche quando l’ordine arriva da un job in coda o da un import, non solo dal form. Nel controller resta parsing e formattazione; i casi d’uso con più passi li metto in una classe applicativa che possiede la transazione. Poi quanto strutturare dipende dal progetto: su un gestionale con regole vere ci metto value object e comportamento sulle entità; su un sito vetrina sarebbe solo costo."
