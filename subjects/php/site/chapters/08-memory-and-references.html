Memory, references and the request lifecycle

Shared-nothing is PHP’s biggest structural difference from Java and .NET, and interviewers who come from those worlds probe it deliberately. It is also the explanation for a whole family of "works on my machine, dies in production" bugs: the request that fits in memory with 200 rows and not with 200 000, the static cache that helps in a worker and does nothing in a web request, the leak that only exists in the queue.

From the advert

Not in any advert. Nobody writes "understands refcounting". But "ottimizzazione delle prestazioni" and "manutenzione ed assistenza" both cash out here the first time a job dies with Allowed memory size exhausted.

Shared-nothing, and what it costs you

🧒 Simple

Every web request starts a brand new PHP with no memory of anything that came before, does its job, and then everything it made is thrown away. Nothing you put in a variable survives to the next visitor.

🎓 Professional

In a Java or .NET application the process is long-lived and holds application state: caches, connection pools, singletons that genuinely live for days. Under PHP-FPM each request gets a clean interpreter state, runs, and has its memory released wholesale at the end.

The gain is enormous and usually undersold: a leak in one request cannot poison the next, and most classes of concurrency bug simply cannot be written, because there is no shared mutable heap for two requests to fight over. It is why PHP tolerates sloppy code far better than long-running runtimes do.

The cost is that anything which must persist has to go somewhere real — Redis, the session store, the database — and that every request pays start-up again. OPcache (ch. 01) removes the compile cost; the connection and bootstrap cost remain, which is precisely what Swoole, RoadRunner and Laravel Octane exist to avoid.

⚠ Trap

A static property used as a cache is a per-request cache under FPM and a process-lifetime cache in a queue worker. The same code, two behaviours. A static array that memoises lookups is harmless on the web and an unbounded leak in a worker that processes fifty thousand jobs before restarting — which is exactly why Laravel Horizon restarts workers after N jobs or M megabytes. If you move code from a controller into a job, re-read every static in it.

Refcounting and the cycle collector

🧒 Simple

PHP counts how many names point at each value. When the count hits zero the memory is released immediately. The one case it cannot handle alone is two objects holding on to each other — then neither count ever reaches zero, and a separate collector has to come and find them.

🎓 Professional

PHP frees on refcount zero, which makes destruction deterministic: unset($x) on the last reference calls __destruct() right there, not "eventually". That is unlike Java or .NET, and it is why RAII-ish patterns work in PHP — a lock released in a destructor is released at a predictable moment.

Cycles are the exception. $a->b = $b; $b->a = $a; leaves both counts at one after you unset your variables. The cycle collector (gc_collect_cycles()) runs when the root buffer fills, which under FPM often means never, because the request ends first and everything is freed anyway. In a long-running worker it matters, and cycles are the usual explanation for a worker whose memory only ever goes up.

Two practical notes: WeakReference and WeakMap (8.0) let you hold an object without keeping it alive, which is the clean fix for observer registries and identity maps; and memory_get_usage(true) reports what PHP took from the OS, while false reports what your script is actually using — quoting the wrong one is a common confusion when someone says a script "uses 30 MB".

Try it. The destructor timing in the first block is the deterministic part; the second block is the leak that needs a collector.

<?php declare(strict_types=1);

final class Handle
{
    public function __construct(private readonly string $name) {}
    public function __destruct() { echo "released {$this->name}", PHP_EOL; }
}

$h = new Handle('db');
echo "before unset", PHP_EOL;
unset($h);                       // "released db" prints HERE, not at script end
echo "after unset", PHP_EOL;

final class Node { public ?Node $peer = null; }

gc_collect_cycles();
$before = memory_get_usage();
for ($i = 0; $i < 20_000; $i++) {
    $a = new Node; $b = new Node;
    $a->peer = $b; $b->peer = $a;      // cycle: refcount never reaches zero
    unset($a, $b);
}
printf("leaked   %6.2f KB%s", (memory_get_usage() - $before) / 1024, PHP_EOL);
gc_collect_cycles();
printf("after gc %6.2f KB%s", (memory_get_usage() - $before) / 1024, PHP_EOL);

References: what & actually does

🧒 Simple

& makes two names for one box. Objects are already like that by default, which is why &$object is almost always a misunderstanding rather than a feature.

🎓 Professional

The distinction that trips people: an object variable holds a handle, not the object. Passing an object to a function copies the handle, so the function can mutate the object — but reassigning the parameter does not affect the caller. That is not pass-by-reference; adding & additionally lets the function replace the caller’s variable, which is a different and rarely wanted power.

clone is shallow: the new object shares the objects its properties point at. Deep copying needs __clone() doing the work by hand. This is the same shallowness as readonly (ch. 03), and it is the follow-up question to both.

⚠ Trap

References inside arrays survive copying, and this is the sharpest corner in the language: an array containing a reference, assigned to another variable, is not isolated by copy-on-write — writing through the reference in one copy changes the other. Combined with foreach ($rows as &$row) (ch. 06) it produces data corruption that looks like a database bug. The rule that avoids all of it: do not put references in arrays.

The request lifecycle, and where memory actually goes

🧒 Simple

Memory problems in PHP are nearly always one thing: you loaded all the rows. Not a leak, not the garbage collector — a query with no limit, or a file read in one gulp.

🎓 Professional

The lifecycle: FPM assigns a worker → PHP compiles (or reads OPcache) → the autoloader pulls in classes on demand → your code runs → output flushes → the request shuts down and the memory arena is released. memory_limit applies per request, and exceeding it is a fatal that only a shutdown function will see (ch. 07).

When you are handed Allowed memory size of N bytes exhausted, check in this order:

  1. An unbounded result set. Order::all(), or PDO buffering the whole table. Fix with cursor()/chunkById(), or a generator (ch. 04).
  2. Eager loading everything. with() on four relations across 10 000 rows hydrates a great many objects; select only the columns you need.
  3. A whole file in memory. file_get_contents() on an upload, or file() on a CSV.
  4. Only then, a genuine cycle or a static that grows — and that is mostly a worker problem, not a web one.

Raising memory_limit buys time and never fixes the class of bug: the table grows again next quarter.

Golden rules
  • Shared-nothing: nothing survives the request. Persist in Redis or the database.
  • Re-read every static when code moves into a worker. Lifetime changed underneath it.
  • Destruction is deterministic — refcount zero, right now — except for cycles.
  • Objects are handles. You rarely want &$object.
  • clone is shallow, like readonly.
  • Never put references in arrays.
  • Out of memory means unbounded rows nine times out of ten. Stream it.

"Un job in coda cresce di memoria fino a morire. Come lo indaga?"

This is the question where the shared-nothing knowledge pays: "Prima cosa: in un worker il processo è longevo, quindi valgono regole diverse dal web. Guardo le proprietà static e i registri di listener che accumulano oggetti, perché lì la cache non muore a fine richiesta. Poi controllo se carico tutti i record in una volta invece di usare cursor() o chunk. Misuro con memory_get_usage() a ogni N job per vedere se cresce in modo lineare — se cresce e poi si stabilizza dopo gc_collect_cycles() sono cicli di riferimenti. E intanto imposto il worker perché si riavvii dopo un tot di job, che è quello che fa Horizon di default: non è la diagnosi, ma ferma l’emorragia."
