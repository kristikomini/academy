WordPress, done professionally

A large fraction of the web runs on WordPress, and a large fraction of Italian agency work is maintaining it. Candidates often hide this on the CV, which is a mistake: the person who can work on WordPress professionally — version control, a local environment, no editing files in the admin panel — is rarer than the person who can write a Laravel controller, and is billed out for exactly the same rate.

From the advert

"Gradita esperienza con CMS (WordPress)". In a Bologna web agency this is not gradita, it is Monday. Treat it as a first-class skill and it becomes a differentiator rather than something to apologise for.

Hooks: the whole architecture in one idea

🧒 Simple

WordPress runs its normal course and, at hundreds of points along the way, stops to ask "does anyone want to do something here?". Your code answers. That is the entire extension model: you never modify WordPress, you attach to it.

🎓 Professional

Two kinds, and mixing them up is the most common beginner error. An action (do_action / add_action) is a notification: do something, return nothing. A filter (apply_filters / add_filter) passes a value through you and you must return it — forgetting the return in a filter silently blanks whatever it was filtering, which is the classic "the title disappeared" bug.

add_filter($hook, $callback, $priority, $acceptedArgs): priority decides order (default 10, lower runs earlier) and $acceptedArgs must be raised to receive more than the first argument — the usual reason a callback receives null where you expected the post id.

Everything else follows from this. Plugins and themes are collections of hook registrations. The load order — mu-plugins, plugins, theme — determines who registers first, and init, wp_enqueue_scripts, template_redirect and save_post are the four you will use most.

⚠ Trap

Never edit core, and never edit a theme or plugin you did not write. The next update overwrites it and the site changes behaviour with no commit to blame. For a theme, use a child theme; for a plugin, use its hooks — and if it exposes none, write a small plugin of your own that filters the output, or fork it deliberately and record that you did. "The client’s site broke after an update" is nearly always someone having edited something in place through the admin file editor, which is also why that editor should be disabled (DISALLOW_FILE_EDIT).

The data model: posts, meta, taxonomies and CPTs

🧒 Simple

Almost everything in WordPress is a "post" with a type. A page is a post, a product is a post, a booking is a post. Extra fields go in a side table of key-value pairs attached to it.

🎓 Professional

wp_posts plus wp_postmeta is an entity-attribute-value model, and knowing that explains both its flexibility and its performance ceiling. Custom post types (register_post_type) and taxonomies (register_taxonomy) give you modelled content with the admin UI for free, and ACF (Advanced Custom Fields) is effectively standard in Italian agencies for the field layer.

The performance consequence is worth having ready, because it is the question that separates a WordPress developer from a WordPress user: querying by meta value does not scale. meta_query joins wp_postmeta once per condition, and the values are LONGTEXT with no useful index — a filter over three meta fields on 50 000 products is a slow query you cannot fix with an index (ch. 11). The answers, in order: use a taxonomy when the thing is a category (taxonomies are properly indexed and designed for filtering), denormalise into a purpose-built table for heavy queries, or put it in a search index (ch. 21).

The other rule: WP_Query and the $wpdb API, never raw string SQL. $wpdb->prepare() is your prepared statement (ch. 15), and options such as 'no_found_rows' => true (skips the SQL_CALC_FOUND_ROWS count when you do not paginate) and 'fields' => 'ids' make a real difference on large queries.

Try it. A small plugin with the three things every professional WordPress feature has: a custom post type, a taxonomy used instead of a meta field for filtering, and correctly escaped output.

<?php declare(strict_types=1);
/**
 * Plugin Name: Bottega Ordini
 * Description: Custom post type for orders, with a taxonomy for status.
 */

if (!defined('ABSPATH')) { exit; }        // never let the file be requested directly

add_action('init', static function (): void {
    register_post_type('bottega_ordine', [
        'label'        => 'Ordini',
        'public'       => false,           // not a front-end URL: admin only
        'show_ui'      => true,
        'supports'     => ['title', 'custom-fields'],
        'menu_icon'    => 'dashicons-cart',
        'capability_type' => 'post',
    ]);

    // Status as a TAXONOMY, not postmeta: taxonomies are indexed and built for
    // filtering. A meta_query over 50k orders is a full scan of wp_postmeta.
    register_taxonomy('stato_ordine', 'bottega_ordine', [
        'label'        => 'Stato',
        'hierarchical' => false,
        'show_admin_column' => true,
    ]);
});

/** A filter MUST return the value — forgetting this blanks the title everywhere. */
add_filter('the_title', static function (string $title, int $postId): string {
    if (get_post_type($postId) !== 'bottega_ordine') {
        return $title;                     // untouched, and still returned
    }
    return 'Ordine ' . $title;
}, 10, 2);                                 // 2 = accepted args, or $postId arrives null

/** Fast, indexed query — and every value escaped for its context on output. */
function bottega_ordini_confermati(int $perPage = 20): void
{
    $q = new WP_Query([
        'post_type'      => 'bottega_ordine',
        'posts_per_page' => $perPage,
        'no_found_rows'  => true,          // skip the pagination count we do not use
        'tax_query'      => [[
            'taxonomy' => 'stato_ordine',
            'field'    => 'slug',
            'terms'    => 'confermato',
        ]],
    ]);

    foreach ($q->posts as $post) {
        printf(
            '<li><a href="%s">%s</a></li>',
            esc_url(get_permalink($post)),        // URL context
            esc_html(get_the_title($post))        // HTML context — different function
        );
    }
    wp_reset_postdata();
}

Security: escaping, nonces and capabilities

🧒 Simple

Three separate questions, and you need all three every time: is this user allowed to do it, did they actually mean to do it, and is what I am printing safe to print?

🎓 Professional

Escape late, by context. WordPress gives you a function per context and using the wrong one is still a hole: esc_html() for text, esc_attr() for attributes, esc_url() for URLs, esc_js() inside script, wp_kses_post() when limited HTML is genuinely allowed. Escape at the point of output, not when storing — the same value may go to HTML today and JSON tomorrow (ch. 15).

Sanitise on input as well: sanitize_text_field(), absint(), sanitize_email(). Input sanitising and output escaping are two jobs, not alternatives.

Nonces (wp_nonce_field() / check_admin_referer()) are WordPress’s CSRF protection — and they are not authorisation. A nonce proves the request came from your form; current_user_can('edit_post', $id) proves the user is allowed. Every form and every AJAX handler needs both, and the overwhelming majority of vulnerable plugins are missing the capability check specifically.

Finally, the honest operational truth: most WordPress compromises are outdated plugins, not clever attacks. Keeping plugins updated, removing unused ones, and being able to say "abbiamo un processo per gli aggiornamenti" is worth more than any code-level hardening.

Working on it professionally

🧒 Simple

The difference between a WordPress developer and someone who clicks around in the admin is process: the site is in Git, it runs locally, and changes are deployed rather than typed into production.

🎓 Professional

The setup that makes WordPress work like any other project:

  • Composer-managed WordPress — Bedrock (Roots) puts core, plugins and themes in composer.json, moves configuration to .env and web root to web/. Suddenly plugin versions are locked and reviewable (ch. 28).
  • Version control the theme and custom plugins; never the uploads directory, never wp-config.php.
  • A local environment — DDEV, LocalWP or Docker. Editing production directly is how sites die.
  • WP-CLI is the professional tool and the one candidates most often do not know: wp search-replace for a domain change during a migration (it handles serialised data, which a SQL find-and-replace corrupts — this is the WordPress migration trap), wp db export, wp plugin update --all, wp cron event run.
  • Know that wp-cron is not cron. It fires on page visits, so a low-traffic site runs scheduled tasks late or never. Disable it and use a real cron entry (ch. 29b).
  • Caching — a page cache plugin plus object caching to Redis where available. WordPress performance work is overwhelmingly caching plus reducing plugin count (ch. 20).
  • Database migrations do not exist. Content lives in the database, so environments diverge by design; plan migrations as one-way exports rather than expecting Git-like merging.
Golden rules
  • Filters must return. Actions must not.
  • Never edit core, themes or plugins in place. Child theme or your own plugin.
  • Taxonomy for filtering, meta for storing. meta_query does not scale.
  • $wpdb->prepare() always. Never build SQL by concatenation.
  • Nonce plus capability. Two checks, two purposes.
  • Escape late, per context. esc_html, esc_attr, esc_url.
  • wp search-replace for migrations, because of serialised data.
  • Replace wp-cron with real cron on any site that matters.

"Ha esperienza con WordPress?" — asked in a tone that suggests it does not count

Claim it, and immediately show the professional version: "Sì, e ci lavoro come su qualsiasi altro progetto: sito in Git, ambiente locale con DDEV, plugin gestiti da Composer con Bedrock, niente modifiche dirette in produzione e niente editor di file dal pannello. Le personalizzazioni le faccio con hook in un plugin mio o in un child theme, così l’aggiornamento non le cancella. La cosa su cui sto più attento è il modello dati: wp_postmeta è comodo ma filtrare per meta su decine di migliaia di post è una scansione, quindi quando un campo serve per filtrare uso una tassonomia. E per le migrazioni uso wp search-replace, perché un find-and-replace in SQL rompe i dati serializzati."
