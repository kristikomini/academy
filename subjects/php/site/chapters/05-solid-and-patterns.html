SOLID and design patterns

Everyone can recite the five letters. Almost nobody can point at a class they wrote and say which principle made them split it, and that gap is exactly what the question is for. This chapter does SOLID with PHP examples small enough to hold in your head, then names the patterns Laravel has already been making you use for years without telling you.

From the advert

"Capacità di scrivere codice manutenibile e riutilizzabile". In an interview this becomes "mi parla dei principi SOLID?" — and the recital scores nothing. The example from your own code scores everything.

S and O: one reason to change, and extension without surgery

🧒 Simple

SRP: a class should have one job, so there is only one kind of news that makes you open it. OCP: adding a new case should mean writing a new file, not editing an old one and hoping.

🎓 Professional

Single Responsibility is better stated as Curly’s formulation: a module should have one reason to change, where a "reason" is a person who can ask for it. An Invoice class that calculates VAT, renders a PDF and emails the customer answers to the accountant, the designer and the marketing lead — three reasons, three eventual conflicts in one file.

Open/Closed is about the shape of change: when a new payment provider arrives, do you add a class or edit a match? The mechanism is nearly always an interface plus a resolver. The honest caveat: applied too early it produces four interfaces for one implementation. Wait for the second case, then abstract — the second case is what tells you where the seam actually is.

Try it. The match on the left is fine until the third provider, and by then it is in six places. This is OCP with the abstraction earned rather than guessed.

<?php declare(strict_types=1);

interface PaymentGateway
{
    public function charge(int $cents, string $reference): string;   // returns a transaction id
}

final class StripeGateway implements PaymentGateway
{
    public function charge(int $cents, string $reference): string
    {
        return 'stripe_' . $reference;
    }
}

final class SatispayGateway implements PaymentGateway
{
    public function charge(int $cents, string $reference): string
    {
        return 'satispay_' . $reference;
    }
}

/* The consumer never learns a provider name. Adding a third gateway adds a file
   and a container binding — this class is closed for modification. */
final class Checkout
{
    public function __construct(private readonly PaymentGateway $gateway) {}

    public function pay(int $cents, string $ref): string
    {
        return $this->gateway->charge($cents, $ref);
    }
}

echo (new Checkout(new SatispayGateway))->pay(2499, 'ORD-114'), PHP_EOL;

L and I: substitutability, and interfaces nobody has to lie to

🧒 Simple

LSP: if something claims to be a duck, it must not explode when you ask it to swim. ISP: do not force a class to implement five methods when it only has one job — the other four end up throwing "not supported".

🎓 Professional

Liskov says a subtype must be usable anywhere its parent is, without the caller knowing. The tell is a subclass that throws on an inherited method, or one that strengthens a precondition — the parent accepted any string, the child rejects empty ones, and existing callers now break for a reason no type checker will find. The textbook case is Square extends Rectangle: setting width independently of height is part of the rectangle’s contract, and a square cannot honour it.

Interface Segregation: many small role interfaces beat one fat one. The working test is throw new BadMethodCallException('not supported') — every occurrence of that is an ISP violation with a stack trace attached. PSR interfaces are the model to copy: LoggerInterface asks for logging and nothing else.

D: depend on the contract, not the vendor

🧒 Simple

Your important code should not know the brand names of the tools underneath it. It should say "I need something that can send an email", and somebody else decides that today it is Mailgun.

🎓 Professional

Dependency Inversion: high-level policy depends on an abstraction, and the low-level detail depends on the same abstraction. The crucial and usually-missed half is who owns the interface — it belongs to the consumer’s layer, not the implementation’s. App\Domain\Clock defined in the domain and implemented in infrastructure is inversion; an interface that lives next to its only implementation in a vendor-shaped folder is just an extra file.

Dependency injection is the mechanism; the container (ch. 16) is the machine that does the injecting. Do not conflate them in an interview — being able to say "DIP is the principle, DI is how you satisfy it, the container is the tool" is a small answer that lands very well.

⚠ Trap

Naming an interface IPaymentGateway, or writing one interface per class as a reflex, is cargo-cult DIP. An interface with exactly one implementation and no test double is pure ceremony. The value appears when there are two real implementations — a second provider, or the fake you test against. If neither exists yet, a final class is the honest design, and extracting the interface later is a five-minute refactor your IDE does for you.

The patterns Laravel already made you use

🧒 Simple

Design patterns are names for solutions people kept re-inventing. You have used most of them already — knowing the names just means you can say in one word what would otherwise take a paragraph.

🎓 Professional

Recognise them where they already live, which is far more convincing than reciting the Gang of Four:

  • Factory — Model::factory(), and every make() the container performs.
  • Strategy — the gateway above; also cache and queue drivers, chosen by config.
  • Observer — events and listeners, and Eloquent model observers by that exact name.
  • Decorator — PSR-15 middleware: each wraps the next and adds one behaviour (ch. 13).
  • Repository — a collection-like interface over persistence. Genuinely useful over Doctrine; over Eloquent it is frequently a thin wrapper that hides the query builder and buys nothing, and saying so out loud marks you as someone who has maintained one.
  • Adapter — Flysystem: one interface, S3 and local disk behind it.
  • Singleton — the one to be careful with. The container’s singleton() is a lifetime, which is fine; the classic static-instance-with-private-constructor is global mutable state that makes tests order-dependent.
⚠ Trap

The pattern answer that goes wrong is enthusiasm. Asked "quali design pattern conosce?", a candidate lists eleven and gets asked to implement Visitor. Name three you have actually used, say where and why, and volunteer one you deliberately did not use — "ho valutato un Repository sopra Eloquent e ho deciso di no, perché duplicava il query builder senza darmi niente in cambio". Restraint reads as seniority; a list reads as revision.

Golden rules
  • One reason to change means one person who can ask. Count the people, not the methods.
  • Abstract at the second case, not the first. The second case shows you the seam.
  • throw new BadMethodCallException is an ISP violation that reported itself.
  • The consumer owns the interface. That is what makes it inversion.
  • DIP is the principle, DI the mechanism, the container the tool. Three different words.
  • An interface with one implementation and no fake is ceremony.
  • Three patterns you used beats eleven you named.

"Mi parla dei principi SOLID?"

Never recite five definitions — pick one and prove it, then offer the rest: "Le dico quello che uso più spesso davvero. Open/Closed: avevo un match sul metodo di pagamento sparso in tre punti, e ogni provider nuovo voleva tre modifiche. Ho estratto un’interfaccia PaymentGateway e ora aggiungere un provider è un file nuovo più una riga nel container. L’ho fatto al secondo provider, non al primo: prima non sapevo ancora dove stesse la giuntura." That answer contains the principle, a concrete before-and-after, and the judgement about when — which is the part that separates you from a candidate who read the Wikipedia page this morning.
