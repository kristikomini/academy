Logging, metrics and tracing

Nobody asks for it at junior level and everybody needs it in the first week. When a client says "stamattina non funzionava", you either have a way to find out what happened or you have a conversation about feelings. This is also the fastest way to look like you have worked on something real, because the habits here can only be acquired by having been on the wrong end of an incident.

From the advert

Not in any advert. But "manutenzione ed assistenza" (ch. 25b) is unanswerable without it. A candidate who mentions correlation ids unprompted has visibly done support work.

Structured logs, not sentences

🧒 Simple

A log line that reads nicely to a human is nearly useless to a machine. Write the message as a fixed label plus separate named fields, and suddenly you can ask questions like "show me every failure for this customer" instead of grepping for a string.

🎓 Professional

PSR-3 is the interface (LoggerInterface), Monolog is the implementation everyone uses, and the part people ignore is the second argument: the context array. $log->error('Order confirmation failed', ['order_id' => 114, 'gateway' => 'stripe']) keeps the message stable and the variables queryable. Interpolating the id into the string means every occurrence is a unique message and nothing can be aggregated or alerted on.

Use a JSON formatter in production. One line per event, machine-parseable, and it works whether the destination is a file, Loki, Elastic or CloudWatch. Log to stdout in a container and let the platform collect it (ch. 28) — a log file inside a container is a log file that disappears with the container.

The PSR-3 levels, used correctly: debug for development detail; info for business events worth keeping (ordine confermato); warning for a recovered problem — a retry that succeeded, a fallback that fired; error for a request that failed but the system continues; critical for the system being broken. The discipline that matters: alert on error and above, and mean it. A codebase that logs everything at error has trained everybody to ignore the channel, and the one that mattered scrolled past at 03:00.

⚠ Trap

Logging personal data. Dumping the whole request body means passwords, card numbers, codici fiscali and email addresses in a log that is retained for a year, replicated to a third-party service and readable by everyone with dashboard access. Under GDPR the log is processing like any other. Redact at the logger — Monolog processors can strip known keys — and never log an Authorization header or a full request body by default. This is a question you may well be asked directly at a company that handles health or financial data.

The correlation id, which is the whole trick

🧒 Simple

Give every request a random id the moment it arrives, put it on every line that request writes, and show it to the user when something breaks. Then "it failed at 14:32" becomes one search.

🎓 Professional

Generate or accept a request id in the outermost middleware (ch. 13), push it into the logger so every subsequent line carries it automatically, propagate it on outbound HTTP calls as a header, carry it into queued jobs — the step everybody forgets, and it is where the trail usually goes cold — and return it in the error response (ch. 14) and in the page footer of a 500.

This is the cheapest possible thing that gives you distributed tracing’s main benefit without any tracing infrastructure. If you also add the authenticated user id and the tenant, you can answer nearly every support question from the logs alone.

Try it. Middleware plus a Monolog processor. Twenty lines, and it changes what support work feels like.

<?php declare(strict_types=1);

namespace App\Http\Middleware;

use Closure;
use Illuminate\Http\Request;
use Illuminate\Support\Facades\Log;
use Symfony\Component\HttpFoundation\Response;

final class RequestId
{
    public function handle(Request $request, Closure $next): Response
    {
        // Accept an upstream id so a trace survives across services; otherwise mint one.
        $id = $request->header('X-Request-Id') ?: bin2hex(random_bytes(8));

        $request->attributes->set('request_id', $id);

        // A processor: every subsequent log line gets these fields with no further effort.
        Log::withContext([
            'request_id' => $id,
            'user_id'    => $request->user()?->id,
            'route'      => $request->route()?->getName(),
        ]);

        $response = $next($request);

        // Give it back, so a user can quote it and support can find it.
        $response->headers->set('X-Request-Id', $id);

        return $response;
    }
}

/* The step people forget: carry it into the job, or the trail stops at dispatch.

   final class SendOrderConfirmation implements ShouldQueue
   {
       public function __construct(
           public readonly int $orderId,
           public readonly string $requestId,        // captured at dispatch time
       ) {}

       public function handle(): void
       {
           Log::withContext(['request_id' => $this->requestId, 'job' => self::class]);
           // ...
       }
   }
*/

Metrics, tracing and the four signals

🧒 Simple

Logs tell you what happened in one request. Metrics tell you how the whole system is behaving over time. Traces tell you where the time went inside one slow request. You want all three, in that order of effort.

🎓 Professional

Metrics are numbers over time: request rate, error rate, latency percentiles, queue depth (ch. 22), worker count. The rule worth internalising is percentiles, never averages: an average response time of 200 ms hides a p99 of 8 seconds, and the p99 is the customer who telephones. Prometheus plus Grafana is the common stack; a hosted APM does it for you.

Tracing follows one request across services and layers, with a span per operation, and shows you the waterfall. OpenTelemetry is the vendor-neutral standard and has a PHP SDK. Worth it once there is more than one service, or when "which of the eleven queries is slow" is a recurring question.

Frame it in an interview with the four golden signals — latency, traffic, errors, saturation — and the practical PHP additions: queue depth, failed jobs, and pm.max_children utilisation, which is the saturation metric that actually predicts a PHP outage (ch. 01).

For error tracking specifically, Sentry is the single highest-value tool to add to a PHP project: exception grouping, release tracking, breadcrumbs and the user affected. It takes twenty minutes and it replaces "the client emailed us a screenshot" as your discovery mechanism.

What to log, and the health check that is honest

🧒 Simple

Log the things you would want to know at 3am, not everything. And make sure the "is it alive" check actually checks the things that break, or it will report green during an outage.

🎓 Professional

Log every state change with the identifier and the actor; every outbound call with its duration and status; every failure with the exception, the previous exception (ch. 07) and the context. Do not log successful reads — that is noise with a retention cost.

Health checks. Two endpoints, and the distinction matters: liveness says the process is running (cheap, no dependencies), readiness says it can serve traffic and therefore checks the database, Redis and the queue. A health check that returns 200 because PHP is running, while the database is unreachable, is worse than no health check — the load balancer keeps sending traffic to it. Package the dependency checks; do not hand-roll a status page that itself needs debugging.

And know what you cannot see: PHP’s shared-nothing model means there is no in-process metric aggregator surviving between requests (ch. 08). Metrics are pushed to a collector or written to Redis; expecting a counter in a static property to accumulate is a category error that catches people arriving from Java.

Golden rules
  • Stable message, variables in the context array. That is what makes logs queryable.
  • JSON to stdout in production; the platform collects it.
  • Alert on error and mean it. Everything-is-an-error trains people to ignore it.
  • Never log credentials, tokens or personal data. Redact at the logger.
  • A correlation id on every line, propagated into jobs and returned to the user.
  • Percentiles, not averages. The p99 is the person telephoning.
  • Readiness checks dependencies; liveness does not.
  • Log state changes and failures, not successful reads.

"Un cliente dice che stamattina l’ordine non è stato inviato. Come lo verifica?"

Describe a trail, not a guess: "Parto dall’identificativo: se ho il request id che restituiamo nell’errore lo cerco direttamente, altrimenti filtro i log per order_id e finestra temporale — per questo i log li scrivo strutturati, con i valori nel context e non dentro il messaggio. Guardo se la richiesta è arrivata, se il job è stato messo in coda e se è finito in failed_jobs: nella maggior parte dei casi è lì, e la tabella non la guardava nessuno. Poi controllo Sentry per l’eccezione con lo stack, e le metriche per capire se era un caso isolato o un’interruzione del provider. Se il request id fosse propagato anche nel job — ed è il pezzo che di solito manca — la catena la vedo tutta in una ricerca sola."
